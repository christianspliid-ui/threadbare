## User Constraints (from CONTEXT.md)

### Locked Decisions

**Monster Identity & Nature**
- Layered system: Primordial baseline fauna + sphere corruption as modifier. A cave bear is dangerous; a Death-touched cave bear is terrifying. Sphere adds flavor, terrain sets the base.
- One archetype per sphere (~9 base monster types at launch). Each sphere gets a signature creature: Force → war beast, Death → undead, Nature → primordial, etc. Terrain determines WHERE they appear, sphere determines WHAT they are.
- Naming: Named elites use descriptive titles from the prose system ("The Blighted Matriarch", "Goreclaw the Relentless"), not generated fantasy names.

**Monster Tiers**
- Generic tier (encounter-only): No graph nodes. Generic monsters exist only as encounter templates that fire based on hex danger level and lair proximity. The lair is the graph presence — generic monsters are its output.
- Named elites (stationary lair bosses): Graph actor nodes attached to their lair. They don't wander — you go to them. Creates deliberate quest targets.
- Monster factions (full faction system): Monster factions are faction nodes with ambitions, reputation, armies — identical to civilized factions. They participate in the same encounter/conflict pipeline. Maximum reuse of existing systems.

**Monster Faction Behavior**
- Sphere-specific goals: Each sphere's monsters have different ambitions.
- Full armies: Monster factions can raise hordes using the existing army system.
- Proactive attacks: Monster factions with expansion/destruction ambitions will target nearby settlements.
- Sphere-aligned coexistence: If a civilized faction's sphere alignment matches a monster faction's, there's a truce or uneasy coexistence.

**Sphere Feedback Loop**
- Bidirectional: Strong sphere energy attracts/creates monsters AND monster lairs increase local sphere pressure.
- Root cause mechanic: Players can't just clear lairs — they need to address underlying sphere pressure to prevent reinfestation.

**Divine Interaction**
- Full divine targeting: Monster lairs and named elites are valid targets for divine actions via the ActionDrawer.

**Danger Gradient & Spawning**
- 4 danger zones: Capital (safe, no monsters), Heartland (very low risk), Borderland (moderate risk), Wilderness/unprovinced (high risk).
- Worldgen + escalation: World generation places sparse initial lairs. Over time, unchecked lairs spawn adjacent lairs, and high sphere pressure creates new ones.
- Moderate density at worldgen: Most wilderness/borderland areas have at least one lair nearby.
- Slow escalation: New lairs appear every ~20-30 ticks if conditions are met. All rates as named constants.

**Lair Mechanics**
- 3 tiers that upgrade: Minor (generic encounters only) → Major (has a named elite) → Legendary (monster faction capital, raises armies).
- Don't block settlement: Lairs threaten settlements and suppress prosperity but don't hard-block settlement placement.
- Cleared lairs become explorable sites: Transitions to 'cleared_lair' location subtype.
- Reinfestation possible: If sphere pressure remains high and site is unoccupied, monsters can reclaim it.
- Lair icon on hex: Distinct lair signifier on the hex using existing location icon layer — monster-themed, sphere-tinted.

**Clearing Lairs**
- Minor tier: Can be cleared by capable agents via Adventuring Guild quests.
- Major/legendary lairs: Require faction army ambitions.
- Named elite lairs: May need both army + hero agent.

**Monster-Army Interaction**
- March attrition + encounter chance: Armies passing through monster-infested hexes pay Quintessence attrition AND have a chance of encountering a lair's defenders.
- Full battle system: Monster horde vs civilized army uses the same battle resolution.

### Claude's Discretion

- Lair icon art direction and signifier design
- Specific encounter template content for monster encounters
- Quintessence attrition rate for monster territory traversal
- Exact escalation thresholds and timing constants
- Monster faction ambition weight tuning
- How sphere-aligned coexistence is computed (threshold matching)

### Deferred Ideas (OUT OF SCOPE)
- Bestiary UI — Player-facing catalog of encountered monsters with type, sphere, known lairs.
- Monster diplomacy via divine action — Player brokering pacts between monster and civilized factions.
- Mobile named elites — Currently stationary lair bosses; patrol/territory behavior deferred.

## Summary

Phase M2.5 integrates monster encounters as a first-class faction system layered onto the Phase 12 conflict infrastructure. The core insight from the codebase inspection is that nearly all required behavior can be achieved by reusing existing systems with minimal new abstractions: monster factions are faction nodes (`actorType: 'faction'` with `isMonsterFaction: true`), lairs are location nodes with `locationSubtype: 'lair'` (extending the existing `LocationSubtype` union), named elites are actor nodes (same shape as agent nodes with `isMonsterElite: true`), and monster armies use the identical `ArmyState` shape on actor nodes already used for civilized armies.

The orchestrator integration adds three new phases: a slow worldgen-seeded lair initialization pass (one-time), a periodic lair escalation/spawn check (every 20-30 ticks), and a monster attrition modifier hook into `phaseArmyAttrition` when armies traverse monster-infested hexes. The sphere feedback loop threads through the existing `phaseSpherePressure` pipeline — lairs emit sphere pressure to their hex, and high sphere pressure at unprovided hexes can trigger lair spawning.

The most complex new work is the lair seeding worldgen pass and the lair escalation orchestrator phase. Everything else is data additions to existing systems: new `FactionDefinition` entries for monster factions, new `EncounterTemplate` entries for monster encounters, new `LocationSubtype` values for lair tiers, and new SVG signifiers for the location icon layer.

**Primary recommendation:** Organize implementation in 4 waves: (1) data types + lair graph model, (2) worldgen lair seeding pass, (3) escalation orchestrator phase + sphere feedback, (4) army integration + UI signifiers.

## Architecture Patterns

### New Graph Node Types

**Lairs — location nodes**

Lairs are `location` type graph nodes. `locationSubtype` is already a string union in `src/types/index.ts`. Add three new values:

```typescript
// src/types/index.ts — LocationSubtype union extension
| 'lair'          // Active minor/major/legendary lair
| 'cleared_lair'  // Cleared lair (explorable site, reinfestable)
// Note: tier stored in properties.lairTier: 'minor' | 'major' | 'legendary'
```

Lair node property bag shape:
```typescript
interface LairProperties {
  lairTier: 'minor' | 'major' | 'legendary';
  dominantSphere: SphereName;          // drives monster type + sphere pressure
  spawnedAtTick: number;
  lastEscalationTick: number;
  dangerZone: 'heartland' | 'borderland' | 'wilderness';
  monsterFactionId?: string;           // set when tier reaches 'legendary'
  namedEliteId?: string;               // set when tier reaches 'major'
  // For cleared lairs:
  clearedAtTick?: number;
  clearedByFactionId?: string;
}
```

**Named elites — actor nodes**

Named elites reuse the existing `actor` node type with `armyState: null` and `isMonsterElite: true`:

```typescript
// Actor node properties for named elite
{
  actorType: 'individual',   // or a new 'monster_elite' actorType if preferred
  isMonsterElite: true,
  dominantSphere: SphereName,
  lairId: string,            // lair they are attached to
  // standard trait/capability properties inherited
}
```

> Design note: The CONTEXT.md confirms named elites are stationary lair bosses, so no movement state needed. They ARE valid divine action targets — the ActionDrawer's existing targeting system already handles actor nodes.

**Monster factions — actor nodes**

Monster factions use the identical `actor` + `actorType: 'faction'` shape, with `isMonsterFaction: true` in properties and standard `pursues` edges for ambitions. The `FACTION_DEFINITIONS` Map already handles arbitrary faction definitions — add monster faction definitions to `src/data/faction-definitions.ts` (or a new `src/data/monster-faction-definitions.ts` that FACTION_DEFINITIONS imports).

```typescript
// Monster faction definition shape (extends FactionDefinition)
{
  id: 'monster_faction_death',
  nameTemplate: 'The {adj} Undead Legion',
  factionType: 'military',       // existing FactionType value
  isMonsterFaction: true,        // new boolean flag
  dominantSphere: 'entropy',
  ambitionWeights: {
    territorial_expansion: 0.5,
    revenge: 0.4,
  },
  // reachWeights, rankTiers, etc. still required for faction system compatibility
}
```

> Note: `FactionType` may need a new value `'monster'` or monster factions can use `'military'`. The former is cleaner but the latter avoids touching the type union. Given architectural rule "additive over destructive", adding `| 'monster'` to `FactionType` is the correct choice.

### Pattern 1: Lair Seeding Worldgen Pass (pass11-lairSeeding.ts)

Runs after sphere affinity seeding (`gameInit.ts`). One-time at world initialization, NOT a worldgen pipeline pass (worldgen is terrain-only; lair seeding uses the completed graph).

```typescript
// Source: codebase inspection of gameInit.ts + pass10-fantasyOverlay.ts
export const LAIR_SEEDING_CONSTANTS = {
  WILDERNESS_LAIR_DENSITY: 0.08,    // fraction of wilderness hexes with a lair
  BORDERLAND_LAIR_DENSITY: 0.03,    // fraction of borderland hexes with a lair
  HEARTLAND_LAIR_DENSITY: 0.005,    // very sparse heartland lairs
  CAPITAL_LAIR_DENSITY: 0.0,        // no lairs in capital zone
  MIN_LAIR_SEPARATION: 3,           // hexes between lairs (prevents clustering)
  PASS_SEED_LAIRS: 90211,           // unique seed offset (check against existing PASS_SEED_* constants)
};
```

The seeding function:
1. Reads `worldGenResult.provinceRoles` (`Uint8Array` with `PROVINCE_ROLE_*` encoding)
2. For each land hex, rolls PRNG against density by zone
3. Creates a `location` graph node with `locationSubtype: 'lair'`, `lairTier: 'minor'`
4. Uses hex's `sphereAffinity.dominantSphere` (already computed by `seedHexSphereAffinity`) to set the lair's dominant sphere
5. Emits a `lair_seeded` trace for inspectability

**Key constraint:** Hexes with `provinceRoles[idx] === PROVINCE_ROLE_CAPITAL` must receive zero lairs. Check existing PASS_SEED_* constant values in `src/engine/worldgen/constants.ts` to avoid collision with `PASS_SEED_LAIRS = 90211`.

### Pattern 2: Lair Escalation Phase (phaseLairEscalation.ts)

New orchestrator phase running every `LAIR_ESCALATION_INTERVAL` ticks (default: 25).

```typescript
// Source: codebase pattern — factionAmbitions.ts uses identical interval pattern
export const LAIR_ESCALATION_INTERVAL = 25;
export const LAIR_SPHERE_PRESSURE_EMISSION = 8;    // per tick, emitted to surrounding hexes
export const LAIR_SPAWN_SPHERE_THRESHOLD = 60;      // sphere score on hex before spawn eligible
export const LAIR_UPGRADE_MIN_TICKS = 30;           // ticks before minor→major eligible
export const LAIR_LEGENDARY_MIN_TICKS = 60;         // ticks before major→legendary eligible
export const LAIR_REINFESTATION_MIN_TICKS = 20;     // ticks after clearing before reinfestation eligible
export const LAIR_ADJACENT_SPAWN_CHANCE = 0.15;    // per eligible adjacent hex per escalation tick
```

Phase steps:
1. Skip if `tick % LAIR_ESCALATION_INTERVAL !== 0`
2. For each active `lair` location node:
   - Emit sphere pressure to adjacent hexes (feeds `phaseSpherePressure`)
   - Check upgrade eligibility (`ticks since spawnedAtTick >= LAIR_UPGRADE_MIN_TICKS` AND no existing army from lair's monster faction)
   - On upgrade: minor→major creates named elite actor node; major→legendary creates monster faction node + raises army
   - Check adjacent hex spawn: roll PRNG per adjacent unprovided/borderland hex
3. For each `cleared_lair` node:
   - Check reinfestation: high sphere pressure + no controlling faction + `ticks since clearedAtTick >= LAIR_REINFESTATION_MIN_TICKS`
   - On reinfestation: reset to active `lair`, `lairTier: 'minor'`
4. Emit `LairTrace` for all changes

### Pattern 3: Sphere Feedback Loop

Lairs contribute sphere pressure to their hex via `phaseSpherePressure`. The existing `SpherePressureEvent` interface already handles this:

```typescript
// Source: src/types/sphereAffinity.ts (confirmed from import in battleAftermath.ts)
const pressureEvent: SpherePressureEvent = {
  targetNodeId: lairHexId,
  sphere: lair.properties.dominantSphere as SphereName,
  delta: LAIR_SPHERE_PRESSURE_EMISSION,
  source: 'environmental',   // existing source value
  tick: state.tick,
};
state.pendingSpherePressures.push(pressureEvent);
```

High hex sphere scores (above `LAIR_SPAWN_SPHERE_THRESHOLD`) increase lair spawn probability in the escalation pass. This creates the bidirectional feedback loop without new infrastructure.

```typescript
export const MONSTER_TERRITORY_ATTRITION = 1.2;    // additional Q loss per tick in monster-infested hex
```

## Common Pitfalls

### Pitfall 1: Adding `locationSubtype: 'lair'` without handling it in existing consumers

**What goes wrong:** `LocationSubtype` is used in `encounter-content.ts` `locationTypes` fields, HexMapV2's `LocationLayer`, the ActionDrawer targeting filter, and potentially fog-of-war visibility logic. Adding new subtypes without updating these consumers causes silent failures (encounters don't fire, icons don't render, actions can't target lairs).

**How to avoid:** Search all uses of `LocationSubtype` and `locationSubtype` before adding new values. Key files to update:
- `src/components/HexMapV2/layers/LocationLayer.tsx` — add lair icon variant
- `src/data/encounter-content.ts` — add lair as valid `locationTypes` value
- Action templates — add lair-specific divine action cards

**Warning signs:** Lairs placed in the graph but invisible on the hex map, or encounters never firing at lairs.

### Pitfall 2: Monster factions joining the existing `FACTION_DEFINITIONS` Map without FactionType support

**What goes wrong:** `FactionType` in `src/types/faction.ts` is `'guild' | 'military' | 'religious' | 'political' | 'criminal'`. If monster factions use an undefined type, TypeScript will catch it — but if they're shoehorned into `'military'`, the faction UI (ArmiesTab, faction list) may display them unexpectedly alongside civilized factions.

**How to avoid:** Add `| 'monster'` to `FactionType`. Then filter monster factions out of civilized-faction UI contexts using `isMonsterFaction: true` in properties.

**Warning signs:** Monster factions appearing in the Adventuring Guild roster or the player's faction list.

### Pitfall 3: Lair seeding using worldgen Uint8Array indices vs graph node IDs

**What goes wrong:** `provinceRoles` is a flat `Uint8Array` indexed by hex index (`col + row * cols`). Graph location nodes use string IDs (e.g., `hex_5_3`). The seeding pass must correctly map between the typed array index and the graph node lookup — using the wrong index causes lairs to spawn on ocean hexes or at wrong coordinates.

**How to avoid:** Use the same index calculation as existing passes: `const idx = coord.col + coord.row * cols`. Cross-check with `pass01-provinces.ts` to use the exact same formula.

**Warning signs:** Lairs appearing on water hexes, CLI `graph` command showing lair nodes with missing `located_at` edges.

### Pitfall 4: Monster army attrition double-counting

**What goes wrong:** If monster territory attrition is applied in `phaseArmyAttrition` AND as part of a separate monster encounter spawn, the same lair can trigger two attrition hits per tick. This rapidly destroys armies that enter wilderness.

**How to avoid:** Make monster territory attrition additive to existing attrition (one calculation path in `phaseArmyAttrition`) and the encounter spawn a separate probabilistic check with a per-army-per-lair cooldown.

**Warning signs:** Armies disbanding immediately upon entering wilderness, `ArmyAttritionTrace` showing double attrition values.

### Pitfall 5: Lair escalation running every tick

**What goes wrong:** If `phaseLairEscalation` runs every tick instead of every `LAIR_ESCALATION_INTERVAL` ticks, lairs upgrade too fast and the world becomes unplayable. The `tick % LAIR_ESCALATION_INTERVAL !== 0` guard must be the first line of the phase.

**How to avoid:** Follow the exact pattern from `phaseFactionAmbitions`: `if (state.tick % FACTION_AMBITION_EVALUATION_INTERVAL !== 0) return;` Use the same guard.

**Warning signs:** CLI `tick 5` causing multiple lair upgrades, legendary lairs appearing within 10 ticks of worldgen.

### Pitfall 6: PASS_SEED_LAIRS constant collision

**What goes wrong:** Existing worldgen passes each have a unique `PASS_SEED_*` constant in `src/engine/worldgen/constants.ts`. If `PASS_SEED_LAIRS` collides with an existing value, lair placement will be seeded with the same PRNG stream as another pass (e.g., province seeding), creating correlated patterns.

**How to avoid:** Check `src/engine/worldgen/constants.ts` for all existing `PASS_SEED_*` values before choosing `PASS_SEED_LAIRS = 90211`. Pick a value not already in use.

**Warning signs:** Lairs always appearing at province capitals, or at the exact coordinates of volcanic hexes.

## Code Examples

### Querying Lairs by Hex

```typescript
// Source: codebase inspection of graph API + existing location query patterns
function getActiveLairAtHex(state: GameState, hexLocationId: string): GraphNode | null {
  const colocated = state.graph.getNodesByType('location')
    .filter(n =>
      n.properties.locationSubtype === 'lair' &&
      state.graph.getOutgoingEdges(n.id, 'located_at')
        .some(e => e.target === hexLocationId)
    );
  return colocated[0] ?? null;
}
```

### Spawning a Lair Node

```typescript
// Source: pattern from worldSeed.ts + gameInit.ts location node creation
function spawnLair(
  state: GameState,
  hexLocationId: string,
  dominantSphere: SphereName,
  dangerZone: 'heartland' | 'borderland' | 'wilderness',
): string {
  const lairId = `lair_${hexLocationId}_${state.tick}`;
  state.graph.addNode({
    id: lairId,
    type: 'location',
    name: `${dominantSphere} Lair`,  // prose system will enrich later
    properties: {
      locationSubtype: 'lair',
      lairTier: 'minor',
      dominantSphere,
      spawnedAtTick: state.tick,
      lastEscalationTick: state.tick,
      dangerZone,
    },
  });
  state.graph.addEdge({
    id: `${lairId}_at_${hexLocationId}`,
    source: lairId,
    target: hexLocationId,
    type: 'located_at',
    properties: {},
  });
  emitTrace({
    tick: state.tick,
    category: 'lair',
    summary: `Lair spawned at ${hexLocationId} (sphere: ${dominantSphere}, zone: ${dangerZone})`,
    lairId,
    hexLocationId,
    dominantSphere,
    event: 'lair_spawned',
  });
  return lairId;
}
```

### Province Role to Danger Zone Mapping

```typescript
// Source: worldgen/types.ts constants
import {
  PROVINCE_ROLE_CAPITAL,
  PROVINCE_ROLE_HEARTLAND,
  PROVINCE_ROLE_BORDERLAND,
} from '../engine/worldgen/types';

function getDangerZone(
  provinceRole: number | null
): 'capital' | 'heartland' | 'borderland' | 'wilderness' {
  if (provinceRole === null) return 'wilderness';            // unprovinced hex
  if (provinceRole === PROVINCE_ROLE_CAPITAL) return 'capital';
  if (provinceRole === PROVINCE_ROLE_HEARTLAND) return 'heartland';
  if (provinceRole === PROVINCE_ROLE_BORDERLAND) return 'borderland';
  return 'wilderness';
}
```

## Orchestrator Integration Points

New orchestrator phases and their insertion positions:


# THR-996 — items can get stronger now; the resolver had been complete and uncalled since it was written

**Shipped 2026-08-10.** Christian's verdict, via Discord 2026-08-06: *"Turn the enchantment system on"* — option 1 of three, recorded as `human gate satisfied via chat review 2026-08-06`. A blade carried since the first hour is no longer mechanically identical to the day it was found.

## What was actually missing

`src/engine/attachmentTierAdvancement.ts` was a complete, tested, fail-soft resolver whose module docstring said it is *"Called by the unified action resolution pipeline when an Enchant or Empower action resolves successfully."* No such call existed. THR-723 had already repointed its **output** onto the live `stat_contribution` substrate — the bag `collectStatContributions` sums and `computeRawScore` reads inside its possesses/bonded_to walk — so the resolver was correct if called. It was never called.

The gap was one step narrower than the ticket's grep suggested, and one step worse:

* **`artifact.enchant` already existed as a template**, carrying `onSuccess: []`. It resolved, charged 4 essence, narrated *"the enchantment sets — power flows through the object"*, and changed nothing.
* **`action-technical-effects.ts` told the player it worked**: *"Engine bridge (attachment-tier system): advances the target artifact one magical tier … Handled outside step ops by the attachment-tier resolver."* There was no such bridge and never had been.
* **`engineEffectRegistry.ts` registered the id as an engine bridge**, so `effectSourceFor` badged the card `wired · engine` in the Codex and the ActionDrawer. The badge whose entire job is to answer *"is this actually wired?"* was answering yes about the one action that was not.
* **`artifact.empower` had no template at all**, only a constant naming it, referenced by a `TIER_ADVANCEMENT_TEMPLATE_IDS` array that nothing consumed.

## The wiring

Advancement runs as a step GraphOp, `advance_artifact_tier`, which is the shape the artifact siblings already use — `attune_artifact`, `curse_artifact`, `nullify_artifact` all dispatch from `graphOpExecutor` and are fired from the template's own `onSuccess`. Reusing that seam means the new verb inherits fail-soft batch semantics, tracing and inspectability rather than growing a fourth private path into the same resolver.

Because the effect is now carried by the template's own ops, `effectSourceFor` classifies both verbs `template-ops` on its first branch, and the engine-bridge registration became a **stale claim about a bridge that does not exist**. It was removed, and the registry's spot-check test — which pinned `artifact.enchant` as a bridge — now asserts the opposite for both tier verbs, so a future re-add cannot silently re-mis-badge them.

`artifact.empower` ships as Enchant's martial counterpart: the same mechanical move through a different reach. Enchant was also **corrected from Iron to Veil**, which `attachment-tier-content.ts` had documented all along (*"Template ID for magical tier advancement (Veil/Rune reach)"* against *"martial/physical tier advancement (Iron/Stone reach)"*). Left on Iron, the two verbs would have rolled the same capability against the same difficulty for the same cost — a reskin adding a catalog row and nothing else. A test pins the reaches distinct for exactly that reason.

## What the numbers do and do not do

The step's cost, difficulty and duration are the authored `TIER_ADVANCEMENT_*` constants rather than literals (NFP #1). They are the **tier-1** entries, because a template step is static and cannot read the target artifact's current tier — so the authored ramp (4 → 8 → 14 essence, 0.20 → 0.35 → 0.50 difficulty) reaches the player only at its first rung. Advancing Mundane→Storied and Mythic→Legendary currently cost the same. That needs target-state-dependent step resolution, which is a substrate change and not this action's to make; filed as **THR-1073** with three candidate directions. Hard-coding the ramp inside the graph op would have put game-feel numbers in engine code, which is the thing NFP #1 exists to prevent.

An advance that lands on an artifact already at Legendary returns a **failure** result rather than a silent success. By the time the op runs the essence is spent, so a no-op reporting success would be indistinguishable from a real advance on every surface the player can see.

## Evidence

End-to-end in a real seeded world (seed 42, medium, 10 ticks, 435 actors), firing the template's own authored ops through the production `executeGraphOps` against a generated artifact — *"Iron Blade"*, held by `ind_0` on a real `possesses` edge — and reading back through `collectStatContributions`, the same query `computeRawScore` uses:

```
artifact.enchant: reach=veil essence=4 difficulty=0.2 ops=[{"op":"advance_artifact_tier","nodeId":"$target"}]
artifact.empower: reach=iron essence=4 difficulty=0.2 ops=[{"op":"advance_artifact_tier","nodeId":"$target"}]

cast 1: ok=true  tier 1 (Mundane) → 2 (Storied)      iron 0.3   → 0.45
cast 2: ok=true  tier 2 (Storied) → 3 (Mythic)       iron 0.45  → 0.675
cast 3: ok=true  tier 3 (Mythic)  → 4 (Legendary)    iron 0.675 → 1.013
at cap: ok=false error="advance_artifact_tier: already_max_tier"
```

The compounding is clamped to `ITEM_STAT_BAND_LEGENDARY`, so repeated bumps cannot become a back door around the authored power budget.

The wiring test was falsified against the pre-fix shape before being trusted: reverting both templates to `onSuccess: []` fails it with `expected [] to include 'advance_artifact_tier'` — which is precisely the build that shipped until today. Asserting the `tier` numeral alone would have passed against a build where advancement strengthened nothing readable, so every assertion reads through the live substrate instead.

**UI pillar: no change needed, and that is a finding rather than a skip.** `AttachmentRow` and `AttachmentDetailView` already render `ATTACHMENT_TIER_NAMES[tier]` and `ATTACHMENT_TIER_COLORS[tier]`, so a tier bump surfaces on the item card and the character sheet the moment it happens. The change touches no file under `src/components/`, `src/hooks/`, `src/contexts/` or `src/index.css`, so the browser-verify trigger does not fire.

Two adjacent defects were filed rather than absorbed: **THR-1074** (Empower ships artless — the THR-769 class, and art generation needs a pipeline an unattended run cannot drive) and **THR-1075** (`artifact.attune` / `nullify` / `curse` still tell the player they are *"NOT YET WIRED"* though THR-605 shipped their GraphOps — the exact inverse of the defect fixed here, filed with a predicate rather than the three names).

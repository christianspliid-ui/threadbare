# THR-862 — joining a faction is its own event, so the beat can finally anchor

**Shipped 2026-08-09.** Project: Attention Tier Model. Pillar: Engine (Content N/A, UI N/A — the
surface this feeds, the Threads-panel faction row, shipped whole under THR-667).

## What was wrong

`src/engine/factionOutcome.ts` emitted **an agent joining a faction** as `type: 'faction_founded'`,
under a code comment that conceded the mislabel outright — *"closest existing type for 'joined
faction'"*. That same type is also the genuine *a new faction now exists in the world* event, minted
from a different producer (`src/engine/initiativeOutcomes.ts`).

One type, two meanings, and the notification threading gate keys on `event.type` alone. So
"Vann has joined The Merchant Consortium" — plainly faction-scoped news that belongs on the
faction's row in the Threads panel — could not be routed there, because anchoring the join would
have anchored **every founding** along with it. Founding is world-scale and correctly sits in
`ALWAYS_GLOBAL_EVENT_TYPES`. THR-667 saw this and deliberately declined to reclassify: silently
changing what a shared type means is how the next reader gets surprised. It left the join beat
toasting globally and filed the split as this ticket.

## What shipped

Joining now emits `faction_member_joined`, a type of its own, and that type joins
`faction_rank_changed` in `FACTION_ANCHORED_EVENT_TYPES`. `faction_founded` retains only genuine
founding and stays world-scale. The conceding comment is gone, replaced by a note at the
`ALWAYS_GLOBAL` entry recording *why* the two were ever one type, so the next reader inherits the
reasoning rather than the puzzle.

Four files: the `TickEvent` union (`src/types/gameState.ts`), the emitter, the gate, and the
wiring-checklist's "Known gap (THR-862)" note, which is now a "Gap closed" entry.

**Nothing needed changing in the router**, and this was checked rather than assumed:
`eventTypeToCategory` and `deriveNavigationTarget` in `notificationRouter.ts` both match on the
`faction_` **prefix**, so the new type categorizes as `social` and navigates to the faction with no
edit. No chronicle or event-type filter enumerates `faction_founded` — the only consumers are the
union, the two producers, the gate, and tests.

## The evidence, and one thing it deliberately does not claim

Two tests carry the acceptance, and they pin different halves:

- `factionUIAndVisibility.test.ts` drives the **real** `processFactionOutcome` with a completed join
  progress and asserts the emitted type. This is the production function, not a fixture standing in
  for it.
- `notificationThreadingGate.test.ts` asserts the **routing**, not just set membership: a join beat
  whose actor is unthreaded but whose faction is threaded resolves to
  `{ kind: 'entity', anchorId: 'faction_threaded', anchorKind: 'faction' }`. Without the set entry it
  would fall through to the unthreaded-mortal path and suppress, so the test genuinely falsifies.
  A second case pins both halves at once — the join anchors **and** founding does not — because
  asserting only the first would still pass if a later change moved joining back under
  `faction_founded`: `ALWAYS_GLOBAL` is checked first, so the beat would silently toast world-scale
  again with the anchored-set assertion still green.

**What a live CLI run did not show.** Over 165 ticks of seed 42 the sampled event stream carried 12
`faction_rank_changed` and **zero** joins — and zero `faction_founded` too, which is the useful half
of that reading: the join emitter was equally unreached *before* this change, so its absence is not
something the rename caused. Faction joins simply do not occur naturally in that window.

Driving the encounter directly did not close the gap either, for a reason worth recording:
`spawn encounter` mints a **unified action**, while `processFactionOutcome` is called from the
orchestrator only on the encounter-**progress** path (`progress.status === 'completed'`). The two
are different pipelines, so the spawn resolved `success` while never reaching the faction outcome
processor — no `member_of` edge, no event. That is a property of the probe, not a defect in the join
path, and it is logged as impediment #514 so the next session reaching for `spawn encounter` to
observe a faction outcome does not read the silence as a broken pipeline.

So the acceptance rests on the headless sweep of the real emitter plus the routing test — which is
what the ticket's Done-when asked for (*"Engine/content acceptance via `npm run cli` or a headless
sweep — no browser evidence required"*) — and the live-run limitation is stated rather than papered
over.

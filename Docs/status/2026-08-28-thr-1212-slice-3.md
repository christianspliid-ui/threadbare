# THR-1212 slice 3 — the no-referent chip ratchet

Law 56 clause 2 asks whether a consequence chip that *names* something points at
something real. It scopes itself to chips that declare a referent, and that
scoping is correct: a chip naming nothing makes no claim the clause could be
about. But the whole-catalog runner then prints **`templates failing 0`** over a
corpus containing 443 chips it never looked at — and "green" there means
*unmeasured*, not clean. This slice puts a number on the silence and a ceiling
over it.

## What shipped

`chipsWithoutReferent` joins `chipAnchorViolations` in `compositionContract.ts`,
walking the same `aftermathFaces` the clause walks. Not reimplemented in the
script, deliberately: a second walk drifts, and two numbers that stop describing
the same corpus is this ticket's own subject in miniature.

`check:chip-anchors --baseline` compares that count against a committed
`chip-referent-baseline.json` and fails only on an **increase**, the
`check:typecheck` pattern the plan named. `--baseline --update` refreshes it when
a retrofit batch legitimately drains some.

The measured count is **443 across 271 templates** — the plan's design-time
figure, reproduced independently by a predicate written from its description
rather than from its number. That agreement is the main evidence the right
population is being counted.

## The predicate, and the one case that needed a decision

A chip counts when **at least one reachable face** authors it with no `stateNoun`
and an empty-or-absent `concepts` list. "At least one" rather than "every",
because a band override substitutes `changes` wholesale: the same chip id can
carry an anchor on the base face and none on `failure`, and a player who rolls a
failure is shown the anchor-less one regardless of how the other reads. Counting
per id rather than per face matches what an author fixes — one chip, once.

## The guard was falsified, not written

A no-referent chip added to `encounter.slice.unsafe_bridge` in the live tree —
a template at zero — moved the count **443 → 444**, failed the gate by name
(`encounter.slice.unsafe_bridge: 0 → 1 (+1)`), and exited 1. Then reverted. The
perturbation was confirmed to have *applied* before the verdict was read, which
is the check impediment #872 exists for: last slice a controlled arm silently did
not apply and made a real guard read as vacuous.

The missing-baseline, invalid-JSON and wrong-shape arms are each red for their
stated reason in the unit tests. A ratchet that reads an absent or corrupt
ceiling as "no ceiling" passes everything while looking green — worse than no
gate at all.

## Three findings

**The existing check was never in CI.** Item 3 asked for the ratchet "beside the
existing check". `check:chip-anchors` had no CI step. `check:encounter --all`
enforces clause 2 only over the `encounter.` prefix, so the whole-catalog runner
— the one THR-1164 built precisely because 19 of the clause's original 48
violations sat under `hod.*` — was running nowhere. Both are now steps in
`Test · Typecheck · Build`; the base gate is green over 698 templates.

**The house entry-guard idiom is unavailable here, and using it would have failed
open.** `check-chip-anchors.ts` is bundled by `esbuild --bundle`, which relocates
the entry so `import.meta.url === argv[1]` stops being a reliable "am I the
entry" test. A guard that silently fails there makes the gate exit 0 without
running — the exact false green this ticket is about. The pure arithmetic moved
to `scripts/chip-referent-ratchet.ts` instead, where importing it does nothing,
and the runner keeps its top-level execution unchanged.

**The gate is total-only, and that is written down rather than left to be
discovered.** A change anchoring three chips in one template while authoring
three unanchored ones in another passes. Per-template growth is printed but
advisory, mirroring `check:typecheck`. If that swap ever actually happens it is
the defect evidence that charters tightening to a per-template ratchet — it is
not assumed in advance, and a gate advertising reach it lacks is the failure
slice 2 spent a section correcting.

## Deliberately not done

`chip-referent-baseline.json` is **not** registered with
`check:generated-freshness`. That gate regenerates an artifact and byte-compares
against `HEAD`; for a ratchet floor it would force the baseline to equal the
current count on every commit and delete the only thing it does. It is a
committed decision, not a derived artifact — the `typecheck-baseline.json`
precedent exactly.

# THR-1422 — one owner per shared constant, and a guard that can actually see duplication

**Shipped 2026-09-07.** Engine + UI. [THR-1422](https://linear.app/threadbare/issue/THR-1422/six-constants-are-defined-twice-with-no-shared-source-sea-level).

## What was wrong

Six constants were declared in two modules each, with **no shared source and no disagreement** — every pair held identical values. That is what made it invisible: no detector can flag it, no test fails, and the cost is entirely deferred to the first person who tunes one copy. An NFP #1 (Tunability) defect, not a correctness one. The remainder of the probe that produced [THR-1409](https://linear.app/threadbare/issue/THR-1409/three-worldgen-constants-are-declared-twice-with-different-values-the), which covered the pairs that had already diverged.

| constant(s) | copies | now owned by |
| -- | -- | -- |
| `SEA_LEVEL` | `engine/worldgen/constants.ts`, `components/HexMapV2/palette/waterPalette.ts` | **worldgen** |
| `TRUST_COOPERATE_DELTA`, `TRUST_DEFECT_DELTA`, `TRUST_DECAY_PER_TICK` | `data/agent-behavior-constants.ts`, `types/disposition.ts` | **agent-behavior-constants** |
| `REACH_TO_SPHERE`, `SPHERE_COLORS` | `components/icons/constants.ts`, `data/premonition-constants.ts` | **premonition-constants** |

`SEA_LEVEL` is the load-bearing one: it crosses the engine/render boundary with neither module importing the other, so moving it in one place paints water where the engine says land. Its three surrounding doc-comments named **three different authorities, one of which does not exist** — `terrain.ts`'s `ELEV` is real but has no `SEA_LEVEL` key (its bands are `DEEP_OCEAN`, `SHALLOWS`, `LAKE_MAX`, …, which classify biomes *within* the water column rather than dividing water from land). Both false citations are corrected; `waterPalette.ts`'s *"must match worldGen … by hand"* is replaced by the import that makes it true by construction.

## Direction of ownership, which was the actual judgement

The ticket left the repoint direction per pair to the executor, and getting it backwards is silent. Each was decided by **which layer has to be able to read it**, not by which copy had more consumers:

- **`REACH_TO_SPHERE` could not stay at the icons site.** The engine reads it (`phaseDivinePremonition.ts`, `premonitionCompulsion.ts`), so a `src/components/` module cannot own it without inverting the layering — the higher-consumer-count copy was the wrong owner. `SPHERE_COLORS` follows it so the cosmology's mapping and its colours stay in one place.
- **The trust triple went to the tunables file**, which carries the `@range` annotations the CMS panel renders. `trustMechanics.ts` — the only consumer — already read that copy, so the `types/disposition.ts` block was three tunables nobody could tune: editing them would have changed nothing in the simulation.
- **`REACH_TO_SPHERE` was re-typed `CreationSphereName`** (from `SphereName`) at its new home. That was already the narrower type at the icons site, and dropping to the wider one would have quietly cost every UI consumer its precision.

All four repairs are **re-exports**, so every existing import site still resolves — no consumer was touched. `SPHERE_COLORS_BASE`, `MAX_AWARENESS_HOPS`, `DEFAULT_DOOM_TICKS`, `TRACE_CATEGORIES` and `OUTCOME_BAND_PROSE` were left alone per the ticket's out-of-scope list.

## The pin, and why the obvious guard could not work

The ticket named the trap and it is worth stating flatly, because **two plausible guards are both tautologies here**:

```
expect(waterPalette.SEA_LEVEL).toBe(0.38)             // passes before the fix
expect(waterPalette.SEA_LEVEL).toBe(wg.SEA_LEVEL)     // also passes before the fix
```

Both copies held equal values, and numbers compare by value — so identity is unavailable for primitives and a cross-module equality assertion holds in exactly the duplicated world the ticket exists to leave. **The THR-1409 guard does not transfer either**: it intersects runtime namespace *keys*, which works only because that fix deleted its duplicates. A re-exported name is still a key of the mirror's namespace, so that sweep would report these six as still-duplicated after a correct repair.

So `src/engine/__tests__/constantOwnership.test.ts` asserts ownership where it is actually visible — in the source: the owner declares the constant, the mirror does not. Two falsification arms, because a source-text guard fails silently in both directions:

1. **The detector fires on every owner** — a regex that stopped matching anything would make every "mirror declares it zero times" assertion trivially true and report perfect compliance on a codebase it cannot read.
2. **Comments do not read as declarations** — this repair added prose naming all six constants; without comment-stripping, a mirror could "pass" by deleting code and keeping the comment, or fail for the reverse.

**Red baseline proven, not assumed.** The three mirror files were reverted to their `origin/main` state and the guard named all six duplicates by file and count, plus the two object-identity assertions — then restored and re-run green. For `REACH_TO_SPHERE` / `SPHERE_COLORS` the identity check is a *real* single-binding assertion, since objects do not compare by value; only the four primitives need the source-text route.

## UI evidence

`Browser-verify substitution: jsdom-render` — unattended scheduled run, no startable dev server (#546). Route decided at claim, before any code.

The change is deliberately **visually neutral**, which is the hardest claim to evidence: every existing icon test derives its expected colour from the very constants that moved, so all of them would keep passing if a surface were re-pointed at a divergent map. They assert self-consistency, not parity. `src/components/icons/__tests__/sphereColorRenderParity.test.ts` supplies the missing oracle — the twelve hex strings and the eight reach mappings are **literals transcribed from the pre-change tree**, so they still say what the UI used to paint after the source of truth moved out from under them. All 8 reach icons and all 12 sphere icons render byte-identical output.

One drafting error, caught by the test rather than shipped: the first version asserted the `base` icon variant paints `SPHERE_COLORS_BASE`. It does not — both variants use `SPHERE_COLORS` as the CSS-variable fallback and differ only in which variable they name (`--sphere-X` vs `--sphere-X-bright`), and `SPHERE_COLORS_BASE` is not wired into that generator at all. The arm now asserts what the code actually does.

**No `__DEBUG` state assertion is offered, and none exists to offer** — this change adds no state field, surface or interaction. The equivalent wiring proof is the object-identity assertion that the icons surface and the engine read the *same binding*, plus the render-parity arms above. Stating that plainly rather than dressing an unrelated probe as evidence.

**UI Laws** (`Docs/design-system/laws.md`): Law 4 (one visual language) and Law 14 are the ones this repairs rather than risks — two sphere→colour maps could paint one Sphere two colours on two surfaces, which renders as "the UI is subtly wrong" and never as an error. Laws 1, 13/14, 17, 21, 33, 37 checked on the icon surfaces as composed: no rendered output changes, so no law's status moves. No new violation introduced; none pre-existing found on these surfaces.

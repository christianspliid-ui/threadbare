**The merge-health probe could not see a red check, so it reported half a diagnosis with total confidence (THR-1020, 2026-08-07).** Three prior fixes widened *which* PRs `check-armed-prs.ts` read (THR-930), *how* it read their merge state (THR-897), and whether a park was a stall (THR-985) — and all three read merge state **only**. A PR has two independent ways to be unmergeable, and `statusCheckRollup` was absent from the probe's `gh pr list --json` field list, so the second one was invisible by construction. Two measured costs: impediment **#466** — PR #1327 reported `conflicted`/`abandoned` at 18h with `conflictFiles: [Docs/project-status.md]`, reading as a one-file hand-resolve when it was *two* blockers, ~15 min of second-pass diagnosis, and a PR that would have re-reported under a **different** verdict next hour while ageing; and impediment **#402** — an armed PR sat ~100 minutes reading as shipped from every surface except the rollup, because `BLOCKED` classifies `waiting` and `waiting` asserts *"auto-merge fires on green"*, a claim the probe had no field capable of falsifying. The rollup is now read and reduced to a per-PR `checkConclusion`, used twice: a red PR in an otherwise-green merge state classifies **`failing`** instead of `waiting`, and a `conflicted` PR that is *also* red keeps its class and its age tiers while naming both blockers in the same row — `conflictFiles` is documented as a lower bound, never the whole diagnosis. **Only the two checks branch protection actually requires are consulted** (`Test · Typecheck · Build`, `Docs gates`, verified against ruleset `15479914`, the sole protection surface since THR-983): reading the whole rollup would report a PR unmergeable on a red `Vercel`, which is deliberately not a gate and must not become one, so the allowlist is what keeps a *notification* concern from turning into a *merge-gate* one. **The fail-soft runs toward silence here, opposite to `Hold:`, and deliberately** — an unreadable rollup or a required check with no entry yields `unknown`, never `failing`, because a missing entry almost always means "not started yet" and a probe that escalated on it would fire on every PR in its opening minutes and be trained away within a day; a genuinely red check always produces an entry, so the escalating signal is a conclusion's presence rather than its absence. `SKIPPED` is kept distinguishable from `passing` for the THR-768 reason — a skip satisfies protection *without having inspected anything* — while `CANCELLED` counts as red, since unlike a skip it does not satisfy protection at all (THR-1013). **The defect was live on the board at pickup and the fix caught it immediately**: the old probe called this repo `verdict: "healthy"` — *"2 are waiting on checks and will merge on green"* — while PRs #1334 and #1335 were both red (`Docs gates` on an `npm ci` ECONNRESET; `Test · Typecheck · Build` on a 5s test timeout with 15088/15089 passing). Both flakes, and a flake is still a *permanent* stall: auto-merge does not retry, so both would have sat armed and unmergeable indefinitely, invisible. The new probe reports `verdict: "failing"`, names both, and the failed jobs were rerun in the same pass. 20 tests added (63 → 83), including the verbatim live rollup shape as a fixture.

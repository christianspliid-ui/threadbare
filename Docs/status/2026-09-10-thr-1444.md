# 2026-09-10 — THR-1444: a harm that outlives the place it was aimed at

**Pillar:** Engine (Content N/A, UI N/A — no player-facing surface changed; the defect is a
missing graph edge, and its visibility fix is a trace field.)

## What was wrong

`createUndertakingOutcomeNode` wrote the outcome event, then stamped it with an
`occurred_at` edge to the site. The site resolved as:

```ts
const siteId = project.originLocationId
  ?? graph.getOutgoingEdges(project.actorId, 'located_at')[0]?.target;
```

`originLocationId` is a **plain string**, stamped once when the undertaking is created
(`strategicActionLifecycle.ts:493`, via `resolveDurableActorLocation`, which validates it
*at that moment*) and never revisited. Undertakings then run for hundreds of ticks.

`WorldGraph.removeNode` cascades incident edges — so a `located_at` edge can never dangle —
but it cannot reach a string held on a project runtime. A settlement retired mid-flight
therefore left the origin pointing at nothing, **and the `??` fallback was never reached,
because a dangling string is still truthy.** `addEdge` threw, the `catch` warned, and the
event landed durably with no site at all.

The write site's own comment states the stake: *"The site is what makes witnesses possible:
the mint lane finds witnesses by walking `occurred_at` back from the location they are
standing in."* A harm nobody can witness mints no grievance — and nothing reads a
`console.warn`, so the sweep that emitted it printed `VERDICT: PASS`.

## What the measurement corrected in the ticket

The ticket's diagnosis pointed at *"what removes a location node while agents are still
`located_at` it"*. That is the right upstream event but the wrong repair site: `removeNode`
already tears down the `located_at` edges correctly. The unreachable half is the **stored
string**, which is why the failure presented as one actor pointing at one dead location and
failing on every cell it ran thereafter. Fixing the remover would not have helped; fixing
the *reader* does, and is the additive direction (NFP #6).

The ticket also predicted **4 failures** on seed 42 at 900 ticks. This run measured **1**
(`evt_und_proj_cell.create.location_ind_10_373_433 → loc_18`). The mechanism is identical;
the count moved because `main` has moved. Stated rather than smoothed over.

## The fix

`resolveOutcomeSite(graph, project)` — exported, unit-addressable — resolves against a node
the graph actually holds, in the same preference order as before:

1. `originLocationId`, **if `graph.getNode` finds it** → `siteResolution: 'origin'`
2. otherwise the actor's live `located_at`, if that resolves → `'actor_position'`
3. otherwise no edge at all → `'unresolved'`

Preference order is deliberately unchanged where both are live: a razing belongs to the
place it happened, not to wherever the razer wandered next. What changes is that a dead
origin now *falls through* instead of throwing.

The `console.warn` becomes trace state (NFP #2, Inspectability). `UndertakingOutcomeEventTrace`
gains `siteId?`, `siteResolution`, and `siteOriginStale?: true` — the last set only when the
origin was present *and* dead, so a rising count says "locations are being retired out from
under in-flight undertakings" instead of scrolling past in stderr. No new trace **category**
(the category has four registration sites; adding fields to an existing one has none).

## What this does not claim

The ticket is honest that four events in 900 ticks cannot explain the zero organic supply
THR-1388 and THR-1383 measured, and this run does not upgrade that. One recovered site per
900 ticks is a mechanism closed, not a supply problem solved. What is now true is that the
mechanism can no longer fail **silently**: `siteOriginStale` is a countable quantity, so the
next reader can size it instead of re-deriving it from stderr.

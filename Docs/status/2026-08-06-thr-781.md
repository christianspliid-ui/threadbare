**The event id was keyed to the agent, but the loop it was minted in iterates memberships (THR-781, 2026-08-06).** `phaseFactionReputationDecay` walks `member_of` edges, so an agent who belongs to two factions decays in both — and on the tick a decay crosses a rank threshold in both, it pushes two demotion events. The id was `faction_decay_rank_{tick}_{agent}`, which does not name the faction, so the two notices collided and React logged *"Encountered two children with the same key"*. Its own wording is the stake: the behaviour is unsupported, so one of the two demotions can be silently dropped and a player never told they were demoted. **The multi-faction case is ordinary, not exotic, and that is what makes the collision reachable:** `factionSeeding` mints faction *nodes* per chapter as `faction_def_{defId}{suffix}`, so two memberships can share one `factionDefId` — hence one decay rate, one threshold, and demotion in lockstep on the same tick. Fixed by putting `edge.target` in the id. **The guard is the deliverable, not the one-token change**, because an id collision is invisible to every gate the repo owns: both events dispatch, both are well-formed, and the only witness is a React console warning nobody diffs. The regression test builds two chapters of one guild, demotes an agent in both on one tick, and asserts two events with two distinct ids and two distinct `factionId`s — falsified against the pre-fix tree, where it reports `expected 1 to be 2` on the id-set size while the event count itself passes, which is precisely the shape that lets the defect hide. Sibling event-id mints in the same file were swept as the ticket asked: there are none. Live confirmation at `?view=game&seeded&size=medium` after `__DEBUG.tick(60)` — `faction_decay_rank_60_npc_92_faction_def_builders_fellowship`, faction now in the id, zero console errors.

# THR-2095 — A won encounter no longer hands out a wound and calls it a boon

**Shipped 2026-10-31.** Onboarding & First-Run Experience. Christian's Faction Bounty aftermath read "Hesper won … The work on Shadow went well", then listed **BOON · CRACKED RIBS ▲** with "Hesper gained Cracked Ribs." Three faults: the success prize pool could draw a `#negative` condition (`fa.bounty_hunt`'s Shadow step weights `condition: 0.30` on success, and the pool never filtered harm); any step reward on a won step reached the aftermath as `item` + `gain` → PRIZE → BOON; and the row named no cause.

**Fix.** Engine: `assembleRewardPoolDetailed` drops every `#negative` template unless the recipe carries the new `admitsHarm` flag (`RewardPoolRecipe`, additive). Only the bad-outcome table sets it: `toBadOutcomeRecipe` in `rewardPool.ts`, and the legacy reward route in `orchestrator.ts`. The tag string is a local `REWARD_HARM_TAG`, because importing `HARMFUL_CONDITION_TAG` would cycle through `effectEventDispatch`; a test pins the two equal. `resolveUnifiedReward` marks a draw `harmful` when it flipped bad or picked a `#negative` template. The aftermath change then carries `harmful: true`, `category: 'scar'`, loss polarity and a cause clause. Content: `REWARD_HARM_CAUSE_LINES` in `aftermathWords.ts` holds eight short cause lines keyed on the template's tags (`#combat`, `#disease`, `#curse`, `#fear`, `#reputation`, `#physical`, `#wound`, fallback). Each has a won line ("Not cleanly: …") and a lost line, and every one fits the 15-word chip budget with its detail. Display: `asHarmIfHarmful` in `buildAftermathConsequences` folds any change flagged `harmful` to SCAR / WOUND with a falling mark, whatever its wire kind or declared category. Rendering code is unchanged.

**Review gate, round 1** found two real defects, both fixed. (1) The filter also emptied recipes authored as harm: four Holy Order failure steps (`tagFilters: ['#wound']`) and the sprung trap (`condition: 1.0` on both bands). `resolveRewardRecipe` now sets `admitsHarm` on every non-win band, and the trap's two recipes set it by design. (2) A bad-outcome flip that drew a `#positive` blessing would have read as a scar. Harm is now the template's `#negative` tag, or a flip that drew anything not tagged `#positive`.

The ticket's first step asked which path drew this one. That was not reproduced from the screenshot alone. Both paths are closed: the success pool can no longer hold harm, and a bad-outcome draw now reads as a scar.

**Evidence.** `src/engine/__tests__/rewardPool-harm.test.ts`, 15 tests: no `#negative` template in a success or critical-success pool against the real condition catalog, with a falsifying arm; 300 seeded success draws deal harm only on a flip; a harmful `item` + `gain` change folds to SCAR / WOUND / loss under any wire kind, and the unflagged twin still reads BOON; the cause clause leads the sentence and fits 15 words. `EncounterVeil.test.tsx` adds a jsdom render of the composed veil: the chip shows SCAR and not BOON, its delta cluster reads `data-direction="loss"`, and the cause line is drawn. `rewardPool-dedup.test.ts`'s condition fixture is a `#negative` wound, so that recipe now sets `admitsHarm`. `npm run gate`: PASS (test, typecheck, build, encounter, god-cards, ui-debt, cli-smoke).

Browser-verify substitution: jsdom-render. This is an unattended run, and the Done-when's subject is the chip's category, its arrow and its cause text. Chip rendering is unchanged, and forcing a specific harmful draw in a live tab has no debug lever.

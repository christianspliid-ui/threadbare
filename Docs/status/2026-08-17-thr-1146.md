# THR-1146 — an ending can hand out a random matching prize

**Shipped 2026-08-17.** Fourth member of the consequence-palette expansion (plan doc `Docs/plans/2026-08-16-consequence-palette-expansion.md` § Primitive D), after THR-1142 (`agent_relocation`), THR-1143 (location conditions) and THR-1144 (`membership_change`).

## What changed

`reward_draw` — a seeded, tag-filtered random attachment draw, available anywhere effects go: aftermath reactions, outcome bands, step effects, card grants.

The director's ask was *"a primitive that allows an encounter to give e.g. a random item with a certain tag, for example a random #gold #weapon"*. Almost all of that machinery already existed. `RewardPoolRecipe` (`categoryWeights` + `tagFilters` + `sphereTint`) has always resolved a tag-filtered, tier-weighted draw through `assembleRewardPool` — but it was reachable **only** from step `successMetadata`/`failureMetadata`. So a *specific ending* — "the keeper pays you off with a blade from the strongbox" — could not draw a random `#weapon`; it could only spawn one fixed authored artifact, the same one every time.

This kind is that recipe reaching the rest of the effect vocabulary. It adds no tuning surface of its own: the tier curve and bad-outcome chance come from the action's already-resolved outcome band, exactly as the step route takes them from the step's. A better ending draws a better prize for free.

## One draw path, not two

The obvious build was to copy the twenty lines out of `resolveUnifiedReward` into a new dispatcher case. That produces two draws which agree on the day they are written and diverge the first time either tier curve is tuned, with nothing to notice.

So the draw moved into `drawSeededReward` (`src/engine/rewardPool.ts`) and **the step route was moved onto it in the same commit**. There is now exactly one seeded draw in the codebase and two callers of it. The identity the ticket asked for is a property of the code, not a claim a test has to keep re-checking.

The test asserts it anyway, because the property is what the structure is *for*: the dispatcher's drawn template is compared against a direct call with the same seed key, and a different key is shown to draw differently — otherwise "identical" would be satisfied by a draw that ignored its seed entirely. Falsified by perturbing the dispatcher's seed key: the identity arm goes red, alone.

## The gate, and why it is not a spelling check

Tags carry their `#`. The library writes `'#weapon'`; `'weapon'` is a perfectly well-typed string that selects the empty set, and nothing at runtime complains — the prose still promises a prize and the player gets nothing. That is the THR-844 rot class exactly: 66 dead hidden-mark references nobody saw for months, because a dead reference costs nothing at runtime.

`validateRewardDrawPools` resolves every authored recipe against the live catalogs at authoring time, and fails it in `check:encounter`'s liveness stage. Crucially it runs the **engine's own** `rewardCategoryNodeQuery` / `rewardCandidateMatchesTags` predicate rather than a reimplementation — a gate that reimplemented the mapping would drift from the runtime it guards, which is the failure it exists to prevent.

Falsified in both directions before being trusted. With the validator stubbed to `return true`, all four RED arms fail; restored, the shipped corpus is green. The RED arms cover the realistic slips: a missing `#`, a tag nobody wrote, and a combination that is *individually* live but jointly empty (`['#weapon','#potion']` — the case a per-tag existence check would wave through).

`check:encounter --all` only sees the `encounter.*` prefix — 191 of 683 templates — so the corpus-wide invariant lives in the test file rather than the CLI gate. The exemplar is an `mc.*` id and would otherwise have been gated by nothing at all.

## Driven live, not just unit-tested

THR-1144's two real bugs were invisible to its unit tests and surfaced only in a seed-42 CLI world, so this one was driven the same way. A real seeded world carries **25** `#weapon` artifacts (24 reward-catalog entries plus `starter_iron_blade`) — my fixture had seeded the catalog by hand, which proves nothing about world seeding. Forcing the exemplar reaction to fire:

```
[aftermath_reward_draw] reward_draw[1]: The Unchained earned Cracked Brass Horn (T1 possession, pool 25)
```

`pool 25` matching the live count exactly is what says the tag filter is applied rather than ignored. The drawn item was then checked rather than assumed — `reward_arms_cracked_brass_horn` genuinely carries `#weapon` (a command horn classed as arms), so the draw stayed inside its filter.

## Two smaller things, both deliberate

`resolveUnifiedReward` now passes a `recipientId` where it previously passed none. That feeds only the companion cap/unique filters (THR-1096), which the orchestrator route has always passed and this one never did — so `companion` category weights were silently unreachable from step metadata. Verified inert on the shipped corpus before changing it: no content sets a `companion` weight in a step `rewardPool`.

And `normaliseRewardOutcome` closes a hole in the shared path: `OutcomeType` carries a fifth member, `success_at_cost`, that `getTierCurveForOutcome` has no arm for — it returns `undefined` and the destructure in `resolveRewardRecipe` would throw inside the tick loop, against NFP #4. Both existing callers happened to map it away first, so the hole was never reachable; closing it in the shared path means the third caller cannot reopen it.

## Content

`mc.quest.collect_bounty` gains a third reaction, `mc_bounty_kept_the_arms` — "Whatever the mark was carrying." The Company pays for the body, not the belt, so the arms go to whoever walked them home. It draws some `#weapon`: 24 templates across all four tiers, so the outcome band genuinely decides how good the prize is.

Placed in `mc.*` deliberately — THR-1130 is retrofitting the 15 nudge-era `encounter.*` templates at volume, and this avoids a pointless content conflict.

**UI: N/A.** The draw lands as an attachment and renders through the existing PRIZE chip path (`item` change kind), untouched.

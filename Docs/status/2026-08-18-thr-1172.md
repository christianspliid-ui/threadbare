# THR-1172 — the entity-reference contract, finished

**Shipped 2026-08-18.** Director bug report from the re-passed Grateful Kin
aftermath on the deployed build: *"now at least the location (sacred grove) and
the game concept (favor owed) is underlined so players can see what it is. but
there is no tooltipping and/or linking to a detail page or explanation of the
concept. this UI pattern needs to be finished and used for all links."*

`NarrativeSegments` has stated the three-tier rule in its own header since
THR-1084 — **link** (click + underline), **explain** (tooltip + underline),
**text** (nothing) — and the underline is drawn on what the surface can actually
*do*, never on the mere presence of an id. It did not hold to it.

## What was wrong, and what each fix was

**1. The underline that answered nothing.** The style condition read
`seg.referenceId || explains`. A `referenceId` is the narrative linker's
colon-grammar bookkeeping (`cast:<key>`, `location:<key>`) and nothing downstream
consumes it — only `explains` gets a `Tooltip`, only `open` gets a click. So a
segment carrying one drew the mark that promises an answer and had none. That is
the pixel the director reported, and "Sacred Grove" reached the screen through
exactly this path: it is a worldgen-minted place name, not authored content.
Now the underline is drawn on `explains` alone in that branch.

**2. `location` was not an entity kind,** so a scene could name the ground it
stood on and the word could not even *declare* itself openable. Added to the kind
union, the veil's `openEntity`, and `visualKind`. It needed no new destination —
`LocationProfileModal` has been reached by the thread list and the hex map all
along, and `GameView`'s handler already mapped every remaining kind to a
`ThreadCategory`. Only the door was missing.

**3. No `location.*` tooltip prefix.** Added, and **deliberately leading with the
static half** rather than the graph-bearing shape the ticket sketched:
`location.grove` resolves the *kind* of place from world-model with no context at
all. That matters because `Tooltip` and `tooltipResolves` both call the resolver
context-free, and `tooltipResolves` is what decides whether a word is underlined
— so a purely context-bearing arm would have been inert at the one call site the
player actually hovers, and Sacred Grove would have kept its silence. The
context-bearing half (a named place by node id) is there and nothing depends on
it. The `agent.*` caveat (THR-1159) is recorded as a live constraint rather than
inherited.

**4. No concept explanation for the favour.** Registered `ui.favour_owed` (173
chars, Law 18) and authored it onto all four Grateful Kin favour chips. The chip
already anchored the debtor correctly, so the *click* was right; what it could
not say was what the thing being owed is. **And the gate was extended**: an
anchored noun's `tooltipId` must now provably resolve, not merely be present — a
dangling one previously discharged Law 56 clause 2 and shipped an underline that
explains nothing. Checked context-free on purpose, because that is the check the
surface makes; a gate that disagrees with the pixels is not a gate.

**5. Conformance sweep.** Every underline site now either earns its mark or loses
it. Table in the PR body. `PlaceOfPowerInspector`'s recorded rationale for *not*
having a location kind ("widening that union would make every existing
`openEntity` contravariant") is now spent — and the variance never bit, since its
handler types `kind` as `string | undefined`. Its behaviour is unchanged and still
correct, on the surviving reason: it is handed no location destination.

## Decisions recorded

- **The codex arm is not cheap, so it is mapped, not built.** `NavigationTarget`
  still has no `codex` kind, so a pure concept has an explain tier and no
  destination. The codex is reachable only via `window.location.search =
  '?view=codex'` — a full page navigation that would destroy the running
  encounter — so the arm needs an in-game codex surface first. Filed as a wave-1
  item on THR-1157.
- **The location link tier is capability-complete but not yet exercised by
  content.** No shipped chip declares `visualKind: 'location'` today, so the
  location half of the fix currently shows up as *"stops lying"* rather than
  *"now answers"*. The producer-side work — resolving a scene's location to a real
  node id so places link systemically rather than per-chip — is filed as a
  deferral.

## Evidence

Both gates falsified before being trusted. The two negative tiers fail on the
pre-fix renderer and pass after; the three new gate assertions fail without the
extension. `check:chip-anchors` goes red on all four faces with a dangling
tooltip id and green across all 686 catalog templates with it registered.

Browser capture was unavailable — `preview_start` is refused in unattended runs
(impediments #546, #574) — so the sanctioned **jsdom-render substitution** stands
in, at both the leaf renderer and the composed veil.

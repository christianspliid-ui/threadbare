# THR-1456 — a raid that did nothing, written in a shape nobody read

**2026-09-11 · Engine · Content**

`applyNodeChanges` understood two spellings for a `changes` entry: a relative change
written as a **string** (`'-25'`, parsed and added to the current value) and a direct
replacement (anything else, assigned verbatim). `monster-encounter-content.ts` has always
authored its hits in a third — the **object** `{ delta: -25 }` — so the horde raid fell
through to the replacement branch and wrote the literal `{ "delta": -25 }` into
`properties.prosperity`.

## Two consequences, and only the loud one got noticed

The quiet one is the expensive one. Every other reader of these fields guards with
`typeof === 'number'` (`phaseUnrest`, `guildSeeding`, `sublocation`,
`complicationEffects`), so from the moment a raid landed, that settlement's prosperity
read as **0** to the whole economy — not as `prosperity − 25`. A devastating raid and a
merely severe one became indistinguishable, and the settlement could never recover,
because the next `+` was applied to a `prev` the guard had reported as 0. The content's
own constants said what a raid should do; the raid did none of it, and nothing anywhere
said so.

The loud one is how it surfaced at all. `battleAftermath` was the single reader without
the guard — `(…prosperity as number) ?? 0`, and `??` catches null, not a wrong type — so
the object went into `.toFixed(2)` and threw inside `runTick`, whose fail-soft catch
returns the unchanged state. The tick stopped advancing and every later tick re-threw the
same way. THR-1155 shipped the guard on that read; the corruption itself is what this
ticket owns, and it predates both.

## The shape question, settled toward the content

Teach the executor the object form, or rewrite the three content entries to `'-25'`
strings? The ticket flagged this as a design call. Two comments on it — the grooming note
and the orchestrator's restored block — both read it as **calibration on a measured
fact**, which is the executor's under `Docs/canon/process.md` § User review interface
rule 4, and they are right: nothing is being invented here. The constants
(`HORDE_RAID_DEVASTATION_PROSPERITY_HIT = -25`) already declare the intended behaviour,
and the raid currently does *nothing*, so there is no balanced behaviour to preserve —
only a broken one to replace. If `-25` reads as too harsh once prosperity actually moves,
that is one number to retune under NFP #1, not a re-litigation of the shape.

So the executor learned the spelling. It is also the additive direction (NFP #6): the
string form keeps working, and the object form joins it rather than displacing it. The
three content entries are unchanged; what they gained is a comment saying **do not
"correct" these to strings**, because the obvious tidy-up is now the regression.

## The asymmetry that let it sit on `main`

A mis-shaped *string* already warned. A mis-shaped *object* was written in silence. That
asymmetry is the whole reason this survived: the failure had no voice anywhere between
the content author and the crash three systems downstream. `applyNodeChanges` now warns
when a non-numeric value lands on a numeric property, or when a `delta`-keyed object
carries a delta that is not a number.

The guard is deliberately narrow rather than "warn on every object replacement" —
object-valued properties are legitimate elsewhere, and a guard that cries on every
legitimate write is one that gets muted. What is never wanted is an object on a key the
readers treat as a number.

## A green test was pinning the defect as the contract

`graphOp-patterns.test.ts` carried an arm named *"{ delta: N } object syntax replaces,
does not increment"*, asserting `typeof courage` is **not** `'number'` after the write,
with a docblock recording the object form as "INCORRECT for the current executor". That
was an accurate reading of the executor and the wrong conclusion about which side should
move — the content had been authoring the object form the entire time. The test has been
repointed, not deleted: same shape, opposite assertion, with the history written into it
so the next reader knows it changed sides deliberately.

`battleAftermath`'s own guard test stays exactly as it is. It hand-builds the corrupt
value rather than producing it through the executor, so it still asserts a live rule —
the tick loop survives bad data *whoever* wrote it — and that rule outlives this writer.
The comment above the guard now says the writer is closed and the guard stays anyway.

## The arm that would actually have caught it

Two arms, different in kind, because either alone says too little.

**Arm A** drives the real executor with the authored constants — a `{ delta: -25 }` onto a
prosperity of 40 must land as the number 15, not merely as *a* number. Asserting only
`typeof` would pass against a branch that coerced the object to 0 and called it fixed.

**Arm B** is the one with the weight. Arm A can only prove the shape the test thought to
write; this defect was found because a *generated world* was carrying corruption nobody
had a test for. So Arm B asks the world: 300 ticks of seed 42 on the medium preset, then
a sweep of every Location for a non-number `prosperity` or `defense`. It carries a
population guard counting the numeric-key writes as they happen during the run, because a
world in which the monster content never fired would sweep clean for a reason that has
nothing to do with the fix.

**Red baseline, run before the fix landed:** `lair_7.defense = {"delta":-10}` — the
corruption reproduces on a generated world, with the population guard green. After the
fix: 7/7. Same file, same seed, both directions.

## What the retroactivity question turned out to be

The grooming note flagged that already-corrupted data outlives a code fix, and left it as
the executor's call whether a normalisation rides here. It does not need to, and the
reason is worth recording so nobody builds one later: **there is no runtime graph
persistence** — no save/load path writes a `GameState` or a `WorldGraph` anywhere, so a
world corrupted before the fix cannot survive into a process that has it. The committed
`src/data/world-model.json` was swept directly and carries **0** non-number
`prosperity`/`defense` across its 252 nodes.

What does exist is the in-session case, and the executor's delta branch handles it by
construction: a non-number `prev` counts as 0, exactly as the string branch has always
done. The original value is unrecoverable — it was overwritten — but the corruption stops
being an *object* the moment any later delta touches the key, so it can no longer reach an
unguarded reader. That is pinned as its own arm.

# THR-1498 — Gate Duty's ending links its cast: the bespoke highlight box is retired for chips

*Deferral from [THR-1459](https://linear.app/threadbare/issue/THR-1459), filed under the
browser-verify contract's rule that a pre-existing UI-Law violation is filed with its law
number rather than fixed in passing. With the `{cast:suspect_courier}` leak gone, the
*What Changed* box read "Someone sent Nessa Vale and needs to know the result." — and
that name was inert text: no image, no tooltip, no link (Laws 1/17/21).*

## Why the fix for the unified path never reached this surface

[THR-1033](https://linear.app/threadbare/issue/THR-1033) fixed exactly this class on the
**unified** stage adapter, which routes every ending change through
`buildAftermathConsequences` — the pure builder that takes `link`, `resolveIcon` and
`resolveAnchor` collaborators and turns a sentence into segments that carry the entity's
node id. `cg.quest.gate_duty` is the one template with a **bespoke** adapter, and that
adapter built its own `aftermath.highlights` boxes with `detail` assigned straight onto
them as a string. The veil drew those boxes only when a model carried no `consequences`,
so the two presentations never met: the shared fix could not reach a surface that never
called the shared builder, and a sweep written against the builder could not see it.

## The decision: arm (b), measured

The ticket offered two arms — teach the highlight box to link, or retire it in favour of
`consequences` — and asked for the choice to be measured rather than assumed. **Retired.**
Three facts settled it:

- **No consumer reads `highlights` outside the veil and the two adapters.** A repo-wide
  sweep found none, so retiring the render branch strands nobody.
- **The veil's highlight branch was already unreachable from the unified path.** That
  adapter emits a chip for every change and a highlight only for some of them, so a model
  with highlights always had chips, and the branch drew only for an adapter that forgot
  the chips — which is precisely the defect shape.
- **The chips already carry the whole law.** Tile, kind tag, category tooltip, linked
  sentence, delta cluster: teaching the box a second copy of that would be the drift this
  ticket exists to end.

So the gate-duty adapter now calls the same builder with the same collaborators, and the
veil's `highlights` render branch is deleted. A model that carries highlights and no chips
draws nothing for them — a visible gap that gets fixed the right way, rather than a quiet
regression to inert text.

## What shipped

**`chipCollaborators.ts` (new)** — `buildChipIconResolver(graph)` and
`buildChipAnchorResolver(graph, activeAction)`, the two graph-holding closures every chip
needs. They were inline in the unified adapter; both adapters import them now, so the next
adapter that emits chips picks them up by import rather than by copy. The unified adapter's
behaviour is unchanged (its 62 tests pass unmodified).

**The gate-duty adapter** builds its link set from the four ids it already resolves for the
cast strip and the narrative paragraphs — captain, courier, witness, gatehouse — via
binding *or* clearance-gate fallback, exactly as the scene has always read them. One
resolution, spent twice, so a name is a link in the chips exactly when it is a link in the
prose. Only a *resolved* name links: `getNodeName`'s literal fallbacks ("the courier",
"Gatehouse") name nothing and must stay text rather than become a dead link (Law 21). The
gatehouse entry carries `entityKind: 'location'` and the subtype tooltip id, per THR-1173.
Actor moments (summary lines and condition marks) are untouched; only the three highlight
push sites are gone.

**The veil** loses the ~50-line legacy highlight block; the `aftermath.highlights` field
stays on the model type for consumers that read it as data.

## The guard fails on the old shape, by construction

Rendered through the real `EncounterVeil` over the real adapter's model from the real
authored content (`encounterVeilGateDutyCastTokens.test.tsx`, the THR-1459 file the
coordination block named as the natural extension point):

- the bound courier's name inside `aftermath-consequences` is a real `<button>`, and
  clicking it calls `onSelectAgent` with the **node id** (`npc.nessa`), not the name — the
  one router, by kind;
- the retired title "The night will keep travelling" is absent, and the name appears
  exactly once in the chip container (no inert copy beside the linked one);
- an unbound courier resolves to the spec name "Harried Courier", which names no node and
  renders as plain text with **no** button — fail-open, never a link to nowhere.

At the adapter, the chip's sentence carries a segment whose `entityId` is the courier's node
and whose `entityKind` is absent (a person). On the pre-THR-1498 shape there was no
`consequences` array and no `aftermath-consequences` container, so every arm throws before
reaching a value comparison — nothing here is a snapshot of the new output. **Falsified
explicitly:** with the three source files reverted to their committed state and the tests
kept, exactly 6 arms go red (the 3 new guards plus the 3 rewritten THR-1459/THR-1212 arms),
each on the missing container or the surviving `highlights`.

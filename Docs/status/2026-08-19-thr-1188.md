# THR-1188 — the four gold trade verbs write real routes now

**Shipped 2026-08-19.** Follow-on from THR-830, which narrowed the `trades_with`
EDGE_SCHEMA row to `location`/`location` and, in doing so, named the four ops that
had never agreed with any row.

## What was wrong

`action.gold.establish-trade`, `.trade`, `.disrupt-trade` and `.tax-trade-route`
carried generic edge ops bound `$actor` → `$target`. `unifiedCandidates.ts:172`
sets `targetId: locationId` unconditionally — its own comment reads *"target is
always the location"* — so all four resolved to `actor → location`. That shape is
written by nothing and read correctly by nothing: `createTradeRoute` writes
`location → location`, and every consumer (`armySupply`, `battleAftermath`,
`tradeRouteMarkers`, `strategicActionCandidates`, `orchestrator`) resolves both
endpoints as locations. `tradeRouteMarkers` derives hex coordinates from each end
and cannot place an actor at all.

Since THR-1177 the executor validates endpoints and refuses fail-soft, so the ops
were *refused*, not silently wrong. But the prose still narrated success and the
`update_node` wealth deltas in the same `onSuccess` block still applied — so the
catalog offered four working-looking trade verbs whose only mechanical effect on
the trade web was a refusal trace. The `update_edge` / `remove_edge` variants were
worse than refused: they could never have matched an edge `createTradeRoute` wrote,
so they were no-ops against the real trade web regardless of schema.

## The path taken, and why not the other two

The ticket offered three: (a) rebind to two locations, (b) a location-pair
targeting mode, (c) retire the four cards. **(a), via typed graph ops.**

(c) was cheapest and the ticket said so, but it retires four player-visible action
cards — a call about what the game offers, which the promotion comment correctly
routed to Christian rather than to an executor. It never had to be asked, because
(a) turned out to be available without inventing anything.

(a) could not be done by editing the templates alone, which is what made it look
expensive: `$location` and `$target` are the *same* node here, so there is no
partner endpoint for a sentinel to name. The four verbs therefore resolve their
own location pair — the same shape `fortify_location` and the THR-611 essence ops
use whenever a verb needs engine logic a generic op cannot express. They are
graph-only, so `unifiedActionResolution` auto-routes them through `graphOnlyOps`
with no interception added.

**Nothing new was tuned.** Partner selection reuses `scoreRoutePairBalance`
(THR-616), the shipped route-formation scorer, rather than inventing a second
notion of which settlements want to trade; the write delegates to
`createTradeRoute`, so the edge carries the same cargo manifest, `establishedBy`
stamp and birth-tick `lastTraded` (THR-669) as one the merchant strategic pack
forms. Three new constants bound the search, all named
(`TRADE_PARTNER_MAX_HEX_RANGE`, `TRADE_PARTNER_MAX_CANDIDATES`,
`TRADE_ROUTE_DEFAULT_TAX_RATE = 0.1`, unchanged from the literal the content
author wrote — only the endpoints it lands on are corrected).

## Prose followed the ops

The verbs no longer name a counterparty, so the narration could not keep asserting
one. `"Wealth flows between {{actor}} and {{the-target}}"` named the caster's own
settlement as the trade partner — true of neither the old binding nor the new. All
four now speak from the settlement the caster stands in: *"A road out of
{{the-location}} carries cargo now, and {{actor}} takes a share of it."* This was in
scope, not polish — Done-when 2 is that no `action.gold.*` template narrates a
success its graphOp cannot land, and a success line naming the wrong party is a
smaller version of the same lie.

## The evidence that nearly wasn't evidence

The ticket asked for a seeded run showing zero `edge_schema_refused` traces naming
`trades_with`. A 120-tick seeded run gives exactly that — and it is **vacuous**:
that world forms **zero** `trades_with` routes on its own, so the absence holds
whether the fix landed or not. An empty population passes any predicate.

So the proof fires the op instead. `graphOpExecutor.tradeVerbs.test.ts` § *"against
a real seeded world"* boots the real `initializeGameState` → `runTick` pipeline,
finds a real agent standing at a real durable settlement, fires the op the template
now carries, and asserts a real route appeared between two real `location` nodes
with neither endpoint the caster — and *then* asserts zero refusal traces, which
means something because the op demonstrably ran.

**Falsified before trusted:** reverting one template binding to the pre-fix generic
op turns 2 tests red (`action.gold.establish-trade carries establish_trade_route`
and the catalog-wide sweep). The content-level guard exists because the engine half
alone would not have caught a rebinding regression — the defect lived in the
content file.

## One duplicate removed, one gap filed

`resolveDurableActorLocation` (THR-669's transient-hex guard) now has one
definition in `tradeRouteOps.ts`, imported by `strategicActionLifecycle`, so the
catalog verbs and the merchant pack cannot drift apart on what counts as a durable
route endpoint. Behaviour unchanged.

`tax_trade_route` stamps two fields; they are not equally alive. `controlledBy` is
genuinely consumed (`phaseEconomicTraits` route-control count, `proseResolvers`
status prose). **`taxRate` is read by nothing** — its only two other mentions in the
tree are the op-union comment and `action-technical-effects.ts:58`, which
*documents the toll to the player*. Typed onto `TradeRouteProperties` here so the
field is first-class rather than an untyped bag entry, and filed as **THR-1189**:
wiring a toll into the economy is a new flow, not a rebinding.

Honest scope: the four verbs now land, but the seeded world still forms few routes
on its own, so the player-visible effect depends on these verbs being cast. The
trade web's density is not something this ticket moved.

# THR-1292 slice 2 — the shared step-resolution library

**2026-08-26 · Engine · Thematic Pressure & Living World**

Slice 2 of six on plan doc 1/6 of the Proactive Agent Actions carve-up. A behaviour-identical
extraction: the six-band ladder now lives in one module that two callers can share, so slice 3's
undertaking checkpoints can roll the same dice encounters roll without inheriting the encounter
runtime.

## What moved

`resolveUncontestedStep` (`unifiedActionResolution.ts`) was ~200 lines of band production wrapped
around ~40 lines of encounter bookkeeping. Everything from *"we know the capability and the
difficulty"* to *"we know which of the six bands happened"* — scale adjustment → d100 → floors →
band mapping → resist → rider → debug pin — is now `src/engine/stepResolutionCore.ts`.

The library **returns, the caller mutates**. It touches no graph, queues no event and emits no
trace: quintessence costs come back as `spendIntents[]` and telemetry as `tracePayload`. That is
what lets caller 2 adopt the ladder without also adopting the encounter runtime's state couplings,
and it matches `resolutionService`'s own stated design one layer down.

## The determinism contract

The core draws **at most two** values, in a fixed order: the d100 always, the resist check only
when a resist is funded and attempted. Riders, both floors and the debug band pin draw zero.

That is the property most at risk in an extraction like this — a reordering can leave every band
intact while shifting the stream for every downstream consumer of the same generator. So the golden
fixtures pin `roll` and `probability` per row, not merely the band.

## Push and resist are split, deliberately

**Resist moved into the core; push did not.** Resist is post-roll — it reads the band the d100
produced and draws a second value against it — so it cannot be lifted out without breaking the
draw order. Push is pre-roll and draws nothing: its whole contribution is a number folded into
`actionModifiers`, which is already an input. Moving push in would mean carrying the template
registry, the raw authored difficulty and the actor node into the core so that caller 2 — which
spends no quintessence in v1 — could ignore all three.

Push's already-built event is instead handed to `pushIntent` and echoed back inside
`spendIntents[]`, so callers drain **one** queue rather than two. (Executor calibration call per
plan § Grey zones. The plan's own input list carries `actionModifiers` as pre-summed, which is what
makes this the reading it already implied.)

One premise in the plan turned out not to hold, and it made the extraction cleaner rather than
harder: the plan expected "the quintessence node mutation" to be a state coupling to unpick.
`spendQuintessence` and `applyResistOutcome` do not mutate — they already return events, and say so
in their own doc comments. The only real coupling was *queueing* those events, which is now the
caller's `spendIntents` drain.

## How parity was proven

`stepResolutionGolden.test.ts` was written and captured **against `main` at `a803d13a`, before
`stepResolutionCore.ts` existed** — 32 rows pinned as an inline literal, so a post-refactor run
reproducing it is genuine before/after parity rather than a snapshot of the refactor agreeing with
itself. Deliberately not `toMatchSnapshot()`, which regenerates under `-u` and would launder exactly
the drift it exists to catch.

The first draft of that file was vacuous in a way worth recording: with one neutral template id
every row reported `pushAttempted: false`, because `isPushEligible`/`isResistEligible` are *prefix*
matches on the template id. It pinned the push and resist paths by never entering them. The matrix
now uses three ids chosen for what their prefix opens, and a guard test asserts both branches of
each gate are reached — so a future edit that neutralises the ids fails loudly instead of quietly
narrowing the pin. Seeds for the ladder's tails (crit = doubles, near-miss = margin ≤ 5) were found
by scanning the stream rather than hoping, and all six bands now appear.

Whole-simulation confirmation: the 30-tick engine smoke returns the outcome distribution
**byte-identical** to slice 1's — clean 30.0% | at-cost 47.1% | fail 11.8% | crit-succ 10.0% |
crit-fail 11.8%, 386 agents, 52 events.

## Contract tests

The plan's three, in `src/engine/__tests__/contracts/stepResolutionCore.contract.test.ts`:

1. **Drift guard** — the encounter entry point and a direct core call agree on band, roll,
   probability and resolver outcome across 18 (difficulty × seed) combinations. Carries a
   falsification arm, and that arm found something: perturbing *difficulty* could not make the two
   disagree, because the fixture's mortal sits past the sigmoid's saturation knee and the threshold
   clamps — 0.5 and 0.99 produce the same probability on every seed. The arm perturbs capability
   instead, and the reason is recorded in the test so nobody re-derives it.
2. **One band ladder** — exactly one module defines the resolver-outcome→band mapping;
   `unifiedActionResolution.ts` imports neither `resolutionService` nor the drifted legacy
   `resolution.ts`; and the set of modules allowed to call the shared resolver directly is pinned so
   it cannot grow silently. The legacy import at line 67 was unused and is now deleted — the
   "cleanup in passing if trivially safe" the plan invited. Removing it took the typecheck ratchet
   **down** one, 2980 → 2979.
3. **Busy-gate invariant** — `busyAgentIds` is built from `state.unifiedActions` alone and its
   neighbourhood never reads `strategicState`, so an agent running an undertaking keeps receiving
   encounters. Source-scan plus a live arm that runs the real phase.

`mapResolverOutcomeToStep` is re-exported from its old path, so `encounter.ts` and
`meetingEncounter.ts` are untouched — additive (NFP #6) — and a test asserts the re-export is the
same function object, not a copy.

## Deferred deliberately

The plan assigns this work an interface-map row, `shared-step-resolution-two-callers`. It is **not
added here**: there is one caller until slice 3 lands `undertakingCheckpoints.ts`, and a row
asserting two would be precisely the fiction the interface map exists to prevent. It belongs in
slice 3 alongside `undertaking-checkpoint-events`, and slice 2's checkpoint comment says so.

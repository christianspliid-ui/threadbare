# 2026-09-26 — THR-1622: Culture names no longer leak raw biome ids

**Ticket:** [THR-1622](https://linear.app/threadbare/issue/THR-1622) · **Project:** Thematic Pressure & Living World · **Plan:** none (self-scoped bug, found by the design lane during THR-1591) · **Pillars:** Engine + Content. UI N/A (names already render; no surface changed).

## What shipped

1. **Name fragments for every biome and every sphere.** `CULTURE_NAME_FRAGMENTS.biome` covered 20 terrains, but cultures originate in any of `BIOME_MODIFIERS`' habitable terrains, so 15 of them (`mountain_pass`, `light_forest`, `floodplain`, `high_mountains`, `sand_dunes`, …) fell through to the raw id. Every `TerrainType` now has four fragments. `CULTURE_NAME_FRAGMENTS.sphere` covered the eight creation spheres, but `selectSpheres` draws from all twelve, so a culture venerating `light` read "…Shadow-Kept light". The four foundation spheres now have fragments too.
2. **Humanised fallback.** `generateCultureName` now humanises any id that still misses the table ("Mountain Pass", not "mountain_pass") in all three slots. Realm names derive from the culture name, so they are fixed by the same change.

## Evidence

- 50-seed sweep, medium map, the CLI's `initializeGameState` path, checking every culture node and every Realm node: **0 offenders** out of 302 cultures and 150 Realms. The same sweep on the unfixed code found **77**, including seed 42's "The Open Earth of the mountain_pass".
- New tests in `cultureGenerator.test.ts`: every `BIOME_MODIFIERS` terrain and every sphere has fragments, the fallback never emits `_`, and a 200-seed `generateCultureIdentities` sweep finds no `_` or raw biome id.
- The ticket also asked about `perceiveRelay.ts`'s `Origin culture identified: <id>` clue detail. No player surface renders a `knows_clue_of` edge's `detail` (only debug tooling reads clue edges), so nothing was changed.

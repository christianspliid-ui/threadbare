### THR-1056 — the property that makes the publish safe is the property that leaves the litter (2026-08-15)

Every scheduled lane writes a dated report into its working tree and publishes it with `scripts/ops-publish.sh`. The script commits to `ops` through `hash-object` / `update-index` / `commit-tree` against a throwaway index and **checks nothing out** — which is precisely what makes it callable from any worktree without tripping the THR-672 home-tree rule or manufacturing THR-671's phantom diffs. The same sentence is the whole bug: a publish that touches no working tree also removes nothing from one. Nothing else ever did, so the strays accrued. The ticket counted 23 on 2026-08-09; this run found **38**, which is the predicted ~3/day arriving on schedule.

**The asymmetry that proves nobody decided this.** `tb-orchestrator` already deletes its drafted report — but only on a `check:substantive` `skip` verdict, where the file was never published. The publish path simply never learned the same move. This is an omission, not a policy, which is why the fix is a bullet in three prompts rather than an argument.

**The `.gitignore` half is load-bearing, and the reason is a git behaviour worth stating plainly.** A fast-forward refuses to clobber an untracked file and aborts the entire sync — THR-937's exact failure, measured there at 11 consecutive skips and 88 commits behind. An **ignored** file is expendable, so git overwrites it silently and the sync proceeds. Verified both directions in a scratch repo rather than asserted: the non-ignored stray produced `error: The following untracked working tree files would be overwritten by merge ... Aborting`, while the ignored one was not named at all and went `stray` → `published` in place. So ignoring these paths converts a permanent autosync deadlock into a no-op. It cannot hide the pre-cutover archive either — `.gitignore` has no effect on tracked files, and the 55 committed report-shaped files under `Docs/ops/` were confirmed still tracked and still visible after the rule landed. Nor can it break publication: `ops-publish.sh` stages with plumbing, which does not consult `.gitignore` the way `git add` would.

**The step that would have shipped a fix defeating its own Done-when.** The ticket asks for the ignore rule *"so a future recurrence doesn't silently re-accumulate unnoticed"* — and its Done-when asks to confirm `git status -uall` stays clean. Those two are in direct contradiction: once the paths are ignored, `git status -uall` reports clean no matter how many pile up, so the check becomes unfalsifiable exactly where it is being relied on. Ignoring is still the right call (it is what closes the THR-937 vector), so the visibility is restored elsewhere rather than traded away — a new bullet in `weekly-project-hygiene` sweeps with the one listing that still sees them:

```bash
git -C "C:\Users\chris\Dev\Projects\TheFantasyWorldSimulator" ls-files --others --ignored --exclude-standard -- Docs/ops/ Design/retros/
```

Verified in both states: it surfaced an injected stray that `git status -uall` did not report.

**Deletion was per-file verified, not asserted from the ticket's own survey.** Each of the 34 `Docs/ops/` strays was hashed and compared against its blob on `origin/ops` — all 34 byte-identical, so removal is loss-free by construction; each of the 4 `retro-*-draft.md` files was removed only after `git cat-file -e origin/main:<final>` confirmed the narrative report it supersedes is committed. The loop deletes nothing that fails its check, and reported `deleted=38 kept=0`. The home tree is now **zero untracked**; the three remaining entries are pre-existing *modified tracked* files (`.claude/settings.json`, `.claude/settings.local.json`, `Docs/impediments.md`), authored by neither this session nor this ticket.

**`weekly-retro` needed no edit**, which is worth recording because the ticket named it. It delegates wholly to the `retrospective` skill, so the draft deletion belongs in the skill — placed immediately after the existing `git ls-files --error-unmatch` tracked-proof, and gated on it rather than on "having written the report". Until that check exits 0 the draft is the only durable copy of the parsed impediment set, which is the same reason THR-798 put that gate there at all.

Full gate run on the code track: `.gitignore` is not doc-excluded, so a change with no source in it still owes the whole suite, and CI classifies it the same way.

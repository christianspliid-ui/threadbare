# THR-1149 — the character sheet's faction is a concept, not a string

The Faction section of the character sheet named a faction and stopped there: a
bare `<p>` carrying a glyph prefix. `FactionSheet` has existed the whole time and
was reachable from nowhere on the surface that names the faction (Law 21), and a
game concept was presented as text alone (Law 1). Found in passing while
shipping THR-1138, which was scoped strictly to the `62%` numeral in the same
section.

The faction name now carries the full concept treatment: heraldry through the
shared entity-visual resolver, a tooltip from the registry, and a click that
opens that faction's own sheet.

## The node id is not the definition id

The ticket flagged one open question — whether the info card carries a faction
**id** at all — and the answer turned out to be "one of the two, and not the one
the sheet needs." `AgentInfoCardData` already carried `factionDefId`, which keys
the static definition table. `FactionSheet` and `resolveEntityVisual` both take a
graph **node** id. Several chapters of one order share a `factionDefId`, so
passing it where a node id belongs opens the wrong chapter's sheet or none at
all.

So the Engine pillar is one additive field, `factionNodeId`, set from the
membership edge the card builder already resolves — not a rename or a widening of
the existing one. Both fields now exist side by side because both are genuinely
needed: the def id keys the tooltip, the node id opens the sheet and resolves the
heraldry.

## Three treatments, three independent degradations

Each treatment depends on different data, so each fails open on its own rather
than the section going all-or-nothing:

- **Heraldry** always renders. `resolveEntityVisual` falls back to a designed
  glyph tile when no sigil resolves, so the missing-art state reads as designed
  (Law 4) — which matters here, since THR-638 covered 13 of 49 factions. It
  replaces the ad-hoc `factionIconGlyph` string prefix: one resolver per
  representation class (Law 3).
- **The link** needs the node id *and* a handler. Without both, the name is plain
  styled text — never a control that looks live and does nothing.
- **The tooltip** needs the def id to resolve in the registry. Absent, there is
  no hover affordance at all, because a tooltip that opens empty advertises depth
  the surface cannot deliver.

## A new `faction.*` tooltip prefix

`resolveTooltip` had no faction route, so the Law 17 requirement had nowhere to
resolve to. The new prefix is keyed by **definition** id rather than node id, and
that choice is load-bearing: `Tooltip` calls `resolveTooltip(id)` with no context
of its own, so a graph-keyed faction tooltip would resolve to null on every plain
`<Tooltip id="faction…">` — a dead hover that reads as wired. The definition
table is static, so this resolves context-free exactly as `archetype.*` and
`sphere.*` do.

The label strips generated name slots (`'The {adj} Beast Pack'` → `'The Beast
Pack'`). Monster definitions template an adjective that worldgen fills per
instance; the concept a tooltip names is the family, and a raw `{adj}` reaching a
player-facing surface would be its own defect.

## A positional selector that would have started measuring the wrong element

THR-1138's surviving assertion found the standing bar as "the first element in
the Faction section carrying an inline width." The heraldry tile renders earlier
in that section and carries its own inline width, so that selector would have
quietly switched to measuring the tile — and still passed its `toBe`, just
against a different element. The bar now carries `data-testid`, and the assertion
selects it directly.

## Evidence

Twelve new assertions across two files, plus the repointed THR-1138 one. Eight of
the twelve fail against the original code; the four that pass both ways are the
fail-open negatives, which is what they are for.

Browser-verify substitution: jsdom-render — unattended run, no startable dev
server. The contractual 1920×1080 capture is appended to THR-1133's pixel-pass
sweep, whose membership predicate covers exactly this case. What jsdom cannot
cover and the sweep must: tooltip placement and above/below flip on this row,
the heraldry tile's alignment against the sibling rank text, and whether the
added tile pushes the section into overflow at the contractual viewport.

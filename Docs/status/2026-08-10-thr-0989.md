**THR-989 — 30 templates' authored endings were unreachable, and the cause was one un-wired click handler.** The ticket was filed as content work: 13 templates carrying `aftermathConfig.variants` with no fork to select them, remedy "give each a reachable decision, or fold the prose into `fallback` and delete the dead variants". Re-deriving its own predicate (as it instructed) against the live catalog changed the shape of the job twice over. First, the list was **stale**: the ten `hod.*` templates had already been resolved by THR-1054, so the literal predicate now selects **3**, not 13 — the `mentorship.*` set. Second, and the reason folding to `fallback` would have been a serious mistake: those three are not dead because nobody authored a decision, but because **the player's decision was being thrown away**. `EncounterVeil` commits with `onIntervene(choice.id, …)` where the card came from `buildChoices`, which renders `template.authoredChoices` — ids like `steady_their_nerve` — while `handleEncounterIntervene` looked that id up in `notification.choices`, the fixed generic triple `generateInterventionChoices` builds (`intervene_support` / `intervene_force` / `intervene_withdraw`). The lookup could never hit; the handler returned early; **nothing was recorded** — no essence spent, no `EncounterChoiceMemory` written. The stage then closed anyway, because `handleEncounterCommitAndContinue` continues regardless, so it read as a working screen. `resolveAftermathVariant` found no choice at `branchOnStep` and returned `fallback` forever. Measured over the catalog: **30 of the 34** templates carrying aftermath variants key them to `authoredChoices` ids, so every authored ending on all 30 was rendered to nobody — the ticket's own "fold them into fallback" option would have deleted thirty templates' endings to accommodate a bug one layer away. The fix is a lookup that mirrors `buildChoices`' precedence (`resolveInterveneChoice`: the authored hand for the step, then the generic set), with the authored cost converted through the same `BOOST_TO_PROBABILITY_RATIO` the generic path uses rather than a second scale. **The guard is the durable half.** `assertAftermathVariantsProducible` now asks the question that was never asked — not "does the fork point at the right step" (THR-979's `assertDecidedAftermathReachable`) but "can *anything at all* emit this key?", there being exactly two writers: a `decidedBy` fork, and the player's pick. It runs catalog-wide with a population guard and a falsification, so the class cannot return; a sweep fixes today's templates, an invariant closes the shape. It found one template the fix did not: `broker.quest.rival_shrine_betrayal` keys `accept_trade`/`refuse_trade` on both its branch and its aftermath and authored no cards to emit them, its step 0 carrying `difficulty: 0` and the comment *"the choice is the point, not the roll"* — the cards were simply never written, so they were, at symmetric cost because pricing the betrayal against the refusal is a balance call this ticket had no mandate to make. **One test was wrong before it was right:** the end-to-end assertion first read "the picked variant differs from `fallback`", which failed on that same template — whose `fallback` is a deliberate copy of its refusal, matching a branch fallback that is also the refusal. Inequality would have failed on correct content and taught the next author to pad prose, so it asserts the precise claim (the pick selects *its own* authored variant) plus a population floor so it cannot pass vacuously. Verified on the live build at 1920×1080: both authored cards render with `{cast:*}` placeholders enriched, and after a click the action carries `choiceHistory: [{ stepIndex: 0, choiceId: 'accept_trade', essenceSpent: 1 }]` — recorded at exactly the index `aftermathConfig.branchOnStep` reads, which is the array that stayed empty before. 982 files / 15,522 tests green, ratchet down 1 to 3450, build clean.

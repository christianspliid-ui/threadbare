# THR-1344 — the genome ran before two of its own five inputs existed

**Shipped 2026-08-29.** Engine pillar; Content reached (215 reach-sourced and 28
culture-sourced sublocations per medium world that no generated world had ever held). UI
N/A — neither `settlementReachProfile` nor `genomeSourcePass` reaches a component.
Deferral filed at THR-1323's closeout, by the measurement that ticket's Done-when asked for.

## What was wrong

`worldSeed.ts` runs the settlement genome at the only point where settlements exist, and
that point sits upstream of two of the genome's five inputs:

| pass in `worldSeed.ts` | line |
| -- | -- |
| Eager Base Sublocations — `runSettlementGenome` + `materializeGenome` | 1198 |
| **Cultures** — `belongs_to` edges Pass 2 reads | 1221 |
| **Faction Definitions** — `seedAllFactions`, the `reachWeights` Pass 4 reads | 1645 |

So Pass 4 summed faction weights over a graph with no factions, and Pass 2 looked up a
culture edge ~35 lines before any was written. Both evaluated against nothing and
contributed nothing to any world this seeder has ever built.

THR-1323 made the *reader* live, which was the whole of its scope; it could not reach this,
because no edit inside `factionSeeding.ts` can change when `worldSeed` calls it.

The ticket named Pass 4. Measuring the fix surfaced that Pass 2 was dead by the identical
mechanism — invisible to the ticket's own measurement, which counted
`genomeSourcePass === 'reach'`. Both are fixed here and both are pinned.

## The arm, and why the cheaper-looking one is the riskier one

The ticket offered three arms. **Reorder** looks cheapest — move the eager pass below
`seedAllFactions` — and is the one that changes the most: the settlement promotion pass
rewrites `locationSubtype`, `seedGuilds` and `seedAllFactions` each write sublocations of
their own, and `seedNpcsAtLocations` places NPCs into whatever exists when it runs. Moving
the genome changes what four unrelated systems observe.

Shipped the **second-pass** arm instead: leave the eager pass alone and run the genome once
more at the tail of the seeder, after all faction wiring. `materializeGenome` was already
idempotent on `sublocationTypeId`, so the second call adds only the delta and re-stores the
fuller `genomeResult`. Running the genome twice changes what only the genome observes. It
is also the additive direction (NFP #6), and it is bounded and paid once at worldgen — one
`runSettlementGenome` per genome-tier settlement, no ticks involved.

**Delete** was never live: `REACH_SUBLOCATION_MENU` is 8 reaches of authored, tier-gated
content, and THR-1323's closeout already recorded why deleting it on the strength of a grep
for a field name would have been wrong.

The two call sites were extracted into one `runGenomeForSettlement` helper. Two call sites
reading the same five inputs through two hand-copied expressions is how the passes drift
apart.

Every seed, `medium`, tick 0. The Done-when asked for 42 and 99; 7 is included because a
two-seed delta cannot distinguish a systematic change from a lucky one.

| -- | -- | -- | -- | -- | -- |
| 42 | 440 → **737** | 0 → 199 | 0 → 28 | 32 → 38 | 0 → **19** |
| 99 | 518 → **920** | 0 → 214 | 0 → 47 | 40 → 54 | 0 → **24** |
| 7  | 562 → **926** | 0 → 224 | 0 → 42 | 45 → 53 | 0 → **22** |

The `withGenome` rise (32 → 38 on seed 42) is a second thing the reorder arm would have got
wrong quietly: the settlement promotion pass promotes locations into genome tiers *after*
the eager pass, and those settlements carried no genome result at all. The second pass
catches them.

Deterministic (NFP #3): the genome consumes no randomness — `seed` is destructured as
`_seed` — so the second pass draws from no stream and the same seed still yields the same
world.

## The volume cap

Passes 2–4 are additive by construction and nothing subtracts, which stayed invisible while
two of the three were dead. Uncapped, seed 42 / medium: **capitals at 38 sublocations**,
cities at 31. Thirty-eight distinct places inside one settlement is a list, not a place.

`SUBLOCATION_BUDGET` (hamlet 10, town 20, city 26, capital 30) is enforced after the
additive passes and **before** archetype recognition, so a settlement's archetype is read
off what it actually holds. Infrastructure is exempt — it is the baseline a tier owes, not
a contribution. Archetype capstones are added after enforcement and sit above the cap by
design, so observed totals run a little over: 32 at a capped-30 capital.

Calibrated deliberately loose from the measured distribution: trimming costs authored
content going unseen, not trimming costs only legibility. It moves seed 42 from 753 to 737.
One edit changes settlement density (NFP #1) — no pass has to change.

## What this costs

Bigger worlds cost more per tick. Measured, 30 ticks, seed 42:

| preset | before | after |
| -- | -- | -- |
| medium | 3003 ms | 3281 ms (+9%) |
| large | 10017 ms | 12441 ms (+24%) |

Accepted against +45% / +25% more world content (NFP #7 — a budget, not premature
optimization).

**One thing this run measured and did not cause.** `buildDistanceMatrix` walks
`getNodesByType('location')`, which returns *both* tiers, so sublocations count toward
`MAX_DISTANCE_MATRIX_SIZE` (1200). On `main` today, before this change, `large` already
seeds 1628 locations and `epic` 2549 — both already over, and CLAUDE.md's claim that 1200
"covers all supported presets (large ~584, epic ~805)" is stale by a factor of three. This
change widens the overflow (large 1628 → 2028) but did not open it, and `medium` stays
under at 951. The overflow is also currently harmless: `getDistance` is imported by
`phaseAgentDecision.ts` and `idleBehavior.ts` and **called by neither**, so the matrix is
rebuilt on every structural change and never read. Filed rather than fixed here — the
interesting half is the dead build, not the cap — as
[THR-1346](https://linear.app/threadbare/issue/THR-1346/the-distance-matrix-is-rebuilt-on-every-structural-change-and-read-by),
which carries the preset table and requires the stale CLAUDE.md figures to be corrected or
deleted with the system.

**And one correction this ticket owes its own predecessor.** THR-1344's description recorded
*"230 sublocations and 264 NPC roles of authored content are one ordering away from
existing."* The sublocations were real and now exist. The NPC roles were not: `materializeGenome`
creates no NPC nodes, and `genomeResult.npcs` has no reader anywhere — `proseResolvers.ts:1232`
is the field's only consumer and it destructures `.sublocations`. So `NPC_BUDGET`'s four tiers
of hand-tuned constants govern the length of an array nothing reads, and no ordering fix could
have changed that. The measurement was taken by reading `GenomeResult`, which cannot tell a
materialized entity from an inert field. Filed as
[THR-1347](https://linear.app/threadbare/issue/THR-1347/genomeresultnpcs-has-no-consumer-every-genome-pass-computes-an-npc).

## Evidence

THR-1323 left a characterization test asserting this defect on purpose so that closing it
would turn red rather than land silently. It did. It is inverted, and three assertions were
added beside it — the Culture pass, the stored `settlementReachProfile`, and the volume cap.

**Every new guard was falsified before being trusted**, in two separate arms:

- Second pass disabled → all four go red.
- Budget enforcement alone disabled (`if (false && …)`) → only the budget test goes red,
  `AssertionError: expected [ { tier: 'capital', …(2) }, …(5) ] to deeply equal []`, and
  the other three stay green. That separation is the point: it shows the budget test is
  measuring enforcement rather than riding on the second pass.

The budget test carries two arms for the same reason a bound alone is not a test: it
asserts no settlement exceeds its cap **and** that at least one settlement sits exactly at
it, which only a trimmed settlement can do. Delete the enforcement block and the second arm
goes red even where the bound would still hold. It also asserts the population spans more
than one tier, so a single-tier world cannot pass it by accident.

All four read **materialized nodes**, never a return value. Calling `runSettlementGenome`
by hand after seeding is precisely the condition worldgen did not meet, so a green
assertion on its return would prove nothing — the second-order form of the fixture trap
that hid THR-1323 for its whole life, and that five fixture tests in this same file still
demonstrate.

The mutex on THR-1345 (soft, test-file only) never contended: THR-1345 was unclaimed in
Ready for Dev throughout, WIP=1 serializes it by construction, and this change touches no
faction-definition data file.

# THR-1213 slice 1 — one catalog, and a spelling the compiler can check

**2026-08-28** · Wave-1 design B, hunger vocabulary unification · Engine item 1 of 3

Two `HUNGER_CATALOG` exports, same symbol name, different key schemes, different field sets, in two modules that never imported each other. One was the catalog the player picks from at the remembrance Hunger beat (`src/data/hunger-catalog.ts`, dotted ids, art and prose for all twelve); the other was the catalog the meeting prose reads (`src/types/hunger.ts`, bare ids, perception style and scoring tags). THR-891 is the record of what that costs: a lookup that type-checked, was false, and silently missed for **every god**.

This slice merges them. Behaviour-identical by construction — a type and data reshuffle, no scoring change, no prose touched.

## The three rulings, as built

**One catalog, merged, in `src/data/hunger-catalog.ts`.** `HungerDefinition` is now the field union of both shapes, and it is **total**: the remembrance half (`imageAssetPath`, `proseVariants`, `mandateDirection`, `courtOptions`, `sphereAlignment`, `domainAffinities`, `ascendantLens`) plus the engine half (`perceptionStyle`, `emotionalTone`, `candidateReachBias`, `dilemmaResonanceTags`), values verbatim from the two pre-merge sources. An entry missing a field is a build error rather than a runtime hole — the plan doc's documented build-time exception to NFP #4. The `types/hunger.ts` catalog is deleted, and with it the THR-891 hand-maintained derivation comment explaining how the two were kept in step by hand.

`buildStubAscendantLens` moved to `src/engine/ascendantLens.ts` with `SPHERE_TO_HUNGER`. It reads the catalog, and the catalog is data: the import direction is now engine → data → types, one way.

**Bare canonical, dotted derived, no save migration.** `HungerId` is unchanged; `StoredHungerId = \`hunger.${HungerId}\`` is derived from it rather than listed a second time, so a spelling the union does not know is a compile error instead of a lookup that misses. `AscendantIdentity.hungerId` re-types `string` → `StoredHungerId`; saved worlds already conform, and `toHungerId` still accepts `string | undefined | null` at the read boundary, so a legacy or corrupt save still fails soft to "no hunger". Its inverse `toStoredHungerId` is the single place the dotted form is built — the catalog stores the bare id once, and every dotted key derives from it: the identity write in `RemembranceFlow`, the three hunger-keyed tables in `src/engine/remembrance.ts` (personality biases, divine-name adjectives, map size), and the `filterHungers` weight lookup.

Two parity assertions became compile-time facts. `SENSING_OPENING_PROSE` and `BOND_PROSE` are total `Record<StoredHungerId, string>`; `meetingProseRegister.test.ts`'s key-set equality check is now something the build enforces.

**One resonance tag space.** `ResonanceTag` is a closed 68-member union — the tags in hunger `dilemmaResonanceTags` (64) plus the four that dilemma registers carry and no hunger does (`compassion`, `desperation`, `devotion`, `nurturing`). It types hunger tag lists, dilemma `emotionalRegister` and `driveResonance`, and `AscendantLens.driveTags`. The member list is a predicate, not a snapshot: it is the union of what those three sources spell, and widening it in the same PR as the content that needs a new theme is the documented move.

`incompatibleWith` is deliberately **not** typed to it — measured, its six values are template ids (`AX-IRON-01`, `GR-FACTION-02`), a different vocabulary that happens to sit in the same interface.

## What the executor moved, and why

Two sequencing calls, recorded because they deviate from the plan's slice boundary rather than from its rulings:

1. **The dilemma-side `hungerResonance` field is not deleted here.** The plan puts its retirement in slice 1's mechanical migration, but its only reader is `scoreDilemmaResonance` in the dormant `dilemmaSelection.ts`, which slice 2 deletes along with the fixtures asserting the dead vocabulary. Deleting a field while keeping the reader that reads it is the awkward half of one move; both halves land in slice 2, per the interface-map rule that retiring a contract deletes the tests asserting its dead side.
2. **`ResonanceTag` is not applied to remembrance fragment `tags` yet.** The plan lists fragment tags among the re-typings; they reach the lens only through `identity.mortalTags` in slice 2's `buildLensFromIdentity`, which is the honest place for that narrowing — it is a resolver boundary, not a data shape.

## Behaviour, pinned rather than asserted

Slice 1's contract is "if any test's observed values change, something moved that shouldn't have" — and the one value this slice genuinely rewrites is the expression that writes `hungerId` into a save. Nothing pinned it, so a new assertion does: the catalog's twelve derived stored spellings are compared against the literal dotted strings the pre-merge catalog authored. That is not derivable from the union — a renamed member would still round-trip through the narrowing check beside it.

`remembrance.test.ts`'s `filterHungers` case is the corroboration that the derivation is load-bearing and correct: the same fragments, the same seed, the same hunger first (`witness`), reading its weight through `toStoredHungerId`.

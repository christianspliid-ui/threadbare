# THR-843 — legendary artifacts can be attuned, cursed and nullified

**Shipped 2026-08-09.** The four artifact verbs refused the one artifact tier most
worth acting on. `artifact_legendary` is a distinct `NodeType`, and five separate
guards tested `node.type !== 'artifact'` — so a legendary relic could not be
imbued, attuned, cursed or nullified at all.

**The ticket left the decision open; the evidence settled it.** THR-843 asked
whether the trio *should* accept the legendary tier, flagging a real possibility
that the answer was "no, by design" — legendary artifacts are documented as
having their own trait graph, which might have meant the `effects[]` substrate
did not apply to them. It does apply. `collectAttachmentEffects`
(`src/engine/effects/effectWalker.ts:66-92`) walks `possesses` / `bonded_to` /
`has_trait` and reads `node.properties.effects` with **no node-type filter of any
kind**; `bonded_to` is schema-declared against `artifact_legendary`
(`src/types/edgeSchema.ts:88`) and is the characteristic way a legendary artifact
is held; and `resolveArtifactHolderId` already walked both edge types. The "own
trait graph" is *additional* — `has_trait` edges alongside the effects array —
not a replacement substrate. So the verbs were refusing a target the engine was
fully equipped to handle.

**This was player-visible, not merely latent.** Three of the four cards —
`artifact.imbue`, `artifact.nullify`, `artifact.curse` — already declared
`targetCategories: ['artifact', 'artifact_legendary']`. The content layer offered
the target, the UI rendered the card, the player spent 1 AP and 2–3 essence, the
action reported success, and the graph op then errored out. Widening the guards
closes that gap from the engine side; `artifact.attune` was the one card still
declaring the narrow set and is widened to match its three siblings, so the
trio's offered targets are finally uniform.

**One predicate, not five widened booleans.** `isArtifactNode` +
`ARTIFACT_NODE_TYPES` now live in `ascendantPrimitives.ts` (the module both
call sites already import from) and every guard routes through it. That shape is
chosen deliberately: THR-661 declined to widen `applyCurseMark` alone precisely
because a mark that fires where the drain does not is a worse split than a
consistent refusal — and five independent copies of the type test are what made
that split possible in the first place. Routing them through one predicate makes
the next such divergence unrepresentable rather than merely unlikely.

The tests assert the chain, not just the gate: the closing case curses a
legendary artifact bonded to a bearer and then walks `collectAttachmentEffects`
for that bearer, so it fails if the substrate claim is wrong rather than only if
the guard is. A companion case fires the verb at a `location` and still expects
refusal — the guard widened, it did not vanish.

Not done here, and deliberately: ~5 other call sites open-code the same
`artifact || artifact_legendary` test (`retinue.ts`, `rewardPool.ts`,
`detailPageGenerator.ts`, `detailPageResolvers.ts`). They are already correct, so
converting them is tidying rather than a fix, and it would widen a small
behavioural diff into a broad refactor.

Evidence: 976 files / 15,426 tests green; typecheck ratchet unchanged (3462, no
baseline refresh); `vite build` clean; engine smoke reached tick 30 with 383
agents and 47 events; both freshness gates run last, green. No browser-verify —
the diff touches `src/engine/**` and `src/data/**` only, no UI-pillar path.

# THR-1194 — three divine actions stop minting orphans

**Shipped 2026-08-22.** THR-1193 fixed the `$created_0` resolution that six
`hexActionBridge` recipes depend on, and in doing so moved two of them one layer deeper
into a second, pre-existing defect. `hex.forge_seer_token` and `hex.forge_instrument`
each minted a `storied` artifact and then tried to bind it with `possessed_by` — an edge
type that **is not registered and never was**. Both were wrong twice over: the registered
edge is `possesses`, whose schema row runs `actor` → `artifact`, and these pointed
artifact → actor. Every cast produced a divine artifact that reached nobody.

Measured before the fix, against a graph holding an ascendant and a location:

```
hex.forge_seer_token  → allSucceeded: false | ["Edge type \"possessed_by\" is not registered in EDGE_SCHEMA"]
hex.forge_instrument  → allSucceeded: false | ["Edge type \"possessed_by\" is not registered in EDGE_SCHEMA"]
```

## `possesses`, not a newly registered `possessed_by`

The ticket left the door open to registering `possessed_by` instead, with a documented
reason. There isn't one, and registering it would have been strictly worse. `possesses`
already carries this exact relationship, and every consumer reads it in that direction —
`agentAttachments` sweeps `getOutgoingEdges(agentId, 'possesses')`, and
`ascendantBeatSeeding` writes the same shape for the Divine Gift. A second spelling would
mint artifacts that no possession reader can see, which is the orphan the ticket exists to
stop. The recipes were drifted, not expressing a distinct idea.

## Found in passing: the herald was an orphan too

The ticket named three recipes for the naming defect, and firing the third surfaced a
fourth finding it did not have. `hex.send_herald` attached its herald with `located_at`
to `$location` — and a hex action's `$location` resolves to the hex *target* id
(`hex_3_5`), which is not a graph node. THR-1193 fixed this recipe's `$created_0` half
and left the `$location` half as out of scope; measured here, the herald still landed
with a thread from the ascendant and **no location at all**:

```
hex.send_herald → allSucceeded: false | ["Target node not found: hex_3_5"]
```

Same failure class as the ticket's own title, in a recipe already being edited, one line
from the ops in hand. It moved to `HEX_ACTION_GRAPH_OP_GENERATORS` for exactly the reason
`hex.restore_fragment` did under THR-1193: the target is a runtime value, no context
sentinel names a location node on the hex, so the recipe has to query the graph and emit a
literal id. **Place-tier only** (the THR-1183 trap — `getLocationsInHex` sweeps a bare
`getNodesByType('location')` and returns sublocations too), and fail-soft on a hex with no
place-tier location: no ops at all, because minting a herald located nowhere is the orphan
being fixed.

Its `action-technical-effects` string already *claimed* the herald was placed at a
location on the hex. The documentation was right and the code was wrong; the string is now
true.

## Names

All three recipes set only `properties.name`, while `executeAddNode` reads the node's
top-level `name` from `op.nodeName` and falls back to the generated id — so the artifacts
and the herald read as `gen_artifact_7` everywhere `node.name` is shown. Each now passes
`nodeName` from a named constant, following the `RESTORE_FRAGMENT_NAME` precedent.

## Evidence

Live proof, seed 42 / medium, a real 1387-node world (`asc.archetype.chaos_0`, hex 6,7,
place-tier `loc_0` "Ardenmor Keep"):

```
### hex.forge_seer_token
  allSucceeded: true | errors: []
  minted gen_artifact_1 type=artifact name="Seer's Token" | in=[asc.archetype.chaos_0-possesses->]
  artifacts 129->130 | asc possesses 0->1
### hex.forge_instrument
  allSucceeded: true | errors: []
  minted gen_artifact_3 type=artifact name="Divine Instrument" | in=[asc.archetype.chaos_0-possesses->]
  artifacts 130->131 | asc possesses 1->2
### hex.send_herald
  allSucceeded: true | errors: []
  minted gen_actor_5 type=actor name="Divine Herald" | out=[located_at->loc_0] in=[asc.archetype.chaos_0-thread->]
```

The new `hexActionMintedNodeBinding.test.ts` (+18) **executes the batch and reads the
graph back** rather than asserting the op array — the THR-1193 lesson, and the reason all
of this shipped green: an op-shape assertion cannot tell a working recipe from one whose
refs and edge types resolve to nothing. It also carries a standing guard over the ticket's
membership predicate, asserting every hex-action `add_edge` names a registered type.

**Falsified in four controlled arms**, each reverting one half of the fix:

| arm | reverted | red |
|---|---|---|
| A | `possesses` → `possessed_by` | 10 of 18 |
| B | direction flipped back to artifact → actor | 8 of 18 |
| C | `nodeName` dropped from all three | 3 of 18 |
| D | herald target back to `$location` | 2 of 18 |

Arm B matters most: it proves the direction is checked independently of the name, so a
future recipe with the right edge type pointing the wrong way is caught too.

1049 files / **17,068 tests green**, typecheck ratchet **3123, down 2** from the 3125
baseline (the unregistered edge type was itself a type error), build ✓ 11.43s, 30-tick
smoke ✓ 384 agents / 42 events.

## Deferred

Two adjacent findings, both measured, neither in this ticket's predicate:

- **THR-1195** — the herald has no `actorType`, so now that it is placed,
  `getAgentsAtLocation` still returns `[]` for it. Adding `actorType: 'individual'` is one
  word and a large behaviour change (the herald enters the Maslow pipeline and the
  encounter pool); what a Divine Herald *is* is a design call, not a drift correction.
- **THR-1196** — `hex.spark_encounter` writes `occurred_at` without the `tick` its schema
  row requires. A warning rather than a refusal, so the edge lands; the fix is one
  property and a widening of the new guard from "type registered" to "required properties
  present".

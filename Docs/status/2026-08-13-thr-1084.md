# THR-1084 — an entity named in a reaction is now the same entity that links one line above it

**Shipped 2026-08-13.** Project: Encounter Experience. UI pillar (Engine / Content N/A — this is a presentation defect end to end).

**The defect.** One aftermath modal named the same person twice. The `SEED` change-detail line rendered *"Councilor Maevis
Drent's network now has a documented basis…"* with the name gold and clickable; the reaction option directly beneath it read
*"Deepen the connection to Councilor Maevis Drent."* with the name as flat prose. Same modal, same screen, same person — Laws 1
and 21, and the entity demonstrably had a page, because the line above opened it. THR-1050 is what made this visible rather than
what caused it: before that fix the reaction printed a raw `{cast:patron}` token and named no entity at all.

**Cause.** `buildAftermathConsequences` receives both an `enrich` and a `link` callback, so consequence chips get enrichment
*and* linking. The reaction mapper immediately above it had gained `enrichProse` (THR-1050) and no `link` step — and
`EncounterStageAftermathReactionModel.label` was a bare `string`, so there was nowhere for link annotations to go.

**The nested-interaction decision** — the part the ticket flagged as a design call, not a mechanical fix. A reaction label lives
inside the `<button>` that picks that reaction, so a link inside it is a click target inside a click target. The call:

- **The entity is clickable.** Law 21 is `[E]`-enforced and carries no "unless it sits inside a control" exception, and the
  filed defect is precisely the inconsistency inside one modal. Not linking it would have been a won't-fix wearing a design
  decision's clothes.
- **It is a `<span role="link">`, never a nested `<button>`.** The button content model forbids interactive content, so a nested
  `<button>` is invalid HTML and browsers diverge on it. A span is not interactive content, so the nesting is valid and the
  keyboard contract is stated explicitly (`tabIndex={0}`, Enter **and** Space).
- **The button keeps every other pixel.** The link stops propagation, and Space additionally `preventDefault`s — otherwise it
  would activate the button underneath. The pick still fires everywhere except on the entity's own gold-underlined name.

**Shape: additive, not destructive** (NFP #6). `label`/`intent` stay plain strings and gain `labelSegments`/`intentSegments`
alongside. That matters beyond taste — the Gate Duty adapter (`buildGateDutyEncounterStageModel.ts:1110`) and the debug-bridge
reaction listing (`GameView.tsx:2928`) both read `label` as a string and are untouched by this change. A renderer without
segments draws the string exactly as before.

**One renderer, one legacy site.** The three-tier segment rules (click where a page exists / hover where the registry explains /
plain otherwise) now live in `src/components/Game/encounter-stage/NarrativeSegments.tsx`. The consequence-chip block in
`EncounterVeil.tsx` still renders them inline — two implementations of one rule, which Law 27 forbids. It was **not** converged
here because that block sits inside the diff of held PR #1415 (THR-1082), whose last `EncounterVeil.tsx` hunk appends
immediately after the segment `.map()`; rewriting it would conflict with a PR that cannot merge until an attended session runs
its pixel pass. Filed as [THR-1105](https://linear.app/threadbare/issue/THR-1105/encounterveils-consequence-chip-block-should-adopt-the-shared).

**Browser-verify substitution: jsdom render assertions on the real component — `preview_start` refused in this unattended run.**
Impediment #546 reproduced verbatim (*"Dev servers can't be started from unattended sessions…"*), so every sanctioned capture
route, which all terminate at a URL, was unreachable. Substituted six `@testing-library/react` assertions against the real
`EncounterVeil`: link rendered with `role="link"` + `tabindex`, click routes to the agent handler **and** the pick does not
fire, Enter does the same, a click on non-entity prose still picks, an unopenable entity stays plain text (fail-open), and a
segment-less reaction renders its plain label. Falsified — disabling the label branch turns exactly those five red while the
intent and fallback tests stay green, proving per-branch isolation. **The 1920×1080 pixel capture is owed** and an attended
session should run it; the change is not layout-moving (an inline span replacing a text node, same text in the same flow), so
it is in scope for the substitution rather than owing an attended checkpoint the way #1415 does.

**UI-Laws judgment** (Laws 1, 13/14, 17, 21, 27, 37 on the composed surface): Law 1 — the reaction's entity now carries link and
tooltip; the image half is not this surface's (a reaction is a sentence, not a chip). Laws 13/14 — no magnitudes or raw keys
added; segment text is authored prose already through `enrichProse`. Law 17 — tooltips route through `tooltipResolves`, never
inline copy. Law 21 — routed by kind via the existing `openEntity`, and fail-open where the host wires no handler, so no dead
link is drawn. Law 27 — the new renderer *is* the reuse; the one remaining duplicate is filed as THR-1105. Law 37 — chrome
untouched. No violation introduced.

**Gates.** 1007 files / 16022 tests green; ratchet 3447 unchanged from baseline; `vite build` clean. No engine files touched, so
no CLI smoke owed.

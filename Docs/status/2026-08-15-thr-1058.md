### THR-1058 — the reported cause was wrong, and the containment never depended on it (2026-08-15)

Two parked issues (THR-860, THR-875) had an explicitly-nulled `assignee` come back populated. The ticket's hypothesis was that Linear defaults `assignee` to the API actor on *any* write omitting it — THR-845's create-path defect, extended to updates. That hypothesis is **false as stated**, and this run's first job was proving it rather than documenting it.

**Seven controlled arms, all negative.** On a scratch issue (THR-1116, canceled at closeout) `assignee: null` survived a priority change, a label replace, a `blockedBy` relation add, a `state` transition into `In Dev`, a second label touch while sitting in the exact park shape, a `save_comment`, and a pushed branch whose name matched the issue's own `gitBranchName`. Every arm was verified with a fresh `get_issue`, never the mutation echo — which per impediment #306 can report pre-write state, and is exactly how a confident wrong answer gets recorded. A sole-field `assignee: null` also applied cleanly against a *freshly* set assignee, so impediment #380's no-op needs an assignee that has been in place a while and is not reproducible on demand inside one run.

**What the negative result is worth.** A ruled-out cause is only useful if it stops the next session re-deriving it, so both the finding and its method are written down where a pickup already reads — the `pull-work` park section and CLAUDE.md's Known Sandbox Limitations — with an explicit *do not re-run the MCP arms*. This class has now cost parts of several sessions across two occurrences plus an absorbed duplicate (THR-867), and every one of them started by re-testing the write path.

**The one candidate left, named honestly rather than asserted.** The branch-push arm left `updatedAt` untouched and created no attachment, so the native GitHub integration does not act on a bare push. That leaves it acting on **PR open/merge** — a path this repo already knows writes to issues from branch name and title (THR-738 vectors 2 & 3) and cannot configure. It fits the residue: both reverted issues carried a `gitBranchName` matching a branch the lanes create, and THR-875's revert landed nine minutes after its closeout comment, a lag no synchronous MCP call explains. Testing it needs a throwaway PR, which was judged not worth the repo noise once the containment made the cause academic.

**Christian's 2026-08-11 direction is what shaped the deliverable** — *"prefer the cheapest containment that stops the practical damage … close this as tolerated-quirk if the containment already suffices."* It does suffice, with one gap: the containment he named (the pickup lane re-verifying at claim time) protects the **claim**, and the damage lands on the **park**. A park is readable only as `assignee: null` ∧ `state: In Dev` — the shape `keep-work-flowing-cc` matches to surface finished work under `## Needs Christian` — so a null that does not hold makes a completed ticket invisible to the only lane that would ask him to close it. THR-875 sat that way ~35 minutes and would have stayed there indefinitely.

**So the fix is one word: verify now means verify *and re-assert*.** The park recipe already said `get_issue(id) # verify-after-write` and stopped there — it detected the failure and prescribed nothing. It now re-asserts once, bundling one other field at its current value, which covers both known failure shapes without needing to tell them apart: the write silently no-ops (#380), or it lands and something later repopulates it (#508). Applied at the canonical park site, at the Step 1.8 churn park that writes the same unassign, in CLAUDE.md, and in the pickup lane's own prompt.

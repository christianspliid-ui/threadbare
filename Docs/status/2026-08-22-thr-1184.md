# THR-1184 — the consecrated route buys the pilgrimage it promised

**Shipped 2026-08-22.** `sacred_route` was registered by THR-1177 with no consumer at all: a zealot faction could spend eight ticks and 30 wealth consecrating a pilgrimage route, the completion prose said *"Pilgrims will follow where the faithful walked first"*, and nothing anywhere read the edge. Four live edges in a seeded world, all inert. A consumer now exists, and the interesting half of this change is the second defect the first fix uncovered.

## Why the destination could never host the pilgrimage

`strategic_establish_sacred_route` targets `['shrine', 'temple', 'town', 'city']`. Every pilgrimage encounter is gated `['shrine', 'temple']`. So the two settlement targets consecrated a route to a place where the pilgrimage was unreachable by construction — and that is not a theoretical corner. Measured on seed 42 / medium at tick 120, **all four** consecrated destinations were `city` or `town`; not one was a shrine or temple. Every route the seeded world actually minted pointed somewhere the encounter could not fire.

The consumer is therefore a pooling supplement rather than a scoring tweak: a location carrying an incoming `sacred_route` pools the encounters named in `SACRED_ROUTE_DESTINATION_ENCOUNTER_IDS` regardless of its subtype. Deliberately not subtype-gated — being ungated is the whole payoff. Deduped by `templateId`, so a shrine, which already pools these by subtype, is unaffected.

It reads the edge in `encounterCache` rather than at the mint site because the cache is already the one place that decides what a location can host. That routes the payoff through the same pooling every other location feature uses and needs no new firing mechanism, which is what THR-1161's ruling asked for. Player visibility comes free and through existing substrate: the surface is the encounter itself, so no new component and no UI-pillar diff.

## The second defect: a correct consumer that still changed nothing

With the consumer in and its unit tests green, a probe against a real seeded world at tick 120 reported **1 of 4** destinations pooling the pilgrimage. A cache built fresh from the identical final graph gave 4 of 4. So the consumer was right and the runtime cache was stale: the encounter cache only rebuilds on structural invalidation, and three routes had been minted after the last one. Left there, this would have shipped the exact defect the ticket exists to close — an edge that changes nothing — only harder to see, because the code reads correct and one destination works.

The fix follows the settlement-promotion precedent. `executeInstantMutation` now reports the destination whenever it mints an edge in `ENCOUNTER_POOL_INVALIDATING_EDGE_TYPES`; `phaseStrategicProjects` and `phaseAgentDecision` — both of which hold the `SimulationRuntime` that `strategicActionLifecycle` deliberately does not — call `applyEncounterCacheUpdate(… onLocationTypeChanged)`. The new return field is optional, so every existing caller and return path is untouched. After the wiring the same probe reports 4 of 4 in the **runtime** cache, each destination's pool up by exactly one, and 0 of 8 unconsecrated towns carrying it.

That the trigger is the edge type rather than "any strategic completion touching a location" is pinned by its own test: `strategic_consecrate_site` mutates a property and must report nothing.

## The premise checks the tests could not make

The fixture tests assert against the literal `'encounter.pilgrimage_trial'`, not against `SACRED_ROUTE_DESTINATION_ENCOUNTER_IDS` — asserting against the same constant the production path reads would be a tautology that passes on an empty list. Reverting the consumer turns three of the five red; the two that stay green are the negative controls, which is the corroboration that the arms are independent rather than five views of one check. The shrine-dedupe test guards its own premise first, asserting a shrine already pools it, or the "exactly once" assertion would pass for the wrong reason.

The `KNOWN GAP` note on the `sacred_route` schema row is gone — both the comment and the mention inside the `description` string, which named this ticket.

### THR-1112 — `aftermath pick` stops re-running an aftermath the tick loop already ran (2026-08-15)

The tool that verification runs reach for was manufacturing the defects those runs were hunting. `phaseAutonomousAftermath` flags an action `autonomousAftermathApplied` once it applies the reaction — and that flag was read by exactly one thing: the phase's own re-scan. Every other entry point (CLI `aftermath pick`, the debug bridge) resolved the same action again and re-ran **every** effect: duplicate agreement edges, duplicate encounter seeds with byte-identical ids (impediments #553, #577). Since a tool-induced duplicate is indistinguishable from an idempotency bug in whatever was just built, the cost landed precisely in the runs least able to absorb it.

**Verify-the-noun paid before a line was written.** The recorded recipe reproduced, and the reproduction corrected the ticket's account of the symptom:

```
fws> eval JSON.stringify(state.unifiedActions.filter(a=>a.templateId==='...bargain_at_crossroads')...)
[{"id":"ua_1","actor":"asc.archetype.chaos_0","resolved":true,"auto":true}]
fws> aftermath pick @hero slice.crossroads.carry_the_promise
Failed to apply aftermath reaction: Duplicate edge ID: agreement_asc...bargain.promise_given
```

`auto: true` is the whole diagnosis — the phase had already consumed it. But the second application no longer duplicates *silently*: the graph now rejects the duplicate edge id and **throws**, so today's shape is a red `Failed to apply…` naming a graph internal, which reads as an engine defect even more convincingly than the duplicate did. The ticket's fix ("apply nothing, print a notice") is still exactly right; only the failure it prevents has changed since it was filed.

**The guard goes in the resolver, not in the CLI**, because the ticket's escape clause ("if it lands purely in the CLI command layer, say so") would have fixed one of three callers. `resolveAftermathContextForAgent` is the chokepoint the CLI, the debug bridge and `GameView` all route through, so an already-applied aftermath is now unreachable from any of them.

**The refusal is an optional field on the existing error shape, deliberately, rather than a third union member.** Every caller already branches on `'error' in resolved` and so refuses correctly *without being touched* — including `GameView`, which has no business being edited by a dev-tooling ticket — while a caller that wants to phrase the refusal as a notice rather than a failure reads `alreadyApplied`. A new union member would have been the more expressive design and would have put a UI file in this diff for no behavioural gain.

**The tick had to be added, because the flag could not answer the question the notice asks.** `autonomousAftermathApplied` is a boolean; the ticket asks the notice to name the auto-resolution tick, so `autonomousAftermathAppliedTick` rides alongside it (additive, NFP #6). Fail-soft (NFP #4): a flag written before the field existed still refuses — it just says "applied autonomously" with no tick, which is pinned by its own test rather than left to inference.

**Done-when, run against the real engine:**

```
fws> tick 4
fws> eval 'seeds=' + ...                    seeds=2
fws> eval 'agreementEdges=' + ...           agreementEdges=1
fws> aftermath pick @hero slice.crossroads.carry_the_promise
○ Aftermath for 'encounter.slice.bargain_at_crossroads' (action ua_1, agent
  'asc.archetype.chaos_0') was already applied autonomously at tick 2. Nothing to apply.
fws> eval 'seeds=' + ...                    seeds=2
fws> eval 'agreementEdges=' + ...           agreementEdges=1
```

**`seeds=2` before the pick is not a duplicate, and checking rather than assuming is the point** — the ticket asserts ticking alone yields one. The two carry different ids from different actions (`seed_ua_1_slice.crossroads.carry_the_promise_1` from the encounter under test, `seed_ua_2_bless_react_acknowledge_2` from an unrelated action that resolved at tick 4). The encounter under test planted exactly one seed and one agreement edge, and the pick adds nothing to either. Had this been read as a duplicate, the ship would have chased a second, non-existent bug.

**Five regression tests**, covering both resolver branches (the notification path and the no-notification fallback the CLI repro actually takes), the missing-tick fail-soft, and — the two that matter most — that a flagged action does **not** suppress an unflagged sibling, and that the world is left untouched where a second application would have mutated it. The refusal is asserted by state, not only by its error string.

**A finding this surfaced, recorded rather than acted on:** `buildHeroSet` collects the ascendant's *threaded agents and avatars*, never the ascendant node itself, so an encounter whose actor is the ascendant is treated as a non-hero and auto-resolved by the phase — which is why `spawn encounter @hero` gets consumed at all. In the browser the player's avatar is an avatar node and so protected; whether any player-sourced action (THR-727 divine receipts) reaches the phase with authored reactions is unverified and is a question about *who chooses aftermath*, not about tooling idempotency. Left out of this diff on purpose, and carried in the completion comment for the retro rather than filed, per the process-work throttle.

# THR-1128 — the type ratchet stops reporting a floor it never measured

**2026-08-15 · Continuous Improvement · CI tooling (Engine/Content/UI all N/A)**

`npx tsc` with TypeScript absent prints ``Use `npm install typescript` to first add TypeScript
to your project.`` and **exits zero**. On 2026-08-15 `node_modules` was wiped out from under a
live session, and the very next `npm run check:typecheck` printed:

```
check-typecheck-ratchet: OK — 0 error(s), DOWN 3184 from the 3184 baseline. Please run
`npm run check:typecheck -- --update` and commit typecheck-baseline.json so the ratchet
holds the new floor.
```

Zero parsed diagnostics, scored as a 3184-error improvement, with an invitation to commit it.
Had `--update` run, `typecheck-baseline.json` would hold `0` and every subsequent PR would have
failed the required check with ~3000 "new" errors.

## Why the guard that existed for this did not fire

The script already carried property 3 — *"a tsc invocation that fails without producing
parseable errors is UNVERIFIABLE and exits non-zero"* — written for precisely this class. It
stood down on two independent conditions, and reading which ones is what shaped the fix:

```ts
if (total === 0 && !/\bFound 0 errors\b/.test(output) && output.trim() !== "") {
  const looksClean = !/error/i.test(output);   // ← true: the npx message has no "error" in it
  if (!looksClean) bail(...);                  // ← never reached
}
```

`execSync` did not throw, because the process exited **0**; and `looksClean` was **true**,
because the message contains no `error` substring. The guard classified a run by *scanning the
text the tool happened to emit*, so a failure that emits benign-looking prose reads as success.
That is the generalisable half, logged as impediment #602.

## Two guards, at two different levels

**Property 4 — prove the compiler before scoring the run.** `findCompiler()` resolves
`typescript/bin/tsc` (the binary `npx tsc` actually executes), falling back to the package
entry, and `main()` bails before invoking anything when neither resolves. Checking the
*precondition* rather than the output's vocabulary is what makes this robust to whatever
message a future npm version prints. The preflight also runs ahead of `--update`, so the
poisoned baseline cannot be written.

Two specifiers rather than one, deliberately: this gate blocks every PR when it fails, so an
ambiguous resolution miss — a future TypeScript shipping an `exports` map that closes the deep
path — must not be read as an absent compiler. Only an exhausted list means "not installed",
and a test pins that the list actually resolves in this repo, so a typo cannot make the gate
false-fail everywhere.

**Property 5 — an implausible drop is SUSPECT, not OK.** Property 4 closes the observed cause;
this closes the class. Any other path yielding zero parseable diagnostics while looking clean
— a warm `.tsbuildinfo` defeating `--force`, a tsconfig that early-exits quietly, a future
runner that stubs `tsc` — lands as a **drop**, and every guard this script had was on the
increase side. A fall of more than `SUSPECT_DROP_RATIO` (50%) now refuses to report a floor
and refuses `--update`. The escape hatch is `--allow-drop`, deliberately explicit: a real
halving of a 3184-error baseline is worth saying out loud in a commit body.

## Shape of the change

The decision moved into a pure `classifyRun(facts)` returning a discriminated verdict, with
`isBlocking()` naming the three verdicts that must never write a baseline. `main()` keeps the
I/O and the reporting. This is the `check-actions-health.ts` house pattern, and it is what lets
the test drive the real decision with the output actually observed rather than asserting
against a re-implementation of it. An entry guard (the `check-armed-prs.ts` idiom) makes the
module importable without firing the gate.

## Evidence, including the end-to-end half

The unit tests pin the classifier. They cannot, on their own, prove the *script* refuses —
a classifier that is right while `main()` ignores it is exactly the shape this ticket is about.
So the script was also run for real against a tree where the compiler cannot resolve:

```
=== check path ===   FAIL — the TypeScript compiler is not installed — cannot verify.
                     Resolved none of: typescript/bin/tsc, typescript. … NOT compared.   EXIT=1
=== update path ===  FAIL — … NOT written.                                               EXIT=1
=== baseline after both runs ===  {"total":3184, …}   ← untouched
```

All three Done-whens, proven on the live path: non-zero exit, a message naming the missing
compiler, and `--update` declining to write.

The healthy path is unchanged and was confirmed on the real repo — `OK — 3184 error(s),
unchanged from baseline` — which also proves the new preflight does not false-fail.

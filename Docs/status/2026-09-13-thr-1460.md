# THR-1460 — a faction draws each town it holds once

**Date:** 2026-09-13 · **Pillars:** UI · Engine (the selector that feeds it) · Content-N/A (no authored content added or edited)
**Issue:** [THR-1460](https://linear.app/threadbare/issue/THR-1460/factionsheet-renders-a-location-twice-react-duplicate-key-loc-58-on)
**Plan doc:** none — the ticket description is the spec.

Opening The Merchant Consortium's sheet logged, three times:

```
Encountered two children with the same key, `loc_58`.
```

## The defect

`getFactionNetworkSummary` builds two lists of Locations. `halls` comes from `located_at` edges stamped `role: 'guild_hall'` (plus sublocations the faction owns, resolved to their parent); `controlledLocations` comes from `controls` edges. Each is passed through `uniqueLocations` — **and each is deduped only against itself.**

A settlement that is both a faction's guild hall and one of its `controls` targets is therefore in both lists, legitimately. `FactionNetworkGraph` then drew `[...summary.halls, ...summary.controlledLocations]` keyed by `location.id` ([`FactionSheet.tsx:561`](https://github.com/christianspliid-ui/threadbare/blob/main/src/components/Game/FactionSheet.tsx#L561)) — and the shared Location arrived twice under one key.

The selector already knew the two lists overlap: `governingSeats` is built as `uniqueLocations([...halls, ...controlledLocations])`. That union existed three lines above the bug and the diagram did not use it.

**Measured, not assumed.** On a generated medium world at seed 42, **13 of 50 factions** hold at least one Location both ways — and the Consortium's shared id is `loc_58`, exactly as reported.

## The fix, and why not at the JSX

The ticket asks for the dedupe at the selector, not in the render, and that is right for a reason worth recording: **the two counts beside the diagram are not wrong.** `hallCount` and `controlledCount` each report a real relationship, and a hall the faction also controls genuinely is both. Filtering `controlledLocations` at the selector to exclude halls would have silenced the warning by making "Control 1" read "Control 0" — trading a React warning for a lie on the sheet.

So `halls` and `controlledLocations` stay exactly as they were, and the selector gains one more list:

```ts
networkLocations: FactionNetworkLocationNode[]   // halls and controls, deduped by id, halls first
```

Each entry carries `role: 'hall' | 'control'`. **Halls lead and win ties** — a Location held both ways reads as their seat rather than as one more town. `mergeFactionLocations` is the fold; neither input list is touched.

This also retires a latent fragility in the diagram. The old code derived each node's label from its *index* (`index < hallNodes.length ? 'Hall' : 'Control'`), so the label was correct only while the two slices stayed adjacent and in order. It now reads `location.role`.

Node limits became named constants (`NETWORK_MEMBER_NODE_LIMIT` and its three siblings, NFP #1) — the 520×260 viewBox is what those numbers actually encode, and that is now written down beside them.

**Naming:** `holdings` was rejected. The UL is explicit — *"Never **holdings** — that noun belongs to the Freehold and the `owns` edge"* (`Docs/ubiquitous-language/Agents.md`) — and `Place` is the inner position tier (THR-1394), not this one. `networkLocations` names the consumer and introduces no player-facing word; nothing renders it.

## Tests — both arms falsified

**`src/engine/__tests__/factionNetworkLocations.test.ts`** (5 assertions), on a **generated** world, per the ticket: the duplicate is a product of worldgen edges, so a fixture would be inventing both sides of the thing under test. Zero ticks are run — the overlap is laid down at worldgen, which is why the file stays out of the heavy lane.

The load-bearing arm is non-vacuity. "Every id is unique" passes trivially on a world where no faction holds a Location two ways, which is exactly the shape that would let a reverted fix sit green — so the first test asserts the overlap *exists* on this seed, and a second asserts the naive concatenation **still** duplicates. Falsified by reverting `mergeFactionLocations` to that concatenation: 2 of 5 go red, naming `The Adventurers Guild` (`expected 3 to be 4`).

**`src/components/Game/__tests__/FactionSheet.duplicateLocationKey.test.tsx`** (3 assertions) renders the real component against the real generated world, for the faction named in the report. React reports duplicate keys through `console.error`, so spying on it reproduces the browser console read exactly. Falsified by restoring the concatenation in `FactionNetworkGraph` — the error comes back **verbatim**:

```
Encountered two children with the same key, `loc_58`.
```

The third assertion is scoped to the diagram's own `viewBox`, because the same settlement legitimately appears again in the "Halls & Seats" list and a sheet-wide count would have swept those in.

## The second surface named in the ticket

The report notes the error firing three more times later with the debug panel open (stack `:0`) and asks the executor to check both. **There is no second producer.** The only other Location-keyed lists in `src/components/Game/debug/` are `ArmiesTabContent.tsx:201` and `EncounterCacheView.tsx:616`, and both key off `getNodesByType('location')` / an id-grouped tally — neither can repeat an id by construction. Three occurrences is also exactly one FactionSheet mount's worth. The `:0` stack is a stripped frame, not a different surface.

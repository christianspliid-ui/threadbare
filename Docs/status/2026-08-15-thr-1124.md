# THR-1124 — the resolution readout stops reporting to the player

**2026-08-15 · Encounter Experience · UI pillar**

`buildSimpleEncounterStageModel` populates `resolutionReadout` unconditionally, and
`EncounterVeil` rendered it into the veil body between the narrative and the complication
prose. Every line of it is a raw magnitude — `Capability 45% · Modifiers +0% · Threshold 12`,
a `45/100` difficulty label, `Roll 47 vs 50 · Margin -3`, `Projected success 33%` — which
UI Law 13 puts on the trace and the designer view and nowhere else.

`ResolutionReadoutBlock` now subscribes to the THR-775 designer-view store and returns null
without it. **Gated rather than banded**, which was the ticket's own recommendation and holds
up: the player already has this information in words one surface over — the nudge stage's
forecast pips and difficulty word — so banding here would be a second, quieter voice saying
the same thing. What is left is the designer's question, *is the resolution math right?*,
which is what the designer view exists to answer.

The gate lives **inside** the block rather than at its one render site, so a future second
caller inherits it. A readout that has to be remembered about is a readout that comes back.

## The sweep closed at one surface

The ticket's predicate asked for every producer assigning a percentage-formatted string to a
player-facing stage-model field, naming `formatProbability` / `formatSignedPercent` as the
known formatters. Both have exactly one call site each, both inside `ResolutionCheckCard`.
The other candidates the sweep turned up — `NudgePhaseShell`'s three `toFixed` sites
(`Δ{forecastDelta}`, `d={difficultyValue}`, `p={probability}`) — are **already** `designerView &&`
gated, which is also where the gating idiom used here comes from. `difficultyLabel`'s
`${Math.round(difficulty * 100)}/100` in the adapter is a raw magnitude too, and rides the
same block, so the one gate covers it. Membership set: one surface.

## The finding that changed the test

The Done-when asked for the assertion at `watched` tier, reasoning that THR-1121 left this
adapter serving watched threads. That is true of the **model** and false of the **render**:
`EncounterVeil` returns early for `threadTier === 'watched'` with a peek shell whose entire
text is a threat word, a background line, a peek offer and an essence cost. It never reaches
`ResolutionReadoutBlock` at all.

So a no-`%` sweep at `watched` **passes against the unfixed code** — a vacuous gate, and the
failure mode this repo keeps logging. It was caught only because the paired designer-view
assertion failed: the numbers did not come back when the view was switched on, because there
was no stage body to put them in.

The sweep therefore runs at `strong`, the tier that renders the full body and where the
assertion can actually fail. `watched` is pinned separately as the peek shell it is, so the
next reader inherits the finding instead of "fixing" the test by moving it back. Calibrating
which tier carries a Done-when is an agent verdict per `process.md` rule 4; the ticket's
premise is corrected in place rather than escalated.

## Falsified, not assumed

Removing `if (!designerView) return null;` turns exactly two tests red — the mock-model
withholding assertion and the adapter-backed no-`%` sweep — and leaves the `watched`
peek-shell test green, which is the point of pinning it. The evidence is built from
`buildSimpleEncounterStageModel` rather than a hand-written fixture, so the assertion cannot
agree with itself while the adapter emits something else.

## Browser-verify

`preview_start` refused with the unattended string (ninth of the family), which also shuts the
Playwright route since it presumes a running server. Took the jsdom-render substitution, which
this ticket's own Done-when explicitly sanctions. At the **adequate** pole of #593's scale, and
for a reason the family has not recorded before: this diff **only removes** an element from the
player path. Overflow and the 1920×1080 viewport contract are one-way risks — content coming
off a surface cannot push anything past an edge — so the pixel pass has nothing to find and
**no follow-up ticket is filed**, unlike THR-1123's and THR-1118's.

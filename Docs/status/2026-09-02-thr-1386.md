# THR-1386 — what vitest's "import" number was made of

**2026-09-02 · build tooling.** The node pool's `import` figure was not module loading. Measured per file with a small custom reporter reading vitest 4's per-module diagnostics (`testModule.diagnostic().collectDuration`, `importDurations`), on one commit, locally:

| band | files | collect (= "import") | what it is |
|---|---|---|---|
| > 30 s | 2 | **236 s** | `encounter-health.regression` and `encounter-tuning.regression`: three seeded worlds × 100 ticks run inside `describe()`, which vitest books as *collect* time, not test time |
| 2–30 s | 27 | 98 s | the first file each worker touches — the engine module graph loaded cold once per worker (~3.6 s each) |
| ≤ 2 s | 943 | 117 s | everything else, **median 83 ms** per file |

So the shared registry (`isolate: false`, `pool: 'threads'`) is doing exactly what THR-940 said: 943 of 972 files pay 83 ms to collect. Half the number was two files simulating worlds where a metric labelled "import" could not distinguish them from a slow `require`, and a fifth was the unavoidable cold load per worker.

## What the `import` metric measures under `isolate: false`

Vitest's summary `import` is the sum of per-module `collectDuration`: the time from the worker starting on the file to the test tree being known — the file's own imports (cheap once the worker is warm) *plus any code that runs at module or `describe()` scope*. It is per file, not per module, so a shared registry cannot make it small for a file that does work at collect time. `transform` is separate (Vite's per-file transform, cached across workers) and was not the driver.

## The one change

Both regression files carry `// @vitest-lane heavy — …` and run in the heavy lane (THR-1384) instead of the PR gate's node pool. Their world-build lives in `runMultiSeed` in a helper, so the partition's mechanical predicate (`initializeGameState*` in the file's own text) could not see them — the tag is hand-applied, with the reason in the docblock, and the partition test still routes exactly the tagged set. Nothing else changed: no config, no skips, the same tests run in a different lane.

| node pool, same commit, same machine | before | after |
|---|---|---|
| files | 972 | 970 |
| `import` (collect) | 451 s | **177 s** |
| tests | 108 s | 96 s |
| transform | 117 s | 98 s |
| wall | 130 s | **12 s** |

The wall-time drop is the two files serialising one worker each for 118 s while the other workers finished in seconds.

## The lever measured and not taken

`@vitejs/plugin-react` 5.1.4 defaults to `include: /\.[tj]sx?$/`, so it transformed every plain `.ts` engine module in the node pools. Scoping it to `/\.[tj]sx$/` on all four projects: transform 98 → 93 s, import 177 → 173 s — inside run-to-run noise, not worth a config change that touches every project. Reverted; recorded so the next person does not re-measure it.

## Why the share stops where it stops

Of the 177 s that remain, ~98 s is the cold engine import once per worker — 16 workers on this machine, ~3.6 s each, plus the two isolated projects paying it per file by design. That cost scales with worker count, not file count; fewer workers would lower the CPU share and raise the wall time, which is the wrong trade for a PR gate. The remaining ~80 s is 943 files at a median 83 ms, which is the shared-registry floor. The full fast suite (`npm test`, three projects) on the same machine: before, import 860 s of 1,425 s CPU (60%) at 229 s wall on the busiest run and 641 s of 1,158 s (55%) at 138 s wall on a quiet one; after, **import 403 s of 911 s CPU (44%) at 30 s wall**. The share stays above the ticket's 25% target for the reason above — the two isolated projects pay the cold engine load per file by design, and the node pool pays it per worker — stated here rather than chased. The heavy lane with the two files: 22 files, 182 tests, 137 s wall.

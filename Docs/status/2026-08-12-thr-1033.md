# THR-1033 — aftermath consequence chips rendered inert

**2026-08-12 · UI + Engine · Encounter Experience**

The Aftermath screen's MARK/STANDING/TOLL/WOUND chips underlined their concept
words — "standing", "Eye", "Star" — the way the surface marks a word that
explains itself on hover. Hovering them explained nothing. THR-986's five-roster
resolution pass caught it on four of five encounters and filed it as a missing
renderer.

**It was not a missing renderer.** THR-1004 had already wired the chip surface:
it resolves `EncounterAftermathChange.concepts`, wraps each declared concept in
`Tooltip`, and routes a click by kind. What shipped broken was the *ids the
producers hand it*.

- `engine/aftermathWords.ts` emitted `tooltipId: 'ui.reputation'` for every
  personal-standing sentence. That id has never existed in `ui-content.ts`; the
  registry entry is `ui.standing`. So **every STANDING chip in the game** carried
  an unresolvable id.
- `reachTooltipId` offered `reach.time` and `reach.life`, because
  `REACH_DISPLAY_NAMES` holds eleven display words while `world-model.json` holds
  nine `reach.*` nodes. Two more dangling ids by construction.
- A nudge exemplar fixture declared `condition.exhausted`, a prefix
  `resolveTooltip` does not route at all.

`Tooltip` no-ops silently on an unresolvable id — it never shows, and never says
why. The chip, meanwhile, drew its underline on the mere *presence* of a
`tooltipId`. Between them: a dead link that looks live, which is the anti-pattern
Law 21 names by hand.

**Two fixes, because one of them is the class and the other is the instance.**
The ids are now correct at the source. And the surface no longer decides on
presence — `tooltipResolves` (new, in `tooltipResolver.ts`, mirroring `Tooltip`'s
own `hasContent` gate) means a word is styled as explainable exactly when hovering
it would explain something. A future dangling id degrades to plain prose instead
of to a lie. A resolvable one additionally gets `tabIndex={0}` and `.focus-ring`,
so the hover tier is reachable from the keyboard at this call site.

**The gate that was missing.** `tooltipValidation.test.ts` checked only
`{{concept.id}}` links *inside* tooltip descriptions — it never looked at the ids
producers emit, which is precisely the gap `ui.reputation` fell through.
`conceptTooltipIds.test.ts` now sweeps every `tooltipId:` literal under `src/`
(the corpus, not a fixture list) and fails on any that does not resolve. It was
falsified in both directions before shipping: reintroducing `ui.reputation` turns
it red, and it caught the `condition.exhausted` fixture on its first run.

**Deferred, with reasons.** [THR-1094](https://linear.app/threadbare/issue/THR-1094)
— should a condition explain itself on hover? Adding a `condition.*` route changes
the registry Law 17 enumerates and needs authored copy per condition, so it is a
design call, not a wiring change. [THR-1095](https://linear.app/threadbare/issue/THR-1095)
— the shared `Tooltip` trigger is a bare `<span>` with `onFocus` handlers and no
`tabIndex`, so its focus path is dead code game-wide; making every tooltip a tab
stop is a decision with a blast radius, not a bug fix.

**Browser-verify substitution** (impediment #546, second occurrence): `preview_start`
is refused in unattended runs, so no sanctioned capture route terminates at a URL.
Evidenced by jsdom render assertions on the real component, including a DOM dump in
the ticket's own probe format. The pixel capture is **owed** — though this change
removes an underline and adds a focus ring, so it cannot plausibly cause the paint,
overflow or z-index regressions only pixels catch.

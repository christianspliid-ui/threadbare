# THR-1299 slice 2 — the moment stream gets a consumable half

**2026-09-02 · code.** Plan doc 5/6 of Proactive Agent Actions ships as six strangler slices. This is slice 2: the moment queue, the three emission fixes, the `moment_surface` trace and the divine-influence stamp. The moment card, the badge, the arc panel and the calling are slices 3–6; the ticket stays In Dev.

## What was true before

Doc 1 shipped the producer half of the moment stream and it died in the trace buffer. `resolveMomentPresentation` computed `interrupt | badge | none` for every checkpoint and the answer went nowhere a surface could read: every moment was a `TickEvent` at a sub-chronicle significance plus a trace row, and nothing else. On top of that, three emission defects the plan located precisely:

- **Completions never emitted from the checkpoint.** A gate at the emission site dropped `momentClass === 'completion'`, so the one moment class that matters most produced no moment.
- **Foundings were a dead branch.** `'started'` sat in the class union with a presentation arm and no emitter anywhere.
- **Interrupt-tier moments never reached the chronicle.** Their significance (0.4 / 0.55) sat under `phaseNarrative`'s 0.8 threshold, so a moment loud enough to stop the player left no chronicle line.

## What this slice does

**One queue, one writer.** `state.pendingUndertakingMoments` is a capped FIFO of `UndertakingMomentRecord` — the receipts idiom, deliberately not the receipts vocabulary (`modal | toast` would re-open the dismiss-spam hazard ruling 2.1 closed; moments stay `interrupt | badge | none`). `src/engine/undertakingMoments.ts` is the only thing that writes the array: it caps at `MOMENT_QUEUE_MAX` (8), evicts acknowledged records before unseen ones, is idempotent on id (two phases merge into the same field in one tick), and traces every `queued` / `dropped` / `opened` / `acknowledged` transition as `moment_surface`. That trace is the point — the checkpoint trace says what presentation was *computed*; this one says whether anything *showed* it, which is exactly the question the LEAKED registration was asking.

**Every emission site builds both halves together.** `buildMoment` returns the TickEvent and the record with the same id and the same words, so a card reached from a chronicle line is the card that line describes. `resolveUndertakingCheckpoint` returns `moments` alongside `events`; `advanceStrategicProjects` and `executeStrategicAction` pass them up; `phaseStrategicProjects` and `phaseAgentDecision` queue them.

**Significance follows presentation, not class.** An interrupt-tier moment emits at `MOMENT_INTERRUPT_SIGNIFICANCE` (0.85) and clears the chronicle threshold; badge-tier keeps the doc-1 values, now named. No orchestrator threshold moved — that one constant is the whole mechanism.

**Foundings emit at badge tier** from project activation, per ruling 2.1 ("foundings badge until nudge cards ship, so no interrupt is ever card-less").

**The divine rider is remembered.** `consumeUndertakingRiders` now says which verbs it folded; the checkpoint stamps `divineInfluence { verb, tick }` on the runtime, and a moment record claims it only when the rider landed on *that* checkpoint. This is the scapegoat-provenance seam (THR-1282 §6) the card's chip will render in slice 3.

## The one judgement call: the completion gate stays, for a different reason

The plan reads the gate as the defect: "the gate drops; completion emits both TickEvent and record." Reading the lifecycle showed why the gate existed. `advanceStrategicProjects` already emits a completion TickEvent — *after* christening, so it can say "completes The Saltway Ring" rather than "completes Establish Trade Network". Dropping the gate outright would have put both lines in the same chronicle for every finish.

So the checkpoint now emits the completion **record** and holds back the **event**; the lifecycle re-labels the record with the christened name after `christenCompletedWork`, gives its existing event the record's id, and sets that event's significance from the record's presentation. One completion, one line, one id, and the card and the chronicle agree on what got finished. The unit test asserts both halves of that — a record is returned *and* no completion event rides with it — and the lifecycle test asserts exactly one completion event whose id and message match the queued record. Technical verdict, recorded rather than escalated.

## What the simulation shows

The liveness test now asserts the queue against the real `initializeGameState → runTick` run, because every unit test on the checkpoint would pass through a producer whose records nobody merged into GameState. Seed 42, 60 ticks: records land, the cap holds, nothing resolves louder than a badge (a CLI world follows nobody), and a founding is present — the dead `started` branch is provably not dead. The 30-tick CLI smoke on seed 42 / medium reads the queue at the cap of 8: one `completion:badge`, seven `started:badge`.

## What is deliberately not done

`undertaking-checkpoint-events` **stays 🔴 LEAKED** and keeps its THR-1293 deferral. This slice gives the stream the queue the surfaces will read; it is still not a surface, and badging LIVE here would badge a path nothing travels. The interface-map row records the queue and says so. The `actionId` on `divineInfluence` is optional and unstamped — the shipped rider flags carry a magnitude, not an action id, so the chip renders unlinked text until a writer records one.

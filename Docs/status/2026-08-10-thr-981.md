# THR-981 — the ascendant's portrait was never missing; the remembrance choice never reached the graph

**Shipped 2026-08-10.** Every `?spawn=` / `?testavatar` review route — the ones the director uses to look at encounter content — rendered a letter tile where the acting figure should be. The ticket recorded the cause as *"the entity genuinely has no art"* and concluded *"no code change can fix that"*. Both halves are false, and the twelve origin portraits it needed have shipped since 2026-04-07.

## Why this was not the design call it was filed as

The ticket offered three options and marked them *"a design call, not an executor one"*: commission avatar art, stamp a portrait on the dev avatar only, or accept the letter tile. Two of the three are creative commitments, which is why it sat in the queue for eight days.

None of them was needed, because the premise is checkable and wrong:

* `getOriginPortraitUrl` is **fail-soft and cannot return null** — it falls back to `origin.ancient-scholar`, and its `DEFAULT_ORIGIN_ID` comment names `origin.dev` (the seeded identity's own origin) as the case that default exists for. So "no assets behind it for this origin" could not be why the slot was empty.
* `IdentityChip` — the player's persistent identity chip, shipped and live — has always rendered `getOriginPortraitUrl(originFragmentId)` for this same ascendant. Showing the origin portrait here is the **established treatment**, not a new choice about what the player's god looks like.

That makes the disposition a technical verdict rather than a creative one: the art exists, the treatment is settled, and the only question left is why the key never arrived. `initializeGameStateFromIdentity` builds a `compatArchetype` to reach the shared init path, `AscendantArchetype` has no origin field, and the remembrance choice was dropped there. The identity was stamped onto `state.ascendantIdentity` and never onto the graph — and the graph is the only thing the resolver gets to look at.

## The half that would have shipped a non-fix

Writing `originFragmentId` onto the ascendant node makes `resolveEntityVisual`'s `avatar` branch resolve, which satisfies the Done-when's literal clause. It would **not** have fixed the reported symptom, and the ticket's own evidence is what hides this: `__DEBUG.resolveEntityVisual('Vara')` matched `asc.hunger.witness`, but that is a *name* match, and both nodes are named Vara.

What the review route actually renders is the other one:

* `?spawn=` stages on `@hero`, which `debugEncounterTools` resolves through the `avatar_of` edge to the **avatar** node — `actorType: 'individual'`, not the ascendant.
* `buildHeader` reads `graph.getNode(activeAction.actorId)` and calls `getAgentPortraitUrlFromProperties`, which consults `portraitAssetPath` → `narrativeArchetype` and **never** `originFragmentId`.
* `NudgePhaseShell` passes that id to `EntityVisual` with a **hard-coded `kind: 'agent'`** (line 429), so the `avatar` branch is unreachable from this surface whatever the id.

So the two nodes take two resolution paths and are not interchangeable. The fix writes both: `originFragmentId` on the ascendant (which is where that fact belongs, and which makes the resolver's `avatar` branch live rather than dead), and the **resolved** `portraitAssetPath` on the avatar, because the agent path cannot see an origin id. An origin portrait is a mortal-looking face, which is exactly what the avatar — *"the mortal vessel"* — should wear.

The identity-less quick-start path (`createAscendant`, bare `?view=game`) is deliberately left alone: no remembrance choice is made there, so there is no origin to carry and the fallback tile is the designed result rather than a gap. That is pinned by a test so a later completeness sweep cannot read it as an oversight.

## Evidence

The ticket's own probe, on its own route, before and after:

```
before  { matchedId: "asc.hunger.witness", descriptor: { tier: "fallback", glyph: "V", kind: "avatar" } }
after   { matchedId: "asc.hunger.witness", descriptor: { tier: "art",
          src: "/portraits/origin-ancient-scholar.jpg", glyph: "V", kind: "avatar" } }
```

Live at 1920×1080 on `?view=game&seeded&size=medium&spawn=encounter.slice.unsafe_bridge`, the test panel's portrait slot renders `data-entity-visual-tier="art"` with `<img src="/portraits/origin-ancient-scholar.jpg">`, in-viewport at (411, 763) and no horizontal overflow.

Five contract assertions hold the chain, each falsified against the unfixed tree first — the three that depend on the fix fail with `expected undefined to be 'origin.dev'`, `expected undefined to be '/portraits/origin-ancient-scholar.jpg'`, and `expected null to be '/portraits/origin-ancient-scholar.jpg'`. That last `null` is precisely what `buildHeader` was handing the panel. The contract deliberately pins the shell's exact call shape (`kind: 'agent'`), because a descriptor resolved as `'avatar'` would pass while the real panel still rendered a letter tile — which is the way the first version of this fix was wrong.

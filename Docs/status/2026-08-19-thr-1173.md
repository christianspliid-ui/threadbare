# THR-1173 — the place answers

**Shipped 2026-08-19.** The location link tier stops being a door nobody walks through.

## What was wrong

THR-1172 built the tier end to end — `location` in `NarrativeEntityKind` and `visualKind`, `EncounterVeil.openEntity` routing it, `GameView` mapping it to `LocationProfileModal`, a `tooltipResolver` arm for `location.*` — and then no producer emitted one. A place named in encounter prose matched the narrative linker's scan, took a `referenceId`, and stopped there. `referenceId` is scene bookkeeping (`cast:<key>`, `location:<key>`); nothing downstream consumes it. So "Sacred Grove" reached the screen as a word that could not even *declare* itself openable.

The id was one line away the whole time. `collectSupportBundleEntities` already held `binding.nodeId` — a real location node — and spent it on `graph.getNode(binding.nodeId)?.name`, keeping the name and dropping the id. `buildGateDutyEncounterStageModel` did the same thing one layer down: the checkpoint's node id was computed inline as an argument to `getNodeName` and never survived the call.

## What changed

`EntityLinkEntry` and `TokenEntry` gained `entityKind` and `tooltipId` alongside the `entityId` one of them already had, and both linker paths — the prose scan (`autoLinkNarrative`) and the explicit `{{token}}` markup (`buildLinkedParagraph`) — now carry all three into the segment. The kind union is taken from the segment field itself (`NonNullable<EncounterStageNarrativeSegment['entityKind']>`) rather than respelled a fourth time.

Three producers now emit it:

- **Bound scene locations** — `entityId: binding.nodeId`, `entityKind: 'location'`.
- **The scene target**, when it is a place. This half was a live defect rather than a gap: the target arm pushed an `entityId` with **no** kind, and an absent kind means *agent*, so a location target opened the agent drawer. A wrong sheet, which Law 21 rates below no sheet at all. It also no longer mints a first-name entry for places — splitting "Sacred Grove" would have linked the bare word "Sacred".
- **Gate Duty's checkpoint** — the hoisted `locationId`, gated on the node still existing *and* being `type: 'location'`, so the `'Gatehouse'` string fallback can never become a dead link.

## The hover half, and why it names the kind

`buildLocationTooltipId` returns `location.<subtype>`, not `location.<node id>`. The resolver has both arms, but `tooltipResolves()` — the call that decides whether a word is underlined at all — is made with **no graph**, so a per-node tooltipId would be committed data that never draws. The subtype is committed world-model content and resolves context-free. It is pre-checked rather than emitted hopefully: a subtype naming no concept is a worldgen outcome, not an authoring error, so it yields `undefined` and the place keeps its link without a hover it cannot honour.

A pleasant consequence, confirmed in the rendered DOM: on a host that *cannot* route a place, the name now lands on the **explain** tier — focusable, underlined, saying what kind of place it is — rather than dropping all the way to inert text.

## What was already done

Done-when 2 asked for at least one shipped chip declaring `visualKind: 'location'`. **THR-1175 shipped four** the day this ticket was filed, in `vertical-slice.ts`'s standing-welcome band, and the renderer-side tier assertions have existed since THR-1172. The remaining half was the systemic one — a place reaching link tier *without* per-chip authoring — and that is what this is.

## Evidence

Every new assertion was **falsified before trusted** — three independent reverts, each confirmed red: the producer arms (4 red), the segment propagation (2 red), the Gate Duty token (1 red). The load-bearing assertions are the negatives, because a producer that stamped `entityKind: 'location'` onto everything would satisfy every positive assertion while being a worse bug than the one being fixed: a cast member must come back with **no** kind, and so must a non-place target.

One trap is worth recording. Every existing graph stub in `buildGateDutyEncounterStageModel.test.ts` answers `getNode` with `{ name }` alone — no `type` — which makes the new `type === 'location'` guard false and the link silently absent. A test written against those stubs would have passed whether or not any of this shipped. The new gate-duty tests use a typed node for the positive case and pin the untyped shape as the negative.

## Not done, stated plainly

The ticket's Done-when mentions "an anchor sentinel for the scene location if one is introduced". **None was introduced.** The aftermath chip path already binds its place through the existing `$target` sentinel (THR-1175), so `classifyAnchorDeclaration` / `resolveAnchorDeclaration` are untouched and `check:chip-anchors` is green on the unchanged rule. Adding a sentinel with no authored consumer would have been the THR-614 error — badging a path nothing travels.

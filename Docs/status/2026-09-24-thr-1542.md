## What shipped

- **`resource_manipulate` takes `resource: 'fight_clock'`.** It is routed to `advanceFightClock`, the one clock writer, at all three sites that read `resource_manipulate`:
  - **the executor** (`executeFightClock`), for reactive, cascade and spell nested effects. It returns a `fightClockRequests` entry, and `applyExecutionResult` writes it. `target: 'self'` is the bearer; `'other_agent'` is the counterpart;
  - **the one-shot item path** (`effectEvents.ts`), on the bearer's first `encounter_outcome` after attach, aimed at the counterpart;
  - **the per-tick path** (`effectTick.ts`), on the bearer's own clock: a bleed, or a regeneration.
- **A write during a clash counts in that clash.** A mortal opponent's write lands in the node mailbox, which the handler drains before the clock-full check. That path already counted a positive drain as a blow landed. This slice adds the same rule for a monster's persistent clock: `landFightBand` reads the clock across the step's raises, and a net-positive change is a blow. So a charm that fills a monster's clock on a failed clash wins the fight.
- **`inflict_condition`** (new effect type 42): `{ conditionTraitId, target: 'self' | 'counterpart', durationTicks?, intensity?, condition? }`. The executor returns a `conditionRequests` entry, and `applyExecutionResult` lands it through `applyConditionToActor`, so tag immunity refuses it and the `damaged` proxy fires. The edge carries `inflictedBy`.
- **`applyConditionToActor` moved** to `src/engine/effects/conditionApplier.ts`, with its option and result types and the two `CONDITION_DEFAULT_*` constants. The effect dispatcher needs to reach it, and importing `encounterAftermath` would have pulled that module into the effect engine's import graph. `encounterAftermath` re-exports everything, so every importer is unchanged and the aftermath `apply_condition` case behaves as before.
- **`clock_above:n`** is a new predicate. It is true while the bearer's own persistent clock (`monsterState.clockFilled`, as last written) is above `n`. `PredicateContext` gains an optional `fightClockFilled`.
- Cascades carry their members' clock and condition requests.
- Docs: rulebook §7 (a new `[IMPL]` rule), the systemic wiring guide (FB6 section), the wiring checklist, the interface map (a new row `effects-write-fight-clock`, and the `fight-band-conditions` row repointed to `conditionApplier.ts`), and two wiki pages (encounters manual, interface map).

## Decisions made in execution

- **Executors stay pure.** The plan said the executor branch "calls `advanceFightClock`". The effect executors' contract is that they return data and let the caller apply it, and `inflict_condition` needs the game state, which executors do not hold. So both new branches return requests, and `applyExecutionResult` is their one applier.
- **`clock_above:` reads the bearer's own clock.** The plan names the predicate but not whose clock it reads. The bearer's own clock is the one a predicate context can see, and it gives "a beast enraged past half its clock". It reads the stored value; lazy recovery applies at the next clock read or write, because the context builder has no tick.
- **A per-tick write also stamps the clock.** It re-stamps `clockUpdatedTick`, so a clock under a per-tick effect never recovers lazily. The effect is the recovery (or the bleed) while it lasts.

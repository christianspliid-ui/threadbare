**No merge driver could have fixed it, because the conflict was the shared write and GitHub never reads `.gitattributes` (THR-1016, 2026-08-07).** Every closeout PR wrote `Docs/project-status.md` at the same two anchors — insert at the top of `## Current Focus`, delete at the tail to hold the 60-line cap — so **any two open closeout PRs conflicted by construction**, whatever either contained. Measured: PRs #1322, #1326 and #1327 sat `DIRTY` for 17, 18 and 20 hours conflicting *only* in closeout docs, and #1322 was hand-resolved **twice in one session** because #1330 merged minutes later and re-staled it with nothing about #1322 having changed. **Both merge-driver routes were tried and both are dead ends**, which is the part worth carrying forward: `union` keeps both sides of a *rewritten* hunk, so the cap trim duplicates rather than merges — the correct reason THR-691 excluded this file; and `merge=ours` is **not a built-in driver** like `text`/`binary`/`union`, it needs `[merge "ours"] driver = true` in `.git/config` that no repo file can ship. Measured in a fresh clone with the attribute committed: `CONFLICT (content): Merge conflict in Docs/project-status.md`, clean only once the config was added by hand. And a *working* driver would still not have been enough, since GitHub's server-side merge ignores `.gitattributes` outright and strands the PR at `CONFLICTING` regardless. So the write stopped being shared: `Docs/status/` holds **one committed fragment per shipped ticket**, and creating that file is now the entire closeout write. **The assembly left the tree** — `Docs/project-status.md` is built by `prebuild` and gitignored, the same trade `Design/impediment-dashboard.html` took under THR-916, reached from the other end; `check:generated-freshness` still asserts the generator produces it and that nobody `git add -f`'d it back. **The cap became a rendering budget rather than an editing discipline**: the generator renders the newest fragments that fit and stops, so nothing is deleted or annotated to make room and everything older stays readable in `Docs/status/`. That also retires the `(THR-XXX's entry moved to project-history.md …)` bookkeeping suffix, which was itself a second write to a *neighbouring* entry and a second conflict source nobody had named. Ordering is by date then **numeric** ticket id — a plain filename sort reads `thr-994` as newer than `thr-1013` — and carries no wall-clock stamp, so the page stays a pure function of its fragments. Proven end to end on two simulated closeout PRs in a throwaway clone: the second merges `EXIT 0 — no conflict` with both entries present at 56 lines, against the same two closeouts on `origin/main` reporting `CONFLICT (content)` at 64 lines, already over its own cap.

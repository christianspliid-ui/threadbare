# THR-1145 — the encounter factory draws its consequences instead of choosing them

**Shipped 2026-08-17.** Last of the five consequence-palette tickets (THR-1141 → 1142 → 1143 → 1144 → 1146 → **1145**), and the one the other four were sequenced ahead of so its family table could name every shipped effect kind.

## The problem this solves

`Docs/plans/2026-04-16-systemic-wiring-guide.md` is a long, good list of things an encounter can do. The palette census behind THR-1141 measured what a list of capabilities actually produces under a deadline: nearly every shipped consequence landed on an item, a reputation delta, or a condition, while a dozen live primitives went essentially unused. That is not authors ignoring the guide — it is what a menu does. Asked to invent a consequence, everyone reaches for the nearest one.

Christian's direction, 2026-08-16: *"a little simple randomizer for the encounter writing factory that randomly assigns a set of primitives that need to be used in context … HEART encounters should have a larger chance of spawning allies or build relationships … gold encounters should have a larger chance of spawning items … most primitives could potentially show up in most types of encounters although chances may vary."*

So the factory rolls the hand instead of offering one.

## What shipped

**The draw.** At brief time, `npm run draw:consequences -- <templateId> --reach <reach> [--rarity n]` prints two **consequence families** — three at `rarityTier ≥ 3` — that the encounter must wire *in context*, plus the concrete effect kinds that satisfy each. Fifteen families cover the palette: `relationship`, `companion`, `standing`, `possession`, `condition`, `knowledge`, `secret`, `story_seed`, `thread`, `drive`, `movement`, `place`, `membership`, `omen`, `formative`.

**The weights carry the reach's flavor; the floor carries the variety.** `CONSEQUENCE_FAMILY_WEIGHTS` is the 15×8 matrix from the plan, shipped as written. `heart` draws `relationship` at 10 and `omen` at 1; `gold` draws `possession` at 10; `star` draws `story_seed` at 10. But **every cell is ≥ 1**, so any family can surface in any reach — a `veil` encounter drawing `possession` is the table asking what a blessing looks like as an object, not a misfire. A zeroed cell would turn the eight reaches into eight rigid genres, which is the same convergence problem one level up; the floor is pinned by a test for exactly that reason.

**Recomputable, therefore tamper-evident.** The hand is a pure function of `(id, reach, rarityTier)`. A template records what it drew in an additive `consequenceDraw?: readonly string[]`; `check:encounter` re-derives it and fails a mismatch, so the field is a claim the gate audits rather than data anyone can edit. It also fails a recorded family that nothing wires, naming the kinds that would satisfy it.

**The one swap.** `consequenceSwap: { from, to, reason }` — exactly one drawn family may be traded, the traded-in family must still hold weight ≥ `CONSEQUENCE_SWAP_MIN_WEIGHT (2)` in that reach, and the reason is required. This is the valve that keeps a drawn `companion` out of a scene with no persistent cast; it is not a second roll, and the gate accepts zero unrecorded deviations.

**The utility is generic on purpose.** `drawFromTable(tableId, weights, seedKey, n)` knows nothing about consequences. THR-1147's plot-hook table is already commissioned against it, and the plan names cast / complication / premise draws as follow-ups. It draws without replacement, mixes `tableId` into the seed so two tables for the same subject are independent, and **sorts keys before sampling** — so reformatting a weight object is a refactor, not a re-roll of every recorded draw in the corpus.

## The judgement call: presence-conditional, not required

The ticket's Done-when reads *"legacy corpus grandfathered via the existing ratchet, new factory output required to carry the field."* Implemented literally — a hard "must carry `consequenceDraw`" rule — that fails **exactly the templates that are not on `RETROFIT_PENDING`**: the six the Encounter Factory has already retrofitted, and only those. The ratchet grandfathers the 185 unfinished templates; it cannot grandfather the finished ones, because they are not on it and the ratchet only shrinks.

So the gate is **presence-conditional**: a template recording nothing is silent. The requirement on new output lives where it can actually be met — the pipeline's brief stage hands the author their hand (SKILL Step 0b) and the authoring spec requires recording it. Measured: `check:encounter --all` reads `191 checked, 6 clean, 0 failing, 185 on ratchet` before and after, unchanged.

That is also what made it safe to claim past THR-1130's mutex. That ticket's stated harm was *"moving the gate under an in-flight retrofit would either red the retrofit mid-batch or grandfather the new field silently."* Neither happens: nothing reds, and the field is documented in three places rather than grandfathered quietly.

## Falsified both ways, and the first attempt was not

The ticket asks for the gate red on a doctored draw and red on a drawn-but-unwired family. Both hold — and the second one **did not, on the first cut**, in a way worth recording because it looked like it did.

The red case derived from the green one by removing the injected effect for one drawn family. It passed the gate anyway: the golden exemplar's hand includes `possession`, and the exemplar **natively** wires `possession` through a `rewardPool` on a step outcome. Removing the injected effect left the native one standing, the "unwired" arm reported nothing, and a green result read as evidence the gate worked. The fix is `bareExemplar()` — strip the base's own writes first, so the injected reaction is the only wiring there is. The revert check now shows both guards failing when disabled (2 of 33 red with `wired.has(family)` short-circuited and `.sort()` removed; 33/33 green restored).

## Evidence

- `npm test` — **1029 files, 16,525 tests, exit 0**
- `npm run check:typecheck` — **3178, unchanged from baseline** (no `--update`; two net-new errors in the new test file were fixed rather than baselined)
- `npx vite build` — clean, 12.80s
- `npm run check:encounter -- --all` — `191 checked, 6 clean, 0 failing, 185 on ratchet` — **OK**, identical to `main`
- Determinism: the same id printed the same hand on repeated runs; `--reach heart` and `--reach star --rarity 3` on the same id gave different hands and a hand of three

No engine smoke owed — nothing under `src/engine/`, `src/types/gameState.ts`, `src/types/graph.ts`, or any tick/orchestrator/phase file is touched; the draw is authoring-time and the engine never imports `content-eval`. `Browser-verify exempt: no UI-pillar file in the diff` — no `src/components/`, `src/hooks/`, `src/contexts/`, or global CSS.

## Where it is documented

Three surfaces, because three different readers need it: `nudge-authoring-spec.md` § The Consequence Draw (the authoring contract, shared verbatim with `template-encounter-rewrite`), `encounter-pipeline` SKILL Step 0b (the orchestrator's roll, before the draft dispatch), and the systemic wiring guide's own capability section (the reader who is browsing for what is possible — which is the reader this whole ticket exists to stop over-serving).

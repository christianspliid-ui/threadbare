# THR-1997 — A reward's kind comes up at the recipe's share

**Shipped 2026-10-23.** The build of the THR-1890 decision (`Docs/audits/2026-10-20-thr-1890-reward-category-shares.md` § 5). A recipe's kind shares (say condition 0.8 / possession 0.2) used to be multiplied into every item's weight inside the rolled rarity, so the kind with more items won: about a quarter of multi-kind prize draws landed off the recipe's shares.

**What changed.**
- **The draw.** `drawTierFirst` (`src/engine/rewardPool.ts`) rolls the rarity as before, then picks the kind by its share among the kinds present at that rarity, then the item. It still spends one roll: the in-tier position is re-scaled once for the kind and again for the item. Master switch `REWARD_KIND_ROLL_ENABLED` (on); `false` reproduces the old pick for every roll.
- **The pool.** `PoolEntry` gains optional `category`, set by `assembleRewardPoolDetailed` for every entry. An untagged entry is a kind of its own, so hand-built pools draw as before.
- **Canon.** Law 2's open instance becomes an established one; rulebook §4 *How rare a reward is gets rolled first* gains the kind sentence.

**Deviation.** The plan said each entry's weight becomes its tier weight alone. Entry weights stay share × tier weight; a kind's group weight is the mean of its entries' weights (one entry's share × tier weight). The pick is the same, and the switch-off path is the old code untouched.

**Evidence.** Census re-run through the real `drawTierFirst` (proto census adapted, 174 recipes, seeds 42/99/7, 4,000-roll sweeps): success off-authored **13.4%** (≤ 14%), tier mix **52.2 / 36.2 / 10.0 / 1.6** (unchanged); switch off measures 26.2% with the same tier mix. `npm run gate` code track: typecheck, build, encounter, god-cards, ui-debt, 30-tick CLI smoke PASS; `npm test` 25,264 pass, 3 timeouts under parallel load in `conceptTooltipIds` / `debug-bridge`, both files 18/18 alone.

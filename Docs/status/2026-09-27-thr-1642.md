# 2026-09-27 — THR-1642: a new cycle starts with a fresh Doom clock

**Ticket:** [THR-1642](https://linear.app/threadbare/issue/THR-1642) · **Project:** Onboarding & First-Run Experience · **Found by:** cold playtest round 1 · **Pillars:** Engine (Content: N/A — no authored data; UI: N/A — no surface changed).

## What was wrong

`transitionToNewCycle` (`src/engine/cycleEnd.ts`) built the next cycle with `...state` and never replaced `doomClock`. Cycle 2 began with `expired === true`, so its first `playing` tick's `phaseDoomExpiry` fired the Unmaking again and the cycle harvested `TWILIGHT_TICKS` (7) ticks later — "the game playing itself and telling me I lost".

## What shipped

- The new cycle gets `createDoomClockState(archetype, DEFAULT_DOOM_TICKS)`: stage 1, progress 0, tick modifier 1, counter-omens and resolved-card history cleared.
- **Same archetype and stage definitions** carry over (a World-Soul redraw of the doom is future design); `doomDefinition.totalTicks` is aligned to `DEFAULT_DOOM_TICKS`.
- Doom-identity milestones (`triggered` runtime flag) are reset on a **copy** of the matrix, so the new cycle's milestones fire again and the shared module table is not mutated.

## Evidence

- `src/engine/__tests__/cycleEnd-doomReset.test.ts` — 3 tests on a real `initializeGameState` world; all three fail with the fix reverted, pass with it. The third runs one `playing` tick after the transition and asserts the phase stays `playing`.
- `npm test`, typecheck ratchet, `vite build`, 30-tick CLI smoke, `npm run test:heavy` — see the closing commit body.

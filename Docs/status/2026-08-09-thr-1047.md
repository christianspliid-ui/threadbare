Implementation item 5 of the Encounter Factory: the batch-brief format (Stage 0), the
Stage-4 headless live-proof sweep, the Stage-5 batch report, and `encounter-pipeline`
promoted to v3 with the six-stage line wired end to end. Items 2 (`check:encounter`,

## The load-bearing idea: Stage 3 asks a different question from Stage 4

`check:encounter` asks whether a template **declares** its composition blocks.
`check:encounter-live` asks whether they **arrive**. A template can pass the contract
and deliver nothing — an `aftermathConfig` whose variants are unreachable renders the
fallback forever (the THR-989 class), a seed on an unreached band never plants, a reward
recipe on a step nobody reaches leaves no node. Neither stage substitutes for the other,
and the split is what makes "same high quality every time" checkable rather than hoped
for.

The sweep spawns the encounter on the ascendant in a seeded world, commits a hand by
writing `activeNudges` (the exact field `collectNudgeModifiers` reads — the resolver
applies no affordability check of its own, so this is the headless equivalent of the
player clicking cards), ticks to resolution, then reads the running state for what the
template promised.

**Every claim is gated on `systemConnections()` — the same function the Stage 3 contract
counts its systems quota with.** One predicate, two consumers. A template declaring no
seeds is never failed for planting none; a template declaring seeds cannot pass by
planting none. A second hand-rolled "does it declare seeds" predicate here would drift
from the gate's within a month, and the drift would be silent in the direction that
matters — this sweep going quiet.

## Vacuity is a verdict, not a pass

The likeliest way this script could fail is by proving nothing loudly. A template
declaring no cast, reward, seed, condition or reachable variant has only the baseline
claims to satisfy — it spawned, it did not crash, its steps resolved — and every one
passes for a template that delivers nothing a player would notice. So a run whose
declared-delivery claim set is empty reports **`vacuous`**, never `proved`, and the batch
report counts vacuous runs on their own line with the instruction to read them as
unproved.

`vacuous` deliberately does **not** fail the command: refusing a template that declares
too little is Stage 3's job, and duplicating that refusal would report one defect twice.
Thirteen tests pin this, including one that walks every baseline claim individually and
asserts each alone still scores `vacuous` — the exact regression that would turn every
clean run green.

## Two findings the harness produced by existing

**An unregistered template cannot be live-proved, and used to fail as if it were broken
content.** The engine's `resolveUnifiedTemplate` searches the action's template list then
`getUnifiedTemplateById`; a template in neither stages fine and then never advances a
step. The golden exemplar is registered in no pool by design, so it burned the full
60-tick bound and reported `steps_resolved: fail` — which reads exactly like a content
defect and is not one. The sweep now detects this up front and says so by name. This is
why the exemplar is a Stage 3 artifact only.

**The slice encounters fail live proof today, and that is the harness working.**
`encounter.slice.unsafe_bridge` resolves cleanly to `success_at_cost` and then fails four
delivery claims: cast declared but bound no live actor, a declared reward leaving nothing
persistent, a declared condition not applying, and one of two aftermath changes carrying
no `concepts` (Law 2). Cast binding is expected to fail until implementation item 1
(`encounter.*` family default support bundles) ships. These are the retrofit-15 not yet
being composition-complete — precisely the population Stage 4 was built to measure.

## The rest of the line

**Stage 0 — the batch brief** (`reference/batch-brief-format.md`). The rule shaping the
whole document: *a brief names variance, not content*. It describes the spread the six
must cover — reaches, shapes, tones, settings — and lets the draft agent find the fiction
inside it. A brief that specifies the encounters has moved the authoring into the brief,
where no gate can see it, and the batch report then reports a variance the brief already
fixed. Agent-drafted, Christian-approved in chat before a batch runs (ruling 2).

**Stage 5 — the batch report** (`npm run encounter:batch-report`). Renders the batch side
by side, one row per encounter carrying gate verdict, live verdict, resolved outcome,
systems connected, band count and two review links (ruling 1: variance is what he reviews
for). The per-encounter detail comes after the table, never before — a report leading
with six dossiers would be six reviews rather than one batch review. **It runs neither
check itself**; it renders their JSON, which is what keeps it from disagreeing with CI —
the most expensive disagreement available here, because it surfaces after the director
has already approved the batch.

**`encounter-pipeline` v3.** v2's draft → editorial → systems → implementation chain keeps
its shape; v3 adds the brief in front, bounds the critic loop at two iterations with
**park, don't kill** (ruling 4 — a parked encounter lands at
`<slug>-parked.md` with both critics' outstanding fix-lists and stays in the batch report,
because an encounter that survived two critics carries real authored prose and redrafting
throws it away), and puts the two machines between the last agent and the PR.

## What this does not do

The batch report's Package View links are rendered ahead of the surface and marked
pending — THR-1046 has not shipped. They are rendered anyway rather than footnoted,
because a link that will resolve is more useful in a committed report than a promise, and
marking it is what stops it reading as broken. The first batch through the line
(implementation item 6, the retrofit-15) is separate work.

# Nothing was deleting node_modules — the precheck's green was, and Vite made the husk (THR-1326)

**2026-08-29** · Infrastructure / Improvement · code diff (2 scripts + 2 docs)

The fresh-worktree `node_modules` class had been tallied ~31×/week for seven weeks as if
something were wiping installs. It is not. Two shapes were being counted as one incident,
neither is a wipe, and the one genuinely broken thing in the story was the precheck line
that reported the tree healthy while the tree was a husk.

This session hit the bug in its own first tool call: `test: yes (1.25s)` printed one line
above `nm: no — session tree stub`, in the same run.

## What the forensics found

**Plain-missing (~170 of 199 pool directories) is the normal fresh state, not an incident.**
`git worktree add` does not create `node_modules`, and `node_modules` is gitignored so no
checkout restores one. Nothing produces this — it is the absence of a step. The pool bears
it out: freshly-created worktrees show missing uniformly, and every one showing a junction
is one a session already repaired.

**The `.vite`-only stub (3 of 199) is created by Vite, not left behind by a deletion.**
Vite's default `cacheDir` is `<root>/node_modules/.vite`, and the dev server `mkdir -p`s it
*during config resolution — even when it then fails to start*. Reproduced on demand: point a
dev server at a tree with no `node_modules` and you get a `node_modules/` holding exactly
`.vite`. So the stub is manufactured by pointing `preview_start` (or any `vite` invocation)
at a worktree **before** repairing its install. The timings agree — `vigilant-bhabha-510e0a`
was created 09:01 and had `node_modules/.vite` by 09:02, far too fast for a 289-package
install to have existed and been destroyed.

**The reaper is not the producer of either.** Its 56 `worktree removal FAILED (in use?)`
events leave the directory with `node_modules` *fully gone* — `sleepy-einstein-c7cbba` is
still on disk in exactly that state. Failed removals do not leave husks, and none of the
three stub worktrees appears in the failed-removal set. The junction-guard's 48 severs are
likewise clean.

## The precheck fix

`session-precheck`'s `test:` probe shells out to `npm test`, and Node resolves vitest by
walking *up* the directory tree. A worktree at `<repo>/.claude/worktrees/<name>` therefore
finds `<repo>/node_modules` and times **the donor's** packages while its own tree holds no
install. Both lines were true in isolation; only one was about install health, and the
misleading one printed first.

`node_modules` health is now resolved *before* the test probe and handed to it. On a session
verdict of `stub`, `absent`, or `shim-stripped` the probe abstains — status `unknown`,
`abstained: true`, fingerprint `test=abstained` — and does not shell out at all. Print order
is unchanged. `unknown` deliberately does **not** abstain: an unreadable health probe is not
evidence of damage, and suppressing a real signal on it would trade one misleading line for
another (NFP #4).

The abstention says "not measured here", not "the suite is broken". A red would have been a
second lie.

A/B on one tree, this session's own conditions:

```
before  - test: yes (1.25s) — src/testing/__tests__/contentInvariants.test.ts in 1.25s
        - nm:   no  (0.02s) — session tree stub: node_modules holds only 1 entry
        fingerprint … test=1.25s … nm=session:stub/donor:healthy

after   - test: unknown — abstained — session tree node_modules is stub, so a timing here
                 would measure the donor's packages resolved through the parent directory,
                 not this tree; repair the install (see nm: below) and re-run
        - nm:   no  (0.02s) — session tree stub: node_modules holds only 1 entry
        fingerprint … test=abstained … nm=session:stub/donor:healthy
```

Healthy arm re-confirmed after restoring the junction: `test=1.18s nm=session:healthy/donor:healthy`.
The abstention silences a lie, not a signal.

## The tally rows are retired

Both arrival shapes are expected states with a documented ~2-minute repair. Logging them as
impediments was counting a normal condition ~31×/week and drowning the log — the 2026-08-22
watch trigger of ≥3/week "firing at ~10×" was measuring the pool's ordinary behaviour, not a
defect. CLAUDE.md's worktree bullet and the catalog now say so explicitly: repair and move
on, do not log either shape. What *is* still worth logging is a damaged **donor**, which is
the shape with no cheap repair.

Consistently with that ruling, this session logged no impediment for the stub it hit.

## Cost note

The ticket priced this at ~2–4 h of forensics against ~1 h/week of repair. The repair cost
was real but the diagnosis inverted its target: the ~1 h/week stays (a missing install still
needs a junction), and what actually goes away is ~30 log rows/week of false signal plus a
standing misleading green on the first line every session reads.

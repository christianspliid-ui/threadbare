### THR-1115 — the donor repair fires by itself, and refuses while anyone is working (2026-08-15)

THR-1111 named the wiper by its shape and shipped a `--repair` arm that **nothing called**. This wires it, and the whole difficulty is that the obvious wiring is unsafe: the diagnosed damage *is* an interrupted or racing `npm install`, so a lane firing `npm install` on a timer is a plausible cause of the class it would be repairing. The ticket's own words — "wiring it blind would have been a fix that manufactures its own evidence."

**The reframing that makes it tractable: the repair can only ever act on an already-damaged donor.** A live session junctioned to a damaged donor is *already* broken — `esbuild` is already not recognized. So the risk is never "a healthy tree we might break"; a working session implies a healthy donor implies no install. That collapses the hazard to one real case — landing on a tree somebody is *currently installing into* — which is exactly what the liveness gate and the lock are pointed at.

**Three guards, each asserted rather than merely added**, because the Done-when asked for the live-session case to be *proved*, not described. (1) A liveness gate vetoing on any active worktree or on the donor's own `node_modules` mtime. (2) A single-flight lock built on `mkdir`, which is atomic on NTFS and POSIX — a check-then-create would have reintroduced, inside the lock, the very race the lock exists to remove. (3) A **re-probe under the lock**, so the loser of a race finds the donor already fixed and installs nothing; without it, two lanes is precisely where a second install lands on a tree the first just finished.

**The guard was falsified against the real machine, not only against fixtures.** Run live from this session's worktree, the collector gathered **117 activity signals** across the registered worktrees and correctly identified *this very session* as the blocker:

```
donor: C:/Users/chris/Dev/Projects/TheFantasyWorldSimulator
activity signals: 117
VERDICT idle=false :: worktree serene-easley-8a22ad (files) touched 1m ago (< 30m idle floor)
  1m ago  worktree serene-easley-8a22ad (files)
  7m ago  worktree serene-easley-8a22ad (git)
 54m ago  worktree infallible-wozniak-e65e78 (files)
```

Had the donor been damaged this hour, the repair would have refused, naming the tree that stopped it.

**One inclusion and one omission in the liveness probe carry the design.** The donor's `node_modules` mtime is probed *on its own* — an install in flight rewrites that directory constantly, making it the freshest evidence that someone is already repairing by hand, and it is excluded from the general tree walk precisely so unrelated churn cannot mask it. Conversely the donor's own **working files are deliberately not a signal**: the home tree is a read-only mirror that autosync fast-forwards hourly, so gating on them would veto every repair forever — and a guard that never lets the lane fire is indistinguishable from the outage it replaced.

**The idle floor is 30 minutes, against the reaper's 180, and the asymmetry is the point.** The reaper's threshold guards an irreversible deletion of authored work; this one guards a re-runnable install on a tree that is already broken. A test pins the floor below 180 so a later edit cannot quietly make the lane unreachable.

**Where the logic lives is itself the ticket's third approach item.** The repair must run on the Windows host against the home tree, so "a tracked lane" cannot mean a workflow — Actions cannot reach it, and the only hourly local schedulers are the reaper and autosync, both untracked. The split taken: **concurrency-critical logic in the tracked, tested, PR-gated `scripts/repair-donor-node-modules.ts`; a single delegating line in the reaper**, with its mirror regenerated byte-identical in the same PR. The script imports `node:*` builtins and its sibling probe and **nothing else** — an import from `node_modules` would make it unrunnable in exactly the state it repairs.

**The policy reversal is recorded where the policy was written.** The reaper said "the reaper NEVER auto-installs (that is a dev action)". That sentence is what converted a ~4-minute problem into an 18-hour outage — the streaks in that same log run 12, 16 and 18 consecutive runs — so detection without repair merely documented the outage hourly while it continued. The reversal, and the reason, now sit at the call site.

16 new tests (29 across both node_modules files), full suite green at 1017 files / 16,249 tests, ratchet unchanged at 3448, build clean in 10.14s.

**Not discharged, and it is not dischargeable in one run:** the third Done-when asks for *a recorded week* with no damaged donor verdict surviving more than one hourly run. That is an observation window, not an implementation step — the mechanism and both guards ship here; the week accrues in `clean-stale-git.log` and is read at the next weekly retro.

# THR-1292 slice 3/6 — checkpoint dice in the strategic runtime

**Date:** 2026-08-27 · **Issue:** [THR-1292](https://linear.app/threadbare/issue/THR-1292/the-undertaking-substrate-proactive-agent-actions-plan-doc-16) · **Plan:** [`Docs/plans/2026-08-26-thr-1292-undertaking-substrate.md`](https://github.com/christianspliid-ui/threadbare/blob/main/Docs/plans/2026-08-26-thr-1292-undertaking-substrate.md) §2 + §5

## What shipped

An undertaking used to advance because a tick elapsed. It now advances because a roll said so.

`src/engine/undertakingCheckpoints.ts` is the **second caller** of the step-resolution core slice 2
extracted. Every `UNDERTAKING_CHECKPOINT_INTERVAL_TICKS` (6) an active undertaking rolls its
template's primary reach against `checkpointDifficulty` on the same six-band ladder an encounter step
uses — clean success advances a full step, a critical success advances two, an at-cost success
advances and leaves a mark, and anything from a near miss down **halts**. Three halts replace the
next checkpoint with a fork the agent decides for itself: abandon, or escalate at higher stakes
(`rebindRequested` is the seam doc 3's binder consumes). One escalation maximum; a second trip
forces abandon.

Failure residue follows visibility (review ruling 2.2): an undertaking the player watched fail
leaves `undertaking_failed_visible` carrying its possessive inputs, one nobody watched leaves
`undertaking_failed_clean` and no graph litter. `resolveMomentPresentation` decides interrupt vs
badge, and `GameState.followedAgentIds` is **additive over the threaded retinue** rather than
authoritative — threads are minted long after world init, so an authoritative snapshot taken there
would follow nobody for the entire run.

Also: the §5 per-verb flags (`requiresLocation`, `canRunBeside`), the two traces, the per-project
PRNG stream (multiplier 97 — deliberately not joining the `*59`/`*53` pile-up), the timeout moved to
`UNDERTAKING_TIMEOUT_TICKS` (60), and the two interface-map rows slice 2 correctly declined to write
while there was still only one caller.

## The two things the tests could not have told us

**A bug the unit tests were structurally unable to see.** The fork compares the undertaking's
`ambitionId` against the actor's `pursues` edge targets — but a project stores a *template* id
(`ambition_conquer_territory`) while the edge points at the *node*
(`ambition.ambition_conquer_territory`). Matching them directly answers "not pursuing that" for every
agent in the world, so the ambition term was structurally unreachable and every fork abandoned: 55
abandonments, **zero** escalations on a 150-tick seed-42 run. Every unit test was green, because each
one built its own fixture and got to invent both sides of the comparison. Fixed by routing through a
new `ambitionNodeIdCandidates` in `ambitionShape.ts` — the shape module, on the principle it already
exists for. After: 43 escalations / 32 abandonments.

**A plan value reversed on measurement.** The plan (§5) sets the conversion default to
`requiresLocation: true`, reasoning that it *preserves today's parallel behaviour*. It does not.
Today an undertaking advances wherever its owner is standing, because nothing walks an agent to its
stage — the plan itself assigns that to docs 3/5. Measured with `true`: of 736 checkpoints on seed
42, **50 rolled** and 686 deferred `actor_absent`; seed 99, 15 of 668. A probe at tick 80 found
**0 of 45** active undertakings with their owner at the stage — actors sat at unrelated settlements
or on transient transit hexes, so the gate was measuring correctly and simply had nothing to wait
for. That is not the variance §2 designs for; it is a system whose dice are 93–97% inert and whose
undertakings die of absence rather than of failure. Shipped `false`, gate fully implemented and
tested, reversal recorded with its numbers in
[THR-1294](https://linear.app/threadbare/issue/THR-1294/requireslocation-defaults-off-undertakings-ignore-their-stage-until).

`undertakingCheckpointLiveness.test.ts` is the guard that would have caught both: it runs the real
`initializeGameState → runTick` pipeline and fails when the *rolled share* of checkpoints drops below
half. Falsified against the exact bug — 0.158 with the default flipped back.

| rolled | 630 | 544 |

| completions | 163 | 150 |

**`success_at_cost` never came up in 1174 rolls, and that is worth knowing rather than hiding.** It
is not dead code: `breakdownToOutcome` never returns it, so for an agent it arises only from the
scale probability floor, which needs an actor incapable enough to drop below the regional floor. At
the plan's default difficulty of 0.45 no undertaking got there. The `advance_at_cost` effect and the
`atCostMomentFired` gate are therefore unit-tested but unexercised by the simulation; doc 2's harder
per-kind band tables are what will reach them.

Likewise `presentation` is `badge` or `none` in every CLI run and residue is 100% `clean` — a CLI
world carries no `thread` edges, so nothing is ever followed and `everInterrupted` never gets
stamped. Both arms are unit-tested; the simulation reaches only one. Recorded in
[THR-1293](https://linear.app/threadbare/issue/THR-1293/undertaking-checkpoints-have-no-player-facing-consumer-the-moment).

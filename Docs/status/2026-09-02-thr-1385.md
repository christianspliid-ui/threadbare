# THR-1385 — a number for engine cost per tick, and the phase that owns it

**2026-09-02 · engine (report-only).** `npm run measure:tick-cost` prints ms/tick on the real `initializeGameState → runTick` path, warm-up and steady bands, the agent count at both ends, and the phases by cumulative time from the profiling ring the tick loop already carries (THR-580). `npm run check:tick-cost` turns one measurement into a trend row on `ops` and a uniform-shape probe (`{verdict, summary, needsChristian: false, needsSession}`) that `keep-work-flowing-cc` folds into the briefing; it says `drift` only when steady ms/tick sits more than 25% above the 7-day median, and it never fails a run. Neither asserts a wall-clock number — the THR-1328 lesson is that timing assertions measure GC scheduling.

Two readings fall straight out of the table.

- **One phase owns the regression.** `groups` (the company layer: upkeep, movement, fray, formation, seeking, reunion) went 14 → 27.5 → 46.5 s while every other phase stayed within a second of where it was. Its share of a tick rose from 58% to 80%. Its worst single tick went from half a second to two and a half. `agent_decision`, the phase the cutover work touched, got *cheaper*.
- **Population is a second, smaller lever.** Between 08-24 and 08-29 the tick-0 population did not move (290) and `groups` still doubled, so that step is the phase's own cost, not the world's size — the commits in that window that touch the company layer are THR-1292 slice 4, THR-1297 slices 1 and 4, and THR-1309 (08-28, *a work that is people*: undertakings that raise companies), which is the shape of more companies re-deciding, though no company count was captured per commit. Between 08-29 and now the tick-0 population rose 290 → 368 (THR-1347's genome NPC top-up, 08-29 afternoon) and the phase went up another 70%, with the 2.5-second spike appearing.

## What the number is made of

A V8 CPU profile of 120 ticks (`node --cpu-prof`, self time by function) says it is not the company logic at all — it is **pathfinding**: `findShortestPath` 37.6%, `getOutgoingEdges` 13.6% (the pathfinder's neighbour reads), `computeEdgeCost` 11.7%, `getIncomingEdges` 3.1% — roughly two thirds of every CPU second, and the only groups-phase caller is `runGroupMovement`. When a company re-decides its heading, every member runs `generateMovementCandidates`, which calls `findShortestPath` once **per location node in the world** — a full Dijkstra per destination, not one single-source run — and the bare `getNodesByType('location')` that list comes from has returned sublocations as well as settlements (about two to one) since THR-1183 landed on 08-22 — already inside the 08-24 baseline, so a standing 3× on the loop rather than one of the steps. The code already knows: the re-decision gate above the loop is commented *"deciding costs a full pathfinding sweep per member … that turns the company layer into the most expensive phase in the loop."* The gate throttles how often; nothing throttles how much. That is the 2.5-second tick — a re-decision tick with several companies deciding at once. The formation scan, for the record, is linear per location bucket and rolls a chance before scoring; it is not the driver.

`origin/ops:Docs/ops/tick-cost-trend.tsv`, one row per hourly `keep-work-flowing-cc` run (§3 measures, §6 publishes; the skill file is the single place the lane's behaviour lives — its scheduled prompt is a pointer to it, so "prompt + mirror" is one edit).

# THR-1412 — three dead debug levers, and one of them was a Law 33 violation

**2026-09-07 · UI · Bug · Repo Health**

Three developer-tooling defects the THR-1133 attended sweep hit while driving verification. Each cost a workaround; none is player-facing. What they share is that all three *reported success* while doing nothing — a tab strip that rendered every tab off-canvas, an existence check that reported every agent non-existent, and a documented gate-bypass that left the gate closed.

## What shipped

### 1. The tab strip wraps and scrolls instead of running off the panel

`TAB_BAR_STYLE` was a bare `display: flex` with no wrap and no overflow, inside ancestors that are `overflow: hidden`. Measured at 1920×1080 with 43 tabs: `clientWidth 479` against `scrollWidth 3751`, with **Tallies** at `x 5125` — 3,200px past the right edge. Everything from Marks onward could only be opened by a scripted `button.click()`, which is how the sweep had to drive it.

This is worth naming as more than a debug annoyance: content rendering outside its container with the overflow suppressed is a **Law 33** violation (*"nothing renders below the fold; panels scroll internally"*). The strip was failing the viewport contract on the designer surface, and the fix is the shape Law 33 actually prescribes — `flexWrap: 'wrap'` so nothing escapes, plus `maxHeight: TAB_BAR_MAX_HEIGHT` (112px) with `overflowY: 'auto'` so the wrap scrolls *internally* rather than eating the trace feed.

The cap is the whole reason wrapping alone was not the answer, and it is the original THR-1133 pass-7(a) concern: 43 tabs in a 480px panel wrap to roughly eight rows, which would have cost ~24% of the panel to navigation. Bounded-and-scrolling keeps both properties — every tab mouse-reachable, the feed still the bulk of the panel. `TAB_BAR_MAX_HEIGHT` is a named exported constant precisely so that trade is a number to change, not logic to rewrite (NFP #1).

`whiteSpace: 'nowrap'` on the tab buttons keeps multi-word labels (`Essence Sources`) wrapping as whole tabs rather than mid-label; `flexShrink: 0` on both the strip and the buttons stops the `flex: 1` scroll area below from squeezing either.

### 2. `fireAction` / `listActions` resolve agents through the shared resolver

Both hand-rolled a matcher reading `(n.properties.name ?? '')`. Actor display names live at the top-level `GraphNode.name`; actors carry no `properties.name` at all. So `fireAction('Kael Thornweaver', …)` and `listActions('Kael')` matched nothing — and since `listActions` is documented as *"doubles as an existence check"*, it reported **every** agent in the world as non-existent.

**The fix was to delete code, not write it.** `resolveDebugAgent` (`src/engine/debugAgentResolver.ts`) already existed, shipped by THR-1032 for exactly this class of defect, and its own header documents this exact failure — *"several matchers looked only in `properties.name` … partial-name matching silently matched nothing at all."* Two callers had simply never adopted it. Both now delegate, which also hands them three things they never had: the `@hero` / `@avatar` aliases, and a miss message that names how many actor nodes were searched, so *"no such agent"* stays distinguishable from *"this matcher is blind"* — the distinction whose absence made the original THR-1032 defect read as six wrong ids.

The `_actionStateRef` now carries the whole `state` slice, because the shared resolver needs `ascendantId` to honour `@hero`.

**The JSDoc gained the actor semantics the ticket asked for**, and it is a genuine trap: `fireAction(agentId, templateId)` fires with the **ascendant as actor** and the named agent as *target*, so a template op carrying `nodeId: '$actor'` — `grant_companion`, for one — lands on the ascendant, not on the agent you named. The sweep observed exactly this as `companion_joined bearerId asc.hunger.witness`.

### 3. Omniscience reaches the character sheet

Two independent faults, both real.

`useAgentInteraction` **never declared** `omniscienceMode`. GameView had been passing it since the flag existed; the hook's params interface had no such field and its body never read one, so the value went nowhere and both `getKnowledgeLevel` calls resolved from earned familiarity regardless. That is why a spawned NPC's sheet stayed at `stranger` with omniscience on. Both the info card and the full profile now resolve at `transparent` when the flag is set.

Separately, the toggle closed over `omniscienceMode` from the render that registered it, so two `toggleOmniscience()` calls inside one tick both read the pre-render value and both returned the same thing. A ref is now the synchronous source of truth — state updates do not land until React re-renders, but a debug lever has to report what it just did.

## What the ticket asked for and did not get

Nothing withheld. All three Done-whens are met. One deviation from the ticket's suggested fix, recorded deliberately: it proposed `flexWrap: 'wrap'` **or** `overflowX: 'auto'`, and the shipped answer is wrap *plus a bounded vertical scroll* — because either suggestion alone reintroduces the other half of the problem (a bare wrap eats the panel; a bare horizontal scroll leaves 43 tabs behind an awkward axis).

## The verification worth recording

**Every guard here was falsified, not merely written.** Reverting `flexWrap` reds the wrap test and nothing else; reverting the `'transparent'` routing reds the omniscience test and nothing else. The other ten stayed green under both reverts, which is the point — each guard bites on its own defect rather than the suite failing as a block.

**The name-matcher guard falsified itself by accident, usefully.** Its first draft asserted `not.toContain('properties.name')` over a 4,000-character slice and failed — on a *comment* explaining the defect. That is the whole hazard of source-level pins: the fix's own documentation is inside the region being searched. The pin now strips line comments and bounds the slice to the two matchers (registration → the `preparePlayerCast` call that follows), and asserts `resolveDebugAgent(` appears exactly twice rather than merely at least once.

**Tests run against a generated world, never a fixture** — for the reason `debugAgentResolver.test.ts` already gives: these are *node-shape* defects, and a fixture free to set both `name` and `properties.name` would have let the broken matcher pass. The suite asserts the premise directly (`agent.properties.name` is `undefined` on a generated actor) so a future shape change fails there, loudly, instead of quietly making the rest vacuous. It also asserts a **miss** for a name nobody has — without that, a matcher returning the first actor for any input would satisfy every positive case.

The omniscience suite carries a controlled arm confirming the agent under test is genuinely a `stranger` before the flag is applied. If worldgen ever hands back an already-transparent agent, the "on" assertion would pass for the wrong reason.

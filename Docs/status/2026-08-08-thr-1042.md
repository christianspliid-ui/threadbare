# THR-1042 — an authored ending overrides the prose, it does not erase the facts

**Shipped 2026-08-08.** Project: Encounter Experience. From the THR-1039 composition audit.

## What was wrong

`buildUnifiedEncounterStageModel.buildAftermath` had one line that decided what the player is told changed:

```ts
const displayChanges = authoredVariant?.changes ?? summary.changes;
```

Read it as a sentence: *if an author wrote an ending, show only what the author listed.* Every engine-derived change — a prize the reward pool actually rolled and granted, a capability that grew, a reputation that moved — was dropped on the floor the moment a template carried an `aftermathConfig`. The world changed and the ending did not say so, which is the exact silent-consequence defect the consequence verdict exists to judge.

The comment above it explained the intent honestly, and the intent was defensible when it was written: `summary.changes` "includes raw mechanical deltas … that we want to suppress in favor of curated content". The problem is that it suppressed the *facts* to get rid of the *presentation*. Those two had already been separated elsewhere — `engine/aftermathWords.ts` bands derived deltas into English, so by the time a change reaches this surface it reads "Vara's Gold grew a little", not `+0.34`. The suppression was solving a problem that no longer existed, at the cost of the one thing the aftermath is for.

It was also a hard blocker on re-adopting `rewardPool` in new-era encounters: any authored aftermath would have hidden the rolled reward, so the two features were mutually exclusive by construction.

## The thing worth knowing before changing this

The engine had already done the merge. `unifiedActionResolution.ts:2418` assembles the summary as:

```ts
changes: aftermathVariant ? [...changes, ...aftermathVariant.changes] : changes
```

So `summary.changes` is *already* `[derived, authored]` — the facts and the curation, together, from the moment the action resolved. The surface was not missing data; it was re-resolving the authored variant itself and throwing away the half it did not ask for. That reframes the fix from "go and fetch the derived changes" to "stop discarding them", which is a much smaller and safer change.

The two sides also resolve the authored variant through the *same* shared function (`resolveAftermathVariant`, THR-969), so there is no risk of the surface disagreeing with the engine about which variant or which band an encounter ended on.

## What shipped

`mergeAftermathChanges` replaces the `??`. Authored changes lead, engine-derived facts follow beneath them. Three properties, each there for a reason:

- **Identical ids collapse**, so the engine's own merge is not double-counted — and a summary that never went through it (an old save, a non-engine path) still *gains* the authored half rather than losing it. The merge is correct from either starting shape.
- **A derived change is suppressed only when an authored change declares the same `concepts`** — the THR-1004 structured refs, never English prose-matching. Two sentences can state one fact in different words, and substring matching would both miss those and collide on unrelated changes sharing a phrase.
- **Authored changes normally carry no `concepts` at all** (the type documents this: authored prose links through the narrative linker instead). So the de-duplication fires rarely, and that is the design, not a gap: stating a fact twice is recoverable, hiding it is the defect being fixed (NFP #4).

## Verification

**Falsified before trusted.** With the merge reverted to the old `??` line and everything else unchanged, 2 of the 4 new tests fail — precisely the two asserting the derived prize survives. The other two pass pre-fix trivially, because pre-fix the authored set was all there was; they guard the merge's own correctness (no double-count, concept de-dup) rather than the defect.

**Browser pass**, `?view=game&seeded&size=medium&spawn=enc.letters_of_introduction` at 1920×1080 — the one shipped template carrying both an `aftermathConfig` and a rolling `rewardPool`. The resolved aftermath model now holds **9 consequence chips where the pre-fix build showed 4**:

On screen the four recovered chips read *"Vara's Gold grew a little."*, *"Vara's reputation for Gold deepened again."*, *"Vara's Gold grew sharply."*, *"Vara's reputation for Gold deepened further."* — magnitudes in words, the concept word carrying its tooltip and link. That is the fix doing exactly what the ticket asked and nothing else.

One honest caveat on the capture: the `?outcome=success` pin reported `unauthored_band` — `enc.letters_of_introduction` authors no `byOutcome` bands, so the base ending was on screen. That is orthogonal to this fix, which is about the change set rather than the band, and the `aftermathConfig` path was genuinely exercised: all four authored chips resolved from the formal-channel branch variant.

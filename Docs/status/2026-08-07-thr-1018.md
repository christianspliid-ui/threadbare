**The detector shipped without the repair, so every closeout merge paid a session to re-derive the same two-way classification by hand (THR-1018, 2026-08-07).** `Docs/impediments.md` is `merge=union` (THR-691), which keeps both sides of a conflicting hunk — right for the rows, wrong for the row *number*, because two lanes appending on the same day each pick "the next free number" independently. THR-881 shipped the gate that rejects the result; what did not exist was the fix. Measured on the 2026-08-07 run that resolved three stuck PRs: `#451` was the same impediment logged on both sides (dedupe) and `#452` was two different impediments sharing an id (renumber) — two collisions in one run, two different remedies, and the gate names the duplicate without saying which case it is. `check:impediment-ids -- --fix` now classifies and applies both. **The classifier is deliberately asymmetric, and that is the whole design.** The two mistakes are not equal: calling a renumber a dedupe *deletes a distinct impediment*, while calling a dedupe a renumber leaves a visible duplicate row under a fresh number. So renumber is the default and dedupe requires strong evidence. The threshold was set from measurement, not taste — similarity across the real shapes reads 1.000 (identical text, a count bump), 0.882 (a bump whose edit appended a dated tag), 0.333 (the same subject in fully independent prose), 0.053 (two different impediments). Only the top band is reliably separable: at 0.333 "the same impediment written twice" is not far enough from "two different impediments", since two entries in one category share plenty of jargon. **So the classifier declines that band on purpose** — such a pair is renumbered, leaving two rows a later reader can merge, rather than one row where an impediment used to be. **The ticket's one specification error was corrected with evidence.** It prescribed "sum the occurrence counts", which is right for two independent observations and wrong for the count-bump shape that produces most case-1 collisions: rows at counts 1 and 2 are one tally before and after an increment, so summing to 3 double-counts. The fix keys that branch on the **Count column itself** rather than on prose similarity — an increment necessarily leaves the counts *different*, two independent appends necessarily leave them *equal* — so the branch that can inflate a tally rests on a hard signal instead of a heuristic. **Which row keeps the number is decided by publication, not file order — the gate's own printed advice was wrong here.** `check:impediment-ids` has always said *"keep the number on the row that appears FIRST in the file"*, and after a union merge that is a merge-order artifact with no meaning. The rule that carries meaning is publication: a row already on `origin/main` is out in the world and may be cited, while a row existing only on this branch has never appeared anywhere else, so moving it costs nothing. Impediment #460 records applying the printed advice on PR #1327 and having to reverse it, and notes the gate goes green either way so nothing catches the wrong direction — which is exactly why automating it unexamined would have been worse than the manual pass it replaces. The repair reads the log as of `origin/main` and keeps the number on a published row, falling back to file order only when publication cannot be determined and **saying so** in the output. Its rule 2 is explicitly *not* solved: two concurrent branches each repairing in isolation still allocate the same next-free id, because neither can see the other's unmerged rows, and the run says that rather than implying the class is closed. **Cross-references are reported, never rewritten** (Done-when 3): a renumber keeps the original number on the row that appears first, so every `#N` still resolves, but whether a given citation *meant* the row that moved is a question about authorial intent, not a mechanical fact. The run lists each one by path and line and leaves the call to the operator. Proven end to end on a real two-branch union merge in a throwaway clone carrying the live 470-row log: both lanes append to the same tail hunk, union keeps all four rows, the gate fails with `#470` and `#471` both doubled, `--fix` dedupes one at `similarity 1.00` (count → max 2) and renumbers the other at `similarity 0.25` (`#471 → #472`, stamped with its old id), and the gate then reports `OK — 472 table rows + 97 paragraph entries, every # unique`. Direction 1 of the ticket's three, extended with direction 2's reporting half; direction 3 (append-time id allocation) was not taken because it is prevention rather than repair and does nothing for the 470 existing rows.

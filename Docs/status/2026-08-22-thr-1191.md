# THR-1191 — the wiki-freshness gate stops failing PRs for `main`'s own commits

**Shipped 2026-08-22.** `check:wiki-freshness:blocking` computed a PR's "changed set" with a two-dot `git diff origin/main`, which is symmetric: every file `main` touched since the branch point counted as the PR's. A branch that never went near a wiki source could therefore fail the required check on somebody else's merge.

## What was wrong, measured

`collectChangedFiles()` ran `git diff --name-only origin/main --`. Two-dot diff compares the *tip* of `origin/main` against the working tree, so it reports changes in both directions — the branch's own, and `main`'s.

On 2026-08-16 that failed PR #1504 (THR-1139) over `src/types/unifiedAction.ts`, a file the PR's own three-dot diff does not contain: THR-1141 merged into `main` *during* #1504's CI run. The PR sat **172 minutes** armed-but-red holding a completed UI ticket. The same session hit the identical mechanism a second time from a different `main` commit, and the repair push for #1504 was itself re-staled by a third merge landing inside its own ~15-minute CI window.

It is a genuine race and it is self-renewing on an hourly lane. It is also structural rather than occasional: since strict mode was dropped (THR-983, 2026-08-02) a branch no longer has to be up to date with `main` to merge, so sitting behind is the normal state, not an anomaly.

## The fix, and why it is not the syntax the ticket named

The diff base is now the **merge base** of `origin/main` and `HEAD`, resolved through a new `resolveDiffBase()`. The base *ref* is unchanged and still fetched.

The ticket proposed `git diff --name-only origin/main...HEAD`. That is the right *semantics* and the wrong *command* here, for a reason the ticket could not have known without reading the collector: the changed set deliberately counts **uncommitted and untracked** work. `git diff A...B` compares two commits and would have silently dropped the working tree — precisely what the local pre-commit path (CLAUDE.md step 3c) runs this gate to inspect. An explicit `git merge-base` gives three-dot's commit range while keeping working-tree semantics, so the local and CI behaviours stay the same shape.

When `merge-base` yields nothing — unrelated histories, some shallow clones — it falls back to the base ref, i.e. the old behaviour. That direction errs toward flagging too much (a false FAIL a human can read and waive) rather than too little (a false PASS that ships a stale page silently).

## The header rationale, which was the actual trap

The script's own header rejected three-dot as a *"deliberate non-fix"*. That was **correct, for one direction, and became the reason nobody fixed the other.** The two are now named separately and neither can be read as covering the other:

- **Stale base** (THR-819): `origin/main` trails its remote, the diff is too **wide**, and the gate false-**PASSes**. Fixed by the fetch. Three-dot genuinely does not help — it recomputes the merge base from the same stale ref.
- **Advanced base** (THR-1191): `origin/main` is perfectly fresh and has moved **ahead** of the branch point, the diff picks up commits the branch never made, and the gate false-**FAILs**. The fetch cannot help; it is what supplies the newer tip.

A rejected-approach note that names only the direction it was written for reads as a blanket prohibition. This one cost the fix roughly six days between the first measured collision and the ticket being filed.

## Evidence the tests are not vacuous

The collector is exercised against **real throwaway git repos**, not a mocked runner: the defect is a property of git's own range semantics, so a fake runner would only re-assert the fixture's opinion of what git does.

The suite carries a **control arm** that asserts the *buggy* two-dot behaviour on the same fixture — without it, the passing test could be explained by a fixture that never actually advanced `base`. **Falsified:** reverting `resolveDiffBase` to return the base ref turns 3 of the 7 new tests red while the control arm and the still-must-fail arm stay green, which is corroboration that the arms are independent rather than three views of one check.

Both Done-when directions are proven end-to-end: the gate passes on a branch behind a `main` commit touching a wiki source it never touched, and a source the branch *does* touch still composes into `computeStaleWarnings` as a blocking `is stale` warning.

## The test-performance finding, which was mine to fix

The first full-suite run went red on the new file with a 5s timeout — 8.5s under contention against 0.4s alone. The second run went green there and red on `impediment-id-allocation.test.ts` instead, with the identical timeout shape; that file passes in 532ms in isolation.

That is not two flakes. Both are git-shelling tests, and **process spawn is the contended resource** once the suite runs 1048 files. Building a fresh repo per test (~11 git spawns each, ×5) was enough extra pressure to starve a sibling. Read as a flake it would have been "rerun and ship"; it was my change's cost, so the fix is mine: the read-only assertions share one fixture, and only the two tests that actually mutate a repo pay for their own. File time 2629ms → 1613ms, and the sibling stopped timing out. The git fixtures also carry an explicit `GIT_FIXTURE_TIMEOUT_MS`, because budgeting the real cost beats shipping a test that goes red on machine load.

## Scope honestly stated

No wiki page or interface contract declares `scripts/check-wiki-freshness.ts` as a source, so neither owed an update. Non-UI, non-engine: no browser-verify, no CLI smoke.

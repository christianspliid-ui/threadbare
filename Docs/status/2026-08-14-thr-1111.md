### THR-1111 — the node_modules wiper, named by its shape rather than by its culprit (2026-08-14)

19 occurrences in a week, and the two prime suspects are both **excluded by their own logs**. The reaper log at `C:/Users/chris/Dev/Projects/clean-stale-git.log` carries 478 hourly runs; 53 printed `HOME-TREE node_modules DAMAGED`. Reading the healthy→damaged transitions gives **six wipe windows**, and in **five of six the damaged run *and* the run before it removed nothing at all** — every worktree logged `skipped (live session)`. THR-753's junction guard is live and working (40 severs, 0 refusals), so the 2026-07-22 junction-follow class really is closed. Autosync is excluded too: it only fast-forwards, its one `Remove-Item` is THR-937's single-file collision fix with no `-Recurse`, and in the 08-14 window the damage was already present at 04:40, *before* that hour's 04:50 sync.

**What the damage actually is, which turns out to matter more than who did it.** Every DAMAGED line reads `.bin has no esbuild (entries: 0)` — `node_modules/.bin` empty **while the packages survive**. That is not a directory deletion; a deletion takes the packages too. It is the signature of an npm install that stripped the bin shims and never re-linked them. So the probe classifies by *shape* — `healthy` / `shim-stripped` / `stub` / `absent` — because the shape is observable from any session and is what decides whether the tree is usable, whereas the culprit is not observable from inside the session at all.

**The finding that actually pays is mean-time-to-repair, not the wipe.** The damage streaks run 12, 16 and **18 consecutive hourly runs**. A ~4-minute problem becomes an 18-hour outage because the reaper deliberately never auto-installs and nothing else looks. That is exactly impediments #501/#502/#503/#506, where both the worktree *and* the donor were dead and plain `npm install` was the only path, four times in one day.

**The instrument closes a gap CLAUDE.md already warned about.** The precheck's `test:` line shells out to `npm test` and **passes green against a stub** — the file says so — so until now nothing in the precheck answered the question it warns about. New `nm=` field, 0.03 s, probing this tree *and* the home-tree donor it junctions to, resolved from git's common dir rather than guessed:

```
fingerprint rg=no git=no test=1.15s cu=unknown nm=session:healthy/donor:healthy freshness=current
```

A degraded verdict also prints a loud `!!!!!` line naming the tree and the repair, because this is the one precheck finding that invalidates the run's later gates rather than merely colouring them.

**Falsified against real damaged trees, not only fixtures.** The first falsification harness was itself broken — `$SP` never reached the node process, so all four shapes returned `absent` for the wrong reason and *looked* like a passing probe. Re-run correctly, the probe separates all four on real on-disk trees. `unknown` deliberately does **not** count as degraded: an unreadable probe is not evidence of damage, and a false alarm costs a needless ~4-minute reinstall.

**Containment shipped is the operator half, deliberately not the automated half.** `npm run check:node-modules [--json] [--repair] [--strict]` collapses the multi-step junction runbook to one command, and the precheck makes the misdiagnosis detour unnecessary. Auto-repair from an hourly lane is **not** wired, and that is a judgment, not an omission: the diagnosed damage shape *is* an interrupted/racing npm install, so a lane firing `npm install` into a tree a live session is using is a plausible **cause** of the very class it would be repairing. Filed as [THR-1115](https://linear.app/threadbare/issue/THR-1115) with the race hazard named and the liveness guard it needs.

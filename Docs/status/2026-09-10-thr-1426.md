# THR-1426 — tick timestamps and per-tick rates get their readings

**2026-09-10 · UI · Game Design · Deferral · Encounter Experience**

The third and last of the Law 13/14 tick sweeps. THR-1423 fixed *remaining* terms, THR-1425 fixed *elapsed and duration* spans, and both deliberately stepped over two shapes that the readings they shipped could not answer: an **absolute tick timestamp** (`t42`, `Tick 42`, `on tick 42`) and a **per-tick rate** (`regen 1.5/tick`, `2/order …/tick`). Neither is a span, so `durationLabel` and `elapsedLabel` — which both answer *"how long?"* — do not convert them as they stand. That is why this was filed as a ruling rather than a swap.

Both rulings were recorded by an attended design session on 2026-09-10 and presented to Christian as decided with a veto invited. **This run implemented them; it did not re-decide them.**

## Shape 1 — timestamps: convert where the row needs ordering, drop where it does not

Dating a timestamp needs a calendar. The game looks like it has one — the top bar reads `{season} · year {year}` — and **it does not**, which this run established rather than assumed: `TemporalEngine.tick()` derives the season from `TICKS_PER_SEASON = 90` and writes a `clock.year` of 360 ticks, while `useSimulation.ts:199` independently computes `year = Math.floor(tick / 120) + 1` and never reads `clock.year` at all. The two disagree threefold and diverge without bound. A season/year pair that disagrees with itself cannot place one chronicle row against the row above it, so the ruling's premise held for a sharper reason than the ticket knew. That defect is **not** fixed here — it is a wrong-number bug, not a reading question — and is filed as [THR-1452](https://linear.app/threadbare/issue/THR-1452) with its evidence and coordination block.

What is left is that nearly every timestamp on a player surface sits in a list already ordered newest-first, where the index was only ever standing in for *how long ago*. So:

- **Converted to `elapsedLabel`** — `ChronicleEntryCard`, `AgentDetailPanel`'s interaction rows, `RecentActivityLog`, `ChronicleTab` (three sites), `OmenDetail`, `EntityCard`'s timeline block, `HexChronicle`'s survey caption, and `MandateDetail`'s checkpoint-evaluation and stage-completion rows.
- **Dropped** — `MandateDetail`'s `Assigned: Tick N` row (when a mandate was handed down is not something a player acts on; its live term is already on the `Time Limit` row), `WorldPulse`'s `Tick` row, and **both** clock readouts in `SimulationControls` (the compact tier's `tick N ·` prefix and the full panel's header counter, plus a tooltip that named the tick while labelling a play/pause button).

## Shape 2 — rates: the ThreadsPanel treatment generalises; the top-bar regen is dropped

THR-1008 settled this shape once, on the ThreadsPanel sustain row — `−12 per tick · +5 per tick` became banded words behind `⤓`/`⤒`. That generalises: `HexChronicle`'s control-effect cost and income now read through the same `SUSTAIN_FLOW_BANDS` ladder and keep the direction glyphs.

The new reading is `sustainFlowSpheres`, and it lives **beside** `sustainFlowWord` in `src/data/sustained-control-status-prose.ts` rather than in the component. These rows show *which* sphere a hold drains, which is the part the player acts on, so the reading is per-sphere — and banding each entry at the surface would have put a second copy of the flow ladder in a component, the drift UI Law 3 exists to prevent. It returns `null` for an empty map so the caller owns the empty phrasing: a cost of nothing and an income of nothing want different sentences.

The clarification worth recording is the **edge of Law 13's persistent-chrome exception**. It was ratified 2026-08-06 (THR-890) for the essence counter — a *balance* that forty pips could not render. A *rate* is not a balance: `regen 1.5/tick` names the engine's unit (Law 14) and is derivable by watching the pool move. So the attention indicator's regen figure is dropped from both the top bar and its tooltip, while the pool balance beside it keeps its figures under the exception.

## The membership was wider than the ticket's list, and that was the expected failure

The ticket named eight sites; the predicate held **eighteen**. THR-1423's lesson — *the grep is a filter, strictly narrower than the membership* — restated by THR-1425 and restated again here. Line numbers had also drifted, because all three prior tick/percentage tickets landed in this file set since it was written, so the sweep was re-run from the predicate rather than trusted from the ticket. `ChronicleTab`, `RecentActivityLog`, `OmenDetail`, `EntityCard`, `SimulationControls` and a third `MandateDetail` row were all found that way. Fixing `t{entry.tick}` in `ChronicleEntryCard` while leaving the identical `t{entry.tick}` in `ChronicleTab` would have left the game disagreeing with itself.

**Deliberately outside membership:** `EventLog`, `NarrativeFeed` and `EssencePanel` still render tick shapes and are **unmounted** — `EventLog` has zero references anywhere, `NarrativeFeed` only tests and the IA manifest, and `EssencePanel` is imported by `GameView` but never rendered (superseded by `AscendantBar`, THR-184). A component that renders to no player is not a player-facing surface, so this is a dead-code question, not a Law 13 one; it is recorded in `laws.md` so the next sweep does not rediscover it as a leak. Per the process-work throttle it is a log line, not a ticket.

## A pre-existing type defect fixed rather than worked around

`CheckpointRow`'s `result` prop was typed `MandateState['checkpointResults'] extends Array<infer T> ? T | undefined : undefined`. `checkpointResults` is optional, so the type under test is `Array<…> | undefined`, which does **not** extend `Array<infer T>` — the conditional always took its false branch and resolved to `undefined`, making every field access on `result` an error against `never`. Adding a second `evaluatedTick` read surfaced it as a ratchet `+1`. The honest fix was the `NonNullable` unwrap the original was reaching for, which also cleared the pre-existing `passed` / `exceeded` / `observedPrimaryDelta` errors the row was already carrying. **Ratchet 2912 → 2905, down 7**; baseline refreshed and committed, per THR-976 as the last action before push.

## One guard caught passing for the wrong reason

The `MandateDetail` arm asserted `container.textContent` — and `Modal` renders through `createPortal`, so RTL's container is **empty** and the assertion passed against a modal it had never looked at. It did not go red when the dropped row was restored, which is the only reason it was caught: **every arm in this change was falsified by reverting its call site**, not merely watched going green. It now reads `document.body` and carries a positive control (`Node Dominance`, `Details`) so an empty surface cannot satisfy it again. This is the same `createPortal` trap THR-1424 hit yesterday on three surfaces — twice in two days is a pattern worth naming, and it is logged as an impediment.

The second trap avoided by construction: `elapsedLabel` renders `less than a day` both for a genuinely recent row **and** for a component never handed a `currentTick`. An arm resting on the floor would pass against wiring that was never done, so every fixture drives a deliberate multi-day span and the guard file pins the separation before relying on it.

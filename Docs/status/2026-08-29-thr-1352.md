# THR-1352 — the budget that was sized once and never re-measured

**Shipped 2026-08-29.** Test-infrastructure calibration. Engine, Content and UI all N/A —
no runtime file is touched; the diff is two constants and the comments that justify them.
Filed and executed inside one `tb-opus-pickup` run under the Rule 0 *"loss actively
corrupting work right now"* exception to the process-work throttle.

## The symptom looked like two broken branches; it was one stale number

Two armed PRs sat red on the required `Test · Typecheck · Build` check — [#1714](https://github.com/christianspliid-ui/threadbare/pull/1714)
(THR-1322, 526 min) and [#1717](https://github.com/christianspliid-ui/threadbare/pull/1717)
(THR-1344, 342 min). They come from unrelated branches touching disjoint files, and both
failed on the *same single test*:

```
FAIL src/engine/__tests__/debugTickBatch.test.ts > runTickBatch
     > clamps a request above DEBUG_TICK_MAX instead of rejecting it
Error: Test timed out in 180000ms.
Test Files  1 failed | 1135 passed (1136)
Tests       1 failed | 18993 passed (18994)
```

One test failing identically from two unrelated diffs is not two branch defects. It is a
shared one, and the failure mode names itself: a **timeout**, not an assertion.

## `main` reading green was a false comfort

The obvious check — is `main` healthy? — returned `success` on every recent run. It was
not evidence. Every merge commit from 2026-08-28T23:16Z through 2026-08-29T06:14Z
**skipped** the `Test · Typecheck · Build` job, its docs-only diff filter having found no
code:

```
33234732211  9d36b9a7  skipped   33232072058  ee2bad8b  skipped
33229350374  6f7fa560  skipped   33223939416  dd1a260d  skipped
```

So the suite had not actually run on `main` in that window at all. The signal that would
have exposed the drift was structurally absent, which is why the drift got to accumulate
in silence. A green tick that skipped the job is not a green suite.

## The measurement

Both heavy end-to-end tests build real worlds and run real ticks behind a hand-set 180s
budget, each justified in a comment against a standalone cost. Measured standalone on
`origin/main` (a0e52b8d), 2026-08-29:

| Test | Comment claims | Measured | Budget | Margin |
|---|---|---|---|---|
| `debugTickBatch` → `clamps a request above DEBUG_TICK_MAX` | ~18s | **44.9s** | 180s | 4.0x |
| `lairClearing` → `WORLD_BUILD_TIMEOUT_MS` | ~15s | **45.7s** | 180s | 3.9x |

Both **pass** locally (`7 passed` / `6 passed`). Nothing regressed. The engine simply grew
real per-tick work underneath two budgets that were set once and never revisited.

The `debugTickBatch` budget was *designed* at a 10x margin — its own comment records being
raised 60s → 180s after PR #830 blew the 60s outright, sized so "a genuinely unbounded loop
still fails without making the required check flaky under load." At 45s that margin is 4x.
On a branch adding engine work it is worse: impediment #940 measured the same test at
**90.8s** on #1717's branch, because THR-1344 *activates a genome pass that was previously
dead* — legitimate new work, correctly costed. A 2x margin on a runner executing 1136 test
files in parallel is not a margin.

So the sequence is: two defensible engine fixes each nudged an already-marginal test past a
budget nobody had re-measured, and the gate converted that into ~14.5 h of stalled delivery
across two finished implementations.

## Fixed as calibration, because that is what it is

420s for both, restoring roughly the original 10x-class headroom over the worst measured
case (90.8s) while keeping the guard rail sharp — an unbounded loop runs 10,000 ticks, 50x
the capped work and well over 2000s, so it still fails here. The `debugTickBatch` literal
also becomes a named constant, `CAPPED_BATCH_TIMEOUT_MS`, per NFP #1.

`lairClearing` carried the identical stale 180s budget against the identical ~3x drift and
was one engine fix away from the same outage. It is recalibrated on the same evidence
rather than left to fail next — the whole failure mode here is a budget waiting to be
outgrown in silence.

**Not in scope:** making the tests faster. NFP #7 is profile-before-optimising, and there
is no profiling evidence of a regression — 200 real ticks plus seven worldgens is
inherently heavy, and both tests measure within a second of each other, which is what
shared world-build cost looks like rather than a defect in either.

## What was actually changed to stop the recurrence

The numbers matter less than the reason they went stale: each comment justified a budget
against a figure with no date and no instruction to re-take it, so re-measuring was nobody's
job. Both comments now carry their measured figure **with the date it was taken** and say
to re-measure before changing it. That is the part intended to outlive this ticket.

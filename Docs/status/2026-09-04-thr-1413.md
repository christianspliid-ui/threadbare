# THR-1413 — a companion can be minted from either surface, and a god's companion is no longer invisible

**Date:** 2026-09-04 · **Pillars:** Engine + UI · **Labels:** UI, Engine, Improvement

## What was wrong

The THR-1133 attended sweep asked for a capture of the companions row (THR-1096) and found there was no way to produce one. Two separate gaps:

1. **No mint route.** The sweep tried `window.__DEBUG.spawnAttachment('Kael Thornweaver', 'companion.wayfarer')` and got *"No attachment template matching"*. `resolveAttachmentTemplate` searches artifact and trait **nodes in the graph**; `COMPANION_TEMPLATES` are a data array that never becomes nodes. The CLI's `spawn attachment` shares the resolver, so both surfaces failed the same way. `mintCompanion` was reachable only from encounter aftermath and the `grant_companion` op — never deliberately.

2. **A companion on the ascendant had no surface at all.** `action.gold.hire-mercenaries` is the only shipped content carrying `grant_companion`, and its op names `nodeId: '$actor'`, which resolves to `action.actorId` — the ascendant on every player cast. `AscendantSheet.tsx` had zero companion references, so the minted person existed in the graph and appeared nowhere.

## Decision 2, recorded: render, do not refuse

The ticket offered a fork — render ascendant companions, or refuse `grant_companion` with an ascendant bearer. **Render.** The deciding fact is that the companion is not inert: `computeRawScore` walks `accompanies` edges on *any* node, and `phaseAscendantProgression` calls `computeCapability(graph, state.ascendantId, reach)` — so a companion granted to the ascendant **was already raising their reach capability and tier**, invisibly. Pinned by a test that asserts exactly this (`computeRawScore` before + contribution === after).

That makes refusal the destructive option: it would delete a capability term that already works and turn a castable action into a silent no-op. Rendering makes live state visible (Law 56 / Law 1). Additive over destructive, NFP #6.

## What shipped

**Engine — the mint route.** `spawnDebugCompanion` in `debugWorldSpawnTools.ts`, with its own `resolveCompanionTemplate` reading the data array (exact id → id prefix → profession substring, the same ladder as its attachment sibling). Wired to `window.__DEBUG.spawnCompanion`, the in-game CLI verb `spawn companion`, and the headless `npm run cli` verb of the same name — the CLI handler **delegates to the same engine function** rather than hand-rolling a clone-and-edge path the way `spawn attachment` does, so the two surfaces cannot drift. Repeat mints of one template on one bearer walk the tick forward, because `mintCompanion` treats a same-tick id collision as "already granted" and returns null; without that, a second call is a silent no-op.

**UI — the ascendant surface.** A Companions section on `AscendantSheet`, rendered only when one exists. Each row: personal name, profession, the authored `goodFor` sentence, and which Reaches the companion steadies.

**The Law 13 call.** `AttachmentsTab`'s `contributionLine` renders `+3 iron` — a raw magnitude and a raw internal reach key. Copying it onto the ascendant sheet would have spread a Law 13/14 violation to a second surface; banding the value instead would have meant inventing a ladder for the raw contribution scale, which **Law 15 makes a ruling, not an implementation choice**. So the new surface names the Reaches through `reachDisplayName` (`Steadies your Iron.`) and lets the authored `goodFor` line carry the "how much" as fiction. The exact term stays where Law 13 puts it — the trace and the designer view. The pre-existing violation on `AttachmentsTab` is filed as THR-1421 with its law numbers rather than fixed here.

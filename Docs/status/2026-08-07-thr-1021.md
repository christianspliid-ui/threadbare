**A 32-world fixture sweep was running on vitest's 5s default, and it red-checked three unrelated PRs in six hours (THR-1021, 2026-08-07).** `ascendantReachFixtures.test.ts` builds **8 reaches × 4 seeds = 32 full `initializeGameState` worlds inside a single `it()`**, against a ceiling nobody chose for it — the framework default, inherited silently. The file declares `node` and calls no `vi.mock`, so THR-940's partitioner routes it to the shared-worker pool (`isolate: false`), where allocation pressure on a 2-core runner stretches it ~7x: `tests 777ms` for the whole file in isolation on the dev box, against **5265ms / 5771ms / 5507ms** on CI. Every one of those is over 5000ms and none is *slow* — the ceiling simply sits below the runner's ordinary range, so the test fails at random on roughly every third PR. Measured the same day across three unrelated branches: run `31182582070` (`fix/thr-1015-contract-test-budgets`, 13:32Z), run `31192219428` (PR #1335, THR-1018, 15:28Z), run `31206694260` (PR #1338, THR-1019, 18:30Z) — no diff among them touching worldgen or the fixture harness. **The cost compounds because a timeout does not retry itself**: auto-merge stays armed and never fires, so the PR reads as shipped from every surface except the check rollup, and recovery depends on a session happening to look. That is the THR-1020 blind spot exactly, and it is why the 15:28Z occurrence surfaced only when THR-1020's own new probe caught it, and why the 18:30Z one sat ~40 minutes until this run's Step 0.8 sweep read the rollup on the way past. **The fix is a hang guard sized to the work, not isolation.** The two sweeps in the file (32 builds and 16) now carry `FIXTURE_SWEEP_TIMEOUT_MS = 60_000` — a named constant per NFP #1, commented with the measurement and with the reason it is not a performance budget: these tests assert that the builds *succeed*, never that they are fast, so the only thing a ceiling should catch here is a genuine hang. 60s leaves >10x headroom over the worst observed 5771ms, which matters because CI wall time varies ~2.2x on unchanged code — a ceiling set just above the observed maximum would buy one week and fail again. **Pinning was considered and rejected**: adding the file to `ISOLATED_PINS` would have worked, and `coastline-integration.test.ts` sits there for a near-identical reason ("a shared worker's added allocation pressure pushes over… the budget was already marginal on a 2-core runner"), but a pin surrenders THR-940's shared-pool economy for this file and grows by one the very list THR-949 exists to empty — a real cost paid to fix a problem that a number solves. The guard was **falsified before shipping**: set to `1`, exactly the two annotated sweeps fail with `Test timed out in 1ms` while the three unannotated tests still pass, proving the third argument is wired *and* correctly scoped rather than decorative.

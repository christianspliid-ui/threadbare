# THR-1311 — a dead term removed, and the deeper one it was hiding

**Shipped 2026-08-28.** Engine pillar. Content and UI N/A — `settlementReachProfile`
reaches no content table and no component; it has no consumer at all, which turned out
to be half the finding. Deferral filed at THR-1297 slice 6 closeout.

## What was wrong

`computeSettlementReaches` in `settlementGenome/runGenome.ts` carried two loops with
byte-identical bodies. The second summed faction `reachWeights` over **incoming
`member_of` edges on a location**, commented *"faction is a member of this
location/group"*.

`EDGE_SCHEMA.member_of` is `actor → actor` — *"Source = member, target =
faction-or-group"*. A location is never a legal target, so no conforming writer could
ever feed that loop. Re-measured before touching it, both seeds at tick 30:

```
seed 42:  731 locations, 0 location-targeted member_of edges
seed 99:  876 locations, 0 location-targeted member_of edges
```

## Why delete rather than repoint

The ticket offered both arms and asked that the fork not be collapsed silently.
Deletion was taken for a reason the ticket did not have, and which only surfaced from
building the test it asked for.

The repoint arm — move the read onto `controls`, the real faction-territory edge —
**would have changed nothing at all.** Repointing swaps which edges get walked, but
the loop body still reads `actor.properties.reachWeights`, and no faction node in any
world carries that key. The golden worldgen comparison the repoint arm called for
would have come back a **null diff**, which reads as "safe repoint" and is in fact
"still dead". That is the worst available outcome: a change that looks verified,
moves nothing, and leaves the term dead behind a green comparison.

Deletion also has the simpler argument on its own terms: the loop was a *duplicate* of
the `located_at` loop above it, not a second contribution. Nothing was lost when it
went.

## The finding underneath — filed, not fixed here

Writing the liveness assertion the Done-when asked for is what exposed it. The
assertion failed, and the reason is not the edge, it is the property:

```
factions in world                                             49
factions carrying `reachWeights`                               0
faction located_at edges into locations                       85 (seed 42) / 91 (seed 99)
locations drawing a non-zero faction reach                     0
```

`factionSeeding.ts:239` **consumes** `definition.reachWeights` to derive
`domainCapabilities` and `reachPreferences`, then writes a node property bag that
contains both derivations and not the source weights. So the surviving `located_at`
loop hits `if (!weights) continue` on every faction, and the whole function returns
`{}` for every settlement in every world.

That is a distinct defect from the one claimed here, it moves worldgen output on every
seed, and the right answer is genuinely open (wire it up, or delete the chain — the
field has no consumer). Filed as
[THR-1323](https://linear.app/threadbare/issue/THR-1323/faction-nodes-never-carry-reachweights-so-computesettlementreaches)
with the measurement, rather than expanded into a Low-priority ticket scoped to one
dead loop.

## Evidence

Two tests changed, and the direction of both is the point.

The old suite contained *"returns non-zero gold reach when merchant faction is present
via member_of"* — a test that **built the schema-illegal edge itself** and then
asserted the reader consumed it. It passed for the entire life of the dead term it was
covering. That is the fixture-invents-both-sides shape: a green test certifying a path
no conforming world can produce. It is now inverted to *"ignores a schema-illegal
member_of edge targeting a location"*, so it pins the deletion instead of the fiction.

**The guard was falsified before being trusted.** The deleted loop was temporarily
restored and the new assertion re-run; it failed as it must —
`expected [ 'gold', 'iron' ] to have a length of +0 but got 2` — then the arm was
removed and the tree re-verified clean. A guard nobody has watched fail is not a guard.

A new `describe` runs `initializeGameState` → `runTick` on a generated world, because
a hand-built graph structurally cannot answer the question this ticket is about —
whether anything still *produces* the shape being read. It carries a non-emptiness
guard on locations first (0 of 0 is not a pass), asserts the faction edges are live
and plentiful so the emptiness reads as a missing property rather than an empty graph,
and then pins the dead profile as an explicit **characterization test** naming
THR-1323 — so fixing that ticket turns this red and forces the assertion to be
inverted, rather than the repair landing silently.

# THR-1459 — the ending names the courier instead of quoting her key

**2026-09-12 · Encounter Experience · Content · UI**

Gate Duty's ending handed the player a raw `{cast:suspect_courier}` in two places — the *What Changed* consequence box ("The night will keep travelling") and the "The cargo tells a story." reaction card. Found by the THR-1133 attended screenshot sweep on `main` @ `089bc19b`.

## What was actually wrong

Not a missing binding, and not a broken enricher. `suspect_courier` is declared in the template's support bundle (`civic-guard-encounter-content.ts:459`), and `proseEnrichment.ts` guarantees both halves of the contract: a **declared** key always resolves (bound node's live name, else the spec's authored `spawnName`), and an **absent** cast block strips the token to nothing. Either path produces a name or a hole. Neither produces a literal `{cast:…}` on screen.

So a token reaching the player could only mean one thing: **that text never entered the enricher.**

`cg.quest.gate_duty` is the one template with a *bespoke* stage adapter. `GameView.tsx:1417` routes it to `buildGateDutyEncounterStageModel` rather than `buildUnifiedEncounterStageModel`, and the unified adapter is where `enrichProse` is applied to `change.detail` (`:646`) and `reaction.intent` (`:727`). The bespoke adapter never inherited that. It assigned both straight onto the model:

- `future_hook` / `shell_state` highlights took `detail: change.detail` raw;
- `rewriteGateDutyAftermathReactions` rewrites three reactions by id and **falls through** for every other, passing `label` and `intent` raw. The authored `gate_duty_note_cargo` takes that fall-through.

This is THR-923's defect on a third text path — the nudge adapter had the identical structural gap, fixed the identical way. The fix follows that precedent: gather the context once (`buildGateDutyEnricher`), thread it through both builders, enrich every authored string the adapter emits.

## Why the existing tests were green the whole time

`engine/__tests__/gateDutyCastProse.test.ts` already sweeps this template's authored aftermath fields — *including the two broken strings* — and asserts no raw token survives `enrichProse`. It was correct. It was testing the enricher, and the enricher was never the problem.

That is the reason the new adapter and render tests exist at those two levels rather than a third enricher test. A defect a **surface** introduces can only be caught by a test that builds that surface.

## Guards added

- **Adapter** (`encounter-stage/__tests__/buildGateDutyEncounterStageModel.test.ts`, 4 arms) — the real template, a real `WorldGraph`, an `activeAction` carrying `supportBindings`. Asserts the bound name in both faces and absence of `{cast:` across the whole composed model.
- **Render** (`Game/__tests__/encounterVeilGateDutyCastTokens.test.tsx`, 3 arms) — the real `EncounterVeil` over the real adapter's model. This file *is* the browser-verify evidence; see below.
- **Corpus** (`data/__tests__/aftermathCastTokenCorpus.test.ts`, 3 arms) — every registered template's authored aftermath strings (overview, change title/detail, reactionPrompt, reaction label/intent, **and** the `byOutcome` band overrides) must reference only cast keys their own `supportBundle` declares.

The corpus sweep deliberately walks the three registries rather than the five files the ticket's grep listed. A file list is a snapshot that rots the moment someone authors a sixth; the membership predicate does not (THR-688 rule A).

**Every one of these is a "no token survives" assertion, which a corpus with no tokens would satisfy for free.** So each suite carries an explicit anti-vacuity arm: the corpus test asserts a non-empty population spanning more than one template and containing Gate Duty by id *and* key; the adapter and render suites assert the authored input still carries the token before asserting the output does not. The render fixture *reads* the strings off the shipped content rather than quoting them, so content drift reddens the guard instead of silently passing beside it.

**Red baseline confirmed by reverting the three leak sites** with the enricher left in place: exactly the 3 new adapter arms fail, and the failure output reproduces the ticket's reported strings verbatim.

## Deferral filed

THR-1498 — with the token gone, the box now reads "Someone sent Nessa Vale…", and *that name is inert text*: no image, no tooltip, no link (Laws 1/17/21). Pre-existing, and a distinct surface from THR-1033, which fixed the same class on the **unified** path only — the bespoke adapter has no equivalent of `buildAftermathConsequences`'s `link`/`resolveAnchor` seam, so that fix landed beside this surface without covering it. Filed rather than fixed in passing, per the browser-verify contract.

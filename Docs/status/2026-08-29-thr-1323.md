# THR-1323 — the property the seeder derived from and threw away

**Shipped 2026-08-29.** Engine pillar. Content and UI N/A — `reachWeights` reaches no
content table and no component. Deferral filed at THR-1311's closeout, by the test that
ticket's Done-when asked for.

## What was wrong

`factionSeeding.ts` read `definition.reachWeights` to derive two things and then wrote
neither the weights nor a pointer to them:

```ts
const caps = deriveDomainCapabilities(definition.reachWeights, rng);
const reachPrefs = deriveReachPreferences(caps);
```

The node it wrote carried `domainCapabilities` and `reachPreferences` — both derivations —
and not the source. `computeSettlementReaches` sums `actor.properties.reachWeights` over
the factions a settlement holds via `located_at`, so its `if (!weights) continue` fired on
all 49 factions of a seeded world and the function returned `{}` for every settlement in
every world. The edges were never the problem: 85 faction `located_at` edges on seed 42.
The read has always had its edges and has never had its property.

The fix is one line — store the weights beside the derivations. `deriveDomainCapabilities`
takes an rng and is lossy, so the weights cannot be recovered from what was kept.

## The fork, and why the ticket's framing pointed the wrong way

The ticket offered deletion as the cheaper arm and asked that the choice be made rather
than assumed: *"the field has no consumer today, so delete the whole chain is a legitimate
answer."* That is true of the **field** and false of the **function**.

`grep settlementReachProfile` returns the producer, its type, and test fixtures — no
consumer, exactly as filed. But `computeSettlementReaches` has a second caller the grep
never touches: its return value drives **Pass 4 of the genome** (`runGenome.ts:148-168`),
which is the sole reader of `REACH_SUBLOCATION_MENU` — 8 reaches of authored, tier-gated
sublocations and NPC roles. Deleting the chain would have deleted that content table
alongside the dead field, on the strength of a grep for a field name.

How much content was one property away from existing, measured by re-running the genome on
a seeded world after the fix (seed 42 / medium / tick 3):

```
genome-tier settlements examined               38
  ...with a non-empty settlementReachProfile   19
reach-sourced sublocations produced           230
reach-sourced NPC roles produced              264
```

Wiring it up is also the additive direction (NFP #6) and the direction the systems-inventory
doctrine points: activate the dormant system, do not green-field or delete it.

## What this did and did not move

**Did:** the reader is live. Seed 42 / medium / tick 3 — locations returning a non-empty
reach profile went **0 → 27**. Holds across seeds: 17 on seed 99 small, 12 on seed 7 small.

**Did not:** worldgen output is byte-unchanged, and that is not luck. `worldSeed.ts` runs
the genome at :1198 and seeds definition factions at :1648, so at genome time no faction
node exists and the profile is still `{}` for every settlement being built. Measured after
the fix — sublocations materialized at worldgen by `genomeSourcePass`:

```
archetype=49  infrastructure=183  none=178  sphere=64      reach=0
```

Zero before, zero after. No rng stream is consumed by the added property, so determinism
(NFP #3) is untouched.

That ordering gap is a real defect and a separate one — closing it moves generated output on
every seed and wants a golden comparison plus volume tuning (Ardenmor Keep draws 18 reach
sublocations in one pass, and `NPC_BUDGET` caps NPCs while nothing caps sublocations). Filed
as [THR-1344](https://linear.app/threadbare/issue/THR-1344/the-genomes-reach-pass-is-dead-at-worldgen-worldseed-runs-the-genome)
with the measurement and three arms, rather than smuggled into a Low-priority ticket scoped
to one missing property.

A second finding surfaced in the newly-visible profiles: two faction definitions declare
`flesh` and `force`, which are not `ReachDomain`s. Inert today — Pass 4's `if (!menu)
continue` drops them fail-soft — but they skew the profile's max-normalization, and the more
interesting half is why the typechecker did not reject them. Filed as
[THR-1345](https://linear.app/threadbare/issue/THR-1345/two-faction-definitions-declare-reach-keys-that-are-not-reachdomains).

## Evidence

THR-1311 left a characterization test asserting the defect on purpose, so that fixing this
ticket would turn it red rather than let the repair land silently. It did. It is now
inverted to a liveness assertion and stays on the generated world.

**The guard was falsified before being trusted.** The one-line fix was temporarily removed
and the new assertion re-run; it failed as it must —
`AssertionError: expected 0 to be greater than 0` — then the arm was reverted and the tree
re-verified clean. That matters more than usual here: five fixture tests in the same file
assert this exact function and **every one of them passed for the entire life of the
defect**, because each hands the reader a `reachWeights` bag the real seeder never wrote.
A test that supplies the missing property is structurally incapable of noticing it is
missing.

The ordering gap is pinned the same way THR-1311 pinned this one — a characterization test
naming THR-1344, asserting on **materialized nodes** (`genomeSourcePass === 'reach'`) rather
than on a return value, because calling `runSettlementGenome` by hand post-seeding is
precisely the condition worldgen does not meet.

The mutex on THR-1311 (both edit `runGenome.ts` and `settlementGenome-vitality.test.ts`) was
reversed on its stated reason: THR-1311 merged as `c8cedbad` via PR #1692, and no open PR
touches either file (THR-688 rule B).

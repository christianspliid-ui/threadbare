# THR-1192 — the freshness gate stops being stricter than the commit it guards

**Shipped 2026-08-22** · `scripts/check-generated-freshness.ts` · [THR-1192](https://linear.app/threadbare/issue/THR-1192)

`check:generated-freshness` byte-compared the working tree against the committed
blob. The commit it guards does not: `.gitattributes` pins these paths to `eol=lf`,
so git erases CRLF at `git add` and the committed copy is already correct. A Windows
text-mode write — Python's `open(p, "w")` — therefore produced a working copy that
`git status`, `git diff` and even `git diff --ignore-cr-at-eol` all called clean,
while this gate failed forever.

Worse than failing: it failed *prescribing the generator*, the one action that cannot
help, since re-running `npm run prebuild` rewrites the same CRLF. Four impediments in
one week (#630, #662, #671, #689) burned 10–15 minutes each on that dead end, always
at closeout with every other gate green, and **CI could never reproduce it** — a Linux
checkout writes LF, so the failure is Windows-local and cannot be diagnosed by pushing.

## What changed

A CRLF-only difference is now its own verdict, `eol-only`, and it does not fail the
gate. It is still *reported*, because CRLF on disk remains a local hazard worth
naming — impediment #677 had it silently defeat a source-parsing gate whose regex
excluded `\r` — and because the repair is a binary rewrite, not `git checkout --`,
which no-ops on a file git considers unmodified. The warning names line endings and
prints that rewrite, instead of the generator advice that is actively misleading here.

The verdict line now reads `OK — N artifact(s) match HEAD, 1 line-ending-only
difference(s) ignored`, mirroring the existing volatile-only note.

## Two decisions worth recording

**Report rather than fail.** The Done-when allowed either. Failing would have replaced
one blocking dead end with another, and there is genuinely nothing to fix before
merging — the blob is right. A gate stricter than the commit it guards is the defect,
so the honest verdict is "pass, and here is a thing about your working tree".

**The comparison became a pure function.** `classifyContent(fresh, committed, volatileKeys)`
returns `identical | volatile-only | eol-only | stale`; `compareArtifact` is a thin
wrapper resolving keys by path. This is not decoration — the loop's inputs are
unreachable to a live test, because `main()` runs `npm run prebuild` *before* reading
disk, so any CRLF or staleness injected into an artifact is overwritten by the
generator before the comparison happens. Extracting the decision is what makes the
three Done-whens testable at all. `VOLATILE_JSON_KEYS` is empty by design (THR-714),
so routing keys through a parameter is also the only way the volatile branch can be
exercised without re-registering volatility the repo deliberately removed.

The module also gained an entry guard, so importing it from a test no longer shells
out to `prebuild`. Nothing bundles this file, so the argv comparison is sufficient —
unlike `build-authoring-brief.ts`, where `esbuild --bundle` defeats it (THR-686).

## Falsified, not merely green

Deleting the `eol-only` branch turns exactly the 4 line-ending assertions red and
leaves the other 10 green. The suite carries the arm that matters most: a CRLF copy
whose content **also** changed must stay `stale`. Had the new branch keyed on the
*presence* of CRLF rather than on comparing normalized content, that case would leak a
genuinely stale artifact past the gate — and every other assertion would still pass.

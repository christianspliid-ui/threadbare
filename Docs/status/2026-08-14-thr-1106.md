# THR-1106 — ActionCard's shake timer clears on unmount

**Date:** 2026-08-14 · **Lane:** `tb-opus-pickup` · **Worktree:** `serene-easley-8a22ad` · **Issue:** [THR-1106](https://linear.app/threadbare/issue/THR-1106)

## What shipped

`src/components/Game/ActionCard.tsx` now clears its shake timer in an unmount cleanup. The timer was armed on a click of an unavailable card and cleared **only on the re-entry path** — a subsequent click — so a card that went away inside the 400 ms window left it armed, and the callback then ran `setShaking` on a torn-down component.

Three changes, all additive:

- `useEffect` added to the existing `react` import.
- The inline `400` hoisted to `SHAKE_DURATION_MS` with a comment tying it to the `anim-shake-no` keyframe (NFP #1 — the timer, not the animation's end event, is what clears the class).
- The cleanup effect itself, matching `src/components/shared/Tooltip.tsx:330`, which is the in-repo reference implementation of exactly this pattern.

## The test is falsified, not merely green

The Done-when asked for a test that the timer does not fire after unmount. A "does not throw" assertion would pass vacuously, so the test instead asserts the timer count directly, and guards its own premise:

1. click an unavailable card, then assert `anim-shake-no` is on the element **and** `vi.getTimerCount() === 1` — if the click failed to arm anything, this fails rather than letting the next assertion hold for the wrong reason;
2. `unmount()`;
3. assert `vi.getTimerCount() === 0`, then advance 1 s and assert no throw.

Falsification was run rather than assumed: with the cleanup commented out the new test fails `AssertionError: expected 1 to be +0` at the post-unmount count, with the other 39 ActionCard tests still passing — which is precisely the pathology, since the old suite could not see this defect at all.

## The sweep the ticket asked for

The ticket flagged the general shape — a `useRef`-held `setTimeout` whose only `clearTimeout` sits on the counterpart handler. Eleven sites carry that spelling; nine are safe:

- **Safe** (effect cleanups present): `Tooltip.tsx`, `AnimateMount.tsx` (returns `clearPendingTimeout`), `Modal.tsx`, `useAmbientContext.ts`, `HexMapV2.tsx`.
- **Harmless**: `ProseQualityView.tsx:188` — its callback only nulls a ref and never touches React state, so there is nothing to fire into a dead component.
- **Genuine hits**: `IdentityStrip.tsx:18` (`useDelayedHover`, 450 ms) and `HooksBlock.tsx:37` (`Chip`, 600 ms), both arming on `onMouseEnter` and clearing only on `onMouseLeave`. A pointer that leaves *because the element unmounted* never fires `onMouseLeave`.

Those two were **filed, not fixed** — [THR-1108](https://linear.app/threadbare/issue/THR-1108), with its coordination block posted at filing per THR-836. No CI strike or play fault has been traced to either, and CLAUDE.md § Prioritization is explicit that "hardening against a failure that has not happened yet" does not jump the queue. THR-1106's Done-when named `ActionCard.tsx`; widening the diff past it would have made a Rule 0 fix carry prevention work through the gate.

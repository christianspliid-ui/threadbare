# THR-1190 — the park-decay toggle does not exist, and now nobody has to look for it again

**Shipped 2026-08-22.** Docs-only. Continuous Improvement.

## What the ticket expected

A **park** is the shape `assignee: null` ∧ `state: In Dev` — the one shape
`keep-work-flowing-cc` matches to surface finished-but-blocked work to Christian under
`## Needs Christian`. The class of it decaying is well documented: impediments #306, #380,
#508, #607, #657 (×2), with measured cost (THR-875 cleared by hand ~35 min later; THR-1168
invisible ~47 min).

The ticket's premise was that a **Christian-owned Linear settings toggle** disables the
GitHub integration's auto-assign, on the model of the THR-738 auto-close change — a
"~2-minute settings toggle" that had simply never been routed to him. Its first Done-when
was explicit about method: *"Do **not** guess the label — read the current integration
settings and record the literal control name and its location."*

## What reading them actually found

The toggle does not exist. Every control in the workspace that can write an assignee was
read directly and is **already in the state the fix would have put it in**, and the GitHub
integration page carries no assignee control at all:

| Surface | Control | State |
| -- | -- | -- |
| Settings → Preferences → *Automations and workflows* | **Auto-assign to self** | off |
| Settings → Preferences → *Automations and workflows* | **On move to started status, assign to yourself** | off |
| Team settings → Workflows & automations → *Pull request and commit automations* | all five `move to…` controls | `No action` |
| Settings → Account → Code & reviews | On git branch copy, move issue to started status | on — writes *status*, never assignee |
| Settings → Account → Code & reviews | On open in coding tool, move issue to started status | on — writes *status*, never assignee |
| Settings → Integrations → GitHub | — | no assignee control; the substring `assign` does not occur on the page |

The two `move to started status` toggles being on is the near-miss worth naming: they are
the trigger half of a plausible mechanism, but the half that would write an assignee — *On
move to started status, assign to yourself* — is off, so they move status and nothing else.

## Why this is a verdict rather than a stand-down

"Does this setting exist" is a fact, not a preference, so it is the agent's call under
CLAUDE.md § User review interface. The finding **removes** the ask rather than answering it:
there is nothing for Christian to click, so parking this for him would have put a non-ask on
the one surface he reads. The ticket's Done-when #3 (park it) and #4 (update CLAUDE.md
*after he confirms the toggle*) are both discharged by the premise being false — recorded
here rather than silently skipped.

What ships instead is the survey itself, in the two places a future session would look:

- `Docs/plans/2026-04-13-linear-coordination-protocol.md` § *Christian-owned Linear settings
  — the standing record*, which now holds both this and the THR-738 auto-close action, with
  the literal control labels and the date they were read.
- `CLAUDE.md` § Known Sandbox Limitations — the park-decay paragraph previously said the
  mechanism "is not configurable from this repo", which leaves a Linear-side fix open. It now
  says the Linear side was surveyed and is empty, so the authorial workaround (keep the issue
  id out of the body, title and branch of any PR not meant to close that issue) is the
  **whole** remedy rather than a stopgap awaiting a toggle.

## The residue, stated so it is not re-probed

If the reversion recurs with every control above still in the state shown, it is
non-configurable product behaviour, not a misconfiguration. The only surface that names the
acting party is the issue's **activity feed** at the instant of the revert. THR-1058 already
exhausted seven controlled MCP arms — priority, labels, `blockedBy`, `state`, a label touch
while parked, `save_comment`, and a pushed branch matching `gitBranchName` — and every one
preserved the null, so re-probing the field path is known-dead work.

## Method note worth keeping

The standing assumption across these docs is that Christian-owned Linear settings are
unreachable from an agent session, which is why the remedy sat in impediment rows for a week.
That is true of the Linear MCP, which exposes no settings surface — but **not** of the
session as a whole: Claude-in-Chrome is attached to a browser already authenticated to the
workspace, so the settings pages are readable (read-only) in about four calls. No setting was
changed. This is what let Done-when #1 be satisfied properly instead of guessed around.

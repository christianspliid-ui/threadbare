# THR-853 — TickEvent ids collided across ticks, so the event list rendered duplicate React keys

**Shipped 2026-08-09.** Four producers repaired, one whole-run invariant pinned.

## The mechanism, which is a property of the reset contract and not of any one module

`orchestrator.resetEventCounters()` runs at the top of **every tick**, resetting each
ephemeral event counter so the same seed replays the same ids (NFP #3 determinism).
That is correct and stays. The consequence nobody had written down is that a counter
reset per tick is unique only *within* a tick — while the events it labels live far
longer. `recentEvents` is a 100-entry rolling buffer spanning many ticks and React
keys the event list on `event.id`, so a minter that omits the tick collides with the
previous tick's Nth event of the same kind. React's own warning states the cost:
"children may be duplicated and/or omitted". The reported symptom was `amb_evt_17`
minted 9× in one 260-tick run.

The producers that got this right already encode the tick — `evt_${tick}_${n}` in the
orchestrator itself, `faction_join_${tick}_${n}` in `factionOutcome`. Three did not,
and all three were the same one-line defect:

| File | Was | Now |
|---|---|---|
| `src/engine/ambitionTick.ts` | `amb_evt_${n}` | `amb_evt_${tick}_${n}` |
| `src/engine/revelationEmitter.ts` | `rev_evt_${n}` | `rev_evt_${tick}_${n}` |
| `src/engine/unifiedActionPhases.ts` | `ua_evt_${n}` | `ua_evt_${tick}_${n}` |

## The fourth producer, which the grep could not have found

The ticket asked whether a shared minter was the common cause. It is not — it is a
shared *contract* with three independent violations, so a grep for `${++counter}`
found exactly those three. The test found a fourth that has no counter at all:
`unifiedActionResolution.ts` minted `ua_${action.actionId}_promotion`, derived from
the action rather than from a sequence. A multi-step action resolves one step per
tick and can cross a tier on more than one of them, so `ua_12_promotion` was minted
on ticks 26 **and** 28 of the seed-42 run. Same fix, same reason.

This is the whole argument for the test being a **whole-run sweep rather than an
`amb_evt` probe**. A probe on the reported id would have gone green while two
identical siblings shipped broken and a fourth defect of a different shape sat
undetected — and would go green again for the next minter added without a tick. The
new assertion is the invariant the reset contract actually implies: no `TickEvent.id`
repeats across a 300-tick run. It failed on the first run, naming the collision and
the ticks it happened on, and passes now.

## What is deliberately *not* claimed as tested

Instrumenting the run showed the three repaired counter-prefixes fire very unevenly:
`amb_evt` **198** ids, `rev_evt` **0**, `ua_evt` **0**. Neither `revelationEmitter`
nor `phaseIdleSelection` emits anything across 300 ticks of seed 42 from a bare
generated archetype. The shape assertion therefore covers `amb_evt` only and says so
in the file, with a note not to "restore" the other two prefixes to the loop without
first making them produce events — a three-prefix loop over two empty populations
reads as three-producer coverage while asserting nothing about two of them. Their fix
rests on the typecheck and on the collision sweep, which covers them the moment they
fire.

That `ua_evt` and `rev_evt` emit nothing at all in a 300-tick full-pipeline run is an
observation worth confirming on other seeds before anyone calls those paths dormant;
one seed and one archetype is not evidence of a dead path, and this ticket did not
investigate it.

## Two collateral repairs, both forced and both stated

**The copied fixture imported type errors.** The obvious archetype/cosmology literal
to reuse was `content-layer1-integration`'s, and it carries two type errors against
the current `AscendantArchetype` / `CosmologyProfile` shapes, surviving only inside
the THR-489 red baseline. Copying it put the ratchet at 3451 → 3453. The fixture is
now *derived* — `generateArchetypes(1, seed)` (the seeded production factory, so it
cannot drift from the type) and a `CosmologyProfile` built from `SPHERE_NAMES`.
Ratchet returned to 3451, unchanged.

**The new test turned a green suite red without touching the code under test.**
`scripts/__tests__/worktree-write-guard.test.ts` spawns a `bash` subprocess per case
at vitest's 5000 ms default. Its cases run 558–866 ms standalone — an apparently
comfortable ~5.8× margin — but adding one 300-tick engine test to the pool was enough
to push its heaviest case past the timeout. Measured both ways: clean `main` is 979
files / 15472 tests green; the same tree plus this test failed exactly that one case,
and the guard test passes standalone. This is the THR-1015 class the repo already
documents, so the fix uses that mechanism: a third named constant,
`SUBPROCESS_TEST_TIMEOUT_MS` (30 s), added to `src/testing/testTimeouts.ts` alongside
the world-sim and heavy-import ones, with its own derivation recorded — the driver
here is process-startup cost under a loaded pool, which is a different cause from the
two already there and would have been mislabelled by reusing either.

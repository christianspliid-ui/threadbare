# THR-1193 — a restored fragment becomes a real place

**Shipped 2026-08-22.** THR-1183 unified the two sublocation mint shapes and left one
writer behind: `hex.restore_fragment`, the divine action that rebuilds a ruin. It minted
the retired `type: 'sublocation'` shape with no `parentLocationId` and attached it with a
`located_at` edge rather than the `contains` every other sublocation uses — "a different
thing wearing the sublocation name", which is why repointing it there would have been a
semantic change disguised as a rename.

Firing it revealed the node was worse off than that description: it reached the graph
**with no edges at all**.

## What was actually happening

Two independent failures, either of which alone was fatal.

`$location` for a hex action resolves to the hex *target id* (`hex_31_7`), and hexes are
not graph nodes — a seeded medium world holds zero. So the edge's target was a node that
could never exist.

It never got that far, because `$created_0` resolved to nothing either. Six recipes
across `hexActionBridge` spell that ref, but nothing in the executor ever resolved it:
`createdIds` is keyed by the *generated* id (`createdIds[id] = id`), and `resolveRef`
never consulted `createdIds` at all. Every such edge failed on its **source**:

```
add_node  → success: true,  createdId: "gen_sublocation_1"
add_edge  → success: false, error: "Source node not found: $created_0"
```

The action still reported success, because a failed op inside a fail-soft batch is a
per-op flag nobody reads. Every successful cast left an orphan named `gen_sublocation_1`
— no parent, no edges, invisible to every sweep, and unnamed on any surface that reads
`node.name`.

## The decision: it is a sublocation

Recorded, not chosen. The template's own description says the fragment "becomes a
functional sublocation"; its success prose says "a blended sublocation bridging past and
present"; the 2026-03-26 hex-actions design doc row reads "Partially rebuild ruin →
create functional blended sublocation". The design had decided this all along and the
node shape had drifted away from it — so this is a drift correction, like THR-1183
itself, rather than a fork needing a director's call.

## Why a generator, and not the property-ref substitution the ticket anticipated

THR-1193 proposed teaching `executeAddNode` to substitute `$`-refs inside `properties`,
so a static recipe could carry `parentLocationId: '$location'`. That would have written
`hex_31_7` as the parent — a **dangling** reference, satisfying the letter of the fix and
none of its point. It would also have changed behaviour for every `add_node` recipe in
the codebase, since a properties-wide `$` scan reaches every string value.

A sublocation's parent is a runtime value, and the bridge already has a mechanism for
runtime values: `HEX_ACTION_GRAPH_OP_GENERATORS`, which receive the graph and can query
it. The recipe moved there and emits literal ids. No new executor capability, no
behaviour change to the other recipes.

What the executor *did* need was the thing its recipes already assumed. `$created_N` now
resolves, positionally over the node-creating ops of the batch, through
`GraphOpContext.extras` — which `resolveRef` has always checked. That adds no new
resolution surface and no new syntax; it makes the existing spelling mean what its six
callers assumed. The batch works on a **copy** of the caller's context, so created refs
die with the batch rather than leaking into a context that outlives it.

## What shipped

The fragment now mints in the canonical shape — `type: 'location'`, a real
`parentLocationId`, `persistence: { type: 'permanent' }` (required by
`SublocationProperties`, and the field whose omission crashed `checkDissolutions` under
THR-1183), attached by `contains` from its parent.

The parent is chosen from **place-tier locations only**. `getLocationsInHex` sweeps a
bare `getNodesByType('location')` and so returns both tiers — the THR-1183 trap — so an
unfiltered pick could nest a sublocation inside another sublocation. Ruins are preferred,
since this is a restoration; it falls back to any place on the hex rather than refusing,
and a hex with no place-tier location yields no ops at all (NFP #4).

The type is `sublocation-type.ruins` rather than a bespoke `restored_ruin`, because
`sublocationTypeId` is what encounter gating matches against — an unregistered type gates
*no* encounters, which would make the fragment inert scenery instead of the "functional
sublocation" the action promises. `restored_ruin` survives as a flavour subtype that no
gate reads.

## Evidence

Fired against a real seeded world (seed 42, medium), targeting `loc_44` "Wolf Remnant"
(ruins) at hex 31,7:

```
OPS: add_node=ok  add_edge=ok
BEFORE: {"legacyTypeNodes":0,"sublocations":440,"placeTier":214}
AFTER : {"legacyTypeNodes":0,"sublocations":441,"placeTier":214}
FRAGMENT: type=location  name="Restored Fragment"
  sublocationTypeId=sublocation-type.ruins  parentLocationId=loc_44
  persistence={"type":"permanent"}  hexCol=31 hexRow=7
PARENT RESOLVES TO: loc_44 "Wolf Remnant"
CONTAINS EDGES INTO FRAGMENT: loc_44 -> gen_location_1
LOCATED_AT EDGES FROM FRAGMENT: 0
```

**Falsified**, both halves: disabling `$created_N` resolution turns 4 of the 14 new tests
red; dropping the place-tier filter turns the "never parents to another sublocation" test
red on its own.

`'sublocation'` now has **no production writer at all** — the tolerance in
`sublocationShape.ts` is a pure back-compat read path for saved worlds, and its doc
comment says so instead of naming this recipe as a live carrier.

## Found in passing — THR-1194

Fixing `$created_0` repaired `hex.send_herald` and `hex.spark_encounter` outright, and
moved `hex.forge_seer_token` and `hex.forge_instrument` one layer deeper into a second,
pre-existing defect: both bind their artifact with `possessed_by`, which **is not a
registered edge type** — the registered edge is `possesses`, and its schema row runs
actor → artifact, so the recipes are wrong in name *and* direction. Two shipped divine
actions each mint a `storied` artifact that reaches nobody. Invisible until now because
the batch failed earlier, at `$created_0`, so the schema refusal was never reached.
Filed as THR-1194 with the measured output, along with the smaller shared defect that
these recipes set only `properties.name` and so leave their nodes reading as
`gen_artifact_7`.

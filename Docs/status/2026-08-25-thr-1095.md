# THR-1095 — every tooltip in the game was hover-only; the default is now reachable

**Shipped 2026-08-25.** `src/components/shared/Tooltip.tsx`,
`src/components/shared/focusableSelector.ts` (new), `src/components/shared/Modal.tsx`,
`src/components/Game/EncounterVeil.tsx` (comment only),
`Docs/design-system/interactions.md`, `Docs/design-system/primitives.md`,
`src/components/shared/__tests__/Tooltip.test.tsx`.

## The defect

`Tooltip`'s trigger rendered as a bare wrapper carrying `onPointerEnter`,
`onPointerLeave`, `onFocus` and `onBlur` — and no `tabIndex`. For any child that
was not itself focusable, the last two were **dead code**: nothing could receive
focus, so they never fired. A tooltip wrapping a `<button>` worked by accident,
because the button was the focusable thing.

The tooltip is the game's explanation layer for reaches, spheres, standing and
doom, so this meant a keyboard player could not read the game's own vocabulary.
Tier 1 of the disclosure ladder did not exist for them.

## Why it sat in `Idea` for twelve days

The ticket filed itself as needing a design decision — *"pick one in design, do
not let an executor guess"* — with three candidate shapes. It was promoted on
the rule-4 reading: all three honour the same agreed outcome (a concept word is
keyboard-reachable without a tab-order storm, Laws 23/46/50), so the fork is
*how*, not *what*, and belongs to the executor with the pick recorded.

## The pick: automatic by default, bounded structurally, with the opt-in kept as an override

**Shape 1 (opt-in prop) was rejected because its default is broken and fails
silently.** With `<Tooltip` at 146 call sites across 49 files, "the caller
remembers" is the exact mechanism that produced this ticket — THR-1033 had to
hand-roll the fix at one site precisely because nothing reached the other 145.

**Shape 2 as written would genuinely storm the tab order**, because it says
nothing about *which* 146 sites. So the shipped rule keeps the automatic default
and bounds it by three structural tests, each of which withholds only stops
nobody could use:

| Test | What it excludes, at no cost |
|---|---|
| `as === 'span'` | SVG. `tabIndex` on `<g>` is inconsistently honoured, and both `as="g"` callers are hex-map overlays — a stop per tile *is* the Law 46/50 storm |
| `depth === 0` | Concept links inside an open popup. The popup portals to the end of `<body>` and the trigger's own blur closes it, so a nested stop is unreachable by construction |
| content resolves | Tooltips that resolve nothing — a stop that opens no popup is a stop that does nothing (Law 21) |

…plus one measured test: a DOM probe checks whether the children already own a
stop, so the wrapper never adds a second one for the same word. The probe runs
on mount and on the structural inputs, deliberately **not** on `children`, whose
identity changes every render and would put a `querySelector` in the render path
of all 146 sites.

Shape 1's prop survives as `focusable?: boolean` — the explicit override in both
directions. Shape 3 (roving/`aria-describedby` container) was rejected as
solving a problem this ticket does not have: roving tabindex is for a *set* of
peer controls navigated with arrows, and concept words are scattered through
prose individually with no container that is a navigation unit.

## Two things the change deliberately does not do

**No `role`.** Law 23's `role="button"` clause governs elements that *act* when
pressed. A tooltip trigger only describes; Enter and Space do nothing on it.
Announcing an unpressable button would be the worse accessibility outcome, not
the more compliant one. `aria-describedby` is the correct association and was
already there.

**The `EncounterVeil.tsx` hand-rolled `tabIndex` stays**, taking the Done-when's
second branch on an argument rather than to avoid a diff: under the new rule it
is not redundant, it is the override for *focus-ring placement*. The consequence
chip is an inline-flex span with a leading glyph, and the ring should hug the
category word rather than the wrapper's box. The probe sees the child's stop and
stands down, so there is exactly one stop either way. Now documented as
sanctioned at the call site and in `interactions.md`. This also leaves the
existing Law-17 regression asserting where the stop actually is.

`FOCUSABLE_SELECTOR` was extracted to its own module en route, because `Modal`
and `Tooltip` had begun keeping the same selector for opposite purposes —
`Modal` *collects* matches for its focus trap, `Tooltip` *detects* one to stand
down — and a selector meaning "focusable" in two files is drift waiting to
happen.

## Evidence, and the gap in it

`npm test` 1065 files / 17,628 tests green — no regressions across the 146 call
sites. Ratchet 3014 unchanged. Build ✓ 9.97s. 11 new tests pin the rule from
both sides: a stop where one was missing, and no stop where one already exists,
is suppressed, is SVG, is nested, or resolves nothing.

**Browser-verify substitution: jsdom-render — unattended run, no startable dev
server.** `preview_start` was refused outright (impediments #546, #574), which
shuts the Playwright route too since it presumes a running server. Focus is
proven by `document.activeElement` after `.focus()`, both arms — jsdom consults
the same focusable-area rules the browser does, so a plain `<span>` genuinely
cannot take focus and the assertion falsifies rather than restates the attribute.

**The Done-when's "at 1920×1080" is not met and is not claimed.** No pixel was
captured. What is unproven is purely visual: whether a `2px` gold ring at `2px`
offset reads cleanly around an inline word mid-prose, or collides with the line
above at body leading. Added to THR-1133's attended pixel-pass sweep as a sixth
owed capture rather than filed as a seventh ticket. If the ring is wrong there,
the fix is CSS — not a reversal of the reachability rule.

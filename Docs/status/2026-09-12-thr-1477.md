# THR-1477 — the encounter's name opens the character sheet, and the ending stays on screen while you read it

**Date:** 2026-09-12 · **Pillars:** UI · Engine N/A (verified, see below) · Content N/A
**Issue:** [THR-1477](https://linear.app/threadbare/issue/THR-1477)

## What the director asked

> is it possible that we can click the agents name on the encounter to get the character
> sheet to pop up on top of the encounter? this would be a good way for the player to check
> what the encounter has changed on the agents character sheet.

Yes — and the click was dead. Two separate things stood between the ask and the surface,
and fixing either alone would have left the feature not working.

## Defect 1 — the click routed to a surface nobody could see

The veil's `onSelectAgent` was wired to `handleAgentSelect`, which opens the **ActionDrawer**
(z-index 40) — underneath the veil (z-index 50). The control looked live, fired its handler,
and produced no visible change: a Law 21 dead click on the surface under review.

`AgentProfileModal` already mounts at `MODAL_Z_ABOVE_INTERRUPT` (65), built that way by
[THR-1139](https://linear.app/threadbare/issue/THR-1139) precisely so it can stack above a
modal-tier interrupt. Nothing routed the veil's name to it.

## Defect 2 — and the obvious one-line fix does not work

**This is the part worth carrying forward.** The ticket's own root-cause section proposes
`openAgentProfileForId`, and that is not sufficient: it is a bare
`setProfileModalAgentId`, while the card the modal renders — `agentInfoCard` — is memoised
on **`selectedAgentId`**, and GameView gates the mount on `profileModalAgentId && agentInfoCard`.
So setting only the profile id either renders **nothing** (no agent selected — exactly the
dead click) or renders the **previously selected** agent's sheet under the new agent's id.

I shipped the one-line version first and the browser said the sheet still did not open. That
is the whole reason the tree-identity probe and the live click are in the evidence rather than
a unit test: the unit layer had no opinion about a memo in a different hook.

New `openAgentSheetForId(agentId)` in `useAgentInteraction` sets **both**, and unlike
`handleAgentSelect` does not open the drawer — a caller behind a full-screen interrupt wants
the sheet on top, not a drawer changing state underneath it.

**[THR-1461](https://linear.app/threadbare/issue/THR-1461) is the same root cause** ("the
premonition's subject-name control opens the previously selected mortal's sheet"). It is a
separate open ticket, so this one builds the primitive and repoints only the veil; that
executor repoints its own surfaces and finds the primitive waiting.

## Defect 3 — the timing, which is what the ask actually turns on

`handleEncounterAftermathReaction` applied the reaction **and closed the veil on the same
click** (`closeAfterSelection ?? true`), and the grants the aftermath chips describe are
written by that reaction's effects. So there was no moment when the writes had landed *and*
the encounter was still open: opening the sheet before the pick shows the pre-encounter
agent, which is the opposite of the ask.

The pick now lands its effects and **stays**. "Return to the world" was already rendered
beneath the reaction box ([THR-1136](https://linear.app/threadbare/issue/THR-1136) §1) and
becomes the single exit. `closeAfterSelection` is authored content and is still returned by
`applyAftermathReactionForAgent` for its non-modal callers; it no longer decides when the
modal closes, **because the player does**.

That makes the spent choice a rendering problem — buttons that still look pickable after the
decision is made are the same Law 21 defect one beat later. New optional veil prop
`aftermathReactionTakenId`: the taken reaction keeps full legibility and is marked
(`aria-label` "… — chosen"), the rest go quiet, the whole set goes inert, and the
"choose which one" prompt drops because the question has been answered (Law 25 — the same
reasoning the existing `reactions.length > 1` check already encodes). A host that omits the
prop gets the previous always-live rendering, which is correct for a host that still closes
on the pick.

State is held per open encounter and reset by an effect keyed on the veil's subject rather
than at each of the six `setTieredEncounterState` call sites — a seventh call site cannot
forget it, and a pick can never leak onto the next encounter.

## Engine pillar — verified, not assumed

N/A as the ticket predicted, and checked rather than taken on trust:
`applyEncounterAftermathReaction` computes against the live ref and commits synchronously, so
the sheet opened from the aftermath reads the written state. **The stated caveat holds:**
`quintessence_shift` queues onto `pendingQuintessenceEvents` by design and will not appear on
the sheet until a tick runs. Snow on the Pass grants a condition, so this run does not
exercise that path — it is not faked and not claimed.

## One finding the director should know about

The sheet is **familiarity-gated**, and that gate is upstream of this change. At `stranger`
familiarity the Attachments tab reads *"Vara carries no known possessions, conditions, powers,
or agreements"* — the `Exhausted` grant is on the graph and the sheet declines to show it.
Verified both ways in one session: `getAgentAttachments('@hero')` returns `Exhausted`
immediately after the pick, and the sheet renders `WOUNDS (1/3) · ✕ Exhausted` once
omniscience lifts the gate.

For a bonded mortal — the case the ask is really about — familiarity is high and the writes
are visible. For a stranger, the routing now works and the knowledge system still hides the
detail. That is the existing design working as specified, not a regression, and not something
this ticket should have silently overridden. Flagging it because the director's stated purpose
("check what the encounter has changed") is only fully served at the familiarity tiers that
permit it.

## Impediment

**#1027** — a long-lived `vite` kept serving a **stale transform** after two edits, so the first
browser pass measured code that was never written. The symptom of a stale bundle is identical
to the symptom of a broken fix (nothing happens on click), so the natural read was "my fix is
wrong" and the natural next step would have been to rewrite correct code. Caught only because
the tree-identity probe was already part of the routine — and the lesson is that the probe
belongs **after every edit the browser is about to be asked about**, not once at the start of
the pass. Match on a **code** symbol (`onSelectAgent: openAgentSheetForId`), never on JSX or a
`THR-` comment: vite transforms the former and strips the latter.

Recorded separately in that row because the #1011/#1025 ordering class keeps looking for it:
`npx vite` started from the **Bash tool** works fine in an unattended run, even though
`preview_start` refuses one.

# THR-1465 — three strangers who were never in the scene

**2026-09-11 · Engine · UI · Content · Bug · High · Encounter Experience**

Found by the [THR-1463](https://linear.app/threadbare/issue/THR-1463) slice pre-flight on the deployed build (`c3ef6c78`): every one of the five slice parents rendered the same three chips under **IN THE SCENE** — `Wayside Keeper`, `Fellow Traveler`, `Road Outrider` — each saying its own name twice, each `disabled`. On **The Swindled Family**, whose prose introduces a man, a woman, three children and a swindler, those three strangers were the *only* cast shown. On **Snow on the Pass**, whose prose names no people at all, they were shown anyway.

## What it actually was

Not the component. `CastStrip`'s Law 21 handling was already right — no node, no live control. The bug was two layers up, in **which specs reach the cast model at all**.

`withDefaultSupportBundle` attaches a setting-class cast to any template that does not author one (THR-1044), and four of the five slice parents *compose* theirs as `[...DEFAULT_SETTING_SUPPORT_BUNDLES.wayside, <their own spec>]`. Those defaults are **bind-only by construction**: `pre-seeded` + `reuseNpcRoles`, which binds an existing NPC at the anchor or stays unresolved, and never materialises. A wayside hex carries no hermit, wanderer or ranger to reuse — so all three stayed unresolved, on all five, every time.

`buildCast` then mapped every actor spec into a chip regardless, falling back to `spec.spawnName` for the name. For a generic walk-on the spawn name *is* the role, so the chip read `Wayside Keeper — Wayside Keeper`: the same words twice, one of them dressed as a person's name (Laws 13/14).

## The design call, and why this one

The ticket left it open — bind them, or stop showing them — and the coordination block asked for the answer with its reason. **An unbound *default* is not in the scene and gets no chip. An unbound *authored* spec keeps its inert chip, unchanged.**

That is not a new rule; it is the one the codebase already wrote down twice, applied to a surface that had not heard it:

- THR-1041 kept unbound specs on the strip for a stated reason — *"the actor is still in the prose, so hiding it would be worse than showing it inert."* That premise is exactly what separates the two sources. An authored bundle is a promise the encounter's own prose makes. A default was attached to a template that never mentioned it, which is why two of the five showed three people their prose had never heard of.
- THR-1132 had already ruled on the same distinction for `check:encounter-live`: an unbound default *"stays unresolved … which is the honest outcome rather than a spawned prop"*, and treating defaults as promises failed 5 of 6 slice templates for behaving as designed.

Binding them instead was the rejected alternative. It would mean spawning walk-ons to populate a row — the "spawned prop" that module forbids in its own header, adding world population to satisfy a UI strip. The scene row's job is to say who is present; when nobody is, the honest render is nothing.

Christian: this is the call the block asked me to make and state. **Veto invited** — if the wayside row should instead be *filled* (ambient faces spawned per scene), that is a content-supply decision, not a bug fix, and it would want its own ticket.

## The change

- **`isDefaultSupportSpec(spec)`** (`src/data/default-support-bundles.ts`) — the per-spec companion to the existing `hasOnlyDefaultSupportBundle`, which answers only at template level and therefore says `false` for all four composed bundles while three of their four specs are defaults. Identity, not value, and scanned across *every* default table rather than the one `primarySettingClass` would resolve to, so the answer never depends on that resolution agreeing with whichever table the author spread in.
- **`buildCast`** drops a default spec that bound nobody. A default that *did* bind keeps its chip — the filter is about binding, not provenance.
- **`CastStrip`** collapses a role line identical to the name, case- and whitespace-insensitively (the two strings come from different producers, `spawnName` vs `supportRoleWord`). Name only, and the `aria-label` and `title` drop the duplicate with it. Kept as a surface-level guard even though the source fix removes today's only trigger.

## Guard

Nine arms across two files, including a vacuity guard (*every slice parent still carries default specs*) so the census arms cannot pass against a template that stopped merging them, and a falsification arm (*an unbound authored spec still renders inert*) so the filter cannot quietly widen into "hide every unbound spec". **The suite was confirmed falsifiable** — disabling both halves of the fix turns it red (4 failed / 185 passed), green again on restore.

# 2026-10-08 — THR-1777: the player's aftermath choice lands

**Ticket:** [THR-1777](https://linear.app/threadbare/issue/THR-1777) · Found by warm playtest round 1 (2/3 testers; dry run 3/3).

## What was wrong — three faults, not one

1. **Wrong target.** The veil's click passed only the agent and the reaction id. `resolveAftermathContextForAgent` then took the agent's *oldest* pending notification, so an agent holding several aftermaths resolved the click against a different encounter, and the clicked id missed ("Unknown aftermath reaction"). This is the cause the ticket named.
2. **No target at all (found in the browser).** The engine prunes a resolved action 20 ticks after it completes (`RESOLVED_ACTION_RETENTION_TICKS`), and trims notifications at 50. The world keeps ticking under an open aftermath, and a warm start runs hundreds of ticks. By the time the player clicks, the live action is gone, and the resolver says "No pending aftermath" even with the pin. At `?seeded&warm=300&spawn=reputation.veil.the_silent_chamber` this reproduced every time: tick 112, no live action, no notification, and the veil still showing the aftermath.
3. **Silent failure.** `if (!result.success) return;`. Nothing on screen changed and nothing said why.

## What changed

- **Engine:** `resolveAftermathContextForAgent(state, agentId, reactionId, { actionId, actionSnapshot })` pins resolution to the on-screen action. If the live action is gone, it answers the host's copy of that action instead. A pin that matches nothing returns an error that names the action, and never falls through to a different aftermath. The two reaction-pick blocks are deduplicated into `pickAftermathReaction`.
- **Engine:** `pruneResolvedActions` (new `src/engine/resolvedActionRetention.ts`; the constant moved there) keeps a resolved action while an unresolved notification names it. The notification trim bounds that.
- **UI:** GameView passes the pin and a ref holding the last live copy of the on-screen action. The receipt path pins `activeReceipt.actionId`. Answering an aftermath resolves only notifications pinned to *that* action; the template match is only for unpinned ones. A refused pick shows a plain line under the reactions (`aftermath-reaction-error`, copy in `src/data/aftermath-reaction-copy.ts`), and the engine's reason goes to the new `aftermath_reaction_refused` trace.

## Evidence

- Unit: two pending aftermaths, with A older than B. Pinned to B, B's reaction resolves and A stays answerable. The cases for a pruned action answered from its snapshot, a mismatched snapshot ignored, a pin to a missing action, and the already-applied refusal are all covered. The retention prune is tested with control arms.
- Browser (Playwright, 1920×1080, worktree Vite): at the reproduction above, clicking "Bring the knowledge forward into the world." gave `aria-label` "… — chosen", both reactions went inert, there was no refusal line, the console showed 0 errors, and the page had no scroll (`scrollHeight` 1080). Screenshot: `Docs/evidence/thr-1777/aftermath-choice-lands-1920x1080.png`. Warm-world popups (a delve dilemma) stack above the veil; that is pre-existing popup layering and not part of this change.

# THR-1151 — four faction-rank readers that could never fire

**Shipped 2026-08-17.** Deferral of THR-1144, which settled the `member_of.rank` scale to revive the `faction_rank:` gate and found this family on the way past.

## What was broken

`MemberOfEdgeProperties.rank` declares its scale in its own doc comment — *"Rank within the faction: 0 (recruit) to 1 (leader)"* — and every live writer honours it. `worldSeed` seeds `0.3`, `tierPromotion` adds `FACTION_RANK_PER_PROMOTION = 0.1`, `factionOutcome` joins at `0`, and `factionMembership` clamps to `[0, FACTION_RANK_MAX]` where `FACTION_RANK_MAX = 1.0`. Nothing has ever written above 1.

Three readers tested against an integer tier anyway:

| Reader | Predicate | Consequence when permanently false |
|---|---|---|
| `journeyEngine.ts` | `rank >= 3` | `factionsLed` on the influence axis counted only explicit `role: 'leader'` holders |
| `proseEnrichment.ts` | `rank >= 3` | `{faction_rank}` enriched for the title-holder alone; a senior member enriched as nobody |
| `returnEngine.ts` | `rank >= 2` | a faction was never a ripple target unless the agent held the leader slot |

Each one ORs with `role === 'leader'`, so none of them broke visibly — they silently collapsed to their role half. That is what made this survivable for as long as it was.

**The ticket named three readers; there was a fourth.** `socialLeverage.getHighestFactionRank` divided raw rank by `RANK_NORMALIZATION_DIVISOR = 10`, justified by a comment describing *"raw rank numbers (typically 1–10)"* — a scale nothing has ever written. That squashed the maximum any agent could return to `0.1`, against a `LEVERAGE_RANK_GAP` of `0.30`. The faction rank advantage bonus was unreachable for **every agent in every world**, and unlike the other three it has no role-based fallback: the bonus simply never applied. The ticket had flagged the divisor as needing "the same correction"; it was in fact the same defect, one indirection further out.

## The fix

Two named constants on the declared scale, anchored to the game's own rank ladder rather than invented. `faction-definitions.ts` already states what standing means on this axis — `journeyman` 0.0, `sergeant` 0.3, `lieutenant` 0.6, `leader` 0.85:

- `FACTION_RANK_SENIOR = 0.6` (the `lieutenant` boundary) — upper hierarchy, short of the title. Replaces both `>= 3`.
- `FACTION_RANK_NOTABLE = 0.3` (the `sergeant` boundary) — above raw recruit, a deliberately wider net. Replaces `>= 2`.

Pairing each with `role === 'leader'` is kept, because the two signals are genuinely different and it would have been easy to read them as redundant: `role` is derived from **reputation** via `getRankTier`, while `rank` is the promotion-accumulated number `tierPromotion` bumps. A high-rank member who has not taken the single leader slot is exactly what the rank clause exists to catch.

`getHighestFactionRank` now clamps to `FACTION_RANK_MAX` rather than dividing — clamping rather than passing through so a stray out-of-scale fixture cannot hand back more than the ceiling.

`returnEngine`'s `significance: rank + (role === 'leader' ? 2 : 0)` needed **no** change and was left alone: on the 0–1 scale it lands in the 0–3 band the other target kinds in that function already use.

## The part worth keeping

The ticket's own falsification note — *"each fix needs an arm proving the reader now fires for a high-ranked member, not only that it stays quiet for a low-ranked one"* — turned out to have a second edge the note did not anticipate, and the first draft of this work walked straight into it.

Every existing test of these readers was vacuous in the same way: `proseEnrichment`'s fixture was `{ role: 'leader', rank: 4 }` and `returnEngine`'s was `{ rank: 3, role: 'leader' }`, so both passed on the **role** half and stayed green through the entire life of the dead predicate. `returnEngine`'s was even named *"finds factions via member_of edges with high rank"*. `journeyEngine` and `socialLeverage` had no rank fixture at all. One fixture also called a member carrying `rank: 1` — the leader ceiling — "rank-and-file".

The first set of new arms wrote `rank: FACTION_RANK_SENIOR` in the fixture. Running the falsification revert (thresholds back to `3` and `2`, divisor restored) showed only the `socialLeverage` arms going red — the other three still passed, because writing the constant on **both sides** of the comparison moves the fixture with the threshold, so the arm holds for any value including the dead one. A test that cannot fail is not evidence, and this one was three-quarters of the way to shipping as evidence.

Fixtures are now literals on the declared scale. Re-run against the old predicates, **all five positive arms across all four files go red**; restored, green. That revert is the only reason any of this counts as proof.

## Pillars

**Engine** — four readers, two new constants. **Content** — N/A, no authored content references these thresholds. **UI** — the two constants registered on the CMS tunable surface (NFP #1), which put a `src/components/` file in the diff; `preview_start` is refused in unattended runs, so browser-verify was discharged by the sanctioned jsdom-render substitution against the real `ConfigManager`, asserting the **live** values reach the surface — something a screenshot could not have shown.

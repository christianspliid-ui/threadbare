# THR-1484 — one spelling for a condition's authored term

**Shipped 2026-09-13.** A condition's duration row is back on the sheet, for the
13-in-14 conditions that never had one.

## What was wrong

A `has_trait` edge's authored total had two spellings. `readEdgeDuration`
(`src/engine/agentAttachments.ts`) reads **`durationTicks`** and then hands it to
the UI under the name `totalTicks` — and that name collision, view prop vs edge
property, is what let writers mint the total under the wrong one. Any condition
granted with the wrong spelling came back with `totalTicks: undefined`, so:

* `AttachmentDetailView`'s **Duration section never rendered** — it is gated on
  `ticksRemaining != null && attachment.totalTicks`.
* `AttachmentRow`'s duration **progress bar had no denominator**.

The condition still expired on time, because `decayConditions` counts
`ticksRemaining`, which every writer set. A display gap, not a simulation one —
which is exactly why it survived.

## The ticket named two writers; there were three

THR-1484 described the divergence as `encounterAftermath.ts` (correct) versus
`phaseEncounterTraits.assignCondition` (wrong). Measuring the live world first
rather than taking the ticket's word found a third writer the ticket never
mentioned — **`rewardPool.instantiateReward`** — and it was the one doing the
damage. Seed 42, medium map, tick 60:

| | `durationTicks` (read) | `totalTicks` (unread) |
|---|---|---|
| before | 1 | **13** |
| after | **14** | 0 |

All 13 came from `rewardPool`, none from the writer the ticket named. The total
count of duration-bearing edges is unchanged at 14 — nothing was created or lost,
only the spelling unified.

The ticket's named writer turned out to be **dormant**: its condition branches gate
on a template `category` (`combat`/`social`/…) that no shipped template carries, and
it is called from the orchestrator's loop over the legacy `encounterProgress`
collection, which the unified-action pipeline no longer populates (the same dead
loop `traitDefinitionSeeding.ts` documents for THR-809). It is fixed anyway, so the
path is correct if that loop is ever revived — but it was never the live defect.

## What changed

* `src/engine/rewardPool.ts` — writes `durationTicks`. The live fix.
* `src/engine/phaseEncounterTraits.ts` — writes `durationTicks`. The dormant one.
* `src/engine/agentAttachments.ts` — the reader's docstring now names the whole
  writer set and says why there is deliberately **no** legacy `totalTicks`
  fallback: the world graph is never serialized, so no saved world can be carrying
  the old spelling and a fallback would be dead code reopening the door.
* `scripts/interface-contracts.ts` — corrects a note calling `durationTicks`
  "inert". It has been live since THR-784.
* `src/engine/__tests__/rewardInstantiation.test.ts` — **repointed**, not deleted.
  It asserted `totalTicks` on the reward edge: green on a dead contract while the
  Duration row it stood for was blank in the game.

## The tests

`conditionDurationContract.test.ts` drives **every** writer through its real grant
path and reads back through the real `getAgentAttachments`. Each arm asserts the
grant happened *and* that the total survives as a number — an empty list would
otherwise satisfy the duration assertion by vacuity. A final arm sweeps every
duration-bearing edge and requires `durationTicks` present and `totalTicks` absent,
so a fourth writer inventing a fourth name fails here.

`AttachmentDetailViewDuration.test.tsx` renders the real component from a
really-granted condition. Its sibling suite hands the component a literal
`{ ticksRemaining: 8, totalTicks: 20 }` — which passes no matter what the engine
writes, and is why this went unseen. Nothing in the new file is hand-authored.

Both were falsified against the unfixed writers: 4 of 5 contract arms and both
render arms go red, failing with "Unable to find an element with the text:
Duration" — the ticket's described symptom, reproduced. The already-correct
aftermath arm stays green, which is the point.

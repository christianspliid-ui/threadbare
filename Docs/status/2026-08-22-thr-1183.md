# THR-1183 — sublocations mint in one node shape

**Shipped 2026-08-22.** Sublocations reached the graph two ways and neither half of the
codebase could see the other: `sublocation.ts` (worldgen, high volume) minted
`type: 'location'` carrying `parentLocationId`, while
`strategicGraphOps.createSublocation` minted `type: 'sublocation'` outright. Every
`getNodesByType('location')` sweep missed the strategic shape; every
`getNodesByType('sublocation')` sweep missed the canonical one.

## The decision

**One shape: `type: 'location'` carrying `parentLocationId`.** `src/types/sublocation.ts`
had documented exactly that all along — *"The node itself has `type: 'location'` and is
distinguished by having a `sublocationTypeId` property"* — so this narrows the one
drifted writer rather than migrating the one that was right. That is also the additive
direction (NFP #6): one strategic-action writer moves, four shipped readers keep their
inputs.

The discriminator is **`parentLocationId`**, not the node type and not a subtype string,
because `encounterAftermath` had already converged on it when deciding whether `$target`
binds the sublocation field or the location field — the two tiers carry different tax and
gating semantics, so one node must never satisfy both.

`'sublocation'` stays a registered `NodeType` (THR-1177) and is still *accepted* by
readers, so a saved world degrades to "still a sublocation" rather than "invisible". No
sublocation producer writes it any more.

## What shipped

New `src/engine/sublocationShape.ts` is the single place the question is asked —
`isSublocationNode`, `isPlaceTierLocation`, `getSublocationNodes`,
`getPlaceTierLocations`, `resolveToParentLocation`. Seven readers were repointed through
it, three of which were genuinely half-blind rather than merely inconsistent:

* `strategicActionCandidates` swept `getNodesByType('sublocation')`, so its
  `sublocation_type` rule matched almost nothing on a normal map.
* `phaseDetectionPressure` skipped the parent hop for the canonical shape and then read
  `regionId` off the sublocation, which carries none — every mortal standing in a
  worldgen sublocation resolved to **no region at all**.
* `retinue` tested `locationSubtype === 'sublocation'`, a spelling no production writer
  has ever emitted, so real sublocations were categorised as locations, not sources.

## What the unification exposed

Bringing strategic sublocations into `checkDissolutions`' sweep crashed the tick loop on
the first one: `createSublocation` never wrote `persistence`, a **required** field of
`SublocationProperties`. The omission was real from the start and invisible only because
the node hid outside the sweep. Both halves are fixed — the writer now writes it, and the
sweep treats a persistence-less sublocation as permanent instead of throwing, which is
what its own doc comment already promised (NFP #4). Refusing to dissolve is the
recoverable direction: a node that lingers can still be removed; one dissolved by mistake
is gone.

## Evidence

Seeded medium world, seed 42, tick 30: **738 location nodes = 473 sublocations + 265
place-tier**, `getNodesByType('sublocation')` returns **0**, and **0** nodes where
`sublocationTypeId` and `parentLocationId` disagree. No sweep misses a tier. Full suite
green (1047 files / 17022 tests), build clean, 30-tick engine smoke reaches tick 30 with
384 agents. The typecheck baseline drops 3126 → 3125.

The 16 new tests in `sublocationShape.test.ts` were falsified against a revert of the
writer change — 2 fail, so the guard is real rather than vacuous.

## Deferred

**THR-1193** — `hex.restore_fragment` is the last production site emitting
`nodeType: 'sublocation'`, but it carries no `parentLocationId` and attaches by
`located_at` rather than `contains`. It is a different thing wearing the name, and
`executeAddNode` copies `properties` verbatim without resolving `$`-refs, so it cannot be
given a runtime parent without new executor capability.

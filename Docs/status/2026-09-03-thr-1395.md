# THR-1395 — conditions and experience as `has_trait` edge state

**Shipped 2026-09-03.** Deferral from THR-1394 (the world-object model). Plan doc: `Docs/plans/2026-09-03-thr-1394-world-object-model.md` § Traits.

## What the measurement changed about the ticket

The ticket's premise was that conditions are minted one node per bearer and the pool grows with every wound. Measured first, on seed 42 / medium at tick 30:

| subcategory | nodes | borne | max bearers per node |
|---|---|---|---|
| `condition` | 70 | 7 | 1 |
| `scar` | 2 | 0 | 0 |
| `experience` | 44 | 44 | 1 |

The 70 condition nodes are the **seeded catalogue** — `gameInit`, the reward pool and the anomaly catalogue write one definition per kind, and 63 of them had no bearer at all. That set is fixed by content, not by bearers, so it never scaled. The kind that actually scaled was **`experience`**, which is registered under the *Trait* kind, not the Condition kind: 44 nodes for 44 bearers, one each, growing with every (agent, domain) pair that ever fought.

So the repair landed on the three writers that genuinely mint per bearer, which is what the ticket's own predicate names:

- `capabilityGrowth.applyEncounterGrowth` — `encounter_experience_<domain>_<agentId>`
- `encounterChains` chain-completion bonus — `chain_mastery_<chainId>_<agentId>`
- `spellActivation` `condition_inflict` — `cond_<agentId>_<template>_<n>` (latent at 30 ticks, but a per-bearer writer by construction)

## The finding that shaped the fix

**Not one of those nodes carried a per-bearer property.** Their `properties` were a pure function of the domain / chain / template; the only bearer-specific thing about them was the id. Every varying quantity — level, acquired tick, source, visibility — was already on the `has_trait` edge.

That is why `HasTraitEdgeProperties` (`TraitAssignmentProperties`) gained **no new field**, against the ticket's Done-when #1. There was nothing left to move: this is a de-duplication, not a migration of state. Adding a field no writer writes would have been dead weight.

Two guarantees the per-bearer node id had been providing for free had to be re-seated on the edge, and both were live defects in waiting:

- **Chain-mastery idempotence.** The old id made a re-entrant grant impossible by construction. It now comes from the bearer's own `has_trait` edge, which is where the existing `alreadyGranted` check already looked.
- **Edge-id collision.** The chain-mastery edge id was `edge_${traitNodeId}`. With the node shared, two agents finishing the same chain would have collided on one edge id. It is now per-bearer.

## Result

`src/engine/traitShape.ts` owns the definition ids and a `findExistingTraitEdge` that accepts the shared id **and** the legacy per-bearer id, so a saved world keeps accruing onto the edge it already holds instead of opening a second one — two edges for one trait double-count capability.

Measured after, same seed and map:

| | before | after |
|---|---|---|
| experience nodes @ t30 | 44 (44 bearers) | **8** |
| experience nodes @ t60 | — | **8, carrying 109 bearings** |
| condition nodes @ t30 | 70 | 70 (unchanged — the seeded catalogue) |

Eight is one per reach domain: the pool is capped by construction, not by tuning. The change also closes a leak — `removeNode` cascades incident edges, so a bearer's death used to strand its experience node in the graph forever with no edge pointing at it.

Expiry needed no work: `conditionDecay` has walked `has_trait` by edge type since THR-761/THR-1143, and every reader (agent profile conditions tab, codex, capability raw-score walk) resolves the definition by following the edge to its target — so shared definitions read correctly with no compatibility code, and the codex can now name a wound once.

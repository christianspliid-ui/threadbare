# THR-2079 — No empty portrait box on The First's page

**Shipped 2026-10-27.** UI Visual Overhaul — Design System v1. Found by the first weekly ux-review (moment *The First's page*).

**What changed.** The *Disposition toward her* section showed a large black box under the First's header portrait, with his name in tiny grey type. It had two causes. `portraitWithDispositionResolver` read `properties.portraitUrl` directly, which is a second portrait resolver (UI Law 3). That property is empty for the seeded First. Then `PortraitSectionRenderer`, given no url, drew an empty frame with the bare subject name (UI Law 4). The fix takes the ticket's "no portrait" option. The Inspector's `SubjectHeader` already shows the subject through `EntityVisual`. So the disposition section carries no url, and a portrait section without art now renders its label and prose with no frame. Item icons and place paintings, which do carry a url, keep their frame.

**Evidence.** `npm run gate` PASS (test, typecheck, build, encounter, god-cards, ui-debt, cli-smoke). `portraitSectionNoEmptyFrame.thr2079.test.tsx` has 3 tests. The resolver ignores `portraitUrl`. A url-less section renders exactly label + prose, with no frame. A section with art keeps its framed `<img>`. Browser-verify ran as the jsdom-render substitution, because the Done-when is structure-shaped and this was an unattended run. The next weekly ux-review re-checks the live frame.

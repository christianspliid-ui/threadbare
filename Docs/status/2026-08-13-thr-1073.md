# THR-1073 — the tier-advancement ramp reaches the player

**Shipped 2026-08-13.** Advancing an artifact charged the same 4 essence at the same 0.20 difficulty whether it was a Mundane trinket becoming Storied or a Mythic relic becoming Legendary. `attachment-tier-content.ts` had authored the whole ramp — `{1:4, 2:8, 3:14}` and `{1:.20, 2:.35, 3:.50}` — but only the tier-1 entries had a consumer, because a `UnifiedActionTemplate` step is static and cannot read the target's current tier. THR-996 imported the constants rather than hard-coding literals and deferred the ramp here.

## The decision: a declarative marker, not a function

The ticket offered three directions. Direction 2 (`difficultyFrom: (target) => …`) was the general one and is the shape this took — but **not** as a function. Templates are serialized into `public/action-catalog.generated.json`; a function field silently becomes `undefined` there, so the published catalog and the running game would disagree about the price, which is the exact drift the generated catalog exists to prevent. It would also put behaviour in a data file (NFP #3).

The codebase already had the right precedent: `step.difficultyContext: 'intel_sensitive'` is a declarative enum the resolver reads to make a step's difficulty depend on world state. `'target_tier_scaled'` joins it, and `essenceCostContext` mirrors it one level up. The two markers sit at two levels because the two numbers do — price is per-template, difficulty is per-step.

Direction 1 (resolver-side cost) was rejected for the reason THR-996 gave: it splits the cost model across two places. Direction 3 (per-tier template variants) triples the catalog rows.

## Three seams, because a price is read in three places

| Seam | What it fixes |
|---|---|
| `targetActions.ts` | The card's price, the affordability gate, **and** the displayed risk line |
| `playerCastDispatch.ts` | What the essence pool is actually charged |
| `unifiedActionResolution.ts` | What the roll rolls against |

The display seam matters as much as the charge: a card advertising 4 while the pool is charged 14 would be a worse defect than the flat price it replaced. The buff pass was re-ordered so Recede discounts the *resolved* price, not the tier-1 one.

`src/engine/targetTierScaling.ts` is the only reader of the tables — no tuning number moved into engine code, and the clamp bounds derive from the table's own keys, so re-authoring the ramp needs no edit there.

## Evidence

Falsification was run, not argued: removing the marker from `artifact.enchant` failed exactly three tests, including the Done-when one at `expected 4 to be greater than 4` — the pre-THR-1073 defect reproduced on demand — while `artifact.empower` stayed green, proving per-template isolation. Full suite 996 files / 15925 tests green; typecheck ratchet unchanged at baseline 3447; 30-tick engine smoke reached tick 30 with 383 agents.

## Deliberately not done

Duration. `TIER_ADVANCEMENT_DURATION[2..3]` is still unconsumed — the draw happens in `createUnifiedAction`, which receives a target *id* but no graph, so scaling it means threading target state through a constructor with call sites across the engine. Wider than this ticket's Done-when, which named cost and difficulty only. Filed as THR-1100 with two approach sketches.

# 2026-09-10 — THR-1114: two actions stop claiming a sphere the cosmology does not have

`SPHERE_NAMES` is the canonical twelve. Two authored action templates carried something else:
`action.secrets.plant_secret` had `sphereAffinity: 'shadow'` — a **Reach** name sitting in a
Sphere field — and `artifact.nullify` had `'void'`, which is neither a Reach nor a Sphere but
nothing in the current cosmology at all.

## The decision, and where it came from

The content call was recorded on the ticket by an attended design session (2026-09-10) against
`Docs/canon/cosmology.md`, with an invitation to veto either alignment. This run implemented it
rather than re-deciding it:

| Template | Was | Now | Canon row |
|---|---|---|---|
| `action.secrets.plant_secret` | `shadow` | **`darkness`** | *"Mystery, shadow, concealment"* |
| `artifact.nullify` | `void` | **`entropy`** | *"Decay, dissolution, transformation"* |

Planting a secret is concealment fuelled by the dark, not an act of intellect — `mind` would make
it the latter, which the `shadow` **Reach** already says it is not. Unmaking an artifact's power is
dissolution; `void` was reaching for an unmaking the twelve already cover. Both canon rows were
read back from `Docs/canon/cosmology.md` before being quoted, so the code comments cite the canon
rather than paraphrasing it from memory.

Neither template is cleared of its sphere. Both actions are fuelled by something, and the field is
read by prerequisite checks and scoring, not only by the Codex.

## What was deliberately not done

The display layer was already correct and is untouched. Adding `shadow` / `void` rows to
`SPHERE_DISPLAY` would have silenced the warning by rendering the wrong data prettily — the
ticket names that as the wrong fix, and it is: the data was what was wrong.

## These were type errors, not only content errors

`sphereAffinity` is typed `SphereName`. Both literals were therefore genuine entries in the red
typecheck baseline, and the ratchet reads **2914 → 2912, DOWN 2** — exactly the count of literals
this change corrects. That is a useful cross-check on the edit: a fix that touched the wrong two
values would not have moved the count by exactly two.

## The corpus invariant, and the three ways it could have been vacuous

The ticket's third Done-when is the durable half: *every populated `sphereAffinity` is a member of
`SPHERE_NAMES`*, pinned across the corpus, "because the two current offenders are only the ones
that exist today". `src/data/__tests__/sphere-affinity-corpus.test.ts` does that.

**Scope.** `UNIFIED_ACTION_TEMPLATES` is one of ~40 exported template arrays across `src/data`.
Sweeping only the array the Codex happens to enumerate would have reported clean while offenders
sat in the faction, army, borderland or thread shards — a guard that reads as corpus-wide and is
not. It globs instead, so a new shard is covered the day it is authored, with no list to extend.

Three things keep it from passing for the wrong reason:

* **A measured floor.** 179 affinity-bearing templates observed across 360 globbed modules; the
  floor is pinned at 150. If the glob ever stops resolving — a moved directory, a renamed export
  convention — the sweep fails loudly instead of passing over an empty set.
* **A falsification arm.** The membership predicate is asserted to still *reject* `shadow`, `void`
  and `star`. Without it, an inverted or mis-typed test passes green over a clean corpus and is
  indistinguishable from a working one.
* **A perturbation before trusting it.** Reintroducing `'void'` fails the sweep naming
  `artifact.nullify -> void`, which proves the glob actually reaches this ticket's own subject.

**One trap worth recording.** `import.meta.glob` *imports* every match eagerly, so the first draft —
which filtered `__tests__` while walking the exports rather than in the pattern — pulled in the
sibling test files and registered **3956 tests into this one file**, re-running the data suite a
second time in 32s. Filtering at walk time is too late; the damage is done at import. The negative
pattern `'!../**/__tests__/**'` is load-bearing, and the test says so where it sits.

The one failure is `scripts/__tests__/check-wiki-freshness.test.ts` — *"resolves the diff base to the
merge base"* — a 5000ms timeout in a git-subprocess test under full-parallel spawn contention. It
passes **40/40 in 1.97s** in isolation. This diff touches no scripts and spawns no processes. It is
recorded as red rather than described as green.

**The Codex claim is a before/after, not an absence.** On `origin/main`'s template file the same
Codex command prints both warn-once lines:

```
[codexRegistry] SPHERE_DISPLAY has no display row for 'shadow' — rendering a plain-English fallback.
[codexRegistry] SPHERE_DISPLAY has no display row for 'void' — rendering a plain-English fallback.
```

and prints neither after. "No warning fired" is only evidence when the warning would have.

## Adjacent finding — not filed, deliberately

The corpus sweep turned up `sphereAffinity` living on a **second carrier** with incompatible reader
shapes. `src/data/artifact-templates.ts` stamps `properties: { sphereAffinity: 'star' }` onto a
`world_tree` landmark, and across the engine that property key is read three different ways:
`agentAttachments.ts` reads it as a **string** (a "tradition"), while `battleAftermath.ts` and
`encounterAftermath.ts` read it as an **object** `{ scores: Record<string, number> }`.

That is a real shape disagreement, but it is a different field on a different carrier from the one
THR-1114 scopes, and whether `'star'` is even wrong there depends on what the key is meant to mean
on a landmark node — a question with no agreed answer to test against. Filing a ticket on that
would be filing a hunch, so it is recorded here instead of guessed at.

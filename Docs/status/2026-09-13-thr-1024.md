# THR-1024 — the detail page becomes a dialog, and keeps the focus it takes

**Date:** 2026-09-13 · **Pillars:** UI · Engine-N/A (no engine module touched) · Content-N/A (no authored content added or edited)
**Issue:** [THR-1024](https://linear.app/threadbare/issue/THR-1024/detailmodal-forks-its-own-overlay-instead-of-composing-modal-no)
**Plan doc:** none — the ticket description is the spec, and the fix shape was decided in [THR-1079](https://linear.app/threadbare/issue/THR-1079/the-modal-primitive-has-no-law-50-focus-contract-so-every-consumer)'s body.

`DetailModal` built its own overlay and set none of the dialog contract: no `role="dialog"`, no `aria-modal`, no `aria-label`, no focus management. Escape and `←` worked, because `DetailModalStackContext` owns a document-level listener — so what was missing was never *dismissal*, it was everything about entering.

That second row is the whole design of this change. THR-1079's finding was that composing `Modal` did **not** fix focus for `EmergenceDilemmaModal`, because the primitive did not have it either — *"the fork was not the reason focus was broken"* — and that N component-level focus traps would themselves be the Law 26/27 defect.

## Why this does not literally compose `Modal`, and why that still honours the decision

THR-1079 wrote the expected consequence as "consumers only need to compose it". That reaches every content-sized dialog. It does not reach this one, because what `Modal` owns *beyond* the contract is a layout the detail stack contradicts in four places:

| | `Modal` | detail panel |
|---|---|---|
| width | `90%` under a `maxWidth` | exact per-kind px (`DETAIL_PLACE_W`, `DETAIL_EVENT_W`, …) |
| height | none — content-sized | exact per-kind px, and the scroll region depends on it |
| cap | `75vh` | `85vh` |
| stacking | one panel, modal band `60` | N panels, `70 + 2·depth`, each backdrop dimming by depth and `pointerEvents: none` beneath the topmost |

Composing would have meant giving the primitive panel-style, backdrop-style and pointer-events escape hatches — which is how a primitive stops being one, and would have moved the fork *inside* `Modal` rather than removing it.

So the contract was extracted instead. `src/components/shared/useDialogFocus.ts` now holds Law 50 — focus-in, Tab cycle, focus-restore — `Modal` calls it, and `DetailModal` calls the same thing. **There is still exactly one implementation of Law 50 in the codebase**, which is the property THR-1079 was protecting; widening it is a change to one file. This mirrors `focusableSelector.ts`, whose own doc comment already frames itself as "one definition, two readers".

The extraction is proved behaviour-preserving by construction: `Modal.test.tsx`'s 19 tests — including its six-case Law 50 suite — pass **unchanged**, with no edit to that file.

Dialog semantics are placed element-for-element where `Modal` puts them (`role`/`aria-modal`/`aria-label` on the backdrop, `tabIndex={-1}` and the trap on the panel), so "follows `Modal`'s contract" (Law 23) is literally true rather than merely claimed.

## The stack detail that is easy to get wrong

`useDialogFocus(panelRef, active)` is passed **`true`** for a panel's whole lifetime, not `isTopmost`.

Gating on `isTopmost` is the obvious reading and it is wrong. Each panel captures the element focused at the moment it opened; for a pushed panel that is a control *inside the panel beneath it*. Deactivating panel N when panel N+1 opens would run panel N's restore, sending focus one level too far out, and then hand panel N+1 the wrong invoker — so popping back would land the player outside the surface they are still looking at. Held across the lifetime, the restores nest correctly: closing the pushed panel returns focus into the panel beneath, and closing the last one returns it to whatever opened the stack. A test pins exactly this.

Trapping needs no `isTopmost` gate either: focus is in the topmost panel and the ones beneath take `pointerEvents: none`, so no other panel ever sees the keystroke.

`aria-modal` **is** per-panel (`true` on the topmost, `false` beneath) — only the panel the player is in claims the page.

## What the tests found

Two Tab-wrap assertions failed on first run with `expected 1 to be greater than 1`, and the cause is a fact about the surface worth recording: **a plain page at depth 0 carries exactly one focusable control.** The back button needs `depth > 0`, the narration button needs prose, the footer CTA needs `hasFullSheet` — leaving only the close button. The wrap is therefore asserted on a full-sheet page (close in the header, "open her sheet ↗" in the footer), which is the ordinary actor card a player opens rather than a contrived fixture, and the one-control case gets its own test that Tab does not escape to the page behind.

12 new tests: dialog role, `aria-modal` true/false across a stack, `aria-label` from the page name, absence of any dialog when the stack is empty, focus-in, focus-restore-to-invoker, focus-hand-back into the panel beneath, Tab wrap in both directions, the single-control hold, and trap containment at depth 2.

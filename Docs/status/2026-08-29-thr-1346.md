# THR-1346 — the matrix was not dead, it was indexing the wrong tier

**Shipped 2026-08-29.** Engine pillar. Content and UI N/A — the distance matrix reaches no
content table and no component; it feeds two engine consumers on the per-tick path.
Deferral filed at THR-1344's closeout, by the preset sweep that ticket's golden comparison
needed.

## The ticket's premise was wrong, and the wrong arm was the cheap one

THR-1346 was filed with two findings. The second was exactly right. The first was not, and
had it been acted on it would have removed every agent-to-agent social encounter in the
game.

Finding 1 said `buildDistanceMatrix` was *"read by nobody"*, evidenced by a grep showing
`getDistance` imported in two files and called in neither. That grep is accurate. The
conclusion does not follow, because **neither consumer uses the accessor** — both want a
whole row rather than a point lookup, so both reach past `getDistance` into the field:

```
socialEncounterGeneration.ts:564   const sourceDistances = distanceMatrix.distances.get(sourceLocationId);
idleBehavior.ts:130                const row = distanceMatrix.distances.get(agentLocationId);
```

`findVisibleAgents` gathers every location within `VISIBLE_AGENT_MAX_HOPS` and then every
agent standing at one — it is the sole source of agent-to-agent social encounters.
`deriveAmbitionTarget` picks an ambitious idle agent's drift destination. Both are called
from `phaseAgentDecision`, on the per-tick path. The ticket's arm 1, *"retire the
producer"*, was listed as the cheapest option and was the destructive one.

This is the debugging protocol's *verify the noun before the verb* at the level of a
ticket premise: the dead symbol was `getDistance`, not the matrix. A dead accessor is not
a dead producer when consumers can reach the field directly.

## What was actually broken

Finding 2, and it was worse than harmless. `buildDistanceMatrix` walked
`graph.getNodesByType('location')`, which since the THR-1183 tier unification returns
**both** place-tier locations and sublocations. Sublocations outnumber real settlements
about 2:1, so they consumed the cap, and everything past `MAX_DISTANCE_MATRIX_SIZE` (1200)
by insertion order silently got no row at all.

Measured on generated worlds, seed 42, tick 0:

| preset | place-tier | sublocations | all `location` nodes | place-tier truncated |
| ------ | ---------- | ------------ | -------------------- | -------------------- |
| small  |        131 |          292 |                  423 |                    0 |
| medium |        214 |          440 |                  654 |                    0 |
| large  |        542 |         1086 |                 1628 |              **235** |
| epic   |        791 |         1758 |                 2549 |              **391** |

235 real settlements on `large` had no matrix row. To both consumers a missing row reads
as *"no other location is near me"* — no cross-location social encounters, no ambition
drift target. `?view=game&seeded` derives a `large` map, so the deployed build has been
running that degradation.

## The fix

One line: index `getPlaceTierLocations(graph)` instead of the bare
`getNodesByType('location')`. Place-tier counts sit under the cap on every preset with
~35% headroom on the largest, so the overflow closes without raising the cap — and it is
the correct read regardless, since hop distance from a settlement to a room inside
*another* settlement is not a quantity either consumer wants.

Excluding sublocations is behaviour-neutral for an agent standing at one. Measured across
all four presets, **zero** sublocations carry an `adjacent` edge in either direction, so a
sublocation's row was always exactly `{self: 0}`; and both consumers derive *"which other
locations are near me"*, for which a self-only row and a missing row are the same answer.
`findVisibleAgents` seeds its set with `sourceLocationId` before consulting the row;
`deriveAmbitionTarget` skips `locId === agentLocationId` and returns `null` either way.
That equivalence is pinned by test rather than left in prose.

The two dead `getDistance` imports went with it. `getDistance` itself stays: it is the
module's documented point-lookup API, it is tested, and the reason it has no caller is
that both consumers need rows — a future point-lookup consumer should use it rather than
hand-rolling a third direct field read.

## Falsified before trusting

Both halves. The unit and generated-world assertions fail on the pre-fix line — 8 of 21
red, including every generated-world case. At the live layer, reverting the one line and
running `npm run cli -- --seed 42 --map large`:

```
[DistanceMatrix] Place-tier location count (1628) exceeds MAX_DISTANCE_MATRIX_SIZE (1200).
428 locations will not be indexed. ...
[DistanceMatrix] Place-tier location count (1736) exceeds ... 536 locations will not be indexed.
```

With the fix, `large` is silent for 30 ticks.

## The test that could not have caught this

`distanceMatrix.test.ts:174` read `expect(MAX_DISTANCE_MATRIX_SIZE).toBe(1200)` — the
constant on both sides of the assertion, unfalsifiable by construction. It passed for the
entire life of the overflow it was nominally guarding, because it pinned the number rather
than the behaviour, and because every other assertion in the file runs on a hand-built
graph that supplies its own location count.

Replaced with an assertion about what truncation actually *does*, plus a
`generated worlds` block that runs `initializeGameState` on `medium`/`large`/`epic` and
checks that every place-tier location is indexed with headroom under the cap. The Done-when
demanded generated worlds specifically, and it was right to: this class of defect is
invisible to fixtures.

One assertion in that block deliberately guards the *guard* — `expect(subs.length)
.toBeGreaterThan(0)` — so that if sublocations ever stop appearing under
`getNodesByType('location')`, the exclusion test fails loudly instead of passing over an
empty population.

## CLAUDE.md

The Load-Bearing Architectural Decisions entry claimed the cap *"now covers all supported
presets (`large` ~584, `epic` ~805)"*. Those figures are close to today's **place-tier**
counts (542 / 791) and were almost certainly measured before THR-1183 folded sublocations
into `getNodesByType('location')` — they were never a measurement of what the matrix was
indexing. Corrected against the fresh measurement, and the entry now states plainly that
the matrix is live, names both consumers, and warns that grepping for `getDistance` callers
will tell you otherwise.

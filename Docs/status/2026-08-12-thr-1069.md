# THR-1069 — the legacy notification branch is unreachable, and now provably so

**Shipped 2026-08-12.** Decision ticket, resolved as *dead branch, pinned rather than pruned*.

## What was asked

THR-1068 wired auto-resolve expiry for `sourceSystem: 'unified_action'` step notifications and
deliberately excluded the legacy half, reasoning that a resolved *legacy* record drops out of
`generateEncounterNotifications`' dedup key set, so expiring one while its `encounterProgress`
entry is still `active` would re-emit it next tick — churn rather than a fix. THR-1069 was the
excluded half, and it asked reachability **first**: run a sweep, and if the legacy pipeline no
longer produces threaded notifications, prune the branch instead of fixing it.

## The finding

**The branch cannot fire at all, and the reason is structural rather than statistical.**
`phaseAgentDecision` reaches its legacy arm only on `template && !unifiedTemplate`, where
`template = getAnyEncounterById(id)` and `unifiedTemplate = getUnifiedTemplateById(id)`. But
`getUnifiedTemplateById` is `index.get(id) ?? getAnyEncounterById(id)` — a **strict superset**
of the lookup that produced `template`. Whenever `template` is truthy `unifiedTemplate` is
truthy too, so the first arm always wins and the `else if` is unreachable by construction.

The other two writers of `state.encounterProgress` are inert for their own reasons:
`initiateEncounter` (`src/engine/encounter.ts`) has **zero production callers** — only tests —
and `debugEncounterTools`' `mode: 'legacy'` path is gated on the identical impossible condition,
because its `resolveTemplate` feeds the same superset relation.

**The empirical arm agrees, with a control.** A 60-tick CLI sweep (`--seed 42 --map medium`)
recorded `encounterProgress = 0`. That zero is only worth quoting because the same run recorded
**52 unified actions across 33 distinct templates** — agents were demonstrably deciding and
acting the whole time. The notification count in that run is *not* usable evidence: the CLI seed
carries no ascendant thread, so `phaseEncounterVisibility` returns early at `threadedAgents.size
=== 0` and every notification reading is a vacuous empty-population pass. `encounterProgress`
is written upstream of threading, which is what makes its zero meaningful where theirs is not.

## Why pinned, not pruned

The ticket offered "prune as dead" as an outcome, and the sweep's zero appears to authorize it.
Two facts moved the verdict.

**The unreachability rests on a single `??`, and 36 ids depend on it.** Measured across the eight
pools `getAnyEncounterById` consults: 260 distinct ids, of which **36 are in no unified pool at
all** (`social_scene.political_audience`, `social_scene.recruitment_pitch`, …). Those resolve
*only* through the trailing `?? getAnyEncounterById(id)` fallback. Delete that one expression and
`unifiedTemplate` goes undefined for exactly those 36 while `template` stays truthy — the dead arm
goes live, and the churn loop THR-1068 described stops being hypothetical. A prune removes the
branch but leaves that resurrection path entirely unguarded.

**The branch is load-bearing for the test suite.** `phaseEncounterVisibility.test.ts` builds its
states from `encounterProgress` and asserts the notifications they produce; pruning the branch
deletes that file's subject. Pruning production code that no live path reaches, at the cost of a
pinned test file, on a Low-priority deferral, is a poor trade against NFP #6 — the old shape does
not block progress, it is simply inert.

So the guard stays, now for the stronger reason: **it excludes a population that is empty**, and a
new contract test fails the moment that stops being true.

## What shipped

`src/engine/__tests__/legacyEncounterBranchUnreachable.test.ts` (new, 3 assertions):

1. **Non-vacuity floor** — the sampled pool set is ≥ 200 ids, so the assertions below cannot pass
   over an empty set if a refactor empties the pools.
2. **The branch condition itself, evaluated over the whole corpus** — no id satisfies
   `getAnyEncounterById(id) && !getUnifiedTemplateById(id)`. This *is* `phaseAgentDecision`'s
   legacy arm, asserted dead.
3. **The fallback is load-bearing** — at least one pool id sits outside the index
   (`UNIFIED_ACTION_TEMPLATES ∪ ASCENDANT_POOL_BEAT_TEMPLATES`, which reproduces the
   module-private index) and still resolves.

**Falsified, not merely green.** Removing `?? getAnyEncounterById(id)` from
`getUnifiedTemplateById` turns assertions 2 and 3 red (`expected undefined to be defined`); the
file was restored and re-verified green.

The three comment sites that carried the speculative justification now carry the proven one: the
`expireOverdueEncounterNotifications` doc block, the guard line in
`isEncounterNotificationOverdue`, and — the silence the ticket actually named — the dedup filter
in `phaseEncounterVisibility`, which explained why `aftermath` and `unified_action` are retained
and said nothing about why legacy is not. The existing exemption test's name asserted the
superseded reason ("whose dedup set would re-emit them") and now states the real one.

## Left alone deliberately

`getUnifiedTemplateById` and `getAnyEncounterById` return **different objects** for 83 of the 260
ids — the same id present in both the THR-811 index and a content pool. That is not this ticket's
business and no behaviour here depends on it, but it is a real duplication worth a look if a
template ever appears to ignore an edit.

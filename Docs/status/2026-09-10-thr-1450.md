# 2026-09-10 — THR-1450: the harvest pays

`use × Location` — the active harvest THR-1439 shipped as the thing that makes a held
Location worth holding — banked **zero** in every live run since it landed. The costs
still fell: the town lost prosperity, the holder lost standing with it. Only the payoff
was missing, on every band, every time.

## The cause, and why it hid

The harvest is an **instant** cell (`UNDERTAKING_VERB_DURATION.use = [0,0,0]`), so its
completion has no checkpoint and carries no band. `yieldBandScale` read that absence as
the failure arm and multiplied the lump by 0.

The contract said otherwise. `executeInstantMutation`'s own `outcome` doc has always
read *"the instant path has no checkpoint, so its readers take the plain-success row"* —
and three readers obeyed it (`CONDITION_TIER_CAP_DEFAULT`, `CURSE_DURATION_TICKS_DEFAULT`,
`plotDeath`'s `?? 'success'`, each equal to its table's `success` row). Two did not:
`yieldBandScale`, and `maybeSpawnSiteClue`, which refused a survey's clue for the same
reason. The convention was stated in a comment and left to each reader to keep, so the
readers that quietly stopped keeping it looked exactly like the ones that never had.

## The fix

The decision moved to the one boundary the bandless path enters. `executeStrategicAction`'s
instant arm now stamps `INSTANT_COMPLETION_BAND` — a named constant, typed by
`StepOutcome`, whose doc block is the single statement of the convention. Every reader is
handed a real band; none re-derives the rule, so none can drift out of it again.

Deliberately **not** changed: the multi-tick arm still passes a possibly-absent
`lastCheckpoint?.band`. There the absence is a *lost reading* rather than a terminal
nothing could miss, and the failure arm is correct — the two cases are now distinguished
at the call site instead of being conflated inside each reader.

`observe`, the other instant verb, was swept as the ticket asked. Its two strict readers
gate on `critical_success`, so the plain-success row leaves them unchanged; its clue
reader was the second defect and is fixed by the same stamp.

## Evidence

Proven by a **live controlled arm** on one seed, not by a fixture. Identical seed-42
medium world, identical setup, 150 ticks, fix toggled:

| | `use × location` completions | `draw_yield` lumps banked |
|---|---|---|
| with the fix | 4 | **5** |
| without | 4 | **0** |

The cell ran either way; only the payout differed. `drawYield` emits its `wealth_delta`
trace *only* when `lump > 0`, so the trace's existence is the non-zero lump:

```
t41  [wealth_delta] Lowen drew the yield of Wraithwood
t80  [wealth_delta] Oswen drew the yield of Horseford
t97  [wealth_delta] Lowen drew the yield of Wraithwood
```

The unit tests were falsified the same way before being kept — reverting the call-site
stamp turns the banked lump from 6 to 0.

## The supply fact this uncovered — worth a look

The live proof needed a constructed world, and that is itself a finding. In a stock
seed-42 medium run at tick 30, **no mortal holds a healthy town**: of 117 `controls`
edges, 114 belong to factions and the 3 individual-held Locations are two wilderness
hexes and a ruin, none carrying a `prosperity` value at all. Top prosperity anywhere is
~45, median 10, and every settlement worth harvesting is faction-held.

So the harvest was doubly unreachable: it paid nothing *and* almost nobody was in a
position to try it. This fix closes the first half only. The second is a supply gap in
who comes to hold a Location — the same census THR-1287 recorded — and it is not this
ticket's to close. Flagging it because a lever that now works correctly is still a lever
almost no mortal can pull.

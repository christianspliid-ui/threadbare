# THR-1447 — the aftermath event id's uniquifier was a saturating quantity

**2026-09-10 · Engine · Bug · Encounter Experience**

## What was wrong

Four aftermath event mints in `encounterAftermath.ts` suffixed their `TickEvent` id with
`nextRecentEvents.length`:

```ts
id: `enc_after_${reaction.id}_${tick}_${nextRecentEvents.length}`,
```

That reads as a uniquifier and is not one. `appendRecentEvent` slices to
`MAX_RECENT_EVENTS` (100), so once the buffer fills the suffix is the constant `100`
**forever** and the id degenerates to `<prefix>_<reactionId>_<tick>` — which any two
resolutions of the same reaction on the same tick both mint.

The reported key was `enc_after_anchored_react_deepen_the_anchor_53_100`. Its trailing
`100` is not the hundredth event; it is the buffer at its fixed point.

This is why the defect is invisible early and appears only deep into a session: below
saturation the length really does vary, so every short run and every unit fixture built
without a full buffer passes. It surfaced at tick 140.

All four sites shared the shape — `enc_after_` ×2 (the `recent_event` and
`intel_referenced_prose` branches), `drift_register_`, `formative_mark_`. Only the first
had been observed; the other three are the same defect and were fixed with it, since
narrowing the fix to the observed prefix would have left three live minters behind.

## Why it matters

React answers a duplicate key by duplicating **or omitting** a child. This is a list the
player reads and chooses from, so an omitted row is an authored choice the engine offered
and never showed — a failure that announces itself nowhere and that no test asserting on
reaction *data* can see.

## The diagnosis the ticket's lead did not reach

The ticket pointed at `EncounterVeil.tsx:1303` and `DivineReceiptModal.tsx:196`, "two
sites [that] render reactions keyed by `reaction.id`", and asked whether reaction ids are
minted per template rather than per offer.

Neither site is involved. Both key on the bare offer id
(`anchored_react_deepen_the_anchor`); the colliding key carries the `enc_after_…_53_100`
mint, so the noun in play is a **`TickEvent`**, not a reaction offer. The mint was the
defect, as the ticket's second branch allowed — but one level down from where it looked.

## The fix

`SimulationRuntime` gains `aftermathEventSeq`, a monotonic session counter stamped in
place of the buffer length. The runtime is the architecturally correct home: it already
owns the session's other monotonic counters, and the engine-caches-per-session rule
forbids the module-scope alternative, which would carry one playthrough's sequence into
the next.

It is deliberately **not** reset by `resetRuntimeCaches()`, matching the version counters
— monotonic within a session is the entire guarantee, and restarting at 0 mid-session
would re-open the collision. Determinism (NFP #3) holds: the counter advances in the
engine's own fixed resolution order, so the same seed replays the same ids. No code parses
these ids — verified — so the suffix's changed meaning is safe.

## Evidence

The revert-check is the load-bearing proof: with the mint restored to
`nextRecentEvents.length`, the new render test fails carrying **the ticket's exact error
string and exact key**:

```
Encountered two children with the same key, `enc_after_anchored_react_deepen_the_anchor_53_100`.
```

Red baseline before the fix: 2 of 3 engine assertions failed — two byte-identical ids, and
12 firings of one reaction leaving **89 unique ids out of 100**, i.e. 11 events silently
collapsed.

Tests are falsifiers, not confirmations. Every one saturates the buffer first; an
unsaturated fixture passes against the unfixed code and proves nothing, and both files say
so where a later reader will need it. Two guard-the-guard arms assert the events were
actually minted, so the console assertion cannot pass on an empty list.

- `encounterAftermath-eventIdUniqueness.test.ts` — engine-level, 3 assertions.
- `RecentEventsView.test.tsx` — a **contract test across the engine→UI seam**: the real
  `applyEncounterAftermathReaction` mints, the real component renders. Uniqueness is a
  contract *between* the two that neither side can check alone — an engine test proves the
  ids differ, a UI test with hand-written fixtures proves only that React renders two rows.

## Two coverage gaps this found

**The CLI cannot falsify this.** A seeded 140-tick large-map run reports zero duplicate
ids — and zero `enc_after_` events at all. The aftermath path needs a threaded agent
choosing a reaction, which the CLI world has none of, so a whole-run uniqueness probe
there is **vacuous** for these four producers. It passes on an empty population and reads
exactly like a clean bill of health. Logged as #1001.

**The existing whole-run guard does not cover them either.** `tickEventIdUniqueness.test.ts`
(THR-853) asserts no `TickEvent` id repeats across a 300-tick run, written against the
*same failure mode* — a minter whose uniquifier does not distinguish — and explicitly
generalized so "any future tick-less minter fails it on arrival". It was green on `main`
while this defect was live, which is the proof that its population never reaches the
aftermath minters. Its generalization was sound; its reachability was not.

## Gates

Suite green (1198 files, 19729 tests), heavy green (29 files, 201 tests), build green.
Ratchet baseline refreshed 2912 → 2914, justified: both net-new errors are one instance
each of the repo-wide `as GameState` fixture idiom, identical to the error the file they
were copied from already contributes to the THR-489 baseline. The alternatives are worse —
`as unknown as GameState` suppresses shape checking entirely, and fabricating `cosmology` /
`worldSoul` objects to satisfy the cast invents shapes the engine never makes.

Browser-verify via the sanctioned `jsdom-render` substitution: `preview_start` is refused
in unattended scheduled runs, and the ticket's Done-when as literally written (a browser
console tail from a 140-tick run) is unreachable here. The render test discharges it on
the same surface and reproduces the exact reported error on revert, which a console tail
could not do repeatably.

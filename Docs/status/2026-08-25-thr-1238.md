### THR-1238 — the "Power" family lands in the UL, and the index footer's tally was seven terms stale (2026-08-25)

**What was ratified.** Christian ratified the Power vocabulary in chat on 2026-08-25 during the wayfinder grilling on the Powers & Spellcraft map (THR-1226). **Power** is the player-facing family name for a carried, capability-granting thing an entity holds — an agent, The First, a monster, a faction — with three variants: **Spell** (learned from a magic tradition; carries an agency, an arena, and a price), **Bestowal** (god-given), and **Innate power** (anatomy, stamped at seeding). This ticket lands that vocabulary in the glossary; it writes no code.

**The reconciliation is the substantive half.** `Effect` stays the **substrate** word — the `AttachmentEffect` primitives in `src/types/effects.ts` that powers, items, blessings and curses are all assembled from — and is never player-facing as a family name. `Attachment` stays the broad **code umbrella** (`AttachmentCategory`, eight members). The two-level ambiguity where "effects" means both the atoms *and* the family built from them is exactly what "Power" was minted to prevent, and **"Effects" was considered for the family name and rejected** — recorded in the Effect entry so it is not re-proposed.

**Scope correction, made and recorded rather than silently absorbed.** The ticket's Done-when says *"Effect and Attachment entries gain a disambiguation line."* **Neither entry existed** — the UL had no `Attachment` and no `Effect` term at all, in any shard. A See-Also pointing at a non-existent entry is a dead link, so both were **created** carrying the disambiguation as their core content rather than amended. Six new terms, not four.

**Three code-vs-vocabulary traps, all recorded in the entries because each is the kind of thing a reader will otherwise get wrong once.** (1) **Power is a conceptual family, not a code identifier** — there is no `'power'` `AttachmentCategory`; its variants sit as *sibling* members (`'spell'`, `'bestowed_power'`), so code meaning "any power" enumerates the variants. (2) **`bestowed_power` does not get renamed** — Bestowal is the player-facing name and the entry is the mapping; this vocabulary landing implies no rename ticket. (3) **Innate power has no code anchor at all yet** — unlike its two siblings there is no category member for it, so content meaning it must not reach for an existing category as a stand-in.

**Two name collisions with the trait layer, which is why the family was seated in `Traits.md`.** The Traits shard already carries a `bestowed` **trait category** and an `innate` **trait category**. The collisions are exact in wording and empty in substance — a bestowed *trait* is a name the world recognises and is inert on its bearer, while a bestowal is a power carrying effects; an `innate` trait is worldgen-minted, while an innate power is stamped at seeding. Both entries state the distinction against the category they are not. Seating the family beside the terms it collides with beat opening a ninth shard, which would have been a structural change the ticket did not ask for.

**Then the footer turned out to be lying.** The README's version line claimed *"127 terms: 123 canonical, 2 deprecated, 1 rejected, 1 proposed."* Measured before any edit of mine, the tree held **134** — and **4** deprecated, not 2. The two uncounted deprecations are `Codex` and `Ready for Codex`, marked `deprecated` in `Coordination.md` when THR-486 retired that lane on 2026-06-23 and never reflected in the tally, so the footer had been wrong for about two months. Index *coverage* held throughout (134 links against 134 terms) — the terms were indexed as they landed and only the count went stale, which is a different defect from the THR-806 anchor drift and is kept distinct in the prose.

**This is the third recorded staleness of that line and the second time it undercounted a status nobody was looking for**, which the footer itself documents at length while being wrong. The remedy was already sitting unused: **`npm run generate-ul-dashboard` prints the authoritative count on every run** — `wrote …ul-dashboard.generated.json (140 terms across 8 shards)` — computed from the same `**Status:**` parse the footer is meant to reflect, and it runs on every UL edit because the JSON is a committed artifact gated by `check:generated-freshness`. The count was produced every time and never read back into the prose. Both that line and the one-command per-status split are now written into the footer, along with a per-shard census so the next drift is cheap to localise. Logged as impediment **#757** with a retro candidate: a two-line assertion in the generator comparing its count against the footer would close the class permanently.

**Result: 140 terms across 8 shards, 140 of 140 indexed** — confirmed independently by the generator's own count line, not by my arithmetic.

**Verification.** Docs-only track, and only the docs-only track: `npm run classify:diff` → **docs-only** (the regenerated `src/data/ul-dashboard.generated.json` is doc-excluded by the THR-922 rule, and is the only non-`Docs/` path in the diff). `check:generated-freshness`, `check:impediment-ids`, and `lint:plan-doc -- --staged` run; `npm test`, `check:typecheck` and `vite build` deliberately **not** run, per the THR-917 two-track rule — there is no code in the diff for them to fail on. The generator's 7 `unresolved_see_also` warnings are all pre-existing and none names a new term.

# THR-1068 — `autoResolveTick` gets the consumer it never had

**Shipped 2026-08-10.** A deadline was written on every `auto_resolve` encounter notification since TB-035 and never read back. `RETINUE_VIGNETTE_TIMEOUT` named a timeout that had never fired.

## The open question, and why it did not go to Christian

The ticket filed this as *"a design call, not only a repair"* — expire the unattended beat, or let it queue — and asked for the intent to be recorded before wiring. It turned out to be a **technical verdict**: the intent is already recorded in four places in the tree, and all four agree.

* the attention mode is named **`auto_resolve`**
* `RETINUE_VIGNETTE_TIMEOUT` is documented *"Ticks before retinue vignette auto-resolves"*
* `autoResolveTick` is documented *"Tick when auto-resolve fires (null for pause mode)"*
* THR-880's comment in `buildEncounterNotification` describes forced visibility as popping the modal *"rather than silently auto-resolving after RETINUE_VIGNETTE_TIMEOUT ticks"*

Nothing anywhere describes an unattended beat as queueing. Reading a spec that already exists is not a design decision, so this did not need a chat gate.

The ticket's second worry — *"the outcome should still resolve through the normal path so consequences fire, not just flip a flag"* — dissolves on inspection. A notification is a **player-facing record**, never the mechanism by which an encounter resolves: the `UnifiedAction` advances and concludes in the tick pipeline whether or not anyone looks. Every pre-existing resolve site (disregard, acknowledge-aftermath, intervention commit) writes that single flag and mutates nothing else. So flipping it *is* the normal path; expiry costs the player the offer to intervene in a moment that has already passed, which is precisely what choosing `auto_resolve` means, and costs the world nothing.

## What shipped

`expireOverdueEncounterNotifications` retires overdue records, called from the orchestrator's State Cleanup immediately **before** the existing `NOTIFICATION_RETENTION_TICKS` trim — so a record that is both overdue and beyond retention reports as *expired* rather than silently vanishing. One aggregate trace per tick, never one per notification.

Two exemptions, both deliberate and both pinned by tests so a later completeness sweep cannot read them as oversights:

* **Aftermath is exempt.** At this tier the badge is the player's *only* route into a concluded beat (`isBadgeWorthy`, THR-943). Expiring the conclusion record 8 ticks after it appears would delete the only surface reporting what happened — narrative loss (NFP #5) at the tier that opted out of interrupts precisely so outcomes would be *reported*. An unread conclusion badging its row is the badge working. Those records still leave state via the 50-tick trim, so their fate is deterministic too; it is just a different deadline. They keep a non-null `autoResolveTick` because that field also carries the "do not auto-open" meaning — nulling it would make every aftermath interrupt at the one tier that must never be interrupted.
* **Legacy-sourced steps are exempt.** `generateEncounterNotifications` keeps resolved records in its dedup key set for `unified_action` and aftermath, so retiring one there is idempotent. Resolved *legacy* records drop out of that set by design, so expiring one while its `encounterProgress` is still active would re-emit it next tick, which would expire, which would re-emit — churn wearing a fix's clothes. Filed as THR-1069, which asks the reachability question first: if the legacy pipeline no longer produces threaded notifications, the answer is to delete the branch, not fix it.

The veil's countdown is clamped at zero and reads **"auto-resolving now"** at the deadline instead of `in 0 ticks`. Engine-side expiry makes a negative unreachable in a live run; the clamp holds anyway, because a surface that renders a lie whenever its upstream slips is a defect on its own terms.

## Two corrections to the ticket's own account

* **"Accumulates forever" is imprecise.** The orchestrator has always trimmed notifications older than `NOTIFICATION_RETENTION_TICKS` (50), so the pile was bounded at ~50 ticks, not unbounded. Still a defect — 50 ticks against an authored 8 — but the badge did drain, at six times the intended deadline.
* **The overdue backlog also cost per-tick work.** `phaseAscendantHandFilter` iterates every unresolved non-aftermath `unified_action` notification each tick and runs template adaptation plus a forecast computation per record, so stale records were not only visual noise.

## How this was evidenced, and what could not be

Accepted as a **headless engine sweep**, not a browser one, and the reason matters for the next person who tries.

The live route could not produce the population. On `?view=game&seeded&size=medium` the seeded First generated **no encounter at all** across 120 driven ticks (`activeEncounters: []`), and `__DEBUG.inspectEncounterPipeline` reads a GameState snapshot that **lags `__DEBUG.tick()`** — it reported `tick: 0` while the engine stood at 120. Either fact alone would have made a browser reading of "zero overdue" an empty-population pass wearing a verdict's clothes. Logged as impediment #521.

So the wiring is pinned where it can actually be falsified: an integration test drives **`runTick`** with the exact measured shape — three notifications 32, 36 and 37 ticks overdue at tick 113 — and asserts the overdue count returns to zero, the three exempt records survive a real tick, and a deadline still in the future is untouched. That last assertion is the guard against a "fix" that drains the badge by retiring everything in sight. The unit suite covers the predicate; this covers the thing that was actually missing, which was a caller.

## UI Laws judgment

Judged on the `EncounterVeil` surface as composed (1920×1080, `?spawn=encounter.slice.unsafe_bridge`): **Law 1** — Vara carries avatar, tooltip and link; `Stone` renders as a concept chip. **Law 14** — `TOLL` / `MARK` / `resolved` are display vocabulary, no raw keys. **Law 21** — the named agent links and `Show on map` routes. **Law 37** — the aftermath wears the same chrome as its steps (title, context strip, step position). **Law 13 — pre-existing violation found and filed, not introduced:** the light-tier strip renders `auto-resolves in 4 ticks`, a raw numeral outside the ratified persistent-chrome exception. This change reduced its blast radius (no more negatives) without removing the numeral, which needs a duration word scale Threadbare does not yet have. **THR-1070.**

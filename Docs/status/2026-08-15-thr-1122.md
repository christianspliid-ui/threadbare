# THR-1122 — attachment names get their hover tier, and the registry stays context-free

**Shipped 2026-08-15.** Law 17 asks that every concept word carry a tooltip from the one
registry. `resolveTooltip` routes strictly by prefix and had no member covering attachments —
so a condition, blessing, curse, bestowed power or possession named on a player surface could
not carry a registry tooltip at all. The ids were not unregistered; there was no namespace to
register them in. THR-1120 had already landed the *link* tier (a chip's `wounded` opens the
attachment sheet); this is the *hover* tier, and it completes the concept: image N/A, link yes,
tooltip yes.

## The finding that shaped the design — the obvious bridge does not work

`src/engine/attachmentTooltip.ts` already exists and formats attachment data well, but it takes
a data **object**, so it is unreachable from any surface holding only an id — which is every
prose/segment surface, including the consequence chip. The ticket's suggested bridge was
"resolve the template node from the graph, then delegate". **That would have shipped a prefix
nothing could reach.** `Tooltip` calls `resolveTooltip(id)` with **no context**; a graph-bearing
prefix is therefore invisible to the component that draws every tooltip in the game. `agent.*`
is exactly that shape and pays for it by being excluded from `conceptTooltipIds.test.ts`'s
Law 17 corpus sweep by hand — a Law 17 gate that cannot see the one prefix most likely to dangle.

Attachment templates do not need the graph. They ship as static `GraphNode[]` literals and are
*seeded into* the graph at construction (`seedEncounterTraitDefinitions`, the reward and starter
catalogs). `attachmentTemplateIndex.ts` reads the same source the graph is built from — the way
`sphere.*` and `reach.*` read `world-model.json` — so `attachment.*` resolves with no plumbing
and is covered by the corpus sweep like every other prefix. A test asserts the no-context call
directly, so a later "improvement" that threads a graph through fails and says why.

## One prefix, not one per subcategory

`attachment.<templateNodeId>` — `attachment.trait.condition.wounded`. The suffix is the
template's own id, so one arm covers conditions, blessings, curses, bestowed powers and
possessions instead of four prefixes that would each need the same lookup. 183 templates index
and all 183 resolve. Masteries are deliberately **not** indexed — they are seeded trait
definitions with no attachment sheet, and `attachmentDetailFromNode` rejects them anyway, so
`attachment.trait.mastery.*` correctly resolves to nothing rather than offering a hover into a
concept class this prefix does not own.

## The body line is the plain register, never `mechanicalSummary`

The single most load-bearing decision, and it is a Law 13 one. `mechanicalSummary` is where this
corpus keeps its numbers — `'-0.05 Iron (decays toward 0 over 24 ticks, self-removes on heal)'` —
so it is the sheet's field, not the tooltip's, and is unreachable from this arm. Precedence is
`description` → `flavorText` → `name`: conditions and bestowed powers carry a description,
reward possessions carry only flavour, and a name is never empty (Law 14 — no blank slot). Had
the arm reused `resolveAttachmentTemplateDetail`'s own precedence, which leads with
`mechanicalSummary` because a *sheet* wants mechanics, every possession tooltip would have shown
the player a raw magnitude. **A sweep asserts no resolved description contains a digit**, over
the shipped corpus rather than a sample, so the failure mode is caught at authoring time.

Three further fields are omitted for the same class of reason and the omissions are tabled in
the source: `ticksRemaining` (per-bearer edge state, THR-784 — a template has none),
`actionTriggers` (renders a `%` chance — Law 13), `lossCondition` (an internal key like
`breakable` — Law 14). Formatting still delegates to `resolveAttachmentTooltip`, so a concept
word and the row it names read identically — one formatter, one registry entry point, which is
the Law 3 half of the ticket.

## The noun was the concept word with nothing on it

The Done-when says "a consequence chip naming a granted condition renders a hover tooltip". The
chip's sentence-decoration path only ever reached words inside prose — but the place a chip most
literally names the condition is its noun (`SCAR · WOUNDED`), rendered as a bare uppercase span
with neither tooltip nor link. Law 17 holds on the surface **as composed**, not on the prose
alone, so the model gained `nounTooltipId` and the veil draws the hover tier there.

The id is **derived, not authored**: a concept declaring `visualKind: 'attachment'` already
carries the template id in `entityId` (THR-1120), so asking ~12 call sites to repeat it in a
second field is where drift starts. Derivation is a fallback and never a rewrite — a test
falsifies that by pinning an authored `ui.standing` noun surviving untouched, and another pins
that a concept naming an agent acquires no `attachment.*` id, which would be a dangling id on a
node that is not an attachment.

## Fail-open, and the underline only where the registry can answer

An id outside the index resolves to `null` and warns **once** (a per-call warning would bury the
console — `tooltipResolves` runs on every render of every segment). The surface gates its
underline and its focus stop on `tooltipResolves`, so an unshipped template stays plain text
rather than becoming a dead link that looks live (Law 21), and the raw id never reaches the
player (Law 14). Both faces are asserted.

## Browser-verify: jsdom substitution

`preview_start` was refused with the unattended string (impediments #546 ×10, #574) and the
Playwright route presumes a running server, so both are closed. The substitution is jsdom render
assertions on the real `EncounterVeil` — and it is at the *adequate* pole of impediment #593's
scale: this diff adds no layout, it changes a `<span>` into a tooltip-wrapped `<span>` inside an
existing flex row, so overflow and the viewport contract are not reachable by it. The pixel pass
is not filed, for that reason; THR-1127 already owns the ascendant bar's, and THR-1125 the veil's.

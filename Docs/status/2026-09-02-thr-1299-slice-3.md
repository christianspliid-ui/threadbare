## What the player sees

A followed mortal's undertaking says something — a costly step, trouble, a doubling-down, an abandonment, a finish — and the world stops. The card wears the encounter family's chrome (Law 37): the mortal's portrait, the work's name (christened where one exists — *The Shadow-shade Shrine*, not *Found Shrine*), the class word, where the work stands as filled dots and a progress word, and the band the checkpoint landed on. Two lines of narrator prose. Then only the state that moved, as `CATEGORY · noun` chips. Then, while the work is still live, the god's hand: *Inspire the Work* / *Sow Doubt*, armed on the first press and fired on the second (Law 48), blocked inline when the pool cannot pay. The footer says *Time holds while you read this* (Law 52). Acknowledge is one reversible click — the record stays for the badge to count.

## The consumer, and why collation is by construction

GameView holds one `pendingMoment` slot. It fills from `nextInterruptMoment(queue)` **only while no other interrupt surface is open**, and the card **renders only while that stays true**. That single gate does everything the review asked of collation (M4, Law 49): an encounter that auto-opens in the same tick wins the race because its scan runs first and flips the gate; a card already up hides behind a veil that opens on top of it and returns when the veil closes; two modals never co-render. There is no priority table to drift. The slot joins the `interruptModalOpen` disjunction and `getDebugOpenModals` (as `MomentCard`) in the same edit, so the auto-pause holds with its cause on the face.

The consumer is deliberately **not** gated on `interruptsSuppressed`: `suppressBeats` exists so a verification run can drive ticks past narrative beats, and the moment card is one of the things such a run is there to observe. The first run of the consumer test found exactly the other case — a premonition modal open and the card correctly holding back — which is the rule working, not the consumer failing; the test now arms suppression the way a verification run does.

## Chips claim only state (Law 56)

Every chip is backed by a runtime or graph write: `Work · finished/abandoned/begun` (status), `Progress · halted / a step, dearly bought` (progress and halts), `Stakes · raised` (escalation), `Cast · lost <name>` (the binder's released binding), `Your hand · inspired/sabotaged this checkpoint` (the rider consumed on that checkpoint — unlinked, since the rider flags carry no action id and a dead link that looks live is worse than none, Law 17), and `Set in motion · <victim> now pursues <ambition>` — the forward provenance chip, read off the outcome node the lifecycle wrote for this project at this tick and the victim's `pursues` edge carrying it as `mintedByEventId` (THR-1298's write), clickable to the victim (Law 21). Absent on every moment that minted nothing, which is most of them. The read-model is pure and tested without a DOM.

## One thing the proof taught

The Inspire cast from the card resolved on the next tick and stamped `divineInfluence { inspire, 79 }` — on **`secure_office`**, not on *Organize Festival*, whose card hosted the slot. The rider is per *mortal*, as the template's own text says ("their next checkpoint"), and The First was running thirty-odd undertakings at once, so the next checkpoint to roll was another work's. The card copy says *It lands on the next checkpoint*, which is true; whether the god should be able to aim at one work rather than one mortal is a design question for the calling/arc slices, not a defect here, and the thirty-concurrent-undertakings figure is a balance observation for the census, not this ticket.

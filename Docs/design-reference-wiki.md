# Design Reference Wiki — pattern

The **Design Reference Wiki** is the set of browsable, hand-built HTML system-design pages served from `public/`. It is kept self-connected by a generator so nav never has to be hand-wired and survives a page being regenerated by another skill.

> Authored as part of THR-521. The original Cowork sandbox draft of this doc was not committed (stale-worktree salvage); this version documents the pattern as actually built.

## Pieces

| File | Role |
|------|------|
| `public/wiki-manifest.json` | Single source of truth. `{ home, title, pages: [{id, file, title, blurb, section, sources?}], backlog?: [{id, title, blurb, section, sources?}] }`. `sources` is an optional array of repo globs — the freshness contract (see below). |
| `scripts/generate-design-wiki.ts` | Generator. Regenerates the hub and re-injects the managed nav into every manifest page. Idempotent. |
| `scripts/check-design-wiki.ts` | Guardrail. Fails if a served `public/*-reference.html` is missing from the manifest, a manifest page points at a missing file, a backlog id collides with a page id, or a `sources` field is present but not an array of non-empty string globs. |
| `scripts/check-wiki-freshness.ts` | Freshness lint. Warns when changed code matches a page's `sources` globs but the page HTML wasn't updated in the same diff. **Advisory locally / `check:process`; blocking in CI** (THR-730). See "Freshness contract" below. |
| `public/design-wiki.html` | **Generated** hub. Cards per page (grouped by `section`) + a "To document next" list from `backlog`. Do not edit by hand. |

## Sections

The `section` field groups pages on the hub (and orders sections by first appearance in the manifest). Two sections are in use:

- **Manual** — player-facing, dual-layer system pages (the Game Manual Wiki, THR-586–602). Player-manual prose first, Designer Notes second.
- **Deep Reference** — the pre-existing deep pages (`encounters-agents-reference`, `tick-cycle-reference`, `action-catalog`). These are the drill-down targets that a Manual page's Designer Notes link into.

### Dual-layer page template (Manual pages)

Every Manual page follows one shape (full spec: `Docs/plans/2026-07-03-game-manual-wiki.md` §3):

1. `<h1>` title + a one-line "what this system is" in plain language.
2. **How it plays** — player-manual voice: plain, concrete, no raw constants or code identifiers. Describes current shipped behavior; design-only behavior is introduced with "planned:".
3. **Designer notes** — a delimited section carrying `[IMPL]/[DESIGN]/[OPEN]` status flags (rulebook convention), named tunables + values + file, pipeline/phase pointers, canon-page links, UL shard anchors, and the relevant Deep Reference page. Open questions are *referenced* from the rulebook — pages never mint new ones.
4. Managed nav via the `<!--WIKI-NAV-->` markers (generator-owned).
5. Self-contained static HTML matching the existing pages' style. No external CDNs.

Terminology is UL-exact (game title in player copy: **Threadbearer**); where a page and the UL disagree, the UL wins and the page is a drift bug.

## Freshness contract

**Working agreement (user directive, 2026-07-03, settled):** *when the code of a core game system is changed, the relevant wiki page must be updated in the same PR.* Made mechanical in three parts:

1. **`sources` globs.** Each manifest page may declare `sources: string[]` — repo globs for the code it documents (e.g. `"src/engine/stealth*.ts"`). This is the contract.
2. **`npm run check:wiki-freshness`** (advisory locally, chained into `npm run check:process`) / **`npm run check:wiki-freshness:blocking`** (the CI gate). For the current branch vs `WIKI_FRESHNESS_BASE` (default `origin/main`), if a changed file matches a page's `sources` and that page's HTML (or a declared `payloads` entry) was *not* also changed, it warns and names the page. Constants: `WIKI_FRESHNESS_MODE` (`advisory` | `blocking`) selectable via env **or the `--blocking` flag**, and `WIKI_FRESHNESS_BASE`.
   - **Advisory mode** (local, `check:process`): warnings never fail; missing inputs skip soft (exit 0). Fail-soft: no resolvable git diff → `skipped`, exit 0; malformed glob → warn, skip that glob, exit 0; missing manifest → defer to `check:design-wiki`, exit 0. Byte-for-byte unchanged from the pre-THR-730 behavior.
   - **Blocking mode** (CI, THR-730 — user verdict 2026-07-23): a stale page fails the required `Test · Typecheck · Build` check (exit 1), and — because a gate that silently disarms is gate theater (the `tsc --noEmit` lesson, THR-686/693) — an unresolvable base ref or a missing/corrupt manifest also exits 1.
   - **Exemption token** (blocking only): a commit body carrying `Wiki-freshness-exempt: <non-empty reason>` downgrades the failure to an audited pass (the step prints `EXEMPT — <reason>`). For behavior-neutral changes — pure refactors, renames, type-only moves — that match a `sources` glob without altering documented behavior. `git log` unavailable ⇒ no exemption (fails closed). Exemptions are audited weekly by `weekly-project-hygiene` (see below).
3. **CLAUDE.md Definition-of-Done bullet** "Update the Design Reference Wiki" closes the loop from a code change back to its page.
4. **Weekly escape-net** (`weekly-project-hygiene`, THR-730). The gate has two blind spots — exemption misuse and code covered by no page's `sources` glob — so both go to the weekly hygiene routine: an exemption audit (`git log --grep='Wiki-freshness-exempt'`, 8-day lookback) and a coverage sweep of recently-changed `src/` files matching no glob. Findings file `Infrastructure` tickets; creative calls surface to Christian under `## Needs Christian`.

## How it runs

`npm run generate-design-wiki` is chained into `prebuild`, so **every `npm run build`**:

1. Rewrites `public/design-wiki.html` from the manifest.
2. Re-injects the managed nav into each manifest page — replacing the content between `<!--WIKI-NAV-->` / `<!--/WIKI-NAV-->` markers, or inserting the block immediately after `<body>` when markers are absent. The active page's nav link gets `aria-current="page"`.

Because the nav block carries its own scoped `<style>` (classes prefixed `wiki-nav__`), it renders consistently on any page regardless of that page's own CSS. The block is fully regenerated each run, so output is stable for a given (manifest, page) pair — a page regenerated by another skill simply gets its nav back on the next build.

`npm run generate-design-wiki:dry` previews without writing.

## Adding a page

1. Drop the HTML in `public/` (e.g. `public/foo-reference.html`).
2. Register it in `public/wiki-manifest.json` under `pages`.
3. Run `npm run build` (or `npm run generate-design-wiki`). The page appears in the hub and in every page's nav, and the generator injects its nav.

The `check:design-wiki` guardrail (chained into `npm run check:process`) ensures a served `*-reference.html` page can't silently drop out of the manifest, and vice-versa.

## Rules for other skills / authors

- **Do not hand-write the nav.** Leave the marker block alone; the generator owns it. Anything written between the markers is overwritten on the next build.
- When a skill regenerates a wiki page wholesale, it may emit the `<!--WIKI-NAV-->` markers (or nothing — the generator inserts after `<body>`), but it must not write its own nav links.
- Sibling generators that follow the same convention: `scripts/generate-ul-dashboard-data.ts`, `scripts/generate-impediment-dashboard.ts`.

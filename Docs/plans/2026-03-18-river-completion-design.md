# River Completion — Pit-Filling, Lake Outflow, Coastal Routing, Forking & Merging

**Date:** 2026-03-18 (updated 2026-03-20)
**Status:** Implemented
**Parent:** `2026-03-10-terrain-gen-phase1-design.md` (rivers/lakes), `2026-03-09-terrain-generation-design.md` (8-pass pipeline)

## Problem

Rivers generated by steepest-descent routing (Phase 1) dead-end in grassland or other inland terrain because the elevation field contains local minima — small basins where every neighbor is higher than the current hex. The algorithm gives up at line 90 (`if (!bestNeighbor) break`), producing rivers that visibly stop mid-land instead of reaching water.

Three specific failure modes:

1. **Depression trapping** — River hits a local elevation minimum surrounded by higher terrain. No downhill or flat neighbor exists, so routing stops. This is the primary bug visible in the screenshot (rivers ending in grassland).
2. **Coastal short-stop** — Rivers terminate at `coastal_shallows` (line 101) but don't route through shallows to open ocean. Visually the river ends in the shallow water band instead of reaching the sea.
3. **Lake dead-ends** — Rivers that reach a lake stop there (line 101). No outflow river spawns from the lake's far side, so lakes are disconnected from the drainage network.

## Solution

A three-part fix applied to the `WorldGenData` pipeline. Each part is an independent, additive function `(data: WorldGenData) => void` that slots into the existing pipeline order in `useRivers.ts`.

### Part 1: Depression Filling (pre-pass before river generation)

**Algorithm:** Priority-flood pit-filling (simplified Planchon-Darboux).

Instead of modifying the canonical `elevation` array (which other systems depend on), produce a **derived** `drainageElevation: Float32Array` that represents the "filled" surface — identical to `elevation` except that every local minimum is raised to its pour-point level.

**How it works:**

1. Initialize `drainageElevation` as a copy of `elevation`.
2. Seed a priority queue (min-heap) with all **edge hexes** and all **ocean hexes** at their true elevation. Mark them as "resolved."
3. Pop the lowest-elevation resolved hex from the queue. For each unresolved neighbor:
   - If `elevation[neighbor] >= elevation[current]`, the neighbor drains naturally. Set `drainageElevation[neighbor] = elevation[neighbor]`. Mark resolved, push to queue.
   - If `elevation[neighbor] < elevation[current]`, the neighbor is in a depression. Set `drainageElevation[neighbor] = elevation[current] + DRAIN_EPSILON`. Mark resolved, push to queue. This "fills" the pit to the pour-point level.
4. When the queue is empty, every land hex has a guaranteed downhill path to an edge or ocean hex via `drainageElevation`.

**River generation then uses `drainageElevation`** for routing instead of `elevation`. The original `elevation` array is unchanged — it's still used for biome classification, rendering, and everything else.

**CRITICAL: `drainageElevation` is a routing-only surface.** It must never be used to classify terrain or influence rendering directly. Rivers are overlay paths, not terrain replacements (per Decision 3 in the parent design). However, Part 4 (below) uses depression metadata to create lakes at multi-hex basins that rivers flow through — this is an intentional, controlled terrain mutation, not an artifact of the routing surface.

| Constant | Default | Purpose |
|----------|---------|---------|
| `DRAIN_EPSILON` | `0.0001` | Tiny elevation bump to ensure strict downhill ordering through filled depressions. Must be small enough to not affect biome classification if accidentally read. |
| `DEPRESSION_LAKE_MIN_SIZE` | `2` | Minimum number of filled hexes in a contiguous depression for it to become a lake when a river flows through it. Single-hex dips stay invisible. |

**Tracing:**

```typescript
interface DrainageFilledTrace {
  type: 'drainage-filled';
  tick: 0; // world-gen phase
  filledCount: number; // how many hexes had elevation raised
  maxFillDepth: number; // largest elevation delta (original → filled)
}
```

**Fail-soft:**

| Failure case | Fallback behavior |
|--------------|-------------------|
| Priority queue exhausted with unresolved hexes | Leave unresolved hexes at original elevation — river routing falls back to current behavior (may dead-end, but won't crash) |
| All edge hexes are ocean | Still works — ocean hexes are seeded too |
| No land hexes at all | `drainageElevation` equals `elevation`, zero fills, no rivers generated (existing behavior) |
| `DRAIN_EPSILON` accumulation exceeds 1.0 | Theoretically impossible on a 20×15 grid (max ~300 fills × 0.0001 = 0.03). On future 60×45 grid, still only ~2,700 fills × 0.0001 = 0.27. Safe. |

**PRNG:** None needed — this is a deterministic, purely geometric operation with no random choices.

### Part 2: Coastal Continuation (change to river termination)

**Current behavior:** River stops as soon as it enters `coastal_shallows` (line 101).

**New behavior:** When a river reaches `coastal_shallows`, continue routing through shallows toward any `ocean` or `deep_ocean` hex. Terminate only when reaching open ocean or running out of shallows (safety cap). The routing within shallows uses the same steepest-descent logic on `drainageElevation`.

Additionally, when the river reaches the **grid edge** (any border hex), it terminates — the river flows off the map into the implied surrounding ocean. This handles rivers that route to the edge of the world where no explicit ocean hex exists.

**Implementation:** Replace the termination check at line 101 with:

```typescript
// Terminate at open ocean or grid edge — but continue through shallows and coast
if (nTerrain === 'ocean' || nTerrain === 'deep_ocean' || nTerrain === 'tropical_ocean') break;
if (isEdgeHex(currentCol, currentRow, cols, rows)) break;
```

Where `isEdgeHex` returns true if the hex is on the grid boundary (col === 0, col === cols-1, row === 0, row === rows-1).

| Constant | Default | Purpose |
|----------|---------|---------|
| `RIVER_COASTAL_MAX_STEPS` | `6` | Safety cap on how many shallows hexes a river can traverse before giving up. Prevents infinite loops in large shallow bays. |

**Tracing:**

```typescript
interface RiverCoastalExtensionTrace {
  type: 'river-coastal-extension';
  tick: 0;
  riverId: string;
  shallowHexesCrossed: number;
  reachedOcean: boolean;
}
```

**Fail-soft:**

| Failure case | Fallback behavior |
|--------------|-------------------|
| River enters shallows but can't reach ocean within `RIVER_COASTAL_MAX_STEPS` | Terminate in shallows (current behavior) — visually acceptable, river appears to reach the coast |
| No ocean hexes adjacent to shallows (landlocked shallows from generation quirk) | Same fallback — terminate in shallows |
| River reaches grid edge before any water | Terminate at edge — river flows "off map" |

**PRNG:** None — deterministic neighbor selection.

### Part 3: Lake Outflow Rivers (post-pass after river generation)

**Current behavior:** Rivers terminate at lake hexes. Lakes are isolated basins.

**New behavior:** After all primary rivers are generated, scan each lake for inflow. If a lake has at least one river entering it, spawn an **outflow river** from the lake's pour-point (lowest-elevation non-lake neighbor that isn't the inflow side) and route it downstream using the same steepest-descent-on-`drainageElevation` logic. The outflow river connects to the existing drainage network — it terminates at ocean, another river (confluence), or another lake (which may in turn have its own outflow).

**Algorithm:**

1. For each lake cluster (identified by `lakeIds`):
   a. Check if any lake hex has `hasRiver === 1` (an inflow exists).
   b. If no inflow, skip — isolated lakes don't spawn outflows (they're fed by groundwater, narratively).
   c. Find the **pour-point**: the non-lake, non-ocean neighbor of any lake hex with the lowest `drainageElevation`.
   d. Route an outflow river from the pour-point using the same steepest-descent logic as `generateRivers`, but starting at the pour-point instead of a mountain source.
   e. The outflow path is prepended with one lake-edge hex (so the river visually exits the lake).
   f. Mark hexes `hasRiver = 1`, push to `riverPaths`.

2. Process lakes in elevation order (lowest first) so downstream lakes receive their inflows before we check whether they have outflows.

| Constant | Default | Purpose |
|----------|---------|---------|
| `LAKE_OUTFLOW_MIN_LENGTH` | `2` | Minimum length for an outflow river to be kept. Prevents trivial 1-hex stubs. |

**Tracing:**

```typescript
interface LakeOutflowTrace {
  type: 'lake-outflow';
  tick: 0;
  lakeId: number;
  pourPointHex: HexCoord;
  outflowLength: number;
  terminatedAt: 'ocean' | 'confluence' | 'lake' | 'edge' | 'stuck';
}
```

**Fail-soft:**

| Failure case | Fallback behavior |
|--------------|-------------------|
| Lake has inflow but no valid pour-point (all non-lake neighbors are ocean) | Skip outflow — lake drains directly to ocean, which is fine |
| Outflow route gets trapped in another depression | Won't happen if Part 1 (drainage filling) ran — every non-ocean hex has a downhill path. If somehow still trapped, terminate and emit trace with `terminatedAt: 'stuck'` |
| Lake has multiple inflows | Still gets exactly one outflow from the single lowest pour-point. Multiple inflows → one outflow is realistic (many real lakes work this way) |
| Outflow river is too short (< `LAKE_OUTFLOW_MIN_LENGTH`) | Discard it — lake appears to drain into nearby water without a visible river segment |
| Circular lake chains (lake A outflows into lake B, lake B outflows into lake A) | Prevented by processing in elevation order and the `visited` set in routing. Lower lake is processed first; its outflow goes further downstream. Higher lake's outflow reaches the lower lake and terminates. |

**PRNG:** None — pour-point selection is deterministic (lowest elevation wins). Tie-breaking uses array index order (stable, deterministic).

### Part 4: River-Fed Depression Lakes (post-pass after river generation)

**Problem:** When Part 1 fills a multi-hex depression so a river can route through it, the terrain stays as grassland/desert/etc. Visually the river just crosses flat land where water would realistically pool. Small single-hex dips are fine to ignore, but a 2+ hex basin that a river flows through should show as a lake.

**Algorithm:**

1. During Part 1 (depression filling), record a **per-hex fill depth**: `filledDepth[idx] = drainageElevation[idx] - elevation[idx]`. This is 0 for hexes that drain naturally, positive for filled hexes.
2. After river generation (Part 2), identify **river-fed depressions**: contiguous clusters of filled hexes (`filledDepth > 0`) where at least one hex in the cluster has `hasRiver === 1`.
3. Flood-fill each cluster. If the cluster size >= `DEPRESSION_LAKE_MIN_SIZE` (default 2), convert those hexes to lakes:
   - Set `terrain[idx] = 'lake'`
   - Assign `lakeIds[idx]` to a new lake cluster ID
   - These lakes automatically get coastline rendering via `CoastlineOverlay` (which already handles lake terrain with tighter `LAKE_BLOB_RADIUS_FACTOR` params)
4. Single-hex filled depressions (cluster size 1) are left unchanged — the river SVG line crosses them invisibly.

**Interaction with Part 3 (Lake Outflow):** These new depression lakes are created *before* the lake outflow pass runs. Since the river already flows through them (they were on the river's path), each depression lake inherently has both an inflow and a natural continuation — the river path itself serves as both. The lake outflow pass will see these lakes as having `hasRiver` on their hexes and may spawn additional outflow segments if the river path exits the lake cluster and continues downstream.

| Constant | Default | Purpose |
|----------|---------|---------|
| `DEPRESSION_LAKE_MIN_SIZE` | `2` | Minimum filled-hex cluster size to become a lake. Below this, the river just crosses the depression invisibly. |

**Tracing:**

```typescript
interface DepressionLakeTrace {
  type: 'depression-lake';
  tick: 0;
  lakeId: number;
  clusterSize: number;
  avgFillDepth: number; // average elevation delta across the cluster
  riverIds: string[]; // which rivers flow through this depression
}
```

**Fail-soft:**

| Failure case | Fallback behavior |
|--------------|-------------------|
| `filledDepth` array not populated (Part 1 didn't run) | Skip entirely — no depression lakes created, river rendering works as before |
| Filled cluster has no river flowing through it | Skip — unfed depressions don't become lakes (same logic as Part 3: groundwater-only basins) |
| Depression lake overlaps with existing lake from `generateLakes` | Won't happen — existing lake hexes are marked as resolved in the priority flood, so they never get filled. Their `filledDepth` stays 0. |
| Very large depression (10+ hexes) | No cap needed — the depression was already in the elevation field. If the terrain had a 10-hex basin, it should be a 10-hex lake. The existing `GREAT_LAKE_SIZE_MAX` from `generateLakes` doesn't apply here since these are different lakes from a different generation mechanism. |

**PRNG:** None — deterministic flood-fill and threshold check.

### Part 5: River Forking & Proximity Merging (integrated into river generation)

**Problem:** Rivers are independent polylines that never split or attract each other. Real rivers form deltas near coasts (forking) and tributaries merge when flowing through the same valley (merging). Without these, the river network looks artificially disconnected.

**Forking (delta distributaries):**

Near coastal areas or low-elevation terrain, a river can fork into 1-2 distributary branches. Each fork is routed independently from the fork point, using the same steepest-descent logic but excluding the main path's hexes to ensure the fork diverges.

Fork conditions:
- River is within 6 hexes of its terminus
- Fork point is near coast (adjacent to `coastal_shallows` or open ocean) OR at low elevation (< 0.3)
- Random chance per eligible hex (`RIVER_FORK_COASTAL_CHANCE`)
- Max forks per river: `RIVER_FORK_MAX_PER_RIVER`
- Min remaining path length at fork point: `RIVER_FORK_MIN_REMAINING_LENGTH`

Fork paths are stored as separate `RiverPath` entries with IDs like `river-0-fork-0`. The `RiverOverlay` renders them 40% thinner than the parent river.

**Proximity Merging (tributary attraction):**

During river routing, the steepest-descent scoring is modified to include a proximity bias. When evaluating a neighbor hex, if any of *that hex's* neighbors already has `hasRiver === 1` (from a previously routed river), the neighbor's effective elevation is reduced by `RIVER_MERGE_PROXIMITY_BIAS`. This makes rivers "attracted" to nearby existing rivers, naturally producing confluence points where two rivers merge.

The merge happens organically: the biased river routes closer and closer to an existing river until it enters a hex adjacent to one, at which point it either enters the same hex (existing confluence logic) or enters the next hex which is the river hex itself (triggering the `hasRiver` termination).

| Constant | Default | Purpose |
|----------|---------|---------|
| `RIVER_FORK_COASTAL_CHANCE` | `0.4` | Probability a river forks at an eligible near-coast hex |
| `RIVER_FORK_MAX_PER_RIVER` | `2` | Maximum distributary forks per river |
| `RIVER_FORK_MIN_REMAINING_LENGTH` | `3` | Minimum remaining path length before fork is allowed |
| `RIVER_MERGE_PROXIMITY_BIAS` | `0.15` | Elevation reduction when a neighbor is adjacent to an existing river |

**Tracing:**

```typescript
interface RiverForkTrace {
  type: 'river-fork';
  tick: 0;
  parentRiverId: string;
  forkHex: HexCoord;
  forkLength: number;
  terminatedAt: 'ocean' | 'edge' | 'confluence' | 'lake' | 'stuck';
}
```

**Fail-soft:**

| Failure case | Fallback behavior |
|--------------|-------------------|
| Fork routing gets stuck immediately | Fork discarded — parent river unchanged |
| No eligible fork points found | No forks created — river renders as single line (existing behavior) |
| Proximity bias causes river to route uphill | Bounded by bias magnitude (0.15) — small enough to not cause visually wrong routing. Safety: plateau traversal fallback still applies. |
| Fork overlaps with another fork | Second fork's routing hits `hasRiver` and terminates at confluence — natural and correct behavior |

**PRNG:** Fork chance uses the river-generation RNG (seeded, deterministic). Proximity bias is deterministic (no randomness).

**Rendering:** Fork rivers render at 60% width of parent. Lake outflow rivers render at 80% width. Both use the same meander/smooth pipeline.

## Pipeline Order

Updated pipeline in `useRivers.ts`:

```typescript
const data = createWorldGenData(cols, rows, seed);
generateLakes(data);                    // existing — find basins, flood-fill
fillDepressions(data);                  // NEW Part 1 — compute drainageElevation + filledDepth
generateRivers(data);                   // MODIFIED — route on drainageElevation, coastal continuation
promoteDepressionLakes(data);           // NEW Part 4 — 2+ hex river-fed depressions become lakes
generateLakeOutflows(data);             // NEW Part 3 — spawn outflow rivers from all fed lakes
return data.riverPaths;
```

**Ordering rationale:**
- `fillDepressions` runs **after** `generateLakes` — existing lake hexes are treated as resolved (water) in the priority flood, so rivers flow *into* lakes, not over filled basins.
- `promoteDepressionLakes` runs **after** `generateRivers` — it needs to know which filled depressions have rivers flowing through them.
- `generateLakeOutflows` runs **last** — it picks up both original lakes and newly promoted depression lakes, spawning outflows from any that have inflows.

## WorldGenData Extension

```typescript
export interface WorldGenData {
  // ... existing fields ...
  drainageElevation: Float32Array; // NEW — filled elevation surface for river routing
  filledDepth: Float32Array;       // NEW — per-hex fill amount (drainageElevation - elevation)
}
```

Initialize both in `createWorldGenData` as zero-filled arrays (populated by `fillDepressions`). If `fillDepressions` hasn't run, `generateRivers` should fall back to `elevation` (fail-soft — existing behavior preserved). If `filledDepth` is all zeros, `promoteDepressionLakes` is a no-op.

## Testing Strategy

**Depression filling:**
- Hand-crafted 5×5 grid with a known depression (valley surrounded by ridges). Assert `drainageElevation` fills it to pour-point level.
- Flat grid — assert no fills (no depressions).
- Grid where every non-ocean hex is a depression (pathological) — assert all filled to edge level.
- Determinism: same input → same output across 5 seeds.

**Coastal continuation:**
- River that reaches `coastal_shallows` — assert path continues to `ocean`.
- River that reaches grid edge — assert termination at edge.
- River in large shallow bay — assert `RIVER_COASTAL_MAX_STEPS` cap prevents runaway.

**Lake outflow:**
- Lake with one inflow river — assert exactly one outflow spawned from pour-point.
- Lake with no inflow — assert no outflow.
- Lake adjacent to ocean — assert no outflow (drains directly).
- Chain of two lakes at different elevations — assert outflow from upper lake reaches lower lake, outflow from lower lake reaches ocean.

**Depression lakes:**
- 3-hex filled depression with a river through it — assert all 3 hexes become `terrain: 'lake'` with valid `lakeIds`.
- 1-hex filled depression with a river through it — assert terrain unchanged (below `DEPRESSION_LAKE_MIN_SIZE`).
- Filled depression with no river — assert terrain unchanged (unfed depression).
- Depression adjacent to existing lake — assert no overlap (existing lakes have `filledDepth === 0`).
- Verify `CoastlineOverlay` renders new depression lakes (integration — coastline picks up any hex with `terrain === 'lake'`).

**Integration:**
- Generate 5 worlds (seeds 1–5), assert every river either:
  - Reaches ocean/deep_ocean/tropical_ocean, OR
  - Reaches a grid edge, OR
  - Merges into another river (confluence)
- No river terminates on a land hex (grassland, desert, etc.) — **this is the regression test for the original bug**.
- Performance: full pipeline (with depression filling) < 500ms for 20×15 grid.

## Performance Note

Priority-flood pit-filling is O(N log N) where N = number of hexes (priority queue operations). On a 20×15 grid (300 hexes), this is negligible — well under 1ms. On the future 60×45 grid (~2,700 hexes), still fast. The min-heap can use a simple array-based binary heap; no external dependency needed.

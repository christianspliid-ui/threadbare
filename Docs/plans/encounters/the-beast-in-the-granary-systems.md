## 3. Runtime Feasibility

**Beat count, branching profile, outcome ladder:** all live and correctly composed. One structural point worth stating precisely, because "will the gate pass" depends on exactly this: **the Composition Contract's structural blocks are blind to `ActionStepBranch` variants, and I traced that blindness function-by-function rather than trusting the draft's general statement of it.**

`plainSteps()` (`compositionContract.ts:315-319`) filters `template.steps` at the top level for non-branch entries. `nudgeBearingSteps()` and `dealBearingSteps()` (`nudgeHandChecklist.ts:106,155-157`) do the same. None of the three ever look inside `ActionStepBranch.variants`/`.fallback`. The concrete consequence for this template, checked one gate at a time against the actual code:

| Gate | Function | Sees step 0? | Sees beat-2 (`positive`/`negative`) steps? |
|---|---|---|---|
| Steps block (reach/difficulty/narrativeTemplate) | `plainSteps` (`compositionContract.ts:1279-1283`) | yes | **no** |
| Hand block (`checkNudgeHand`/`checkComposedHand`) | `nudgeBearingSteps`/`dealBearingSteps` | yes | **no** |
| Images (`imageTag` resolution) | `nudgeBearingSteps` (`compositionContract.ts:1431`) | yes | **no** |
| Enrichment dry-run (`{...}` token check) | `authoredProse` → `plainSteps` (`compositionContract.ts:1486`) | yes | **no** |
| Forecast arithmetic (difficulty + hand ≤ [0,1]) | inline `if (isActionStepBranch(step)) continue` (`scripts/check-encounter.ts:113`) | yes | **no** |
| Grant liveness (`validateNudgeGrantRefs`/`RewardDrawPools`/`FavorDebtors`) | `allTemplateEffects` → inline `if (isActionStepBranch(step)) continue` (`nudgeGrantLiveness.ts:363`) | yes (step effects) | **no** for step-level card grants/effects; **yes** for aftermath-variant reactions (separate code path, unconditional) |
| Register detectors (vagueness, second-person, not-X-but-Y, divine authorship) | `collectClassedTemplateProse` (`nudgeAuditDetectors.ts:289-311`) | yes | **yes — explicitly handles both shapes** ("Branching steps carry their variants under `variants`/`fallback`… sweep both shapes") |
| Aftermath (`byOutcome` floor, `overview`, Law 56 chip backing) | `aftermathVariants`/`stepBackingForFace` → `allRunnableSteps` (`compositionContract.ts:390-400,501-522`) | yes | **yes — this one correctly descends** |
| Consequence draw | `allAftermathEffects` (reactions unconditional + `plainSteps` for step effects) | yes | **partially** — reaction effects yes, step-level effects no |
| Systems quota | same `allAftermathEffects` | yes | partially, same split |

**This matters to the verdict in two directions.** First, the good news the draft/editorial could state only in general terms: the **register detectors** — which is where most of the editorial's actual fixes landed (the seven vagueness hits, the second-person sentence, the seam echoes) — correctly walk into both branch variants. Those fixes are not merely applied, they are gate-verified. Second, the precise bad news: beat 2's two composed hands, its card grants (`granary.narrow_their_sight`'s `axiological_mark_apply`), its step-level `condition_attachment` writes (Festival/Blighted Harvest/Wounded on the branch steps themselves, as opposed to the reactions), its `imageTag`s, its enrichment tokens, and its forecast arithmetic are **all** structurally invisible to `check:encounter` — not "partially checked," genuinely never inspected. This is finding #7, confirmed accurate and, if anything, wider in scope than the draft stated (the draft named the hand checks and the consequence-draw gate; forecast arithmetic and grant liveness are two more instances of the identical bug I found by tracing rather than assuming).

**Will `check:encounter -- encounter.hunt.the_beast_in_the_granary` pass?** Yes, and I can say why with certainty rather than confidence:

- **Steps/hand/setting/cast/images blocks**: satisfied entirely by step 0 (2 specials + `deal`, reach `shadow`, difficulty 0.40, `narrativeTemplate` present) and the top-level `supportBundle`/`settings` fields, none of which touch the branch.
- **Rewards block**: `hasReward()` is true via step 0's `spawn_artifact` (success) — `PERSISTENT_EFFECT_KINDS` includes it — so this passes without needing branch-step effects at all.
- **Aftermath block**: correctly checks both variants via `allRunnableSteps`/`aftermathVariants` — `positive` authors `critical_success`/`success`/`critical_failure`, `negative` authors `success`/`success_at_cost`/`failure`/`critical_failure`; both clear the ≥3-bands-with-one-extreme floor; every variant carries an `overview`; every chip declares `concepts`.
- **Systems quota (≥3, target 4)**: `cast` (supportBundle actor spec) + `rewards` (step 0's `spawn_artifact`/`condition_attachment`) + `conditions` (step 0's `failureMetadata` wound) + `factions` (keeper's `factionDefId: 'civic_guard'` on the cast spec — **not** `membership_change`, confirmed below) = 4, entirely earned from step 0 and the cast spec. It does not need the branch steps' condition writes to clear the floor.
- **Consequence draw**: `possession` is wired by step 0's `spawn_artifact` — a plain step, visible. `membership` is wired by `granary.swear_them_in`'s `membership_change` — and this is on the `positive` **variant's base reactions**, which `allAftermathEffects` walks unconditionally (`aftermathVariants(template)` reads `config.variants`/`config.fallback` directly — this is a *separate* branch-keyed structure from `template.steps`, untouched by the `plainSteps` filtering problem). So both drawn families resolve to `wired`, and `checkConsequenceDraw` passes. I traced `familiesWiredByEffects` (`consequenceDraw.ts:298-329`) and `CONSEQUENCE_FAMILY_EFFECT_KINDS.possession = [spawn_artifact, attachment_grant, reward_draw]` / `.membership = [membership_change]` (`consequenceDraw.ts:184,193`) to confirm this by hand rather than by inference — it is exactly why the editorial's finding #7 note is correct that routing `membership_change` through a reaction (rather than the `positive` step's `successMetadata`, which would have been invisible) was the only way to make this gate pass at all.
- **Forecast arithmetic, grant liveness for beat-2 cards, enrichment tokens in beat-2 prose**: never run, so cannot fail. Nothing in beat 2 can turn the gate red because nothing in beat 2's structural shape is inspected — only its prose (register detectors) is.

**Net: `check:encounter` goes green.** Not narrowly or by luck — every block it actually enforces is satisfied by content that sits where the gate looks (step 0 + the aftermath config), and the content that sits where the gate does not look (beat 2's structure) cannot produce a violation because nothing reads it. The risk this leaves is not "the gate will fail," it is "the gate cannot prove beat 2 is correct" — which is a corpus-level defect (finding #7) the packet correctly declines to work around, not a defect in this packet.

**One second-order confirmation**: `encounter-package-format.md`'s compiler validation list ("Hand rules per nudge-bearing step, from the shipped authoring constants") is described in exactly the same terms as `check:encounter`'s hand block, which by name is `nudgeBearingSteps`-scoped. So `compile:encounter`'s package-time validator inherits the identical blindness — Stage 4 will not catch a beat-2 hand-composition mistake either, for the same structural reason.

## New findings from this pass

**11 · The register detector correctly descends into branch variants; the Composition Contract's structural blocks do not — and this split is precise, not partial.** Worth stating as its own finding because the draft and editorial both describe "the gate" as one blind spot, when it is actually two different modules with two different answers to the same question. `collectClassedTemplateProse` (`nudgeAuditDetectors.ts`) explicitly branches on `'branchOnStep' in rawStep` and walks both variants plus fallback — every vagueness-lexicon, second-person, and divine-authorship check the editorial pass fixed on beat 2 is gate-verified. Every *structural* check (hand composition, image resolution, token resolution, forecast headroom, grant liveness) is not. An author relying on "the gate is green" as proof of beat-2 correctness would be half right and would not know which half. Recommend the retrospective/impediment log capture this precisely, since the natural reading of finding #7 ("the gate is blind to branches") undersells the one place where it is not blind and oversells nothing — but a future encounter author reading only the summary line could reasonably assume prose-quality is unverified there too, when it is the one thing that *is*.

**12 · `axisRegistry.ts`'s own commentary for the `star` reach conflicts with the `REACH_VALUE_PAIR` table it is documenting a legacy bridge to — pre-existing, not this encounter's defect, zero runtime consequence for this packet.** `CANONICAL_AXES`'s `star` entry carries a code comment stating Star was "re-scoped (THR-545): wayfinding/fate, not inner outlook… Star's reach axis now points at its real domain — guiding others' journeys vs leading them astray," with virtue/vice pole words `Beacon/Guiding` ↔ `Wrecker/Misleading`. But `REACH_VALUE_PAIR.star` (`src/types/agent.ts:46`) still hard-codes `'sacrifice_survival'` — the exact `ValuePair` this packet's fork runs on, and the exact one `granary.narrow_their_sight`'s `axiological_mark_apply` targets at `reach: 'star'`. The packet's own shorthand pole labels ("Martyr" / "Survivor", used only in internal design-table headers, never in player-facing prose) are not derived from the registry's stated Beacon/Wrecker vocabulary — they are the packet's own gloss on what `sacrifice_survival` means. The packet's *technical* usage is correct: `sacrifice_survival` genuinely is the `ValuePair` keyed to Star's reach axis via the live lookup table, and the same live precedent (`the-unfinished-rite.ts`'s reach-scoped mark) uses the identical mapping. The mismatch is between the registry's own prose comment and its own data table, not between the packet and the registry. No action needed in this packet; worth a one-line note if the registry's `star` comment is ever revisited, since a future reader could reasonably conclude `sacrifice_survival` is no longer live there when the code says otherwise.

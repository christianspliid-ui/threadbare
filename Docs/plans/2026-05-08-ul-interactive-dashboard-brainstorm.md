# Brainstorm — UL Interactive Dashboard (`?view=ul`)

**Companion to:** `Docs/plans/2026-05-08-ul-interactive-dashboard.md`
**Linear:** THR-289

This is the dialogue layer for the plan doc. The plan is the executable; this is the *why* and the alternatives we considered.

---

## 1. Why this surface exists at all

The UL ships in three forms today:

1. **Canonical source:** `Docs/ubiquitous-language/*.md` — seven shards. PR-edited. Authority on terminology.
2. **Obsidian mirror:** generated by `scripts/mirror-ul.ts` (THR-288, shipped). Human read-friendly inside Obsidian, with backlinks and graph view.
3. **Drift scan signals:** weekly GH Action emitting Linear issues against `Docs/ubiquitous-language/` for stale canonicals and used-uncanonicals.

What's missing is the **in-app cross-reference**. When an agent or designer is staring at the running game (CMS browser, Codex, Style Guide) and wonders "is this term canonical?" — they currently context-switch to Obsidian or `grep Docs/ubiquitous-language/`. Cheap, but the friction is real, and the IA manifest already cross-links to the other three reference surfaces.

The Idea ticket (THR-289) lists four affordances the dashboard adds that the Obsidian mirror can't: cross-shard search, drift visibility, content-adjacency filter, and term-graph overlay. Of those, the first three are clearly worth shipping; the fourth is a "wow" feature with high payoff potential but uncertain play value at v1. We deferred it.

## 2. Tensions surfaced

### 2.1 "Why not just keep using Obsidian?"

The mirror is fine for the read-only case. The dashboard wins on three dimensions:

- **Always-on availability inside the game tab** — no context switch.
- **Drift integration** — Obsidian doesn't know which terms have open `UL-proposal` Linear issues or which got flagged stale this week. Surfacing this *next to* the term definition turns drift into a workflow signal instead of a separate Linear scan.
- **Cross-shard browsing** — Obsidian has graph view, but it's not optimized for "show me all `Status: canonical` terms across all 7 shards, filtered to content-adjacent". A purpose-built table view is.

The trade-off is one more surface to maintain. We accept it because the maintenance is mechanical (JSON regen on UL edits) and the upside is workflow.

### 2.2 Build-time JSON vs. live markdown read

Three options were floated in the Idea ticket:
- (a) build-time imported markdown parsed at startup
- (b) static JSON generated by a build step
- (c) markdown fetched per-view at runtime

(a) and (b) produce identical UX; (b) is preferred because it makes the parsing failure mode visible at *build time* instead of *page load time*. CI catches malformed shards before they ship. (a) defers the failure to the user.

(c) was tempting because it makes the dashboard "live" — edit a shard, refresh, see new content. But it pushes parsing into the browser, breaks NFP #4 fail-soft, and the offline determinism we get from (b) is more valuable. Vite hot-reload can give us *most* of the live-edit feel during dev (regenerate + restart), so the only loss is the polish of "literally watch it update". Acceptable.

### 2.3 How aggressively does the dashboard own term presentation?

If the dashboard becomes the place humans read UL definitions, the canonical source could drift in formatting without anyone noticing. We mitigate by:

- Surfacing a "View source on GitHub" link prominently in every detail pane.
- Surfacing build warnings in the footer disclosure — anyone who opens the dashboard sees "(N issues)" if shards are malformed.
- Re-exporting drift-scan constants instead of duplicating them, so a constant change in one place ripples.

We're not trying to make the dashboard *better* than the markdown. We're trying to make it more *navigable*.

### 2.4 Drift status — committed vs. live-fetched

Plan doc §11 records the decision (committed via GH Action). The tension is between a clean repo and a clean wiring story. Committing a generated file feels weird, but it's already the pattern (`drift-scan-baseline.json`, Obsidian mirror outputs). Treating drift status as data — not as code — means committing it is normal.

The follow-up ticket to wire the auto-commit step into CI is intentional. We don't want v1 to slip on a CI complexity. v1 ships with an empty status JSON; the dashboard renders the "drift unavailable" state gracefully; the follow-up adds the live data.

### 2.5 Term-graph view in or out of v1?

Out. Three reasons:

1. **Uncertain payoff** — the See-Also network is interesting in principle, but until we can see the real shape of the graph, we don't know if force-directed is the right viz. Could be a Sankey, could be clusters, could be nothing.
2. **D3 / vis-network learning curve** — the project doesn't have a graph-viz library wired up; adding one for a single feature is expensive.
3. **The table + search covers 80% of the Idea ticket's value.** Don't gold-plate v1.

Filed as a deferral. Promote when someone says "I keep wanting X" and X is the graph view.

## 3. Considered and rejected

### 3.1 Markdown rendering library

Options:
- **`marked`** — small, fast, no React.
- **`react-markdown`** — React-native, but pulls in remark + plugin ecosystem.
- **Hand-roll a tiny markdown subset** — UL bodies use a tight subset (paragraphs, code spans, wikilinks, links, lists). A 50-line custom renderer is feasible.

Recommendation: **`react-markdown`** if it's already a dep; otherwise hand-roll. The UL body subset is so narrow that the ecosystem cost of `react-markdown` is wasted. The CC pickup should check `package.json` first — if it's there, use it; if not, hand-roll. (Plan doc doesn't lock this; it's a CC-time decision.)

### 3.2 Routing — `?view=ul` vs. nested `#fragment`

We could have shipped UL as a CMS sub-tab (`?view=cms#ul`). Rejected because:
- The UL is its own first-class surface in the IA manifest model.
- The CMS is for content-table browsing; UL is glossary, distinct intent.
- Every other reference surface has its own route (`?view=codex`, `?view=styleguide`); consistency wins.

### 3.3 Sidebar shape — shard tabs vs. shard accordion

Tabs win. With 7 shards, an accordion would be too tall (7 collapsibles + sub-items inside each = >800px before any term is visible). Tabs keep the sidebar compact and put filter chips below.

### 3.4 Whether to generate during `vite dev`

Watching `Docs/ubiquitous-language/*.md` and regenerating during dev would be slick. Rejected for v1 because:
- Vite plugin authoring overhead.
- The `npm run generate-ul-dashboard` workflow is fast (<2s) and explicit.
- A contributor editing a UL shard already has muscle memory for `npm run mirror-ul`; this fits the pattern.

If it becomes a friction point, file a ticket for a Vite plugin. Don't build it speculatively.

## 4. Vision premises invoked

- **"UL wins on terminology disagreements"** — the dashboard reinforces this by making UL canonical definitions reachable from inside the running app. If a designer is staring at a CMS row and wonders if "intel" is the canonical term or if it should be "intelligence record", they're 1 click from the answer.
- **"Reference surfaces are first-class IA"** — this is the unstated principle behind `?view=cms#ia-surfaces`, `?view=codex`, `?view=styleguide`. UL joining the family is consistent with this principle, not a new claim.
- **"Don't let the LLM knowledge base drift"** — the Obsidian-mirror + drift-scan workflow already protects against shard-text drift. The dashboard adds a fourth check: humans browsing the dashboard will see warnings if the mirror has malformed entries, providing a visible signal that the mechanical scans are catching real issues.

No Vision premises are challenged or updated by this work.

## 5. Open questions left to CC at implementation time

These are NOT design questions — they are routine implementation choices the CC pickup makes. Listed here so they're not surprises:

1. **Markdown renderer choice** (§3.1 above). CC checks `package.json`; uses `react-markdown` if present, else hand-rolls.
2. **Shard ordering in sidebar.** Plan doc lists 7 shards in the order they appear in `README.md`. CC may reorder if a designer-driven order makes sense (e.g. by content-adjacent first, then non-adjacent).
3. **Detail pane width.** §5 says 480px. CC may adjust to 440 or 520 if the table column count + content collide. Document the chosen value in `ul-dashboard-constants.ts`.
4. **Whether to inline a "?" help affordance.** Optional polish; CC's call. If included, copy: "UL is the canonical glossary. Open issues are tracked in Linear with the `UL-proposal` label."

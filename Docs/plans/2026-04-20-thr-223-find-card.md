# Codex brief — THR-223: Find-card detailed spec + implementation

## Context

The find-card is the heart of Threadbare's composition DSL. It's the mechanism behind `FindRenameCreateResolve` — a recipe node that says "find an existing content item matching these criteria; if found, optionally mutate it; if not, create a new one." Find-cards make recipes composable across world states: the same recipe can work whether the world has a pre-existing merchant consortium (found and marked) or not (created).

This brief is the full find-card spec and implementation. It sits underneath THR-222 (the DSL grammar) but has its own complexity worth specifying separately.

## Spec — REVIEW-PENDING (pinned by Claude in Cowork, not yet Christian-reviewed)

### The four outcomes of a find-card resolution

Every find-card resolution falls into one of four outcomes. The validator and runtime both emit which outcome happened, for debugging and replayability:

1. **FOUND_AND_MARKED** — one or more candidates matched the filter; tie-breaking selected one; all mutations applied successfully.
2. **FOUND_BUT_REJECTED** — candidates matched the filter, but mutations violated the node-class gate (THR-224), so the find-card fell over to create.
3. **CREATED** — no candidates matched; create fallback ran.
4. **HARD_FAILED** — no candidates matched AND `allowCreate: false`. Composition's essential-tier handling applies (fails recipe if tier === "essential").

### Filter composition

Filters are the `FilterQuery` type from THR-222. The find-card evaluates the filter against the entire content graph. Key semantics:

- **Evaluation is eager but cached within a single composition firing.** Two find-cards in the same recipe that share a subquery should re-use the result (same world snapshot).
- **Filters are pure** — no side effects, no random choice. Any randomization happens in tie-breaking.
- **Node visibility** — find-cards see all nodes regardless of class (generic/promoted/threaded). Class only matters at the mutation step.

### Tie-breaking (deterministic for replay)

When a filter returns multiple candidates, tie-break in this order:

1. `tagMatchCount` descending — prefer nodes that match more tags in the filter (if the filter is "archetype=consortium OR sphere=coastal_trade", a consortium in a coastal sphere beats a consortium in a mountain sphere)
2. `nodeClass` ascending — prefer `generic` over `promoted` over `threaded` (keeps find-cards away from on-screen content when a background alternative exists)
3. `id` ascending — stable string sort on content ID for deterministic fallback

Authors can override tie-breaking with an `orderBy` clause in v1. Not in v0.

### The mutation step

`MutationSet` from THR-222:
```ts
type MutationSet = {
  rename?: string
  promoteClass?: "promoted" | "threaded"
  addEdges?: Array<{ edgeType: string; toNodeKey: string }>
}
```

Mutation semantics:
- Applied **atomically** — either all mutations succeed or none do.
- If any mutation would be blocked by the node-class gate (see THR-224: writing to a promoted/threaded node requires `respects_promoted: true` on the recipe), the whole mutation step fails and the find-card falls over to CREATED outcome. The rejected candidate is logged as FOUND_BUT_REJECTED for debugging.
- Mutations never silently overwrite stated attributes (THR-224 tripwire). If a rename would change a stated `name` attribute, the tripwire rejects it → find-card falls over to create.
- `addEdges`: `toNodeKey` references another node in the *same recipe*. Edges are resolved to real content references after all nodes in the recipe resolve.
- `promoteClass` is one-way: generic → promoted, promoted → threaded. Cannot demote. Cannot skip (generic → threaded is invalid; must go through promoted).

### Create fallback

`CreationSpec` from THR-222 plus two implicit steps:
1. The created content inherits initial tags from the recipe's intent.
2. If `initialEdges` reference recipe nodes that haven't resolved yet, creation deferred until they do (edge resolution phase runs after all nodes resolve).

### Debugging and observability

Every find-card resolution emits a structured log:

```ts
type FindCardLog = {
  nodeKey: string
  recipeId: string
  outcome: "FOUND_AND_MARKED" | "FOUND_BUT_REJECTED" | "CREATED" | "HARD_FAILED"
  candidateCount: number              // how many the filter matched pre-tie-break
  selectedId?: string                 // the winning candidate, if any
  rejectionReasons?: string[]         // populated on FOUND_BUT_REJECTED with specific gate violations
  mutationsApplied?: MutationSet      // what actually landed
  createdId?: string                  // on CREATED outcome
  durationMs: number
}
```

These logs are essential for authoring — when a recipe fires in an unexpected way, the log tells the author which find-card went sideways and why.

## Goal

Implement the find-card resolution logic and its observability layer. Tested independently of full recipe evaluation.

## Approach

1. Build on top of THR-222's schema module. Import types; don't duplicate.
2. Implement `resolveFindCard(nodeKey, spec: FindRenameCreateResolve, world: WorldSnapshot, recipe: Composition): FindCardResult`.
3. Filter evaluation: walk the FilterQuery AST; against a sample in-memory WorldSnapshot initially (real CMS integration is a later task).
4. Tie-breaking: implement the three-level sort.
5. Mutation: atomic application against the world snapshot. For v0, stub the node-class gate check to always pass unless `mutatingPromotedWithoutRespect` is set on the world-state fixture (Codex can simulate the gate until THR-224 lands).
6. Create fallback: produce a new content record in the snapshot.
7. Emit the structured log per resolution.
8. Tests: cover all four outcomes explicitly with hand-crafted world fixtures.

## Output

Under the DSL package (same location as THR-222):
- `findCard.ts` — the resolution logic
- `findCard.test.ts` — tests covering all four outcomes
- Updates to the validator (from THR-222) to call `resolveFindCard` for find-rename-create nodes
- Update the reference event recipe (Winnowing) to include at least one find-card per outcome class, and add test cases that drive it through each

## Acceptance criteria

- All four outcomes have test coverage with hand-crafted fixtures.
- Tie-breaking is deterministic — running the same recipe against the same world twice produces the same selected candidate.
- Structured logs are emitted and cover all four outcomes.
- Mutation is atomic — a test verifies that if one mutation would violate the stubbed gate, none of the others apply either.
- `allowCreate: false` hard-fails with a clear error when find yields nothing.
- README updated with a "How find-cards resolve" section summarizing the four outcomes and tie-break rules.

## Non-goals

- Do **not** implement the full node-class mutability gate. That's THR-224. Stub it such that Codex's THR-223 work doesn't block on it but the integration point is clear (one function call at the mutation step).
- Do **not** implement the stated-attributes tripwire. Also THR-224. Stub similarly.
- Do **not** wire real CMS reads/writes. WorldSnapshot is an in-memory JSON fixture for v0.
- Do **not** implement `orderBy` override for tie-breaking. v1.

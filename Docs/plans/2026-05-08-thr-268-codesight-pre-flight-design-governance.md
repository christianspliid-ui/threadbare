## Goal

Promote Codesight from a passively-described orientation aid (under the `# Codesight — Codebase Intelligence` section near the bottom of `CLAUDE.md`) to a **procedural pre-flight step** in the design-governance checklist. The agent runs a Codesight blast-radius / dependency-chain query *before* drafting the design, and — when the change touches any high-impact file — surfaces that radius up front in the plan doc as a named "Blast Radius" section.

The Pocock framing from the parent brainstorm: *in an agent-primary codebase, principles don't enforce themselves; named loadable steps do.* Codesight already exists. It just isn't required, so it gets skipped, and the cascade risk of touching `src/engine/graph.ts` (370 importers) or `src/types/index.ts` (186 importers) only becomes visible after CC has already started writing code. This issue closes that gap with a two-line CLAUDE.md edit.

## Why these triggers, why these thresholds

- **`src/` gate on Step 0.5** keeps the pre-flight from firing on tiny doc/skill/governance edits (like this very issue). Codesight's value is in catching coupling surprises in source code; running it on a markdown-only change is noise. The gate is mechanical and grep-able.
- **≥100 importers as the "high-impact" threshold** matches the existing CLAUDE.md `# Codesight — Codebase Intelligence` named list — the smallest entry there is `traceBuffer.ts` at 106 importers. Round number, easy to remember, no separate constant to maintain. Codex/CC do not need a new lookup table; the named list in `CLAUDE.md` (currently five files: `graph.ts` 370, `types/index.ts` 186, `gameState.ts` 176, `traits.ts` 156, `traceBuffer.ts` 106) is the contract.
- **Blast Radius as a *named section*, not a constants-style table.** The point is to push the cascade-risk discussion in front of the human reader, not to standardize a metric format. A one-line cascade note per file is the entire spec — wider rituals are out of scope for this issue.
- **Fall-back to manual `grep`** when Codesight is unreachable preserves NFP #4 (fail-soft). Documented in the bullet itself so future agents don't bounce on missing tooling.

## Rejected approaches

- ❌ **Make Codesight pre-flight required for *all* design work, including doc-only and skill-only changes.** Rejected — for tiny process tweaks the Codesight query is noise. The `if change touches src/` gate keeps the requirement proportionate. (This very issue is an example of the doc-only case the gate excludes.)
- ❌ **Promote Codesight to its own loadable skill in `.claude/skills/`.** Rejected — Codesight is already documented in CLAUDE.md `# Codesight — Codebase Intelligence` (a top-level always-loaded section). Wrapping it in a skill adds load-time cost without adding capability. The CLAUDE.md section *is* the skill, just inlined.
- ❌ **Auto-generate the Blast Radius section via tooling (e.g. a script that scans `git diff` and emits a markdown block).** Rejected as scope creep. Manual surfacing keeps the agent in the loop ("here's why this matters") rather than producing a wall of metric output the human will skim past. Revisit only if agents start mechanically copying boilerplate Blast Radius sections without reasoning about cascade risk.
- ❌ **Update `Docs/plans/wiring-checklist.md` in this issue.** Rejected for blast-radius reasons (ironic, but real): wiring-checklist is touched by several other in-flight design docs and this issue should keep its surface to one file. If a wiring-checklist update proves needed after this lands, file a follow-up.
- ❌ **Lower the threshold below 100 importers.** Rejected — 100 matches the existing named list in CLAUDE.md. Lowering it floods plan docs with Blast Radius sections for medium-impact files (50-100 importers) where the cascade-risk note is "minor." Better to keep the bar high enough that surfacing actually means something.

# Extending the UI — one entry per kind

> **Law 58** (`laws.md` § XVI, Christian, chat 2026-10-14): *the UI grows by adding entries, not by writing screens.* This page is where an agent looks first when the game gains a new action, field, object kind, icon, lens or ask. Each row names the one place to add it, the check that catches a missing entry, and where to see the result.
>
> **Keep this page true.** A PR that adds or changes an extension point updates its row in the same PR. A row marked **several places** is a Law 58 debt with a ticket; when the ticket lands, the row becomes one place.

## A new player action

Add the template to `src/data/unified-action-templates.ts`. If its id uses a prefix that is already filed (`divine.`, `hex.`, `loc.`, `company.`, …), that is the whole edit. If the prefix is **new** (for example `company.bless` before `company.` existed):

1. **One row:** add the prefix to `ACTION_CATEGORY_RULES` in `src/data/action-categories.ts`, naming its category. Only if the action needs a new home, add one entry to `ACTION_CATEGORIES` (Codex tab label, catalog facet), plus its glyph in `ACTION_CATEGORY_GLYPHS` and its mapper in `ACTION_ENTRY_MAPPERS` (both in `codexRegistry.ts`); the typecheck names all three. If you forget the row, `action-categories.test.ts` and `npm run generate-action-catalog` fail with *add `<prefix>` to src/data/action-categories.ts*.
2. **Beat grant:** if a beat grants the action, add its id to `ASCENDANT_ACTION_BUCKETS` (`src/data/ascendant-beat-content.ts`). Tests fail and name the id if you forget.
3. **Generated artifacts:** regenerate `public/action-catalog.generated.json` and commit it before running `npm run check:generated-freshness`, which compares against HEAD.

The action catalog and the Codex both read the one table; neither keeps prefix arms of its own (THR-1886). `invest.*` is filed in the Codex but kept out of the designer catalog by `DESIGNER_CATALOG_EXCLUDED_PREFIXES`, as before.

## When there is no row for what you are adding

Add the thing as one entry in one list, add a check that fails and names that list when an entry is missing, give unknown members a plain fallback, and add a row to the table above. If that is not possible without a new list that must agree with an existing one, derive the new list from the old one instead.

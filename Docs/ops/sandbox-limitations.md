# Known Sandbox Limitations

> **Authoritative home** — moved out of `CLAUDE.md` § Known Sandbox Limitations by THR-1336 (2026-08-28, context-cleanup round 1). CLAUDE.md keeps the five highest-frequency rules and points here. Content moved verbatim; no rule changed in the move. The Claude Code automation sandbox has several quirks that recur often enough that agents waste time rediscovering them — **read this before debugging environment failures.** (Carried from the 2026-04-11 retro; first-class entry per 2026-04-18 retro.) New limitation? Log it via `impediment-reporter` and add it here in the next retro.

- **`rg.exe` (ripgrep) is blocked / absent in the agent sandbox** — direct `rg.exe` invocation fails with `Access is denied` or `ENOENT` even on standard repo paths. The `Grep` tool works fine — it does not call `rg.exe` directly. **Workaround for shell use:** use PowerShell `Get-ChildItem -Recurse -Filter <pattern> | Select-String <regex>` instead of `rg`. Repeated occurrences: impediments #15, #28, #33, #37 (≈19 hits). The Glob tool can also time out on trivial patterns while plain `ls` returns instantly (#917) — same family.
- **PowerShell variable scoping leaks across blocks.** Variables assigned inside `foreach`/`if` blocks remain visible at the surrounding scope, which can mask bugs in throwaway scripts. **Workaround:** prefer small checked `.ps1` files over inline one-liners when logic is non-trivial; for complex regex with mixed quoting (impediment #44), write to a script file rather than escaping inline.
- **`npm test` may time out at sandbox-default limits** on the full suite. **Workaround:** run scoped subsets via `npx vitest run <path>` for fast feedback; full-suite runs should be kicked off with explicit longer timeouts. **Three false-red shapes recur at closeout — the moment a red is deciding whether your diff ships** (impediments #483, #516, #522, #527, #554 ×3, #562 ×3, #576): (a) *worker-contention flakes* — a full-suite red on a file the diff cannot reach (typically `scripts/__tests__/`, git-shelling or timing-sensitive) that passes in isolation; (b) *worker-fork crashes* — `[vitest-pool]: Worker exited unexpectedly` with **no failing test name printed** and a test-file total one lower than a clean run, because the crashed worker's file is dropped rather than reported; (c) *piped exit codes* — `npm test 2>&1 | tail` reports `tail`'s exit 0 while tests failed, so never pipe the gate run (redirect to a file and read it). **Triage protocol:** before treating a closeout red as real, rerun the failing file in isolation *and* rerun the full suite once; if both go green and the shape matches one of the three tells, record it as a flake with the outputs — do not ship on the red, and do not debug your diff against it.
- **`esbuild` / `npm install` may fail with `spawn EPERM`** in restricted sandboxes (impediment #21). **Workaround:** retry once, then fall back to running the failing step on the user's machine; do not loop indefinitely.
- **Bash-tool heredocs silently corrupt file content** (impediments #211 ×2, #329, #352). A quoted heredoc (`cat > f << 'EOF'`) has eaten backslashes from regex literals and failed to parse with `unexpected EOF`; content piped through `node -e` / `python - <<PY` inside a double-quoted shell string corrupts twice over. **Workaround:** write files with the Write/Edit tools, never via shell heredocs; if a shell must produce a file, write the script to a `.ps1`/`.mjs` file first and run it.
- **Python text-mode writes silently CRLF-convert repo files, and git hides it while the freshness gate fails on it** (impediments #630, #662, #671, #677, #689 — five entries in one week, ~55 min). `io.open(p, 'w')` translates every `\n` to `os.linesep` on Windows; `.gitattributes` (`eol=lf`) normalizes the blob on `git add`, so `git status` and `git diff` report the tree **clean** — but `check:generated-freshness` byte-compares disk against `git show HEAD:<path>`, so it fails a generated artifact naming the *generator*, and re-running `npm run prebuild` cannot help. CRLF also breaks source-parsing gates outright: JS regex `.` excludes `\r`, so a `//`-comment-stripping scan silently matches nothing on a CRLF file (#677 — four red tests pointing at a correct edit). **Workaround:** prefer the Write/Edit tools (they preserve endings); any Python write to a tracked file must pass `newline=''` (`open(p,'w',encoding='utf-8',newline='')`) or write bytes. **Diagnosis:** "regenerating changed it" on a file git calls clean = line endings, not the generator — count `\r\n` bytes on disk vs the blob. **Repair:** binary rewrite (`b.replace(b'\r\n', b'\n')`); `git checkout --` does not help because git considers the file unmodified.
- **Worktree `node_modules` is unreliable in every direction** (impediments #203, #207 ×2, #283 ×2, #287 ×2, #294 ×3, P95, then #370, #394 ×2, #412 ×3, #431 ×2, #458, and the thirty-plus stub tallies since): fresh worktrees arrive with none, reused pool worktrees carry a stub directory holding only hidden Vite caches, and the home tree's own `node_modules` has lost `.bin` while packages sat intact. **Repair sequence (updated for #394/#412 — the old `cmd /c rmdir` step is guaranteed to no-op on the exact stub shape it was written for, because the stub is *not* empty):** (1) pre-flight probe `[ -e node_modules/.bin/vitest ]` — not `[ -d node_modules ]`; the session-precheck's `test:` line used to pass green against a stub and now **abstains** instead (`test=abstained`, THR-1326), so `nm:` is the install-health signal and the two lines can no longer contradict each other; (2) inspect with `ls -a` or PowerShell `Get-ChildItem -Force` — the Vite caches are hidden, so an unforced `ls` reports a directory that looks empty and is not; (3) probe the **donor** too (`.bin/vitest` in the home tree) before junctioning — a `.bin`-less donor propagates the fault and looks like it worked (#370, #458); if no healthy donor exists, plain `npm install` in the worktree is the only path (~4 min); (4) remove the stub with PowerShell `Remove-Item -Recurse -Force` **as a call of its own** — never `cmd /c rmdir`, which refuses non-empty directories and makes the *subsequent* `mklink` fail with a misleading `Cannot create a file when that file already exists`; (5) create the junction **in a separate call**, preferring the native cmdlet `New-Item -ItemType Junction -Path "<wt>\node_modules" -Target "<home>\node_modules"` (#659 — no `cmd` for the guard to mis-parse); `cmd /c mklink /J` also works but **only as the sole statement in the call**: chaining anything with `cmd /c` makes the harness path guard mis-bind `/c` as the *preceding* cmdlet's path argument and refuse the whole call with `Remove-Item on system path '/c' is blocked` (#659 controlled arm; #686 ×5 — the message names a cmdlet and a path that are not in your command, so do not argue with `Remove-Item` — split the call). Git Bash mangles the `mklink` target path (impediment P69); (6) verify `Test-Path <wt>\node_modules\.bin\vitest`, not the directory; (7) **remove the junction at closeout** — the reaper's `git worktree remove --force` follows a junction into the home install (the 2026-07-22 double wipe). `cmd /c rmdir` for the strip is refused from PowerShell however spelled or isolated (#663 ×3, #686): use `[System.IO.Directory]::Delete($path, $false)` — non-recursive, drops the reparse point without following it — or, from the Bash tool, `cmd //c rmdir "<path>"` (MSYS needs the doubled slash or it rewrites `/c` into a Windows path).
  - **What produces each arrival shape — `cant-fix`, and neither one is a wipe (THR-1326, 2026-08-29).** The fresh-worktree class was tallied ~31×/week as if something were deleting installs. Forensics over all 199 pool directories say otherwise, and the two faces have unrelated causes:
    - **Plain-missing (~170 of 199 dirs) is the normal fresh state, not an incident.** `git worktree add` does not create `node_modules`, and `node_modules` is gitignored so no checkout restores one. Nothing produces this; it is the absence of a step. Newly-created pool worktrees show it uniformly, and the ones that show a junction are exactly those a session already repaired.
    - **The `.vite`-only stub (3 of 199) is created by Vite, not left behind by a deletion.** Vite's default `cacheDir` is `<root>/node_modules/.vite`, and the dev server `mkdir -p`s it **during config resolution — even when it then fails to start**. Reproduced on demand: a dev server pointed at a tree with no `node_modules` leaves a `node_modules/` containing exactly `.vite`. So the stub is manufactured by pointing `preview_start` (or any `vite` invocation) at a worktree *before* repairing its install. The timings corroborate it — `vigilant-bhabha-510e0a` was created at 09:01 and had `node_modules/.vite` by 09:02, far too fast for a 289-package install to have existed and been destroyed.
    - **The reaper is not the producer of either.** Its 56 `worktree removal FAILED (in use?)` events leave the directory with `node_modules` *fully gone* (e.g. `sleepy-einstein-c7cbba`, still on disk, plain-missing) — failed removals do not leave husks, and none of the three stub worktrees appears in that set.
    - **Consequence: the per-arrival tally rows are retired.** Both shapes are expected states with a documented ~2-minute repair; logging them as impediments was counting a normal condition ~31×/week and drowning the log. Repair and move on. What is worth logging is a *donor* that is damaged, since that is the shape with no cheap repair.
- **`preview_start` reports a port the dev server may not be listening on** (impediments #368, #376 ×2, #384 ×2, #396 ×2, #403 ×3, #450 — ~10 occurrences in one week). The tool's `"port"` field and "available at http://localhost:NNNNN" message are the harness's guess, not Vite's binding — when the default port is taken, the `autoPort` remap the harness reports can differ from the port Vite actually chose, and every navigation to the reported port fails `ERR_CONNECTION_REFUSED` (or worse, silently reaches *another session's* Vite — the wrong-tree capture hazard). **Workaround:** treat the reported port as a hint; before the first navigation, read `preview_logs` and take the port from Vite's own `Local: http://localhost:NNNN/` banner — that is the authoritative binding, and the check costs one call.
- **The Browser pane's *page* is unavailable in unattended / scheduled runs** (impediments #448, #472, #493, #499 — four occurrences on four consecutive days, 2026-08-06 → 08-09). How far it fails varies, and the failure text never names the cause: at minimum the pane cannot composite (`computer{action:"screenshot"}` returns "not compositing frames", `read_page` returns `(empty page)` at `Viewport: 0x0`, `find` fails with `no read_page tree cached`); at worst `navigate` is denied outright. **Workaround — decide attendance *before* any preview setup, not at the capture (#499):** in a scheduled or unattended run use **Playwright MCP for the whole browser pass**, driving as well as capture. `preview_start` is still the right way to launch the dev server (never Bash) and `preview_logs` is still the authoritative source for Vite's real port; it is only the pane's *page* that is unavailable. Two wideners: **`preview_start` itself can be refused outright in unattended runs** (impediments #546 ×10, #574), which shuts the Playwright workaround too — the sanctioned fallback is the jsdom-render substitution in `Docs/canon/verification-gates.md` § Browser-verify; and the compositing failure is **not exclusive to unattended runs** — it fires in an interactive session whenever the pane is simply not displayed (#570).
- **Linear `save_issue` returns 200 but does not always update state** (impediment #48). **Workaround:** always verify-after-write by re-querying the issue; do not trust the success response alone.
- **A deliberately-nulled `assignee` on a parked issue does not reliably stay null** (THR-1058; impediments #508, #380, #306, #607, #657). A park is only readable as `assignee: null` ∧ `state: In Dev` — the shape `keep-work-flowing-cc` matches to surface finished work to Christian — so a null that does not hold makes a completed ticket invisible to the only lane that would ask him to close it. **Workaround:** verify-after-write on the assignee too, and re-assert once if the key comes back — `save_issue(id, assignee: null, priority: <current value>)`, bundling one other field at its existing value (#380). Read absence off the `get_issue` re-query, never off the mutation echo (#306). **Do not re-investigate the MCP write path** — seven controlled arms all preserved the null; only the *create* path defaulted, and that is fixed (THR-845). **The settled cause: Linear's native GitHub integration re-assigns on PR open, and again on merge, whenever the PR names the issue id — the body alone is enough** (impediment #607). Prevention is a writing rule: **keep the issue id out of the body, title and branch name of any PR not meant to close that issue**, and **verify the park *after* opening the PR**. The Linear-side settings fix has been surveyed and **does not exist** (THR-1190, 2026-08-22): every workspace control that can write an assignee is already in the desired state, and the GitHub integration page carries no assignee control. If it recurs, capture the issue's **activity feed** at the instant of the revert — the only surface that names the actor. Survey table: `Docs/plans/2026-04-13-linear-coordination-protocol.md` § Christian-owned Linear settings.
- **Linear `list_issues orderBy: 'priority'` is rejected at runtime** even though the schema accepts it (impediment #49). **Workaround:** omit `orderBy` (or use `createdAt` / `updatedAt`) and sort by priority in memory.
- **Obsidian vault writes go through the filesystem, not the MCP** (structurally closed 2026-07-21, THR-654 — was impediments #66, #71, #75, #86, ~12 occurrences over 8 days of silently-dropped `log.md` appends). Vault skills write directly to `OBSIDIAN_VAULT_PATH`; if unset, they fail loud rather than dropping the entry. Add to `.claude/settings.local.json`: `{ "env": { "OBSIDIAN_VAULT_PATH": "C:\\Users\\chris\\Dev\\Obsidian" } }`.
- **The CC harness mutates the home tree's git state at session spawn** (THR-671/672, proven 2026-07-20) — two behaviors, neither attributable to any agent: (a) an hourly empty-reflog-message update of `refs/heads/main` via plumbing, and (b) a bare `git checkout HEAD` that parks the home tree on a detached HEAD. Moving `main` under a checked-out tree manufactures phantom "staged" diffs that look like catastrophic damage but are not. **This is harness-level and cannot be fixed from the repo.** **Containment:** `threadbare-autosync.ps1` reattaches the provably loss-free park (detached ∧ 0 unique commits ∧ 0 tracked modifications → `git switch main`) within the hour; any other detached state is left untouched with one loud log line carrying the manual repair. Never read a behind-count off a detached HEAD — `HEAD..origin/main` on a parked HEAD is arithmetically true and semantically meaningless (see the freshness-signal table in CLAUDE.md § Session Workflow). Upstream bug report: [anthropics/claude-code#79713](https://github.com/anthropics/claude-code/issues/79713) (report body at `Docs/audits/2026-07-20-git-cicd-forensics/upstream-report.md`).
- **An untracked file in the home tree stops autosync permanently when `main` later commits the same path** (THR-937, measured 2026-08-01). A fast-forward that must *create* a file refuses to clobber an untracked one sitting there, and aborts the whole sync — so the tree stops updating and **never resumes on its own**. Measured: 11 consecutive hourly skips, `24 → 88` commits behind. The producing pattern is a scheduled lane writing a report into `Docs/ops/` **in the home tree** and then committing the same bytes **from its own worktree** (impediment #269). **Containment:** autosync step 5.5 deletes such a file when `git hash-object` matches the incoming blob sha (loss-free by construction) and leaves anything that differs untouched with one loud log line. **Detection:** a repeating `skip:` / `MANUAL REPAIR NEEDED` line in `C:\Users\chris\bin\threadbare-autosync.log`.
- **Scheduled sessions must never run git state ops with the home tree as CWD** (THR-672) — no `checkout`/`switch`/`commit`/`merge`/`rebase`/`reset` against `C:\Users\chris\Dev\Projects\TheFantasyWorldSimulator`. It is a read-only mirror of `main` owned by autosync. **Workaround:** home-tree access is read-only `git -C` queries and file reads; all branch/commit/push work happens in the session's own worktree (branches are repo-global, push works from any worktree).
- **A reaped worktree silently retargets git at the home tree** (THR-797, evidenced 2026-07-26) — the only route where a *live session can author commits onto `main`*. `.claude/worktrees/<name>` sits **inside** the home tree's working copy, so when the hourly reaper deletes a worktree's `.git` file, git's discovery walks *up* and finds the home tree's `.git`. The next `git checkout -b …` then creates that branch **in the home tree, with no error**: `pwd` still reads the worktree path while `git rev-parse --show-toplevel` has become the home tree. The tell is an `Edit` failing "File does not exist" on a file `grep` just matched. **Detection (cheap, before any git state op late in a session):** `[ -e .git ] || echo "WORKTREE GONE"`. **Repair** is the THR-671 park recipe. **Containment shipped:** the reaper's liveness guard reads working-tree file mtimes too, holds a merge-grace window, and refuses to delete a branch whose unregistered worktree corpse is still active. The harness owns `.claude/worktrees/`, so relocating it is not available to us. Disposition of any stale worktree belongs to the reaper alone (THR-674 single-owner rule, `pull-work` § Ownership) — sessions never remove worktrees themselves.

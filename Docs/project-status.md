**A skip can mean "nothing to check" or "could not tell", and branch protection cannot tell them apart (THR-842, 2026-07-29).** The billing block is cleared and Actions execute again, so what remained of this ticket was the part no outage fixes: **recording which `SKIPPED` we accept.** GitHub offers no setting to stop a skipped required check from satisfying branch protection, and the skip is *load-bearing* — every orchestrator sweep and briefing refresh is docs-only, which is why **all fifteen** `ci.yml` runs on `main` since the block cleared show `Test · Typecheck · Build: skipped`. A naive "fail closed on any skip" guard would block the majority of this repo's merges. So the recorded rule is narrower: **a skip may only ever come from a decision, never from an absence**, and the discriminator is the *gating* job — `Detect code changes` reading `success` means the filter chose to skip; anything else means the check never inspected the change and THR-768's guard step fails it closed. Never audit a skip by reading the required check's own conclusion; the 2026-07-29 grooming verdict had to spend a paragraph warning readers off exactly that misreading. **The residual risk is named and accepted rather than papered over:** nothing mechanically asserts that a code-carrying diff cannot produce a skip — the guarantee rests on one YAML `if` that no test exercises, backed operationally by `pull-work`'s stand-down on `check:actions` and its post-arming rollup read. **Retro-verification needed an enabler, not a workaround.** No full gate run on a `main` commit existed to cover the three unverified merges, and forcing one meant inventing a code change, so `ci.yml` gains `workflow_dispatch` (filter step skipped on that event — a dispatch payload carries no diff base for paths-filter; the `check` job runs unconditionally). This PR then discharges the literal Done-when for free: it *is* a non-doc change, so the suite runs on the PR and again on the push to `main`.

**A mortal who stops moving has answered the question (THR-822, 2026-07-28).** Nothing in the world could ask *where is this agent from* or *how long since they last moved* — no actor carried a home, and `located_at` edges are rewritten on move carrying no timestamp. Two authored abandonment beats described exactly that state and had been permanently false for it, so *flee the ravaged land* and *reclaim the homeland* ran forever once assigned. **The implementation everyone reaches for first is the wrong one:** stamping `arrivedTick` on the `located_at` edge means instrumenting **24 writers** whose count is not stable, and the 25th added later silently strands its movers at a stale tick — reading as *more* settled than the agent is, which is the exact "state that looks live and is not" this ticket exists to end. Residence is **observed** instead: `phaseAmbitionProgress` already walks every individual actor each interval, so it compares each one's position against the last recorded and restamps on a change. Every mover is covered including ones not written yet, no movement code knows this exists, and the cost is one indexed lookup per actor per interval — no new phase. **The measurement window is the whole safety argument, and it is what THR-813 was missing.** That ticket refused these repoints because abandonment is evaluated from an ambition's first tick with no grace period, so any "has stayed put" proxy fires immediately for an agent who was already sitting still. The blocker was stated one level too generally: the danger was not that the proxies were current-state, but that they measured the *agent's* history rather than the *ambition's*. Dwell now counts from `max(arrivedTick, assignedTick)`, so a settledness trigger **cannot** hold before `assignedTick + minTicks` — a guarantee by arithmetic, stronger than the `ambition_dominate_trade` idiom that relies on an eligibility floor happening to exclude the state. `KNOWN_DEAD` goes 3 → 1; `homeless_wanderer` stays with a **narrower** reason recorded (it names a loss of *bonds*, not a place, so residence has nothing to say about it). Live seed-42 run: all 396 individuals carry origin + arrival by tick 45, 16 away from origin, arrival ticks exactly `[15,30,45]` — the documented observation quantization. Verification found the neighbouring `agent_in_region` read is dead *world-wide* — **zero** locations carry `regionId` at all, wider than the ticket's guess — filed as **THR-841** rather than absorbed.

**A god's power is rooted in the land their people work (THR-618, 2026-07-28).** The mortal economy and the divine economy sat on the same map and never touched — the P4 extraction checkpoint proved it (`essenceSources.ts` imported nothing from `resourceEconomy.ts`), and that same evidence was the diagnosis. A **typed** essence source now drifts its sanctity each tick from the stock tiers of the goods at its host location that share its Sphere: a Spirit shrine lives off its valley's pearls, a Matter nexus off its ore. Two asymmetries carry the design. Upward drift stops at a ceiling deliberately **below** the flowering threshold, so a rich valley readies a source and only a Sanctify cast flowers it — without that bound, a well-sited shrine would flower unattended and the Build verb would be decoration. Withering has **no** floor above zero and stacks with the contested drain in the same tick: the world takes away more than it gives, which is what makes tending and defending a source worth attention. Untyped (migrated, unbuilt) sources are skipped by construction, preserving THR-611's contract that a save which has done nothing keeps exactly its old income. No new phase, node type, edge type, or income channel — one signed number per source per tick, inside the `controls` walk that was already running, reading the same coarse tier the Livelihood line renders so what the player is shown and what the divine economy acts on cannot drift apart.

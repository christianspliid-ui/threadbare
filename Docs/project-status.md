**A skip can mean "nothing to check" or "could not tell", and branch protection cannot tell them apart (THR-842, 2026-07-29).** The billing block is cleared and Actions execute again, so what remained of this ticket was the part no outage fixes: **recording which `SKIPPED` we accept.** GitHub offers no setting to stop a skipped required check from satisfying branch protection, and the skip is *load-bearing* — every orchestrator sweep and briefing refresh is docs-only, which is why **all fifteen** `ci.yml` runs on `main` since the block cleared show `Test · Typecheck · Build: skipped`. A naive "fail closed on any skip" guard would block the majority of this repo's merges. So the recorded rule is narrower: **a skip may only ever come from a decision, never from an absence**, and the discriminator is the *gating* job — `Detect code changes` reading `success` means the filter chose to skip; anything else means the check never inspected the change and THR-768's guard step fails it closed. Never audit a skip by reading the required check's own conclusion; the 2026-07-29 grooming verdict had to spend a paragraph warning readers off exactly that misreading. **The residual risk is named and accepted rather than papered over:** nothing mechanically asserts that a code-carrying diff cannot produce a skip — the guarantee rests on one YAML `if` that no test exercises, backed operationally by `pull-work`'s stand-down on `check:actions` and its post-arming rollup read. **Retro-verification needed an enabler, not a workaround.** No full gate run on a `main` commit existed to cover the three unverified merges, and forcing one meant inventing a code change, so `ci.yml` gains `workflow_dispatch` (filter step skipped on that event — a dispatch payload carries no diff base for paths-filter; the `check` job runs unconditionally). This PR then discharges the literal Done-when for free: it *is* a non-doc change, so the suite runs on the PR and again on the push to `main`.

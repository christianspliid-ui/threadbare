**The guild economy is running for the first time (THR-815, 2026-07-27).** THR-810 measured guild reputation gain at exactly **zero**; THR-814 fixed two mechanical blockers and found the dominant one — faction membership sits on `ambient` NPCs (225 of 227) while the phase that draws guild content iterates `spotlight` actors only, so **2 of 227 members could reach the draw path at all**. Since ambient actors are by definition not simulated individually, content that reaches them now resolves at the tier that *is* — the faction node. `factionMemberWork.ts` sweeps from `phaseFactionActions` on its own 6-tick gate and settles one authored job per selected member, **re-using the attended path rather than paralleling it**: the same `getAccessibleTemplates` for rank access, the same `processFactionEncounterReputation` for payout, scaled by one constant so unattended work cannot out-earn a watched encounter. Two selection rules are load-bearing. The window **rotates** with the pass counter — filling it from the head every pass is precisely the positional starvation THR-814 found at the cap stage. And it is **proportional** to membership: under the flat cap first written, per-member cadence scaled *inversely* with guild size, and the 45-member Merchant Consortium topped out at 0.765 against an apex of 0.85 while a 3-member court saturated — the largest guilds, carrying the most authored content, were the ones structurally unable to reach it. Measured on seed 42 / medium / 150 ticks: reputation gains **0 → 449** (+32.6 across 185 memberships), **944 jobs resolved** with 462 successes and 135 promotions, apex holders **0 → 33**, rank-blocked templates **21 → 0**. `npm run sweep:rank-reach` **exits 0 and is now a live gate** after three tickets of it correctly failing. Cost is **0.109 ms/tick amortized** — the axis on which promoting members to spotlight (~14× decision cost) was rejected. Only promotions surface to the player; individual jobs stay in one aggregate trace per faction per pass. Two findings filed rather than absorbed: **THR-816** (Builders' Fellowship is seeded **zero members** because `pickFactionForNpc` takes the first faction matching a type and six definitions share `factionType: 'guild'` — the same first-match starvation shape again, now reported by the sweep as `unowned`, distinct from `blocked`), and a **recalibration of the `encounter-health` completion floor 0.78 → 0.70**, done only after confirming by A/B on that exact harness that every unresolved action in both arms is an ordinary encounter 0–1 steps in, so nothing is stalled — a live economy shifts faction leadership, and at ~20 actions per seed one action is worth 5 points of rate.

**The guild rank ladder is not mis-tuned — it is unfed (THR-810, 2026-07-27).** The ticket asked which of three levers should make the apex tier (`minReputation` 0.85) reachable. **All three are void, because the quantity they adjust is zero:** a headless sweep of the real `initializeGameState` → `runTick` pipeline records **0 reputation increases in 200 ticks** across 227 faction memberships, and **3 faction-template draws, none by a member of the owning faction**. `processFactionEncounterReputation` is correctly wired at both call sites and returns at its `if (!factionEdge)` guard every time, so `member_of.reputation` only ever decays. Three of the ticket's own premises were artifacts of how it was measured: there is no equilibrium (the max falls dead-linear at ≈0.0008/tick, unbroken, from 0.900); the 0.6 floor is not safe either (`>=0.60` goes 72 → 33 → 5 → **0 by tick 450**, so senior content is not reachable, only slower to die); and the run enters `twilight` between ticks 150 and 225, so the 300/600/900 rows the ticket reasoned from describe a post-game world — the CLI's `doTick` **stops early** on that transition, which is how a piped `tick 150` silently advanced 15 ticks and looked like a plateau (impediment #238). Its Done-when "apex holder at tick ≥ 300" was therefore unreachable by construction, same class as the THR-689 `document.hidden` trap. **Deliberately shipped no tuning change** — every floor or reward edit is unverifiable while gain is zero, and three of them were the ticket's proposed scope. What shipped instead is the measurement kept as a repeatable check (`npm run sweep:rank-reach`, exits non-zero until the apex is reachable), the verdict with each lever's rejection reasoned (`Docs/audits/2026-07-27-thr-810-guild-rank-reachability.md`), and the real defect scoped as **THR-814**. The `bf.*` floor query resolved as **authored, left unchanged**: Builders' Fellowship sits one rung lower at *both* senior and elite (not only elite as reported), and a uniform shift of the whole upper ladder reads as intent where a copy error would misplace one rung — aligning it upward would make the only guild inside the reachable band unreachable too. Pinned by test on both sides rather than by prose.

**A silent deploy stoppage now surfaces within the hour (THR-785, 2026-07-27).** `main` could advance while the deployed site did not, and the only native signal was a red `Vercel` check deliberately kept **out** of the required set — so it is precisely the signal the executor lane is trained to step past. The originating stoppage went unnoticed until an unrelated closeout happened to read the error body. **The one-command confirmation the ticket specified would have shipped a check that reports healthy during the exact failure it was built to catch:** `gh api .../commits/<sha>/status --jq .state` returns `success` for `main` tip `a9c33078`, a commit with **no deployment record at all** — `vercel.json`'s `ignoreCommand` skipped the build, and Vercel reports a skip as a *successful* status. A green Vercel check means "Vercel is not unhappy", never "production serves this commit". The shipped probe (`npm run check:deploy`, `scripts/check-deploy-health.ts`) reads the **deployments** API instead and classifies HEAD into six verdicts, only `failed` and `stale` (plus a build stuck past a 20-minute grace) waking a human. The anti-drift property is that a *benign* skip is judged with the path list **parsed out of the `ignoreCommand` itself** rather than a copy, so probe and platform cannot drift into disagreeing about what a build-relevant change is; parse failure falls back deliberately **wide**, because over-reporting a stale deploy is an annoyance and under-reporting one is this defect. **Falsified both ways rather than assumed** — `1a9e4cd5..HEAD` (docs-only) reads build-irrelevant → `skipped`, `a406dc83..HEAD` (carrying the THR-812 `src/engine/` fix) reads build-relevant → `stale`; a predicate that only ever answered "benign" would have made the whole check vacuous. The signal lands in `keep-work-flowing-cc` step 2.5, which already runs hourly against `main` and owns the briefing: `needsChristian` summaries go verbatim into `## Needs Christian` in plain language (a test asserts no API vocabulary leaks into them), and a healthy deploy says nothing at all. Recorded permanently in CLAUDE.md: **Vercel is not a required check and must not become one** — it is not a correctness gate, and promoting it would couple every merge to a third-party service. The fix for silence is a notification path, not a new gate.

**Five prerequisite gates were reading a template the pipeline could not find (THR-811, 2026-07-27).** The root cause THR-805 hit and routed around. `filterByPrerequisites` resolved the template every gate reads its authoring off with `getAnyEncounterById`, which covers only the encounter pools — so **43 of the 213 template ids the cache can register** returned `undefined` and every `template?.` gate fell straight through: broken, group-exclusive, confrontation, `requiredTraits`, `blockedByTraits`. The membership predicate was worth running rather than assuming: the ticket found the defect on the 17 `CACHE_REGISTERED_REGIONAL_TEMPLATES` guild ids, but the set is **more than twice that** and reaches families nobody had connected to it — the branching quest lines (`enc.*`, `crafting.quest.*`, `liminal.quest.*`) and the whole `reputation.*` / sphere-themed set-piece tier. Fixed at the lookup (`getUnifiedTemplateById`, 0 of 213 unresolvable) rather than per gate, because five gates sharing one broken input is one defect, not five. **The cost question the ticket flagged was real and inverted by an index:** the superset lookup ran two linear scans over ~1.5k templates and measured **4× slower** than the narrower call it replaces, on a path that runs per cache entry per agent per tick — a lazily-built id Map (derived-constant, module-scope beside `FACTION_ENCOUNTER_META`, lazy because this module sits in an import cycle with the engine) makes it **18 ns against 78 ns, 4.3× *faster* than before**, measured over a live 30,968-entry cache. **The identity risk the ticket's "strict superset" argument did not cover:** for 39 ids *both* lookups resolve, they return **different objects** — `UNIFIED_ACTION_TEMPLATES` holds the `withGroupAffinity`-swept copy, the raw pool the pre-sweep original — so the pipeline had been reading the unswept one. Harmless here (the copies differ only by an appended `'group'`, and the group gate needs `'group'` *without* `'individual'`), and the polarity trap is closed by test rather than by argument: 0 ids change group-exclusivity verdict, and the 9 genuinely party-exclusive templates were already so. Nothing became newly unreachable — a 60-tick seed-42 A/B run is **byte-identical** under both lookups, as it must be while no shipped encounter template declares a trait gate. This widens what the gates *can* see; the authoring that will use it is THR-808's.

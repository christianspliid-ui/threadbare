**Condition countdowns actually count down (THR-784, 2026-07-26).** `decayConditions` decrements `ticksRemaining` on the `has_trait` **edge**; `buildAgentAttachments` read `ticksRemaining`/`totalTicks` off the trait **node** — the shared catalog template. So the number the player saw was per-*template*, not per-carrier, and could not move: `gameInit` seeded condition nodes with `ticksRemaining: null`, so every ticking condition rendered `'until dispelled'`, and **nothing anywhere has ever written `totalTicks`**, so the `AttachmentRow`/`ProwessTab` progress bars had no denominator and had never rendered at all. Both reads now come from the edge (`durationTicks` is the denominator — the authored total THR-761 kept as provenance), with **no node fallback**, since a fallback would reinstate the same frozen value. The membership sweep (THR-688 rule A) also caught the **bestowed-powers** block, which read no duration at all while `hex.plant_dream` grants a genuinely temporary power that `decayConditions` expires — permanent grants are unaffected because both fields stay absent. The misleading `ticksRemaining: null` node seeds are deleted rather than documented, so the field stops looking like live state. Falsified against the unfixed read path: 6 of 14 red, including the two pre-existing tests that asserted the dead side.

**A lost brawl can mark you again (THR-783, 2026-07-26).** The THR-101 tavern migration converted the legacy `appliesWound` flag into a `failureMetadata.onFailureEffects` block at five sites — a key **never declared on the type and never read by any engine module**, so from 2026-04-24 until today losing a tavern brawl wounded nobody. The per-key sweep came back clean: of the five keys authored across every step-metadata literal in `src/`, `onFailureEffects` was the **only** one with no reader. The suite was **falsified against the unwired build** (5 of 11 red — exactly the five asserting the effect *fires*), and `near_miss` is asserted rather than assumed, since `isStepSuccess` counts it a **success**. **The finding is worth more than the fix:** the effect still cannot land in play. The original repro now resolves `["success_at_cost", "failure"]` — the failure side fires — and still mints zero edges, because `trait.condition.wounded` **is not a node in the graph**: `ensureTraitNodes` is called only from the orchestrator's loop over legacy `encounterProgress`, which the unified pipeline no longer populates (measured tick 60, seed 42: 1 of 6 condition and 2 of 7 mastery definitions present, all minted elsewhere — a partial set proves the seeder never ran). Filed **THR-809**. Typecheck went **down 3**, which independently confirms the field was undeclared.

The three `fa.*` templates needed `locationSubtypes` **authored first, having shipped with none**: the cache matches on that field, so registering a template without it is a silent no-op, which is the same class of bug as the orphaning itself. **The plan's rank-gate clause was deliberately not executed, and that is the finding worth the ticket:** it routed the guild tier behind `encounterChains`, but `recordChainStageCompletion` has **zero production callers** — `chainProgress` is read by four modules and written by none, so it is permanently `{}` and anything past chain stage 0 is undrawable. Filed as **THR-803**, which also carries the 6 dead starter-chain stages the same defect has been hiding. **The reaper no longer reaps live sessions (THR-797, 2026-07-26).** The hourly `clean-stale-git.sh` judged a worktree's liveness by **git-admin-dir mtime only** — a signal that stops moving the moment a session finishes pushing, even though its closeout (Linear updates, doc appends, impediment logging) keeps writing files for hours. On 2026-07-26 it removed a still-live session's worktree; because `.claude/worktrees/<name>` sits **inside** the home tree's working copy, deleting the worktree's `.git` file left git discovery to walk *up*, and the session's next `git checkout -b` silently created and checked out that branch **in the home tree** with no error — `pwd` still read the worktree path while `git rev-parse --show-toplevel` had become the home tree. This is the first route in the THR-671/672 family where a live session can author commits onto `main`. **The ticket's stated cause was wrong and the fix it specified would not have worked** — its Done-when called for skipping worktrees merged within N minutes, on the premise that the `:40` run two minutes after the 03:38 merge did the damage. The reaper's own log says the 03:40 run never touched it and the 05:40/06:40/07:40 runs each logged `skipped worktree (live session)`; the removal fired at **08:40**, ~5h after the merge, once the admin mtimes finally aged past `WORKTREE_MIN_IDLE_MINUTES=180`. No sane merge-grace window covers a 5h gap. **The decisive evidence sat inside that single 08:40 run:** the removal `WARN` and a `skipped orphan dir (recent activity)` line name the **same path two lines apart** — the orphan sweep's filesystem probe knew the session was alive, and the worktree pass never asked it. So `is_live` now asks the same question, with the same threshold and semantics (pruning `node_modules`/`dist`/caches so dependency churn cannot masquerade as a session). Two smaller guards ride along: a `WORKTREE_MERGE_GRACE_MINUTES` (90) hold covering the narrower post-merge case the ticket hypothesised, kept as cheap defence-in-depth rather than as the fix; and the branch pass now keeps any branch whose **unregistered-but-still-active** worktree corpse is on disk, closing the second half of the THR-673 chain that deleted `claude/happy-swartz-826e7d` at 09:40 once the partial removal had stripped its `is_checked_out` protection. Verified by a fully neutered dry-run of the real script against the live 24-worktree tree (both live sessions correctly skipped, including this one) plus 8 unit assertions over the new helpers — the decisive one reproducing the incident shape exactly: stale `.git` + a fresh closeout write now reads **live**. Relocating `.claude/worktrees/` out from under the home tree, the other candidate fix, is **not available** — the CC harness owns that path.

**A template can finally declare a trait gate (THR-801, 2026-07-26).** The phantom API THR-786 found on the way, now real. `filterByPrerequisites` has read `template.requiredTraits`/`blockedByTraits` every tick since THR-773, but neither field was declared on `UnifiedActionTemplate`: the gate was evaluated by the engine and authorable by nobody, and any template that tried would not typecheck. Declaring them cleared **13** baseline errors (3517 → 3504) with **zero net-new**, verified by diffing the full `tsc -b` error set either side of the change — six `TS2339` plus the `TS7006` implicit-any cascades they caused. The ticket predicted "two ... errors in one file" and both halves were low: there were 8 in `encounterFilterPipeline.ts`, and a **second production reader** nobody knew about — `src/engine/kpi/branchingDistance.ts`, the diagnostic that reports how many agents a gate excludes, carrying the other 5. That file was invisible to THR-786's migration precisely because its reads sat in the red baseline (THR-489) as "property does not exist", so a grep for typed readers could not see them; it still resolves refs by raw node-id compare instead of the shared ANY-match resolver, which is latent-wrong rather than wrong-today (**THR-802**). **Authoring is deliberately deferred to THR-778 (WS5)** under the Done-when's stated alternative: THR-800 has just established that all 62 authored trait refs are dead because bare snake_case keys never intersect the `trait.<category>.<kebab>` / Title Case / `#tag` forms, so minting a gate now would author the 63rd dead ref and pre-empt the vocabulary THR-788 is still settling. The regression guard is therefore **type-level, and its teeth are the ratchet rather than vitest** — site 1's existing cases mock `getAnyEncounterById` with *untyped* literals, so they pass whether the interface declares the fields or not, which is exactly how the gap survived two shipping tickets.

**Every trait gate in the engine now means one thing (THR-786, 2026-07-26).** The buildable floor of the THR-789 trait-trigger program. Six trait-predicate vocabularies that had drifted apart — the encounter filter pipeline (node id + `minLevel`), the effect-predicate `has_trait:` sugar (tags), `graphConditions` (`trait.<key>` short id), the ambition snapshot (id ∪ name ∪ tags), spell prerequisites, and item-granted keys — now resolve through one `collectBearerTraitRefs` + `bearerMatchesPredicate`, matching a trait by **any** of its four ref forms (node id, short id, display name, tag) on ANY-match. ANY-match is what preserves the old union semantics *by construction*: an earlier draft resolved a shared tag to the lowest id, which is a behavior change wearing a fail-soft costume. **The unchanged-behavior contract suite was written first and is the kill criterion** — 31 assertions pinning each site's pre-migration vocabulary, all green before and after, plus 6 separately-labelled cases for the deliberate widenings and dead-read repairs, each verified *failing* pre-migration so none is vacuous. The two vocabularies have **never intersected**, so trait-driven ambition steering has contributed zero in every run ever played. It survived because the one working path is self-closing: a `trait_grant` returns its bare key and a gate naming that same key passes without touching a definition, which is why THR-737's `master_smith` test is green. Filed as **THR-800**; the sweep distinguishes those 21 phantom grants from the dead gates rather than conflating the two severities. Also found: the template gate fields WS0 was supposed to declare never landed, so the phantom API is still phantom (**THR-801**). **Conditions wear off again (THR-761, 2026-07-26).** The latent bug THR-719 spotted in passing, now confirmed and closed. `decayConditions` is the only tick-driven condition-expiry path and it counts down the `has_trait` edge property **`ticksRemaining`**; both condition-minting aftermath effects — `apply_condition` and `condition_attachment` — wrote only `durationTicks`, which has **zero production readers**, so an authored duration was decorative and every wound, curse or blessing applied through aftermath was permanent for the rest of the run. The regression suite was written first and **falsified against the unfixed build** (4 of 5 red, the 5th being the indefinite case that should survive): each test drives the real `applyEncounterAftermathReaction` and the real `decayConditions` tick by tick and asserts the condition is *gone* on its authored tick — the pre-existing tests asserted the *write*, which passed happily while the condition never expired, and they are repointed to bind `ticksRemaining` too. The two fields are kept distinct rather than unified, recorded as the ticket's open decision: `ticksRemaining` is the live counter, `durationTicks` the authored total retained as provenance and as the duration-UI denominator; `0` still means indefinite, expressed by omitting `ticksRemaining` so the decay loop skips the edge. **The blast radius is smaller than the ticket predicted, and that is the more useful finding:** the membership sweep over every `has_trait` `addEdge` site found only these two wrong (the THR-719 payload path, `rewardPool`, `seedAttachments` and `hexActionBridge` already wrote the right field; culture/capability/mentorship grants are permanent by design), and **no reachable content authors either effect kind today** — the only uses are two unregistered example templates and five `onFailureEffects` blocks in tavern content whose field has no reader at all (**THR-783**), which is why a 155-tick `--auto-aftermath` seeded run mints zero of these edges. So the fix is correct and the path is now sound for the authors the wiring guide points at, but it was not producing observable permanence in play yet. Also found: the condition-duration UI reads `ticksRemaining` off the trait *node* rather than the edge, so the countdown never moves (**THR-784**).

**Every template now says who may draw it (THR-736, 2026-07-26).** `actorAffinities` is required on `UnifiedActionTemplate`, but 18 shipped templates carried none — 15 `mc.*` mercenary-company, 3 `encounter.shell_proof.*` — and the candidate path reads the field as an *opt-in* gate (`generateUnifiedCandidates` skips the actor-type check entirely when the list is absent), so those 18 were drawable by **every** actor type: faction, culture, place-spirit alike. All 18 now declare `['individual']`, matching their `source: 'agent'`; this **narrows** candidacy rather than widening it. **The ticket's predicted typecheck decrease did not materialize, and that is the more useful finding:** the count held at 3519 with per-file counts identical (46 / 7), because these literals already fail assignability on *other* properties (`reach: 'resolve'` is not a `ReachDomain`), and TS reports the property-level mismatch instead of a separate missing-property error — the same masking hides absent `apCost`/`crudType` on the proof pack. So the type system never flagged this and never would have; a **runtime registry invariant test** is the real gate, asserting the offending-id *list* is empty rather than `.every(...)`, which is vacuously true on an empty array — the predecessor test would have passed no matter what once the set emptied. Guard falsified by deletion before being trusted.

**Aftermath reactions apply once again (THR-780, 2026-07-26).** The dev-only double-apply THR-741 found on the way. `applyEncounterAftermathReaction` mutates the live `WorldGraph` in place, and GameView called it from *inside* a `setGameState` updater — which `<StrictMode>` double-invokes in development — so every accumulating effect landed twice while idempotent ones (a `hidden_mark` deduped by deterministic id) looked correct, which is exactly why it survived this long: the damage was silent and uneven, and dev is where balance is played and where every `__DEBUG` measurement is taken. The call moved out of the updater into the shape `resolveBeat` already uses for graph-mutating aftermath — compute against the live state ref, commit the finished object with a constant-returning updater, so a double-invoke returns the same object and re-runs nothing. `<StrictMode>` stays (it was doing its job, surfacing an impure updater), and the THR-114/THR-133 workarounds that shielded the *reads* — a mutable write-out object, a deferred trace list — retire with the cause they were compensating for. **The guard was falsified before it was trusted:** against the stashed pre-fix build it reports `expected 0.7 to be close to 0.35`, the ticket's exact doubling. Live A/B on one seed, agent and reaction: pre-fix `delta: 2` / 2 `encounter_aftermath_applied` / 4 effect traces vs post-fix **1 / 1 / 2**. Found and *not* mine — two duplicate-key console errors, measured identical either side of the fix (**THR-781**: `faction_decay_rank` ids omit the faction, so one agent demoted in two factions on a tick mints the same id twice).

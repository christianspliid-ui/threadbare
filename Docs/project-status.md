## Current Focus

**A template can finally declare a trait gate (THR-801, 2026-07-26).** The phantom API THR-786 found on the way, now real. `filterByPrerequisites` has read `template.requiredTraits`/`blockedByTraits` every tick since THR-773, but neither field was declared on `UnifiedActionTemplate`: the gate was evaluated by the engine and authorable by nobody, and any template that tried would not typecheck. Declaring them cleared **13** baseline errors (3517 → 3504) with **zero net-new**, verified by diffing the full `tsc -b` error set either side of the change — six `TS2339` plus the `TS7006` implicit-any cascades they caused. The ticket predicted "two ... errors in one file" and both halves were low: there were 8 in `encounterFilterPipeline.ts`, and a **second production reader** nobody knew about — `src/engine/kpi/branchingDistance.ts`, the diagnostic that reports how many agents a gate excludes, carrying the other 5. That file was invisible to THR-786's migration precisely because its reads sat in the red baseline (THR-489) as "property does not exist", so a grep for typed readers could not see them; it still resolves refs by raw node-id compare instead of the shared ANY-match resolver, which is latent-wrong rather than wrong-today (**THR-802**). **Authoring is deliberately deferred to THR-778 (WS5)** under the Done-when's stated alternative: THR-800 has just established that all 62 authored trait refs are dead because bare snake_case keys never intersect the `trait.<category>.<kebab>` / Title Case / `#tag` forms, so minting a gate now would author the 63rd dead ref and pre-empt the vocabulary THR-788 is still settling. The regression guard is therefore **type-level, and its teeth are the ratchet rather than vitest** — site 1's existing cases mock `getAnyEncounterById` with *untyped* literals, so they pass whether the interface declares the fields or not, which is exactly how the gap survived two shipping tickets.

**Reputation titles render for the first time (THR-787, 2026-07-26).** Three `properties.category` reads where every trait definition stores `subcategory`. The load-bearing one is `proseEnrichment.ts`: the title filter read a field **no trait node has ever carried**, so `ctx.titles` was empty for every agent in every run — `{title}` silently fell back to the plain agent name and `{?has_title}` was permanently false. Measured on a live 40-tick seeded game: `subcategory === 'reputation'` selects **19** of 196 live trait nodes (Feared Champion, Monopolist, Patron, Brutal Thug…); `category === 'reputation'` selects **0**, and **zero** live trait nodes carry a `category` field at all. This is the same shape as THR-786's node-level `name` finding — a read site pointed at a vocabulary the write side never used, invisible because nothing downstream errors on an empty list. **The existing tests were green throughout the defect's life** because the fixture wrote `category: 'reputation'` too: test and production agreed with each other and disagreed with all shipped content. The new regression suite is therefore anchored on real entries from `REPUTATION_TRAIT_DEFINITIONS` rather than a hand-made node, so fixture drift can no longer make it vacuous, plus a guard asserting every shipped reputation definition stores `subcategory` and none stores `category`. Falsified against the unfixed build: 3 of the 4 new positive cases red, the negative control correctly green. The other two sites were **not** live defects and are reported as such — `cultureGenerator` wrote a stray `category: 'innate'` that contradicted its own `subcategory: 'cultural'` and had no reader (removed), and `trait-modifiers.ts` was self-consistently paired with its CMS column and test (renamed to `subcategory` for one vocabulary, readers updated together).

**Every trait gate in the engine now means one thing (THR-786, 2026-07-26).** The buildable floor of the THR-789 trait-trigger program. Six trait-predicate vocabularies that had drifted apart — the encounter filter pipeline (node id + `minLevel`), the effect-predicate `has_trait:` sugar (tags), `graphConditions` (`trait.<key>` short id), the ambition snapshot (id ∪ name ∪ tags), spell prerequisites, and item-granted keys — now resolve through one `collectBearerTraitRefs` + `bearerMatchesPredicate`, matching a trait by **any** of its four ref forms (node id, short id, display name, tag) on ANY-match. ANY-match is what preserves the old union semantics *by construction*: an earlier draft resolved a shared tag to the lowest id, which is a behavior change wearing a fail-soft costume. **The unchanged-behavior contract suite was written first and is the kill criterion** — 31 assertions pinning each site's pre-migration vocabulary, all green before and after, plus 6 separately-labelled cases for the deliberate widenings and dead-read repairs, each verified *failing* pre-migration so none is vacuous. Writing it first paid immediately: five cases pinned from reading the code were wrong, and correcting them surfaced a third dead-read family — `effectPredicates` and `spellActivation` both union `traitNode.properties.name`, but every authored trait carries `name` at the **node** level, so display-name matching had never resolved anywhere except the one site that read it correctly (same shape as THR-787's `category`/`subcategory`). **The finding that outgrew the ticket:** `__DEBUG.validateTraitRefs()`, the new dev sweep over all six authored surfaces, reports **62 dead gates** against the 64 shipped trait definitions — 43 ambition boosting/blocking/required, 15 ambition graph conditions, 4 `has_trait:` choice-set predicates — because authored refs are bare snake_case (`master_smith`) while every definition uses `trait.<category>.<kebab>` ids, Title Case names and `#tags`. The two vocabularies have **never intersected**, so trait-driven ambition steering has contributed zero in every run ever played. It survived because the one working path is self-closing: a `trait_grant` returns its bare key and a gate naming that same key passes without touching a definition, which is why THR-737's `master_smith` test is green. Filed as **THR-800**; the sweep distinguishes those 21 phantom grants from the dead gates rather than conflating the two severities. Also found: the template gate fields WS0 was supposed to declare never landed, so the phantom API is still phantom (**THR-801**). Predicate-only floor — no minting, no tick phases, no PRNG, no new node or edge types; `Personality & Emergent Traits` gets its first two interface rows (one LIVE, one measured-LEAKED).

**Conditions wear off again (THR-761, 2026-07-26).** The latent bug THR-719 spotted in passing, now confirmed and closed. `decayConditions` is the only tick-driven condition-expiry path and it counts down the `has_trait` edge property **`ticksRemaining`**; both condition-minting aftermath effects — `apply_condition` and `condition_attachment` — wrote only `durationTicks`, which has **zero production readers**, so an authored duration was decorative and every wound, curse or blessing applied through aftermath was permanent for the rest of the run. The regression suite was written first and **falsified against the unfixed build** (4 of 5 red, the 5th being the indefinite case that should survive): each test drives the real `applyEncounterAftermathReaction` and the real `decayConditions` tick by tick and asserts the condition is *gone* on its authored tick — the pre-existing tests asserted the *write*, which passed happily while the condition never expired, and they are repointed to bind `ticksRemaining` too. The two fields are kept distinct rather than unified, recorded as the ticket's open decision: `ticksRemaining` is the live counter, `durationTicks` the authored total retained as provenance and as the duration-UI denominator; `0` still means indefinite, expressed by omitting `ticksRemaining` so the decay loop skips the edge. **The blast radius is smaller than the ticket predicted, and that is the more useful finding:** the membership sweep over every `has_trait` `addEdge` site found only these two wrong (the THR-719 payload path, `rewardPool`, `seedAttachments` and `hexActionBridge` already wrote the right field; culture/capability/mentorship grants are permanent by design), and **no reachable content authors either effect kind today** — the only uses are two unregistered example templates and five `onFailureEffects` blocks in tavern content whose field has no reader at all (**THR-783**), which is why a 155-tick `--auto-aftermath` seeded run mints zero of these edges. So the fix is correct and the path is now sound for the authors the wiring guide points at, but it was not producing observable permanence in play yet. Also found: the condition-duration UI reads `ticksRemaining` off the trait *node* rather than the edge, so the countdown never moves (**THR-784**).

All 18 now declare `['individual']`, matching their `source: 'agent'`; this **narrows** candidacy rather than widening it. **The ticket's predicted typecheck decrease did not materialize, and that is the more useful finding:** the count held at 3519 with per-file counts identical (46 / 7), because these literals already fail assignability on *other* properties (`reach: 'resolve'` is not a `ReachDomain`), and TS reports the property-level mismatch instead of a separate missing-property error — the same masking hides absent `apCost`/`crudType` on the proof pack. So the type system never flagged this and never would have; a **runtime registry invariant test** is the real gate, asserting the offending-id *list* is empty rather than `.every(...)`, which is vacuously true on an empty array — the predecessor test would have passed no matter what once the set emptied. Guard falsified by deletion before being trusted.

**Aftermath reactions apply once again (THR-780, 2026-07-26).** The dev-only double-apply THR-741 found on the way. `applyEncounterAftermathReaction` mutates the live `WorldGraph` in place, and GameView called it from *inside* a `setGameState` updater — which `<StrictMode>` double-invokes in development — so every accumulating effect landed twice while idempotent ones (a `hidden_mark` deduped by deterministic id) looked correct, which is exactly why it survived this long: the damage was silent and uneven, and dev is where balance is played and where every `__DEBUG` measurement is taken. The call moved out of the updater into the shape `resolveBeat` already uses for graph-mutating aftermath — compute against the live state ref, commit the finished object with a constant-returning updater, so a double-invoke returns the same object and re-runs nothing. `<StrictMode>` stays (it was doing its job, surfacing an impure updater), and the THR-114/THR-133 workarounds that shielded the *reads* — a mutable write-out object, a deferred trace list — retire with the cause they were compensating for. **The guard was falsified before it was trusted:** against the stashed pre-fix build it reports `expected 0.7 to be close to 0.35`, the ticket's exact doubling. Live A/B on one seed, agent and reaction: pre-fix `delta: 2` / 2 `encounter_aftermath_applied` / 4 effect traces vs post-fix **1 / 1 / 2**. Found and *not* mine — two duplicate-key console errors, measured identical either side of the fix (**THR-781**: `faction_decay_rank` ids omit the faction, so one agent demoted in two factions on a tick mints the same id twice).

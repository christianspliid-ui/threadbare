## Findings filed

**[THR-1283](https://linear.app/threadbare/issue/THR-1283/the-stale-claim-sweep-destroys-parks-it-can-see-are-parks-and-pull)** — *The stale-claim sweep destroys parks it can see are parks, and `pull-work` reads a park as live work.* High, `Ready for Dev`, Continuous Improvement.

Four failures of one mechanism in four days (impediments #703, #706, #752, #755). The mechanism is the **park shape** — `In Dev` ∧ `assignee: null` ∧ `Parked` — which is the only shape `keep-work-flowing-cc` matches to surface a question under `## Needs Christian`.

Two defects are now root-caused rather than described, which is what moved this from an impediment row to a ticket:

1. **The sweep's `Parked` opt-out is checked only when an issue is first warned, never again at release.** `scripts/stale-claim-sweep/index.ts` has the check at line 354; the release path (~390–415) tests only `state` and `hasActivitySince`. So applying the label *in response to the sweep's own warning* — exactly what the warning comment instructs — does not save the issue. Proven from the sweep's own log ([run 32574121699](https://github.com/christianspliid-ui/threadbare/actions/runs/32574121699)): it traced `released`, not `skip-parked`, 39 seconds before THR-1130 left `In Dev`, with the label applied and verified 5h37m earlier.
2. **The same trace line carries the deeper bug: `previousAssignee: null`.** A sweep whose whole purpose is releasing *stale claims* released an issue that had no claim to release — and had that fact in hand at the moment it acted. A park is the sweep's prime target precisely because it never moves.

Also folded in: `pull-work` Step 3's mutex-liveness table maps an `In Dev` partner to *"genuinely live and moving"*, but a park is awaiting a human — the deadlock row wearing the live row's state (#752, which nearly cost a whole run). That table already learned this exact lesson once for `Todo` partners after impediment #224 ×3.

**Impediment #703 is corrected by the ticket.** It concluded *"the root cause sits in the sweep, which is not repo-side code, so this is a detection-and-repair rule rather than a fix."* The sweep **is** repo-side — `.github/workflows/stale-claim-sweep.yml` plus `scripts/stale-claim-sweep/` — so a real fix was available all along, and four workaround rules were written instead.
